# はじめに

2026年10月のリリースノートで、サーバーレスコンピュートでの DataFrame キャッシュがパブリックプレビューになりました。

- [Databricksプラットフォームのリリースノート: 2026年10月](https://docs.databricks.com/aws/ja/release-notes/product/2026/october#dataframe-caching-on-serverless-compute-is-now-in-public-preview)
- [Serverless コンピュートでDataFramesをキャッシュする](https://docs.databricks.com/aws/ja/compute/serverless/dataframe-cache)

これまでサーバーレスコンピュートでは、`df.cache()` や `df.persist()` を呼ぶと例外になっていました。クラシックコンピュートから移したコードは、キャッシュの行を外して動かす必要がありました。今回のプレビューで、同じ API で重い計算の結果をセッションの中で使い回せるようになります。

ただし、呼べるようになっただけではありません。キャッシュの動き方はクラシックコンピュートとかなり違います。実際にノートブックで動かして確かめたので、その違いも含めて書いていきます。

# キャッシュとは

本題に入る前に、Spark のキャッシュそのものを簡単に説明しておきます。

Spark の DataFrame は、データそのものではなく「どのテーブルを読んで、どう加工するか」という処理の手順を持っているだけです。`spark.table(...)` や `join()` を書いた時点では何も計算されず、`count()` や `collect()`、`display()` のように結果が必要になったときに、ソーステーブルを読むところから処理が実行されます。

これは、同じ DataFrame から何度も結果を取り出すと、そのたびに最初から計算し直すということでもあります。たとえば、4つのテーブルを結合した DataFrame から国別売上とセグメント・年別売上を集計すると、重い結合が2回実行されます。

キャッシュは、この計算結果を一度保存しておき、2回目以降は保存した結果を読むようにする仕組みです。結合は1回で済み、集計はその結果を読むだけになります。

![fig_cache_basics.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/f6bade13-c4d2-47a6-9277-c484699831d4.png)

同じデータに何度も集計をかける分析や、同じ特徴量で複数の機械学習モデルを学習する場面で効いてきます。

# サーバーレスの DataFrame キャッシュとは

サーバーレスで `df.cache()` を呼ぶと、Databricks はその場でクエリを実行し、結果を「スナップショット」として保存します。以降、その DataFrame と、そこから作った DataFrame はソーステーブルを計算し直さず、スナップショットを読みます。

保存先はワーカーのメモリではなくクラウドストレージです。ワークスペースの種類によって次のように変わります。

- サーバーレスワークスペース: デフォルトストレージ
- クラシックワークスペース: ワークスペース作成時に設定したストレージバケット

スナップショットはキャッシュしたセッションだけが読めます。同じノートブックを開いている別のユーザーも読めません。セッションが終わるか最大7日で読めなくなり、ストレージはバックグラウンドで自動的に回収されます。

クラシックコンピュートとの違いは、ドキュメントで次のように整理されています。

| 挙動 | サーバーレスコンピュート | クラシックコンピュート |
| --- | --- | --- |
| キャッシュが使われる条件 | キャッシュした DataFrame と、そこから派生した DataFrame だけ | 同じプランの形のクエリなら使われる |
| データの鮮度 | `cache()` を呼んだ時点のスナップショット | ケースによって更新されることがある |
| 共有の範囲 | セッション専用 | クラスター内のセッションで共有 |
| 計算のタイミング | `cache()` を呼んだ時点ですぐ | DataFrame への最初のアクション時 |
| `unpersist()` | DataFrame ごと破棄し、スナップショットを解放 | メモリ上のキャッシュを解放 |

この表の内容を、上から順に手を動かして確かめていきます。

# 準備

## プレビューと環境バージョン

使うための条件は次のとおりです。

- ワークスペースで「DataFrame caching on serverless compute」プレビューが有効になっていること (デフォルトで有効)
- ノートブックとジョブでは、サーバーレスの環境バージョンが 5 以上であること
- Databricks Connect から使う場合は、Python 版が 18.1.8 以上、Scala 版が 18.1.5 以上であること

コンプライアンスセキュリティプロファイルが有効なワークスペースでは使えません。

プレビューの状態は、ワークスペースの **プレビュー** ページで確認できます。私の環境ではオンになっていました。

![Screenshot 2026-10-23 at 10.34.01.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/ff409d4f-bf4f-4ad7-b190-5771958f0dee.png)

環境バージョンは、ノートブック右側の **環境** パネルで 5 以上を選びます。古いクライアントから `cache()` を呼ぶと `CACHE_REQUIRES_NEWER_CLIENT_ON_SERVERLESS_GC` エラーになります。

## 使うデータ

重い処理の題材には、サンプルデータの `samples.tpch` を使います。挙動の確認用に、自分のスキーマに小さなテーブルも作ります。カタログ名は書き込めるものに変えてください。

```python
import time
from pyspark import StorageLevel
from pyspark.sql import functions as F

CATALOG = "takaakiyayoi_catalog"  # 書き込めるカタログに変更
SCHEMA = "df_cache_demo"

spark.sql(f"CREATE SCHEMA IF NOT EXISTS {CATALOG}.{SCHEMA}")
spark.sql(f"USE {CATALOG}.{SCHEMA}")


def timed_repeat(label, fn, n=3):
    """fn を n 回実行し、各回の時間と中央値を表示する。1回だけの計測はばらつくため"""
    times = []
    for _ in range(n):
        start = time.time()
        fn()
        times.append(time.time() - start)
    times_str = ", ".join(f"{t:.1f}" for t in times)
    print(f"{label}: 各回 [{times_str}] 秒 / 中央値 {sorted(times)[n // 2]:.1f} 秒")
```

集計時間は1回だけだとばらつくので、3回ずつ測って中央値を見ます。

# 重い結合をキャッシュして使い回す

明細 (lineitem) に注文、顧客、国を結合し、国・市場セグメント・年ごとに売上を集計できる形にします。この結合を集計のたびに実行しないように、結果をキャッシュします。

```python
def build_enriched():
    lineitem = spark.table("samples.tpch.lineitem")
    orders = spark.table("samples.tpch.orders")
    customer = spark.table("samples.tpch.customer")
    nation = spark.table("samples.tpch.nation")
    return (
        lineitem.join(orders, F.col("l_orderkey") == F.col("o_orderkey"))
        .join(customer, F.col("o_custkey") == F.col("c_custkey"))
        .join(nation, F.col("c_nationkey") == F.col("n_nationkey"))
        .select(
            F.col("n_name").alias("nation"),
            F.col("c_mktsegment").alias("segment"),
            F.year("o_orderdate").alias("order_year"),
            (F.col("l_extendedprice") * (1 - F.col("l_discount"))).alias("revenue"),
        )
    )


def revenue_by_nation(df):
    return df.groupBy("nation").agg(F.sum("revenue").alias("total_revenue")).collect()


def revenue_by_segment_year(df):
    return df.groupBy("segment", "order_year").agg(F.sum("revenue").alias("total_revenue")).collect()
```

`build_enriched()` は呼ぶたびに新しい DataFrame を返す関数です。後のセクションで「同じ処理を書いて作り直した DataFrame」を用意するために、関数にしています。

## キャッシュなしで集計する

比較のために、まずキャッシュしていない DataFrame で2種類の集計の時間を測ります。

```python
no_cache = build_enriched()

timed_repeat("キャッシュなし: 国別売上", lambda: revenue_by_nation(no_cache))
timed_repeat("キャッシュなし: セグメント・年別売上", lambda: revenue_by_segment_year(no_cache))
```

```text
キャッシュなし: 国別売上: 各回 [3.3, 2.4, 2.3] 秒 / 中央値 2.4 秒
キャッシュなし: セグメント・年別売上: 各回 [2.4, 2.3, 2.7] 秒 / 中央値 2.4 秒
```

## cache() はその場で計算する

キャッシュします。かかった時間と `storageLevel` を表示します。

```python
enriched = build_enriched()

start = time.time()
enriched.cache()  # サーバーレスではここで結合が実行され、結果が保存される
print(f"cache() の呼び出し: {time.time() - start:.1f} 秒")

print("storageLevel:", enriched.storageLevel)
print("DISK_ONLY と一致:", enriched.storageLevel == StorageLevel.DISK_ONLY)
```

```text
cache() の呼び出し: 6.7 秒
storageLevel: Disk Serialized 1x Replicated
DISK_ONLY と一致: True
```

`cache()` の呼び出しだけで 6.7 秒かかりました。キャッシュなしの集計1回分の倍以上です。クラシックコンピュートの `cache()` は印を付けるだけで、計算は最初のアクションのときに走ります。サーバーレスでは `cache()` の時点で結合を実行し、結果を書き出すまで戻ってきません。ノートブックで `cache()` のセルだけが妙に重いのは、この動きによるものです。

`storageLevel` は `DISK_ONLY` でした。`persist()` にどのストレージレベルを渡しても無視され、常に `DISK_ONLY` が返るとドキュメントに書かれています。保存先がクラウドストレージなので、当然といえば当然です。

## キャッシュした DataFrame から集計する

キャッシュした `enriched` から、同じ2つの集計を実行します。

```python
timed_repeat("キャッシュあり: 国別売上", lambda: revenue_by_nation(enriched))
timed_repeat("キャッシュあり: セグメント・年別売上", lambda: revenue_by_segment_year(enriched))
```

```text
キャッシュあり: 国別売上: 各回 [1.1, 0.9, 0.8] 秒 / 中央値 0.9 秒
キャッシュあり: セグメント・年別売上: 各回 [0.9, 0.8, 0.9] 秒 / 中央値 0.9 秒
```

中央値で並べると次のとおりです。

| 集計 | キャッシュなし | キャッシュあり |
| --- | --- | --- |
| 国別売上 | 2.4 秒 | 0.9 秒 |
| セグメント・年別売上 | 2.4 秒 | 0.9 秒 |

どちらの集計も短くなりました。`cache()` に 6.7 秒かかっているので、この程度の差だと元が取れるのは集計を何度も繰り返す場合です。時間は計測環境やそのときの混み具合で変わるので、目安として見てください。

キャッシュの効果が出やすいのは、ドキュメントのベストプラクティスにあるとおり、結合や集計のように計算の重い結果を何度も読む場面です。`spark.table(...)` を読んだだけの DataFrame をキャッシュしても、テーブルのコピーをもう一度スキャンするだけなので、ほとんど得はありません。

# キャッシュを使うのは、キャッシュした DataFrame から作ったものだけ

ここからが本題です。クラシックコンピュートでは、同じ形のクエリであれば、別に書いた DataFrame や SQL でもキャッシュが使われました。サーバーレスでは、キャッシュした DataFrame と、そこから `select()` や `filter()` などで作った DataFrame だけがスナップショットを読みます。

![fig_cache_derivation.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/e7406bbb-7e6a-46a6-a146-33c7640d700f.png)

図の `derived` は、キャッシュした `enriched` に `filter()` をかけて作っているので、スナップショットを読みます。`rebuilt` は、`enriched` と同じ結合を書き直してから `filter()` をかけています。結果として得られるデータは同じですが、`enriched` とはつながっていないので、ソーステーブルを読み直して結合を最初からやり直します。

`enriched` から作った DataFrame と、`build_enriched()` を呼び直して同じ処理を書いた DataFrame を比べます。時間よりも確かなのは実行計画なので、まず `explain()` で結合が残っているかを見ます。

```python
# enriched から作ったので、スナップショットを読む
derived = enriched.filter(F.col("order_year") >= 1995)

# 処理は同じでも enriched から作っていないので、ソーステーブルを読み直す
rebuilt = build_enriched().filter(F.col("order_year") >= 1995)

derived.groupBy("nation").agg(F.sum("revenue").alias("total_revenue")).explain()
rebuilt.groupBy("nation").agg(F.sum("revenue").alias("total_revenue")).explain()
```

`derived` の実行計画では、結合が1つもなく、`nation`、`order_year`、`revenue` の3列を持つデータを直接スキャンしていました。スキャンの部分を抜き出します。

```text
+- PhotonScan parquet [nation#13056,order_year#13058,revenue#13059] DataFilters: [isnotnull(order_year#13058), (order_year#13058 >= 1995)], ..., Format: parquet, Location: PreparedDeltaFileIndex(1 paths)[dbfs:/Volumes/__databricks_internal_catalog_temp_table_manager_50..., ...
```

一方、`rebuilt` の実行計画には、`samples.tpch` の4テーブルのスキャンと、`PhotonShuffledHashJoin` が2つ、`PhotonBroadcastHashJoin` が1つ並んでいました。処理の中身は同じでも、`rebuilt` は結合を最初からやり直しています。

時間も3回ずつ測りました。

```python
timed_repeat("enriched から派生", lambda: revenue_by_nation(derived))
timed_repeat("同じ処理を作り直し", lambda: revenue_by_nation(rebuilt))
```

```text
enriched から派生: 各回 [1.1, 0.8, 0.8] 秒 / 中央値 0.8 秒
同じ処理を作り直し: 各回 [1.7, 1.6, 1.6] 秒 / 中央値 1.6 秒
```

どちらの DataFrame がスナップショットを読むかは、処理の中身ではなく **どの変数から作ったか** で決まります。

ドキュメントでは、この仕組みによってキャッシュが使われる条件が明確になり、利用者が制御できると説明されています。実務上は、キャッシュした DataFrame を変数として持ち回り、後続の処理はその変数から組み立てる書き方に揃えておけば迷いません。

SQL の `CACHE TABLE` や `spark.catalog.cacheTable()` は、サーバーレスでは引き続き使えません。SQL でクエリ結果を使い回したい場合は、セッションローカルの一時テーブルを使います。

## スナップショットの置き場所

`derived` のスキャン部分からは、スナップショットの実体も読み取れます。`Location` が `dbfs:/Volumes/__databricks_internal_catalog_temp_table_manager_...` で始まる内部のボリュームを指していて、ファイルの索引は `PreparedDeltaFileIndex` でした。結果は Delta 形式で、内部のボリュームに書き出されていると読めます。

ドキュメントの制限事項に、多くのセッションがキャッシュすると `information_schema.volumes` と `information_schema.schemata` へのクエリが遅くなる、という記述があります。スナップショットがボリュームとして管理されているのであれば、この記述とも整合します。ボリューム名に temp_table_manager とあるので、セッションローカルの一時テーブルと同じ仕組みに乗っているのかもしれませんが、そこまでは今回は確認できていません。

# キャッシュはその時点のスナップショット

キャッシュした結果は、ソーステーブルが後から変わっても変わりません。小さなテーブルで確かめます。

```python
spark.sql("DROP TABLE IF EXISTS sales_events")
spark.sql("CREATE TABLE sales_events (region STRING, amount DOUBLE)")
spark.sql("INSERT INTO sales_events VALUES ('東日本', 100), ('西日本', 200)")

by_region = spark.table("sales_events").groupBy("region").agg(F.sum("amount").alias("total_amount"))
by_region.cache()
display(by_region.orderBy("region"))
```

| region | total_amount |
| --- | --- |
| 東日本 | 100.0 |
| 西日本 | 200.0 |

キャッシュした後で、ソーステーブルに東日本の行を1件追加します。

```python
spark.sql("INSERT INTO sales_events VALUES ('東日本', 1000)")
```

キャッシュした `by_region` と、ソーステーブルから新しく作った DataFrame を並べて表示します。

```python
# キャッシュした DataFrame
display(by_region.orderBy("region"))

# ソーステーブルから新しく作った DataFrame
display(spark.table("sales_events").groupBy("region").agg(F.sum("amount").alias("total_amount")).orderBy("region"))
```

| DataFrame | 東日本 | 西日本 |
| --- | --- | --- |
| キャッシュした `by_region` | 100.0 | 200.0 |
| 新しく作った DataFrame | 1100.0 | 200.0 |

キャッシュした `by_region` は、追加前の 100.0 のままでした。最新のデータが必要なときは、ソーステーブルから DataFrame を作り直します。

分析の途中でソーステーブルが更新されても、キャッシュした結果を起点にした集計はすべて同じデータを見ます。複数のステップにまたがる分析で数字がずれないので、これは保険として効きます。

同じ理由で、キャッシュした時点で読めたデータは、その後に権限や行フィルター、列マスクを変えてもスナップショットに残ります。この点もドキュメントに明記されています。

# 集計列には別名を付けてからキャッシュする

ここは最初にハマりそうなところです。`F.sum("amount")` に別名を付けずに集計すると、列名が `sum(amount)` になります。この DataFrame はキャッシュできません。

```python
no_alias = spark.table("sales_events").groupBy("region").agg(F.sum("amount"))
print("列名:", no_alias.columns)

try:
    no_alias.cache()
except Exception as e:
    print(str(e).split("\n")[0])
```

```text
列名: ['region', 'sum(amount)']
[DELTA_INVALID_CHARACTERS_IN_COLUMN_NAMES] Found invalid character(s) among ' ,;{}()\n\t=' in the column names of your schema.
```

`.alias()` で別名を付ければ、問題なくキャッシュできます。

```python
with_alias = spark.table("sales_events").groupBy("region").agg(F.sum("amount").alias("total_amount"))
with_alias.cache()  # 列名が total_amount になるのでキャッシュできる
```

ドキュメントの制限事項には、ほかにも列名が重複している DataFrame、interval 型の列を持つ DataFrame などがキャッシュできないと書かれています。クラシックコンピュートでは通っていた `cache()` が、サーバーレスに移したとたんにエラーになるとしたら、まずここを疑うとよさそうです。

エラーコードが `DELTA_` で始まっているのは、前のセクションで見たとおり、スナップショットを Delta 形式で書き出しているためだと思われます。列名に使える文字の制約が Delta テーブルと同じなのも、それで説明が付きます。

# unpersist() で DataFrame ごと使えなくなる

クラシックコンピュートの `unpersist()` は、メモリ上のキャッシュを解放するだけで、DataFrame はその後も使えました。サーバーレスの `unpersist()` は、スナップショットを解放すると同時に DataFrame 自体を破棄します。

`unpersist()` の前に `by_region` から派生させた DataFrame も用意して、両方を確かめます。

```python
east_only = by_region.filter(F.col("region") == "東日本")

by_region.unpersist()
print("unpersist 後の storageLevel:", by_region.storageLevel)

for label, df in [("by_region", by_region), ("east_only", east_only)]:
    try:
        df.count()
    except Exception as e:
        first_line = str(e).split("\n")[0]
        print(f"{label}: {first_line[:100]}")
```

```text
unpersist 後の storageLevel: Serialized 1x Replicated
by_region: [CACHE_DATAFRAME_ACCESS_AFTER_UNCACHE] This DataFrame, or a DataFrame it was derived from, has b
east_only: [CACHE_DATAFRAME_ACCESS_AFTER_UNCACHE] This DataFrame, or a DataFrame it was derived from, has b
```

`unpersist()` の後は、`by_region` も、そこから派生させた `east_only` も `CACHE_DATAFRAME_ACCESS_AFTER_UNCACHE` エラーになりました。エラーメッセージには、元のデータソースから DataFrame を作り直すよう書かれています。`storageLevel` の `Serialized 1x Replicated` は、`StorageLevel.NONE` を文字列にしたときの表記です。

データがもう一度必要になったら、ソーステーブルから作り直します。

```python
by_region = spark.table("sales_events").groupBy("region").agg(F.sum("amount").alias("total_amount"))
display(by_region.orderBy("region"))
```

作り直した `by_region` では、東日本が 1100.0 になっていました。

注意したいのは、クラシックコンピュートで「`unpersist()` してから読み直すと最新データになる」という使い方をしていたコードです。サーバーレスではエラーになります。ドキュメントでも、`unpersist()` はデータを更新するために使わず、ストレージを早めに回収したいときに使うよう案内されています。

なお、`unpersist()` を呼ばなくても、セッションが終われば保存先は自動で回収されます。

# まとめ

サーバーレスコンピュートで DataFrame キャッシュを試して分かったことをまとめます。

- 環境バージョン 5 以上のサーバーレスコンピュートで、`df.cache()` と `df.persist()` がそのまま使える
- 結果はスナップショットとして保存される。実行計画では、内部のボリュームにある Delta 形式のデータをスキャンしていた。`storageLevel` は常に `DISK_ONLY`
- **`cache()` を呼んだ時点で計算が走る。今回は `cache()` の呼び出しだけで 6.7 秒かかった**
- **キャッシュを読むのは、キャッシュした DataFrame とそこから作った DataFrame だけ。同じ処理を書き直した DataFrame は、実行計画に結合が残り、ソーステーブルを読み直す**
- キャッシュした結果は、その後のソーステーブルの更新を反映しない
- 集計列に別名がないと `DELTA_INVALID_CHARACTERS_IN_COLUMN_NAMES` でキャッシュできない。`.alias()` を付ける
- **`unpersist()` すると、その DataFrame と派生した DataFrame は使えなくなる。データが必要なら作り直す**
- キャッシュ後の集計は中央値で 2.4 秒から 0.9 秒になった。`cache()` 自体の時間もかかるので、元が取れるのは何度も読む場合

一番の収穫は、同じ `cache()` という名前でも、クラシックとは別の仕組みとして捉え直す必要があると分かったことでした。クラシックのキャッシュは「クラスターのメモリやディスクに置く、速くするための一時置き場」でしたが、サーバーレスのキャッシュは「セッションの中で固定された、ストレージ上の途中結果」です。キャッシュした変数を持ち回る書き方に揃えておけば、クラシックからのコードはほぼそのまま動きます。一方で、`cache()` の位置で処理が止まる、`unpersist()` 後に DataFrame を使い回せない、といった違いは移行時につまずく場所になりそうです。
