# はじめに

2026年6月のData + AI Summitで、DatabricksはLTAP (Lake Transactional/Analytical Processing) とLakehouse//RT (レイクハウスリアルタイム) を発表しました。前年に発表されたLakebaseとあわせて、この3つの名前は同じ文脈で語られることが増えています。

- [LTAPアーキテクチャ](https://docs.databricks.com/aws/ja/oltp/projects/ltap-overview)
- [レイクハウス リアルタイム](https://docs.databricks.com/aws/ja/compute/sql-warehouse/real-time)
- [Lakebase Postgres](https://docs.databricks.com/aws/ja/oltp/projects/)

ただ、どれも「コピー不要」「低遅延」「アプリやエージェント向け」と説明されるので、何がどう違うのかが掴みにくいと感じていました。Lakehouse//RTのベータを試す前に、まず自分の理解を固めておきたかったので、ドキュメントを読んで関係を整理しました。

この記事は動かした結果の報告ではなく、概念の整理です。提供状況はAWS版ドキュメントの2026年11月時点の記載にもとづいています。

# 3つは同じ種類のものではない

最初に押さえておきたいのは、3つが同じ種類のものではないということです。データベース、コンピュート、設計の名前と、それぞれ別のものを指しています。

| 名前 | 何か | 役割 |
| --- | --- | --- |
| Lakebase | データベース (Postgres) | アプリが数行ずつ読み書きする |
| Lakehouse//RT | SQLウェアハウスの種類 | 分析用のテーブルへの読み取りクエリーを、多数の同時アクセスに1秒未満で返す |
| LTAP | 設計 (アーキテクチャ) の名前 | アプリ用のデータと分析用のデータを、コピーせず1つのストレージで持つ |

関係を図にすると次のようになります。

![Lakebase、Lakehouse//RT、LTAPの関係を示した図](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/1ffbfb7e-27f6-424e-b482-d1b5530118bc.png)

Lakebaseとレイクハウスのテーブルという2つのデータの置き場所があり、その2つを1つのストレージでつなぐ設計がLTAPです。Lakehouse//RTは、その両方を読み取る側にいます。以降、1つずつ見ていきます。

# Lakebaseはアプリが読み書きするPostgres

LakebaseはフルマネージドのPostgresです。決済の処理やAPIの応答のように、少数の行を素早く読み書きする用途 (OLTP) を担います。

通常のPostgresと違うのは、コンピュートとストレージが分離されている点です。コミットされたデータは、最終的にクラウドのオブジェクトストレージに書き出されます。この構造のおかげで、データベースのブランチ作成や特定時点への復元が、データの物理コピーなしで行えます。

そして、この「データがオブジェクトストレージに出ていく」構造が、後述するLTAPの土台になっています。

Lakebase自体は以前の記事でも使っています。

- [Databricks Free Edition + Lakebase で「記憶を持つ」LangGraphエージェントを動かす](https://qiita.com/taka_yayoi/items/2ab8f7fc484e834e216b)
- [Lakebase Search (ベータ) を試してみた: Databricks AI Searchとどう使い分けるのか](https://qiita.com/taka_yayoi/items/95a510bfda30d24a7d43)

# Lakehouse//RTは読み取り専用の高速なSQLウェアハウス

Lakehouse//RTは、サーバーレスSQLウェアハウスの種類の1つです。現在はベータです。対応リージョンのワークスペースで、ワークスペース管理者がプレビューのページからLakehouse//RTを有効にすると、SQLウェアハウスの作成画面で「リアルタイム」を選べるようになります。プレビューのページに表示されない場合は、アカウントチームに確認してください。

![Screenshot 2026-11-25 at 17.29.38.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/afb121f2-1290-4628-8d66-e1d4afee4641.png)

対象は、Unity Catalogで管理されたDelta LakeまたはApache Icebergのテーブルです。これらのテーブルへの読み取りクエリーを、数百から数千の同時ユーザーに対して1秒未満で返すことを目指しています。想定されている用途は次のとおりです。

- カスタムアプリケーションのバックエンド
- AIエージェントのツール
- 運用分析
- 多数のユーザーが同時に見るBIダッシュボード

## 通常のサーバーレスSQLウェアハウスとの違い

速くなる代わりに、できることは絞られています。

- 実行できるのは読み取りクエリーと `CREATE TABLE AS SELECT` のみ。`INSERT` や `MERGE` などの書き込みは対象外
- Genieとジョブタスクからは使えない
- クエリーごとに実行時間などの上限 (ガードレール) があり、超えたクエリーは遅くなるのではなくエラーになる

3つ目は設計の考え方がよく表れています。重いクエリーを時間をかけて完走させるのではなくエラーにすることで、同時に走っているほかのクエリーの応答時間を守っています。長時間のクエリーやETLは、従来どおりサーバーレスSQLウェアハウスの担当です。

ドキュメントには、ワークロードごとの推奨が表でまとめられています。

| ワークロード | 推奨 |
| --- | --- |
| 多数の同時アクセスがあり、1秒未満の応答が必要な `SELECT` | Lakehouse//RT |
| 長時間のクエリー、大きなテーブル同士の結合、ETL、書き込み | サーバーレスSQLウェアハウス |
| 行単位の挿入、更新、削除が頻繁なトランザクション処理 | Lakebase |

# LTAPは機能ではなく設計の名前

3つのなかで一番誤解しやすいのがLTAPです。LTAPは、ワークスペースで有効にする機能の名前ではありません。ドキュメントにも「LTAPは単一の機能ではなく、アーキテクチャです」と書かれています。実体は、Lakebaseのいくつかの機能の組み合わせとして提供されます。

## これまでは2つのシステムをパイプラインでつないでいた

アプリの処理 (OLTP) と分析 (OLAP) は、求めるものが逆です。前者は少数の行を素早く読み書きしたい。後者は大量の行をまとめて集計したい。そのため長い間、アプリ用のデータベースと分析用の基盤を別々に持つのが定石でした。

手間がかかるのは、この2つをつなぐ部分です。チェンジデータキャプチャ (CDC) やストリーミングのパイプラインを組み、アプリ側のデータを分析側にコピーし続ける必要があります。パイプラインは壊れることがあり、書き込みから分析できるまでに遅れが出て、アプリ側のデータベースにも負荷がかかります。

## ストレージ層で列形式に変換する

LTAPは、よりよいパイプラインを作るのではなく、パイプラインを不要にするという考え方です。

前述のとおり、Lakebaseはコミットされたデータをオブジェクトストレージに書き出します。LTAPではこのとき、行形式のPostgresのデータを列形式のParquetに変換します。変換されたデータは、DeltaやIcebergといったオープンなテーブル形式で読み取れます。

ポイントは、この変換がストレージ層で行われることです。アプリの読み書きを処理しているPostgresのインスタンスとは切り離されているので、アプリの処理に影響しません。利用者がパイプラインを組む必要も、データベースを定期的に見に行く外部のプロセスもありません。

なお、LakebaseがPostgresであることは変わりません。インデックス、拡張機能、既存のアプリのコードはそのまま動きます。2つを統合するとアプリのデータがIcebergに置かれるだけのデータになる、というのはよくある誤解だとドキュメントでも説明されています。

## LTAPを構成する機能

LTAPの考え方は、次の機能として提供されています。

| 機能 | 内容 | 提供状況 |
| --- | --- | --- |
| LakebaseをUnity Catalogに登録 | Lakebaseのデータへの分析側からのアクセスをUnity Catalogで管理する | 一般提供 |
| 同期テーブル | Unity CatalogのテーブルのデータをLakebaseに渡し、アプリが低遅延で読む | 一般提供 |
| Lakehouse//RTによるLakebaseのクエリー | Lakebaseの最新データを、アプリの処理に影響を与えずに分析する | プライベートプレビュー |
| Lakebaseチェンジデータフィード | Lakebaseのテーブルの行単位の変更を、Unity CatalogのDeltaテーブルとして保存する | パブリックプレビュー |

提供される機能はクラウドによって異なります。お使いのクラウドのドキュメントで確認してください。

ガバナンスについては1点注意があります。Unity Catalogが管理するのは、Lakehouse//RTやチェンジデータフィードのような分析側からのアクセスです。アプリがPostgresに直接つなぐ経路は、これまでどおりPostgresの権限 (`GRANT` と `REVOKE`) で管理します。

# 混乱しやすい2つのポイント

ここまでを踏まえて、混乱しやすい点を2つ挙げます。

## 「コピー不要」は2つの意味で使われている

Lakehouse//RTもLTAPも「データをコピーしなくてよい」と説明されますが、指しているコピーが違います。

- **Lakehouse//RTの「コピー不要」** : 分析用のテーブルを、応答を速くするための別のデータベースに写さなくてよい
- **LTAPの「コピー不要」** : アプリのデータベースのデータを、パイプラインで分析側に写さなくてよい

前者は分析データを外に出すときのコピー、後者はアプリのデータを分析側に取り込むときのコピーです。向きが逆だと捉えると整理しやすくなります。

## Lakehouse//RTには2つの使い方がある

Lakehouse//RTは、読み取る相手によって2つの使い方があります。

- **DeltaやIcebergのテーブルを読む** (ベータ) : Lakebaseとは関係なく、単独で使えます。「レイクハウス リアルタイム」のドキュメントが説明しているのはこちらです
- **Lakebaseの最新データを読む** (プライベートプレビュー) : LTAPの文脈で語られるのはこちらです

後者の仕組みはドキュメントで説明されています。Lakehouse//RTは、データの大部分をオブジェクトストレージ上の列形式のコピーから読みます。Postgresに問い合わせるのは、現在どこまで書き込まれているかを示す値 (LSN) だけです。まだ列形式になっていない直近の変更は、ストレージ層から読んで上に重ねます。分析のクエリーがアプリの処理と競合しないのは、この仕組みによるものです。

「Lakehouse//RTを使う」と聞いたときに、どちらの話かを確認すると話が噛み合います。

# どちらが書き込むかで使う機能が決まる

では、実際にどの機能を使えばよいのか。LTAPのドキュメントは、データセットごとに「そのデータを書き込むのはどちらか」で考えることを勧めています。1つのテーブルに書き込めるのは、Lakebaseかレイクハウスのどちらか一方だけです。

書き込む側ごとに、データの流れと使う機能を図にまとめました。

![書き込む側ごとのデータの流れと使う機能を示した図](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/e34583ab-74eb-4081-8cd1-62e4375c3499.png)

レイクハウス側が書き込むデータと、Lakebase側が書き込むデータの両方を、1つのアプリが扱うこともよくあります。参照用のデータはレイクハウスからLakebaseに渡し、アプリ自身が書いたデータは分析側に見せる、という形です。

## レイクハウス側が書き込むデータ

夜間のジョブで計算したおすすめ商品や価格表のように、レイクハウス側で作られるデータです。これをアプリから低遅延で読みたい場合は、同期テーブルでLakebaseに渡します。

同期テーブルを作るときには、大きなロードを速くするオプションであるLTAP Direct Writesを有効にできます。通常の同期はLakebaseのコンピュートを通してデータを書き込みますが、このオプションを有効にすると、初期ロードとフルリフレッシュのデータがストレージ層に直接書き込まれます。大きなロードが速く終わり、アプリのクエリーとも競合しません。

## Lakebase側が書き込むデータ

アプリが記録する注文や支払いのように、Lakebase側で作られるデータです。これを分析に使いたい場合は、目的に応じて2つの方法があります。

- **今の状態を分析したい** : Lakehouse//RTでそのままクエリーする。売上のライブダッシュボードなど
- **どう変わったかの履歴を使いたい** : Lakebaseチェンジデータフィードで、行単位の変更をDeltaテーブルに保存する。変わった行だけを処理する下流のパイプラインや、監査ログなど

たとえば注文が「受付」で登録され、そのあと「発送」、「配達完了」と更新された場合、Lakehouse//RTで見えるのは現在の「配達完了」です。チェンジデータフィードには、登録と2回の更新のあわせて3件が記録されます。

![注文の登録と更新に対して、Lakehouse//RTで見える今の状態と、チェンジデータフィードに記録される変更の履歴を比べた図](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/c7a2be2f-eb2d-4a7d-a6c0-d00e7c5a23d2.png)

# アプリに分析データを出すときはどちらを使うか

一番迷いやすいのがこの場面です。レイクハウスにある分析データをアプリに出したいとき、同期テーブルでLakebaseに渡す方法と、Lakehouse//RTで直接読む方法の両方が考えられます。

ドキュメントの推奨をもとにした、私なりの整理は次のとおりです。

| 場面 | 選ぶもの |
| --- | --- |
| アプリが行を頻繁に挿入、更新、削除する | Lakebase |
| 主キーで1件ずつ引く。アプリ自身の書き込みと一緒にトランザクションで扱う | Lakebase (同期テーブル) |
| 集計や絞り込みを含む分析クエリーを、多数の同時アクセスでさばく | Lakehouse//RT |

Lakehouse//RTは読み取り専用なので、アプリからの書き込みが必要なデータはLakebaseに置きます。パイプラインが頻繁に更新するテーブルをLakehouse//RTで読むことはできますが、結果は最新のコミットから数秒遅れることがあります。

Lakebaseは行単位の読み書きのためのデータベースで、Lakehouse//RTは分析クエリーのためのウェアハウスです。どちらも「速い」のですが、得意なクエリーの形が違う。ここは実際に動かして確かめたいところなので、別の記事で取り上げる予定です。

# まとめ

Lakebase、Lakehouse//RT、LTAPの関係を整理しました。

- Lakebaseはデータベース、Lakehouse//RTはSQLウェアハウスの種類、LTAPは設計の名前。3つは同じ種類のものではない
- **LTAPは有効にする機能ではない。Lakebaseのいくつかの機能の組み合わせとして提供される**
- LTAPの中心にあるのは、Lakebaseのストレージ層がPostgresのデータを列形式のParquetに変換する仕組み
- 「コピー不要」は2つの意味で使われている。Lakehouse//RTでは分析データを外に出すときのコピー、LTAPではアプリのデータを分析側に取り込むときのコピーを指す
- **Lakehouse//RTには、Delta / Icebergのテーブルを読む使い方 (ベータ) と、Lakebaseの最新データを読む使い方 (プライベートプレビュー) がある**
- どの機能を使うかは、そのデータを書き込むのがレイクハウス側かLakebase側かで決まる

一番の収穫は、LTAPを「機能」として探すのをやめられたことでした。LTAPという名前の設定画面を探しても見つかりません。同期テーブルやチェンジデータフィードのように、すでに使える機能がLTAPの一部だと分かると、発表の内容と手元のワークスペースがつながります。新しい名前が続けて出てきたときは、それがデータベースなのか、コンピュートなのか、設計の名前なのかを最初に分けて考えるのがよさそうです。
