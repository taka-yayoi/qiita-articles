あなたが以下の質問をするのが聞こえます:

*「オーケイ、わかりました。明示的な`.save()`を呼ぶ必要はないのですね。私のコードはより綺麗になり、私のロジックは配管工事から分離され、そしてついに宣言的に考えられるようになりました。しかし、今では目の前にこれらのデコレーターがあります - `@dp.table`、`@dp.materialized_view` - そしてこれらは両方がテーブルを作るようです。待って、もう一つ`@​​​dp.temporary_view`があります。ブロンズレイヤーではどちらを使うのですか？どちらがゴールドレイヤー向け？」*

この記事では、これらのビルディングブロックに踏み込み、特定のユースケースで適切なものをどのように選択するのかを説明します。

# 基礎: すべてはフローです

宣言型の世界では、単にテーブルを作るだけではありません。それらにデータを供給するフローを定義します。フローはあなたのソースと目的地の間の「データ契約」として考えてください。

フローは2つのことを決定します:

- **どの**データが移動するのか(クエリーやデータフレームで定義されます)
- **どのように**到着するのか(Append、Upsert、Replace)

フローは単なるクエリーではありません - 配管工事不要でステートフルかつインクリメンタルな処理です。それぞれの処理が新規あるいは変更されたデータのみを対象にするように、処理済みのものを追跡します。これによって、ストリーミングやバッチモードのいずれで実行したとしてもインクリメンタルなセマンティクスが可能となります。

SDPでは、フローがあなたのパイプラインのコアとなります。時には、これらはデコレーターを通じて暗黙的に定義され、時にはより複雑なロジックに対応するために、フローを明示的に定義することになります。

そして最後になりますが、それぞれのフローには自身の目的地を持つことになります - Unity Catalog(UC)の物理テーブル、あるいは外部システムのシンクとなります。

# 仮想のロジック: `@​​​dp.temporary_view`

すべてを永続化する前に、**ビュー**について話しましょう。あなたのパイプラインのすべてのステップが物理テーブルであるわけではありません。

`@​​​dp.temporary_view`デコレーターによって、一時ビューを定義することができます。あなたのコードを構造化し、よりモジュール化し、可読性を上げるためには最適なものです。ストレージコストを発生させず揮発性です。あなたのパイプライン内で簡単に参照できます。ビューはパイプライン内にのみ存在します。追加の物理ビューを作ることなしにパイプラインを小規模な変換ステップに分割したい際には、一時ビューは有用です。そして、結果は下流のストリーミングテーブルやマテリアライズドビューで永続化されます。

こちらが、再利用可能な変換処理を作成する際の典型的な方法です。SDPバージョンでは、同じロジックをデコレーターでラッピングし、名前付きの参照可能なパイプラインオブジェクトにしていることに注意してください:

**Spark命令型コード**

```py
cleaned_sales_logs = (
  spark.readStream.table("raw_logs")
    .filter("amount > 0")
    .withColumnRenamed("ts", "event_timestamp")
)
```

**SDP宣言型パイプライン**

```py
@​dp.temporary_view
def cleaned_sales_logs():
    return (
     spark.readStream.table("raw_logs")
        .filter("amount > 0")
        .withColumnRenamed("ts", "event_timestamp")
    )
```

# Appendフロー

Kafkaトピックや生のJSONファイルのディレクトリがあることを想像してください。あなたのゴールは、カラムのフォーマット、`CASE WHEN`文の追加や静的な参照テーブルとのjoinのような軽量で行ごとの変換処理を用いて、可能な限り高速にあなたのブロンズレイヤーに取り込むことです。これは古典的な**Appendフロー**です。Appendフローはステートフルなので、どれが処理済みのデータなのかを自動的に追跡します。処理のたびに新規の行のみが取り込まれます - 手動での記帳は不要です。

**ストリーミングテーブル**(@​​​dp.table)がAppendフローの主要なターゲットとなります。

これは、Spark構造化ストリーミングの**writeStream API**と`.outputMode("append")`と直接的に等価なものとなります。

`@​​​dp.table`デコレーターを使用する際、SDPは暗黙的にあなたのためにAppendフローを作成します:

```py
@​​dp.table
def bronze_orders():
    return spark.readStream.table("raw_kafka_orders")
```

しかし、ソース・ターゲットのリレーションシップに対してより多くのコントロールを必要とする場合には、**明示的に**フローを定義することも可能です。これは、同じストリーミングテーブルをターゲットとする複数のフローがある場合に役立ちます。

```py
# First, declare the target destination
dp.create_streaming_table("bronze_orders") 

# Then, explicitly define the flow 1 that hydrates it 
@dp.append_flow(target="bronze_orders")
def flow_cleaned_sales_logs():
    # This refers to our .temporary_view above!
    return dp.read_stream("cleaned_sales_logs")

# Define the schema for Kafka JSON messages
# order_schema = StructType([StructField("order_id", StringType()), ...])

# Define a second flow that hydrates from a Kafka topic
@dp.append_flow(target="bronze_orders")
def append_kafka_orders():
   return (
       spark.readStream
       .format("kafka")
       .option("kafka.bootstrap.servers", "<broker-host>:9092")
       .option("subscribe", "orders_topic")
       .option("startingOffsets", "latest")
       .load()
       .select(F.from_json(F.col("value").cast("string"), order_schema).alias("data"))
       .select("data.*")
   )
```

あなたのAppendフローが、テーブルではなく外部データベースやKafkaトピックに書き込む必要がある場合にはどうしたらいいのでしょうか？任意のシンクに対して、`dp.create_sink()`関数と`@​dp.foreach_batch_sink()`デコレーターがあります。今後の記事でカスタムシンクを深堀します。

# Append Onceフロー

あなたがこう考えていることを知っています: *「私は本当にストリーミングアプローチが好きなのですが、移行できません。私の古いデータはすべてレガシーなテーブルに存在しており、私のKafkaトピックは7日間しか保持されません。今ストリームを開始したら、履歴を失ってしまいます。このギャップを埋めるにはどうしたらいいのでしょうか？」*

これは、**Append Onceフロー**にとって完璧なユースケースです。レガシーデータをテーブルに供給するために一度のみのバッチフローを使うことができ、新鮮なデータはAppendフローに引き継がせることができます。

```py
# 1. Declare the target table
dp.create_streaming_table("bronze_orders")

# 2. THE BACKFILL: Fill the table once from your legacy Parquet data
@​dp.append_flow(target="bronze_orders", once=True)
def backfill_historical():
    return (
         spark.read.format("parquet")
         .load("/Volumes/catalog/schema/historical_data")
    )

# 3. THE STREAM: Let the real-time flow handle everything moving forward
@​dp.append_flow(target="bronze_orders")
def stream_cleaned_sales_logs():
    return spark.readStream.table("cleaned_sales_logs")
```

# AUTO CDCフロー

あなたのソースが単なるイベントのリストではなく、データベース変更のストリームだったらどうなるでしょうか？更新や削除が発生しており、あなたのテーブルは**現在の状態**を反映している必要があります。これは、古典的なSlowly Changing Dimension (SCD) Type 1やType 2のシナリオです。

従来のアプローチでは、これは`foreachBatch`内にある膨大な`MERGE INTO`ブロックを記述することを意味しました。さらに悪いことに、構築したすべての単一のパイプラインで同じ定型コードを繰り返さなくてはなりませんでした。

SDPでは、それを**AUTO CDCフロー**で置き換えます。そして、AUTO CDCフローの物理的なターゲットはなんでしょうか？ストリーミングテーブルです。

使用するには、はじめにストリーミングテーブルとしてターゲットを宣言し、`dp.create_auto_cdc_flow()`関数を使用します。

**Spark命令型コード**

```py
from pyspark.sql import DataFrame
from pyspark.sql.functions import col, struct, max_by
def upsert_to_delta(micro_batch_df, batch_id):
    # Deduplicate within the micro-batch to get the latest record per key
    (micro_batch_df
     .groupBy("key")
     .agg(max_by(struct("*"),
          col("ts")).alias("row"))
     .select("row.*")
     .createOrReplaceTempView("updates"))
    # Execute the MERGE logic
    # Note: Replace the ellipses with your actual column mapping
    spark.sql("""
        MERGE INTO cdc_data_raw t
        USING updates s
        ON s.key = t.key
        WHEN MATCHED AND s.is_deleted = true THEN 
            UPDATE SET DELETED_AT = now()
        WHEN MATCHED THEN UPDATE SET 
            A = CASE WHEN s.ts > t.ts THEN s.a ELSE t.a END,
            B = CASE WHEN s.ts > t.ts THEN s.b ELSE t.b END,
            -- ... for every column ...
            ts = CASE WHEN s.ts > t.ts THEN s.ts ELSE t.ts END
        WHEN NOT MATCHED THEN INSERT *
    """)
# Start the stream
(cdcData.writeStream
    .foreachBatch(upsert_to_delta)
    .outputMode("append")
    .start())
```

**SDP宣言型パイプライン**

```py
from pyspark import pipelines as dp
from pyspark.sql.functions import col, expr
@​dp.view
def users():
    return (
          spark.readStream
         .table("cdc_data.users")
        )
dp.create_streaming_table("target")
dp.create_auto_cdc_flow(
    target = "target",
    source = "users",
    keys = ["key"],
    sequence_by = col("ts"),
    apply_as_deletes = expr("is_deleted = True")
)
```

# マテリアライズドビュー

データがシルバーにやってきたら、通常は日次の収益やアクティブユーザーを計算するために、ゴールのために集計をしたいと考えるでしょう。ここで、マテリアライズドビュー(`@​dp.materialized_view`)が登場します。

マテリアライズドビューはクエリーの結果を保存する特殊なパイプラインオブジェクトです。

マテリアライズドビューはクエリー高速化機構として考えてください。あなたのクエリーの結果を永続化し、ソースが変更された際にはインクリメンタルな**自動更新**を行います。フレームワークが現在の真実を反映するように、追記、更新、削除を行います。

従来のETLを解決するために、通常は2つの困難な道を選択しなくてはなりません:

- **再計算の道:** 更新が生じると、データのすべてのチャンク(一日や一月)に対して再計算を実行しなくてはなりません。これは、**到着が遅れるデータ**に対応する際にはさらに複雑になります。
- **ウォーターマークの道:** 時間ウィンドウを定義するためにウォーターマークを使用します。トレードオフは？ウォーターマークの後に到着するすべてのデータは削除され、考慮されません。

マテリアライズドビューは**「状態」の鏡**として動作することで、これを解決します。クエリーの結果を永続化し、インクリメンタルな更新を行います。データの到着が遅れた場合、SDPは、あなたに1行のマージロジックを書かせることを要求せずに、その状態への再訪やサマリーの更新方法を知っています:

**Spark命令型コード**

```py
def update_aggs(microBatchDF, batchId):
    # 1. Identify affected dates
    distinct_dates = microBatchDF
.select("order_date").distinct().collect()
    date_list = [row.order_date for row in distinct_dates]
    
    if len(date_list) > 0:
        # 2. Recalculate chunks from source
        new_aggs = (spark.read
            .table("silver_orders")
            .filter(F.col("order_date")
                    .isin(date_list))
            .groupBy("order_date")
            .agg(F.sum("amount")
                 .alias("total_revenue")))
# 3. Sink: Merge into target
new_aggs.createOrReplaceTempView("updates")
spark.sql("""
    MERGE INTO daily_sales t 
    USING updates s ON s.order_date = t.order_date
    WHEN MATCHED THEN UPDATE SET t.total_revenue = s.total_revenue
     WHEN NOT MATCHED THEN INSERT *
     """)
(spark.readStream.table("silver_orders").writeStream.foreachBatch(update_aggregates).start())
```

**SDP宣言型パイプライン**

```py
@​dp.materialized_view
def daily_sales():
    return (spark.read
       .table("silver_orders")
       .groupBy("order_date")
       .agg(F.sum("amount").alias("total_revenue")))
```

違いを明らかにしましょう。このように不思議に思っているかもしれませんね: *「私の集計処理で、単純にAppendフローとストリーミングテーブルを使っちゃっダメなの？」*

**Appendフロー**は処理済みのデータに対して決して振り返りません - 前進するのみで、行が到着すると新規行を追記するだけです。過去のデータを再訪しないので、**Appendフロー**に対する標準的な`SUM`や`GROUP BY`を実行するには、エンジンは成長し続ける過去に処理したすべての行を維持する必要があり、計算を完了させるべき自然なポイントが存在しません。

集計を行うには、**有限のテーブル**が必要です - 現在の真実を表現する特定の「状態」や「スナップショット」です。**これが、マテリアライズドビューの中で`spark.readStream`ではなく`spark.read`を使う理由です。** `read`を用いることで、クエリーする完全なデータセットとしてソースを取り扱うことをSDPに指示し、背後ではフレームワークがインクリメンタルに更新を行うためにインテリジェントに最適化を行います。

# 最終的な意思決定ツリー

| 必要なものは... | これを使いましょう | フロータイプ |
|:--|:--|:--|
| ストリーミングの追記のみのソースから生のデータが到着  | `@​dp.table`  | Appendフロー  |
| CDCデータの処理|  `dp.create_auto_cdc_flow` | AUTO CDCフロー  |
| 一度のみのバックフィル  | `@​​dp.append_flow(once=True)`  | 	Append Onceフロー  |
| 集計 / 現在の真実  | `@​​​dp.materialized_view`  | N/A*  |
| コードのリファクタリング  | `	@​​​dp.temporary_view`  |  N/A* |

**思い出してください、マテリアライズドビューと一時ビューはフローではなくパイプラインオブジェクトです。フローはデータが目的地にどのように流れるのかを定義しますが、これらのオブジェクトはどのようにデータを保存するのか、パイプラインでどのように構造化されるのかを定義します。*

# 重要なポイント

フローはSDPのコアなプリミティブです - 処理されたものを追跡するステートフルでインクリメンタルな処理でなので、あなたはデータがどのように到着するのを決めるだけで良く、残りはフレームワークが対応します。ストリーミングテーブルとマテリアライズドビューはフローのターゲットです。まとめると、これらは技術的な複雑性にインテリジェントに対応し、あなたはビジネスロジックに完全にフォーカスできます。
