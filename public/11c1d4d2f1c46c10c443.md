Databricks Apps に待望の **Git リポジトリからの直接デプロイ** 機能がベータとして追加されました。これまではワークスペースフォルダにファイルをアップロードしてからデプロイする必要がありましたが、GitHub や GitLab などのリポジトリを指定するだけでデプロイできるようになります。

https://docs.databricks.com/aws/ja/dev-tools/databricks-apps/deploy#git%E3%83%AA%E3%83%9D%E3%82%B8%E3%83%88%E3%83%AA%E3%81%8B%E3%82%89%E3%83%87%E3%83%97%E3%83%AD%E3%82%A4%E3%81%99%E3%82%8B

本記事では、実際にこの機能を試した手順と、何が嬉しいのかを整理します。

# 何が変わったのか

従来の Databricks Apps のデプロイフローは以下のようなものでした。

1. ローカルでアプリを開発
2. `databricks sync` や UI からワークスペースフォルダにファイルをアップロード
3. ワークスペースフォルダをソースとしてデプロイ

Git デプロイが加わったことで、以下のフローが可能になります。

1. ローカルでアプリを開発
2. Git リポジトリに push
3. リポジトリの**ブランチ、タグ、コミット SHA** を指定してデプロイ

つまり、ワークスペースへのファイルアップロードというステップが不要になり、Git を Single Source of Truth としたデプロイが実現します。

# Git デプロイのメリット

**ソースコードの一元管理**: コードは Git に、データやノートブックはワークスペースに、という関心の分離がきれいにできます。「ワークスペース上のファイルと Git 上のコードがどちらが最新か分からない」という問題が解消されます。

**CI/CD パイプラインとの統合**: ブランチ・タグ・コミット SHA を指定できるため、GitHub Actions などと組み合わせた自動デプロイが組みやすくなります。例えば `main` へのマージで本番デプロイ、`v1.0.0` タグで特定バージョンを固定デプロイ、といった運用が可能です。

**チーム開発との親和性**: プルリクエストによるレビュー → マージ → デプロイという標準的なワークフローがそのまま使えます。

**ロールバックの容易さ**: 問題発生時に前のタグやコミット SHA を指定して再デプロイするだけでロールバックできます。

## 前提条件

- ベータ機能のため、ワークスペース管理者によるプレビュー機能の有効化が必要です
![Screenshot 2026-02-09 at 9.22.25.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/22f51c90-8c59-4484-b4a8-fe779e590d79.png)
- GitHub、GitLab、Bitbucket など主要な Git プロバイダーに対応しています
- プライベートリポジトリの場合、アプリのサービスプリンシパルに Git 資格情報の設定が必要です

# 設定手順

## 1. Git リポジトリの準備

アプリのソースコード一式を Git リポジトリに用意します。通常の Databricks Apps と同様に、以下のファイルが含まれている必要があります。

- エントリポイントファイル(`app.py` や `app.js` など)
- `app.yaml`(カスタムコマンドや環境変数が必要な場合)
- `requirements.txt` や `package.json`(依存関係)

こちらのリポジトリを使います。

https://github.com/taka-yayoi/app_git_sample

![Screenshot 2026-02-09 at 9.57.36.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/c654641e-fd21-4779-b4fd-7956ba3ba3f9.png)

## 2. アプリの作成と Git リポジトリの設定

Databricks ワークスペースのサイドバーから **コンピュート** → **アプリ** タブに移動し、**アプリの作成** をクリックします。
![Screenshot 2026-02-09 at 9.39.45.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/6395e7e4-a80b-41da-be87-a3df523ff8cf.png)

**Git リポジトリの構成** ステップで、リポジトリ URL(例: `https://github.com/taka-yayoi/app_git_sample`)を入力し、Git プロバイダーを選択します。
![Screenshot 2026-02-09 at 9.44.55.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/0fa2a915-6aef-48ad-bc8a-ad606a8d7390.png)

**アプリを作成** をクリックして保存します。
![Screenshot 2026-02-09 at 9.48.55.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/7711f310-29cc-4024-8c2a-fe7d5ed1943c.png)

## 3. Git からデプロイ

アプリの詳細ページで **デプロイ** をクリックし、**Git から** を選択します。
![Screenshot 2026-02-09 at 9.49.07.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/a13327e7-54a3-4230-bf85-883358ca8129.png)

以下の項目を指定します。

- **Git 参照**: ブランチ名、タグ、またはコミット SHA(例: `main`、`v1.0.0`、`abc1234`)
- **参照タイプ**: ブランチ / タグ / コミット のいずれか

デプロイが完了すると、アプリの詳細ページでステータスが「実行中」に変わります。アプリのリンクをクリックして動作を確認できます。

# 再デプロイの流れ

コードを変更した場合の再デプロイもシンプルです。

1. 変更を Git リポジトリに push する
2. アプリの詳細ページで **デプロイ** をクリック
3. 同じブランチなら最新コミットが自動で取得される

ブランチ参照の場合はそのブランチの最新コミットが、コミット SHA の場合は常にその特定のコミットがデプロイされます。

# 注意点

**デプロイソースの切り替え時に Git 資格情報がリセットされる**: Git からワークスペース、またはワークスペースから Git にデプロイソースを変更すると、サービスプリンシパルの Git 資格情報が削除されます。Git 参照(ブランチやタグ)の変更だけであれば資格情報は維持されます。

**ベータ機能の無効化時の影響**: 管理者がベータ機能を無効にした場合、既存の Git デプロイアプリは引き続き実行されますが、再デプロイや再起動はできなくなります。

**サービスプリンシパルの Git 資格情報はプロバイダー単位**: あるサービスプリンシパルの GitHub 資格情報を更新すると、同じサービスプリンシパルを使う全アプリに影響します。

# まとめ

Git からの直接デプロイにより、Databricks Apps の開発・運用フローが大幅に改善されます。特にチーム開発や CI/CD を意識した運用では、ワークスペースフォルダ経由のデプロイと比べてメリットが大きいです。

まだベータ版ではありますが、本番運用を見据えたアプリ開発を行っている場合は早めに試しておくことをおすすめします。
