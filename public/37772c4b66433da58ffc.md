# イントロダクション

知識の強化やビジネスインテリジェンスのために、オープンなインターネットから洞察を抽出するためにWebデータの収穫とAIを活用することは、生成AIの発展によって再燃しています。様々なツールがエンドツーエンドの個別の側面をサポートしていますが、Databricksでは円滑な処理とコラボレーティブな取り組みのための統合プラットフォームを提供しています。

この記事では、Webコンテンツを活用したDatabricksにおけるテキスト抽出ソリューションの詳細を説明します。DeltaテーブルのURL列から並列でコンテンツをダウンロードするためにDatabricksのSparkクラスターを活用します。そして、DatabricksのLLMバッチ処理とモデルサービングの機能を通じて、キーワード、エンティティ、コンセプト、カテゴリー、コンテンツの言語を含む基本的なテキストの要素が抽出されます。

# Webコンテンツの生成

自動化された方法でWebからテキストを収集することは、様々なドメインからクイックかつ完結に情報を取得する便利な方法となりえます。これは、URLを一つづつ逐次に処理を行うと遅くなる場合がありますが、Databricksではこの取り組みを並列化することができます。コンテンツを収集できるように、ウェブサイトが最新でアクティブであるように、URLのリストのドメインが多岐に渡るようにすることを強くお勧めします。

Databricksにおいては、取り組みを並列化する助けとなるようにマルチスレッドを用いてBeautifulSoupやHTML2TextのようなオープンソースのPythonライブラリを活用することができます。URLリストでドメインを分散させるかもしれませんが、ウェブサイトを圧倒しないようにレート制限のロジックを追加することもお勧めします。最も並列化された体験のために、このロジックのすべてはPandas UDF内で行われるべきです。ご自身のWebデータ抽出ソリューションで試せるようにコードの例を以下に示します。

コンテンツを並列でダウンロードするPandas UDFは以下のようになります。いくつかのWebサーバーで除外されることを回避するためにUser-Agentヘッダーを使用します。変数`TCP_CONNECTION_LIMIT`はSparkパーティションごとの同時接続数の合計を制限します。さらに、`TIMEOUT`はタイムリーにリクエストのタイムアウトが行われるようにするためのTCPタイムアウトです。また、これは全体的なジョブのレイテンシーの上限値も設定します。変数`MAX_CONCURRENCY`、`NUMBER_REQUESTS_PER_PERIOD`、`PERIOD_IN_SECONDS`はともに、Webサーバーからコンテンツを収集する際のレート制限を定義します。これによって、Webサーバーを圧倒しないようにすることができます。これらの変数の正確な値は、ご自身のユースケースにおいて読者の方が洗練、研究していただけたらと思います。

```py
@pandas_udf("string", PandasUDFType.SCALAR)
def download_url_content(urls: pd.Series) -> pd.Series:


   async def download_content(session, url):
       try:
           headers = {
              'User-Agent': USER_AGENT
           }
           async with aiohttp.ClientSession(connector=aiohttp.TCPConnector(limit=TCP_CONNECTION_LIMIT)) as session:
               async with session.get(url, headers=headers, timeout=TIMEOUT) as response:
                   response.raise_for_status()
                   return await response.text()
       except Exception as e:
           return str(e)


   async def download_url_content(urls):
       session = RateLimitedClientSession(
           max_concur=MAX_CONCURRENCY,
           reqs_per_period=NUMBER_REQUESTS_PER_PERIOD,
           period_in_secs=PERIOD_IN_SECONDS
       )
       tasks = [download_content(session, url) for url in urls]
       results = await asyncio.gather(*tasks)
       return pd.Series(results)


   return asyncio.run(download_url_content(urls))
```

これで生のHTMLを入手できたので、Webサイトのコンテンツのデータをクリーンにする必要があります。以下に、BeautifulSoupを用いてコンテンツをクリーンにするPandas UDFの例を示しますが、お好きな高性能のHTMLパーサーをお使いいただいて構いません。このコードは、コンテンツからJavaScriptやCSSを除外し、テキストベースのHTMLタグを抽出します。

```py
@pandas_udf("string", PandasUDFType.SCALAR)
def clean_text(contents: pd.Series) -> pd.Series:
      
   def extract_text_from_html(html_content):
       soup = BeautifulSoup(html_content, 'html.parser')
       # kill all script and style elements
       for script in soup(["script", "style"]):
           script.decompose()    # rip it out
       text_tags = soup.find_all(text=True)
       return ' '.join(text.strip() for text in text_tags if text.strip())


   return pd.Series([extract_text_from_html(content) for content in contents])
```

そして、Sparkデータフレームに対してこれらのPandas UDFを実装するには、Webデータの収穫を進めるにつれて、データを部分的に保存するようにチェックポイントを設けられるようにストリーミングを用いることをお勧めします。

上で定義したレート制限のパラメータはそれぞれのSparkパーティションに適用されます。入力のデータフレームを再パーティションすることでえられるパーティションの数は、これらのパラメータと密接に関係しています。お使いのクラスターの設定に応じて、それぞれのSparkワーカーは並列で特定数のSparkパーティションを処理します。最適なレート制限と(あなたのジョブの全体的なレイテンシーを決定する)並列度を得るために、これらの数値を調整しましょう。

```py
contentDF = streamingInputDF
.repartition(NUM_PARTITIONS)
.withColumn("content", download_url_content(col("url")))
.withColumn("text", clean_text(col("content")))
```

パイプラインの回復性を確認するために小規模なバッチを行い、結果に対してDatabricks SQLのAI関数を適用できるようにこのSparkデータフレームをDeltaテーブルに保存することをお勧めします。

```py
# Write the results to a destination in append mode
query = (
   contentDF
   .writeStream
   .outputMode("append")
   .format("delta")
   .option("checkpointLocation", "/Volumes/location_of_path")
   .toTable("main.web_extract.cleaned_content")
)
```

# 洞察の生成

我々は、Webサイトのコンテンツから、キーワード、コンセプト、カテゴリー、エンティティ、コンテンツの大部分を占めている言語のような数多くのタイプのテキストを抽出したいと考えていました。これを行うために、高性能な方法でLLMを用いたバッチ処理を実行するためにDatabricks AI関数の`ai_query`を用いることにしました。

現時点では、URLから収集したデータのコンテンツは、Llama 3.1 8B、70Bであってもそのコンテキストウィンドウに対して大きすぎます。例えば、あるURLは6.4Mトークン以上となっており、Llama 3.1 8Bと70Bのコンテキストウィンドウは128kトークンです。入力サイズがコンテキストウィンドウに対して大きくなりすぐないようにし、バッチ処理が動作するようにする必要がありました。テキストをチャンクに分割すると全体的なテキストの意味を喪失する可能性があったため、分析を行う前にテキストを特定数のトークンに要約するためにSBERTを用いることにしました。また、これによってソリューションのパフォーマンスを改善し、コストを削減することができました。

```py
# Load SBERT model and tokenizer globally
sbert_model = SentenceTransformer('paraphrase-MiniLM-L6-v2')
tokenizer = GPT2TokenizerFast.from_pretrained("gpt2")
max_tokens = 1000  # Adjust token limit as needed
```

上のようにHTMLテキスト抽出のPandas UDFの中でSBERTメソッドを使用することができます。この例では、p、h1とh2を選択していますが、ご自身のWebデータ抽出ツールに合わせて多くのタグを選択しても構いません。以下では、SBERTが抽出されたコンテンツのエンべディングを作成し、トークン制限の最大数に到達するまで、最も類似した追加のセンテンスに追加するために、メインのコンテキストとして最初の文を追加している様子を確認することができます。

```py
# Define the pandas UDF to clean and tokenize text
@pandas_udf("string", PandasUDFType.SCALAR)
def clean_text(contents: pd.Series) -> pd.Series:
   def extract_and_reduce_text(html_content):
       # Parse HTML and extract text
       soup = BeautifulSoup(html_content, 'lxml')
       for element in soup(["script", "style"]):
           element.decompose()  # Remove scripts and styles
       main_text = " ".join(tag.get_text() for tag in soup.find_all(['p', 'h1', 'h2']))
      
       # Tokenize once for both embedding and length check
       tokens = tokenizer.tokenize(main_text)
       token_length = len(tokens)
      
       if token_length <= max_tokens:
           return main_text  # Return if within token limit

       # Reduce text using SBERT relevance scoring if above token limit
       sentences = main_text.split('. ')
       embeddings = sbert_model.encode(sentences)
       main_embedding = embeddings[0].reshape(1, -1)  # Use the first sentence as the main context
       similarities = cosine_similarity(embeddings, main_embedding).flatten()
      
       # Rank sentences by relevance and accumulate until max_tokens is reached
       ranked_sentences = [sentences[i] for i in np.argsort(similarities)[::-1]]
       reduced_text, current_tokens = [], 0
       for sentence in ranked_sentences:
           sentence_tokens = tokenizer.tokenize(sentence)
           if current_tokens + len(sentence_tokens) > max_tokens:
               break
           reduced_text.append(sentence)
           current_tokens += len(sentence_tokens)
      
       return ' '.join(reduced_text)

   return pd.Series([extract_and_reduce_text(content) for content in contents])
```

# プロンプトエンジニアリング

ai_queryを実行する際には、テンプルチャを設定したり、[構造化された出力フォーマット](https://docs.databricks.com/aws/ja/machine-learning/model-serving/structured-outputs)のセットアップ、フィットするプロンプトの中で他のカラムの値を埋め込むためにCONCATを行うことを選択できます。これらのテストを通じて、LLMがクリエイティブになるようにテンプルチャを設定せず、レイテンシーが重要な場合には構造化アウトプットを用いないことをお勧めします。

我々のプロンプトエンジニアリングを通じて、キーワード抽出でフィラーワード(ストップワード)を抽出しないようにLLMに指示することで、パフォーマンスが改善されることがわかりました。さらに、エンティティをどのようなフォーマットで参照したいのかをタイプの例とともに支持することで、必要とする構造と結果を得ることができました。最後に、プロンプトを可能な限り短くすることで、バッチ処理のレーテンシーを改善し、ソリューションのコスト削減の助けとなりました。

# 例

バッチ処理を行うには、プロンプトエンジニアリングを行った行のサブセットに対して処理が行われるように`SELECT`を使うことをお勧めします。そして、ステージング環境での実行の準備ができたら、このクエリーによって全ての行が処理されるように新規テーブルを作るか既存テーブルにカラムを追加することをお勧めします。以下の例では、新規テーブルを作成し、[サーバレスバッチ処理](https://www.databricks.com/jp/blog/introducing-serverless-batch-inference)を活用するLlama 3.1 8Bの[Databricksペイパートークン](https://docs.databricks.com/aws/ja/machine-learning/foundation-model-apis/supported-models)のモデルサービングオプションを使用しています。

```py
CREATE OR REPLACE TABLE target_8b_3
AS
(SELECT
 text,   
 ai_query(
   'databricks-meta-llama-3-1-8b-instruct',
   CONCAT(
     "Instructions:
     1. Extract exactly 50 contextually meaningful keywords or phrases from the text. Avoid filler words like 'and', 'the', 'to', 'it'.
     2. Identify the top 7 concepts representing the main ideas.
     3. Include 5 entities, each in the format {\"text\": \"...\",
     \"type\": \"...\"}, where types are like 'Organization', 'Person', 'Location', 'Company', 'Facility'.
     4. Include up to 5 categories aligned with the IBM Watson Natural Language Understanding taxonomy which are categories such as /sports/team_sports/american_football.
     5. Detect and specify the language of the text.
     Text:",
     text
   )
 ) AS final_reponse
FROM main.web_extract.cleaned_content);
```

# Databricksのモデルサービング

AIモデルの開発、本番運用への投入において、DatabricksでAIモデルを使用するためのいくつかの選択肢が存在します。上で説明した例では、我々がお客様に提供する共有かつサーバレスのGPU計算リソースである[Databricksペイパートークンモデル](https://docs.databricks.com/aws/ja/machine-learning/foundation-model-apis/supported-models)の使い方を説明しました。ここで提供されるモデルには、最新のLlamaモデル、English GTE Largeエンべディングモデル、English BGE Largeエンべディングモデル、Shutterstock ImageAI画像生成モデル、Anthropic Claude Sonnet 4モデルが含まれています。Databricksの[サーバレスバッチ推論]((https://www.databricks.com/jp/blog/introducing-serverless-batch-inference))製品は、シームレスなパフォーマンスとアイドル時間に課金されることのないバッチ推論の要件に応えるために、この技術をベースにして構築されています。

最後になりますが、他のワークロードでこのサーバレスモデルサービング製品のコストを追跡するためには、[サーバレス予算ポリシー](https://docs.databricks.com/aws/ja/admin/usage/budget-policies)をセットアップすべきです。また、あなたのビジネスゴールに向けてどのように予算を消費するのかをより理解する助けとなる、[生成AIコストダッシュボードを構築したソリューションアーキテクト](https://medium.com/@AI-on-Databricks/unlocking-ai-observability-a-deep-dive-into-databricks-model-serving-cost-attribution-dashboard-6bea0ddf0ddd)がいます。

# まとめ

Webからテキストを収集し、AIとDatabricksと結びつけることで、インターネットから洞察を抽出するパワフルなソリューションを提供することができます。Webデータの収集で並列処理を活用し、SBERTの主要で大規模テキストを要約し、キーワード、エンティティ、カテゴリー識別のようなテキスト抽出タスクのためにDatabricksのAI関数を活用することで、効率的でスケーラブルな手法を提供できます。LLMにストップワードを最小化し、出力フォーマットの例を提供するプロンプトエンジニアリングによって、LLMベースの分析の精度と性能を改善することができます。Databrikcsにおいて最適化されたモデルサービングは特定のタスクやバッチ処理に採用されたモデルに依存します。重要なことは、DatabricksはWebデータから価値のあるビジネス洞察を得るための包括的でエンドツーエンドのソリューションを可能にするということです。
