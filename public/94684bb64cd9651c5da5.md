# はじめに

Databricksで「複数のデータを並列に処理したい」と思ったとき、選択肢は大きく2つあります。

- **Apache Sparkの並列処理**: DataFrame APIによるデータレベルの分散処理
- [**Lakeflow Jobsのfor-eachタスク**](https://docs.databricks.com/gcp/ja/jobs/for-each): ワークフローレベルのタスク繰り返し実行

どちらも「並列に処理する」という点は共通していますが、動作するレイヤーがまったく異なります。この違いを理解せずにデータの並列処理にfor-eachタスクを使ってしまうと、**クラスターリソースの競合**という深刻な問題に直面します。

この記事では、それぞれの並列処理がどのレイヤーで動作しているのかを明らかにし、データ処理でfor-eachタスクを使うと何が起きるのかを具体的に説明した上で、適切な使い分けの判断基準を提示します。

# Sparkの並列処理とは

## データレベルの並列性

Sparkの並列処理は**データレベル**で機能します。1つのジョブの中で、データを複数のパーティションに分割し、クラスター内のExecutorが各パーティションを同時に処理します。

重要なのは、**ユーザーが書くコードは逐次的に見える**という点です。Sparkエンジンが裏側でデータの分割・分散・集約を自動的に行います。

```python
# コードは逐次的に見えるが、Sparkが内部で並列処理する
df = spark.read.table("sales.transactions")

result = (
    df
    .filter(col("date") >= "2026-01-01")
    .groupBy("region")
    .agg(sum("amount").alias("total_amount"))
)

result.write.mode("overwrite").saveAsTable("sales.regional_summary")
```

このコードを実行すると、Sparkは以下のように動作します。

1. `sales.transactions`テーブルをパーティション単位で複数のExecutorに分配
2. 各Executorがフィルタリングとローカル集約を並列実行
3. シャッフルを通じてリージョンごとにデータを再分配
4. 最終集約を実行して結果を書き込み

![01_spark_parallel.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/9c0b1d29-0cb1-4144-96d7-524dc37237b0.png)

ポイントは、**1つのSparkジョブがクラスター全体のリソースを効率的に使い切る**ということです。Driverがデータの分割を制御し、各Executorは自分が担当するパーティションだけを処理します。

# Lakeflow Jobsのfor-eachタスクとは

## オーケストレーションレベルの並列性

for-eachタスクは**ワークフローのオーケストレーションレベル**で機能します。パラメータのリスト(顧客一覧、テーブル名、リージョンなど)を受け取り、そのリストの要素ごとに**同じネストタスクの独立したインスタンス**を起動します。

![02_foreach_orchestration.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/5cd340b1-96f7-4d0c-9a55-366a7b1d7618.png)

for-eachタスクの主な設定項目は以下の通りです。

| 設定項目 | 説明 |
|---|---|
| 入力(Inputs) | 反復処理するJSON配列(手動指定またはタスク値参照) |
| 同時実行(Concurrency) | 並列で実行するイテレーション数(デフォルト: 1、最大: 100) |
| ネストタスク | 各イテレーションで実行するタスク(ノートブック、Pythonスクリプトなど) |

## for-eachタスクの適切なユースケース

for-eachタスクは、以下のようなシナリオで威力を発揮します。

- **外部システムへのAPI呼び出し**: 顧客ごとに異なるAPIエンドポイントを呼ぶ
- **異なる設定でのML モデル学習**: ハイパーパラメータセットごとにモデルをトレーニング
- **異なるクラスター構成が必要な処理**: GPU クラスタとCPU クラスタを使い分ける
- **独立したリトライが必要な処理**: 1つの失敗が他に影響しない独立したバッチ

共通するのは、**各イテレーションが独立した「タスク」として管理されるべき処理**であるという点です。

# データの並列処理にfor-eachタスクを使うと何が起きるか

ここからが本題です。「100テーブルの変換処理を並列化したい」というシナリオを考えます。

## アンチパターン: for-eachタスク + 共有クラスター

for-eachタスクのネストタスクに**同一の共有ジョブクラスター**を指定し、同時実行数を5に設定したとします。

![03_antipattern_contention.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/a883c5ea-12b2-475a-84f3-0d7fab87c402.png)

このとき、以下の問題が連鎖的に発生します。

## 問題1: Executorリソースの奪い合い

5個のSparkジョブが同一クラスター上で同時実行されると、2台のWorkerのExecutorリソース(CPU、メモリ)を5個のジョブが**取り合い**ます。

FIFOスケジューラ(デフォルト)の場合、先に起動したジョブがリソースを占有し、後続のジョブは空きリソースが出るまで**待機状態**になります。FAIRスケジューラに変更しても、各ジョブに割り当てられるリソースが細切れになり、個々のジョブの処理時間が大幅に増加します。

## 問題2: メモリ不足とSpill

各Sparkジョブは独自のシャッフルバッファやキャッシュを確保しようとします。4台のWorkerのメモリを10個のジョブで分け合うため、1ジョブあたりのメモリが不足し、ディスクへのSpill(メモリからディスクへの退避)が頻発します。これにより、本来メモリ上で完結するはずの処理がディスクI/Oを伴い、**処理速度が劇的に低下**します。

## 問題3: 障害の連鎖

リソース不足によるOOM(Out of Memory)エラーが1つのタスクで発生すると、Executorが強制終了されます。そのExecutor上で実行中だった他のタスクのデータも失われ、**複数タスクが同時に失敗**する可能性があります。

## 問題4: 不要なオーバーヘッド

for-eachの各イテレーションは独立したタスクとして管理されるため、タスクの起動・監視・完了通知といったオーケストレーションのオーバーヘッドが発生します。データの読み書きが主体の処理に対して、このオーバーヘッドは無駄なコストです。

## 具体的なシナリオで比較

100個のCSVファイル(各100MB)をDeltaテーブルに変換する処理を考えます。

**for-eachタスク(同時実行数5)の場合:**

```
[パラメータ生成] → [for-each: 100イテレーション]
  ├── ネストタスク 1: file_001.csv → delta (Sparkジョブ起動 → クラスターリソース確保待ち)
  ├── ネストタスク 2: file_002.csv → delta (Sparkジョブ起動 → クラスターリソース確保待ち)
  ├── ...
  └── ネストタスク 100: file_100.csv → delta

各イテレーションで:
  - タスク起動のオーバーヘッド
  - Sparkジョブ投入 → リソース待ち
  - 100MBのデータをクラスター全体で処理(しかしリソースは1/5)
  - タスク完了通知
```

**Sparkの並列処理の場合:**

```python
# 1つのSparkジョブで全ファイルを並列処理
df = (
    spark.read
    .format("csv")
    .option("header", "true")
    .load("/data/input/*.csv")
)

df.write.mode("overwrite").saveAsTable("bronze.all_data")
```

```
[単一タスク]
  Sparkジョブ起動 → 100ファイルをパーティションとして分配
  → 全Workerが効率的にフルパワーで並列処理
  → 結果をDeltaテーブルに書き込み

タスク起動は1回のみ、オーケストレーションオーバーヘッドなし
```


# 使い分けの判断フローチャート

以下のフローチャートで、どちらのアプローチを使うべきか判断できます。

![04_decision_flowchart.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/aa1d4fb0-e8a2-4aae-8970-721d6bf34f44.png)


## 判断基準の要約

| 判断基準 | Sparkの並列処理 | for-eachタスク |
|---|---|---|
| データの読み書き・変換 | ✅ 最適 | ❌ リソース競合のリスク |
| 大量ファイルの一括処理 | ✅ ワイルドカード読み込み | ❌ 不要なオーバーヘッド |
| 外部API呼び出し | ❌ Sparkの仕組みと合わない | ✅ 最適 |
| 異なるクラスター構成が必要 | ❌ 不可 | ✅ タスクごとに設定可能 |
| イテレーション単位のリトライ | ❌ ジョブ全体のリトライになる | ✅ 失敗したイテレーションだけリトライ |
| ML モデルの並列学習 | △ 場合による | ✅ 各モデルを独立管理 |
| 処理のモニタリング粒度 | ジョブ単位 | イテレーション単位 |

# for-eachタスクを使うべき場面のコード例

最後に、for-eachタスクが**正しく活躍する**場面のコード例を示します。

## 例: 顧客ごとに外部APIからデータを取得して保存

パラメータ生成タスク(generate_customers):

```python
customers = ["customer_001", "customer_002", "customer_003", "customer_004", "customer_005"]
dbutils.jobs.taskValues.set(key="customer_list", value=customers)
```

ネストタスク(fetch_customer_data):

```python
import requests

customer_id = dbutils.widgets.get("customer_id")

# 外部APIを呼び出し(Sparkの並列処理では効率的に扱えない処理)
response = requests.get(
    f"https://api.example.com/customers/{customer_id}/transactions",
    headers={"Authorization": f"Bearer {token}"}
)
data = response.json()

# 取得したデータをDeltaテーブルに保存
df = spark.createDataFrame(data["transactions"])
df.write.mode("append").saveAsTable("bronze.customer_transactions")
```

for-eachタスクの設定:
- 入力: `{{tasks.generate_customers.values.customer_list}}`
- 同時実行: `5`(APIのレート制限を考慮)
- ネストタスクのパラメータ: `customer_id = {{input}}`

この例では、各イテレーションの主体が**外部API呼び出し**(非Spark処理)であり、APIのレート制限に応じた同時実行数の制御や、失敗した顧客だけのリトライが求められます。まさにfor-eachタスクの出番です。

# まとめ

Sparkの並列処理とfor-eachタスクの並列性は、まったく異なるレイヤーで動作します。

- **Sparkの並列処理**: データをパーティションに分割し、クラスター内のExecutorが並列処理。1つのジョブがクラスター全体のリソースを効率的に使い切る
- **for-eachタスク**: パラメータリストに対してタスクインスタンスを並列起動。各タスクはオーケストレーションレベルで独立管理される

データの並列処理にfor-eachタスクを使うと、同一クラスター上で複数のSparkジョブがリソースを奪い合い、メモリ不足やSpill、OOMエラーの原因になります。「データを並列に処理したい」ならまずSparkのDataFrame APIを検討してください。for-eachタスクは「タスクを並列に実行したい」場面で使うものです。
