個人開発の読書管理サービス [ReadNest](https://readnest.jp)（PHP製・PWA対応）で、「スマホでサイドメニューの本棚をタップすると、反応せず画面が真っ白になる」という報告がありました。

直していく過程で症状が `白画面 → 表示は出るが遅い → そもそも全体的に遅い` と変化し、最終的に **Service Worker / キャッシュ戦略 / Tailwind CSS** の3つの落とし穴を順番に踏み抜くことになりました。どれも「PCでは気づきにくく、モバイルだけ顕著に出る」たちの悪い問題です。同じPWA構成の人の役に立てばと思い、経緯と対策をまとめます。

:::note info
環境: PHP 8.2 / 自前テンプレート / Tailwind CSS / Alpine.js / Service Worker による PWA。デプロイはFTP。
:::

# 症状: スマホだけ、タップすると真っ白

- スマホでサイドメニューの「本棚」などをタップすると、**反応がなく、しばらくして画面が真っ白**になる
- PCでは再現しない
- メニューのリンクはごく普通の `<a href="/bookshelf.php">`

リンクは素のアンカーなので「タップ → 画面遷移」するだけのはず。にもかかわらず白くなる。怪しいのは、遷移に割り込める存在 = **Service Worker** です。

# 地雷①: Service WorkerのSWRが、低速回線で「古い/空のHTML」を配信していた

当時の Service Worker は、HTMLナビゲーションに対して「**キャッシュがあれば3秒だけネットワークを待ち、超えたらキャッシュを返す**」という Stale-While-Revalidate 的な実装になっていました。

```js
// Before: 3秒タイムアウトでキャッシュ返却
async function navigationHandler(request) {
  const cache = await caches.open(HTML_CACHE);
  const networkPromise = fetch(request).then((response) => {
    if (response && response.status === 200) {
      cache.put(request, response.clone()); // ← 200ならとにかくキャッシュ
    }
    return response;
  });
  const cached = await cache.match(request);
  if (cached) {
    // ネットワーク vs 3秒タイマーの競争。遅ければ古いキャッシュを返す
    const timeoutPromise = new Promise((resolve) =>
      setTimeout(() => resolve(cached), 3000));
    return Promise.race([networkPromise, timeoutPromise]);
  }
  return networkPromise; // 初回はネットワークを待つ
}
```

何が起きていたか:

1. **モバイルの低速回線では3秒を頻繁に超える** → タイムアウトで**キャッシュ版を返す**
2. ところがそのキャッシュには、過去に **PHPの致命的エラーで途中で切れた“空の200レスポンス”** が紛れ込むことがあった
3. `status === 200` だけを条件にキャッシュしていたため、**空のHTMLも保存・配信**してしまう
4. 一度空がキャッシュに入ると、`Cache-Control: no-store` を付けても**SWは無視**するので、白画面が固定化する

PCで再現しないのは、回線が速くて常に3秒以内にネットワークが勝ち、新鮮なHTMLが返るから。 **「モバイルだけ」「しばらくして真っ白」** という症状にぴったり一致しました。

## 対策: 「完全なHTMLだけキャッシュ」+「Navigation Preload」

方針を「ネットワーク優先」に倒しかけたのですが、今度は後述のとおり遅くなったので、**安全なSWRに作り直し**ました。ポイントは2つ。

```js
// After: 完全なHTMLだけキャッシュする
async function isCompleteHtmlResponse(response) {
  if (!response || response.status !== 200
      || response.type !== 'basic' || response.redirected) {
    return false;
  }
  const text = await response.clone().text();
  // 終端タグがあれば完全なページとみなす（途中で切れた応答を弾く）
  return /<\/html\s*>/i.test(text);
}

async function navigationHandler(event) {
  const request = event.request;
  const cache = await caches.open(HTML_CACHE);
  const cached = await cache.match(request);

  const networkUpdate = (async () => {
    try {
      const preload = await event.preloadResponse;       // ← Navigation Preload
      const response = preload || await fetch(request);
      if (await isCompleteHtmlResponse(response)) {        // ← 完全なHTMLだけ保存
        await cache.put(request, response.clone());
      }
      return response;
    } catch (err) {
      return null;
    }
  })();

  // キャッシュがあれば即表示（SWR）。更新は裏で継続。
  if (cached) {
    event.waitUntil(networkUpdate);
    return cached;
  }
  // 初回はネットワークを待つ。失敗時はオフラインページ
  const response = await networkUpdate;
  if (response) return response;
  return (await caches.match('/offline.html'))
      || new Response('Offline', { status: 503 });
}
```

`activate` で Navigation Preload を有効化:

```js
self.addEventListener('activate', (event) => {
  event.waitUntil((async () => {
    // 古いキャッシュ削除 ...
    if (self.registration.navigationPreload) {
      await self.registration.navigationPreload.enable();
    }
    await self.clients.claim();
  })());
});
```

- **`isCompleteHtmlResponse()`**: `</html>` で終わる完全なHTMLだけをキャッシュ対象に。空・途中切れ・リダイレクト結果を弾く。これで白画面の固定化が根絶。
- **Navigation Preload**: SW起動と並行してネットワーク取得を先行させ、初回（キャッシュなし）の待ち時間を短縮。
- **キャッシュのバージョンを上げる**（`readnest-html-v1.4.0` 等）ことで、既に汚染されたキャッシュも `activate` 時に破棄。

## 教訓: 症状が変わったら、対症療法を重ねず“直前の修正”を見直す

最初は「ネットワーク優先（常に `await fetch`）」に変えました。白画面は消えましたが、今度は**毎回サーバー応答を待つので体感が悪化**。ここで対症療法を積まず、**SWR自体を安全に作り直す**方向に戻したのが結果的に正解でした。「症状が変わったら、ひとつ前の修正を疑う」は鉄則です。

# 「直ったが遅い」→ なぜモバイルだけ遅い? 3つの真因

白画面は消えたものの、依然としてモバイルが重い。PCでは気にならない。これは**ネットワーク律速ではなくCPU律速**を疑うサインです。ページが読み込んでいる“中身”を調べると、3つの真因が出てきました。

## 地雷②: `?v=time()` がブラウザもSWもキャッシュ無効化していた

```php
<!-- Before -->
<link href="/css/ai_assistant.css?v=<?php echo time(); ?>" rel="stylesheet">
<script src="/js/onboarding.js?v=<?php echo date('YmdHis'); ?>"></script>
```

`?v=time()` / `?v=date('YmdHis')` は**毎リクエストで値が変わる**ため、ブラウザキャッシュもSWのキャッシュも一切効かず、5本のCSS/JSを**毎回ダウンロード**していました。モバイルは遅延が大きいぶん損が積み上がります。

```php
<!-- After: ファイル更新時のみ変わるバージョン文字列 -->
<?php
function asset_ver($rel) {
    $path = (defined('BASEDIR') ? BASEDIR : dirname(__DIR__)) . $rel;
    $mtime = @filemtime($path);
    return $mtime ? (string)$mtime : date('Ymd');
}
?>
<link href="/css/ai_assistant.css?v=<?php echo asset_ver('/css/ai_assistant.css'); ?>" rel="stylesheet">
```

`filemtime()` ベースなら、**ファイルを更新したときだけURLが変わる** = 普段はキャッシュが効き、更新時は確実にバスティングされる。キャッシュバスティングの正攻法です。

## 地雷③: Chart.js + moment.js を全ページで同期読み込み

グラフを描くのは読書分析やレポートなど一部のページだけなのに、Chart.js（約200KB）+ moment.js + アダプタを**全ページで同期（描画ブロッキング）読み込み**していました。本棚やトップなど大半のページには不要です。

問題は、各ページのグラフ初期化が `DOMContentLoaded` で囲まれず**インラインで即時 `new Chart()`** しているため、ライブラリに `defer` を付けると壊れること。そこで「**本文にチャートがあるページだけライブラリを読む**」自動判定にしました。

```php
<?php
// 本文（$d_content）に new Chart( を含むページだけ true。
// 自動判定なのでフラグ付け忘れで壊れない。
$g_need_charts = !empty($g_load_charts)
    || (isset($d_content) && stripos($d_content, 'new Chart') !== false);
?>
<?php if ($g_need_charts): ?>
<script src="https://cdn.jsdelivr.net/npm/chart.js@4.4.0/dist/chart.umd.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/moment@2.29.4/moment.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/chartjs-adapter-moment@1.0.1/dist/chartjs-adapter-moment.min.js"></script>
<?php endif; ?>
```

テンプレートは `$d_content = ob_get_clean();` でページ本文を確定してからベーステンプレートを読み込む構造だったので、`$d_content` を文字列検索するだけで「このページはグラフを描くか」を**取りこぼしなく**判定できました。これで大半のページから約300KBのブロッキングJSが消えます。

## 地雷④（本丸）: Tailwind Play CDN を本番で使っていた

最大の犯人がこれです。

```html
<!-- Before: 実行時コンパイル版 -->
<script src="https://cdn.tailwindcss.com"></script>
<script>tailwind.config = { /* ... */ }</script>
```

`cdn.tailwindcss.com`（Tailwind Play CDN）は、**ブラウザ内でDOMを走査してCSSをその場でコンパイルする開発用ビルド**です。300KB超のJSをダウンロードし、**ページを開くたびに実行時にCSSを生成**します。

- PCのCPUなら数十msで終わり気づかない
- **モバイルCPUは数倍遅いので体感に直結**
- しかも描画ブロッキング + FOUC（一瞬スタイルなしで表示される）

Tailwind公式も「Play CDN は本番では使うな」と明言しています。これを**事前ビルドした静的CSS**に置き換えました。

```jsonc
// package.json
{
  "scripts": {
    "build:css": "npx -y tailwindcss@3.4.17 -i ./css/tailwind.src.css -o ./css/tailwind.css --minify"
  }
}
```

`tailwind.config.js` には、これまで `tailwind.config = {...}` にインラインで書いていた設定（`darkMode: 'class'`、カスタム `screens`、独自カラー）をそのまま移植します。注意点として、**文字列連結で動的生成しているクラス**（`text-<?= $color ?>-500` のような箇所）はビルド時のスキャナが検出できないので `safelist` に登録します。

```js
// tailwind.config.js（抜粋）
module.exports = {
  darkMode: 'class',
  content: ["./template/**/*.php", "./*.php", "./js/**/*.js", /* ... */],
  safelist: ['text-green-500', 'text-orange-500', 'text-red-500',
             'text-yellow-500', 'text-purple-500'], // 動的生成クラス
  theme: { extend: { /* screens, colors ... */ } },
};
```

```html
<!-- After: 事前ビルドした静的CSS -->
<link rel="stylesheet" href="/css/tailwind.css?v=<?php echo asset_ver('/css/tailwind.css'); ?>">
```

結果:

| | Before（Play CDN） | After（静的CSS） |
|---|---|---|
| 配信物 | 300KB超のJS + 実行時コンパイル | **約116KB（gzip 16.4KB）のCSS** |
| 描画 | ブロッキング + FOUC | キャッシュ可・FOUCなし |
| キャッシュ | SWバイパスで毎回取得 | `Cache-Control: public, max-age=2592000`（30日） |
| モバイルCPU | 毎ページ重いコンパイル | **コンパイルなし** |

**トレードオフ**: Play CDN のような自動コンパイルが無くなるので、クラスを追加・変更したら `npm run build:css` で再ビルドが必要になります。CIに組み込むか、`watch:css` を回すのが現実的です。

# まとめ: モバイルの「なんか遅い」はCPU律速を疑う

今回の3つ（+SW）は、いずれも **「PCでは速いCPUに隠れて気づかない」** タイプの問題でした。

1. **Service Worker** — SWRの「タイムアウトでキャッシュ返却」は、低速回線で古い/空のページを配信しうる。**完全なレスポンスだけキャッシュ**し、`navigation preload` を使う。
2. **`?v=time()` は禁じ手** — ブラウザもSWもキャッシュできない。**`filemtime()` ベース**にする。
3. **重いJSは必要なページだけ** — 全ページ同期読み込みをやめ、本文から自動判定で出し分け。
4. **Tailwind Play CDN は本番で使わない** — 実行時コンパイルがモバイルCPUを直撃。**事前ビルドの静的CSS**に。

そして一番の学びは、**症状が変わったら対症療法を重ねず、直前の修正そのものを疑う**こと。「白画面 → 遅い → やっぱり遅い」と転んだ先で、毎回ひとつ前の判断に立ち返ったのが収束への近道でした。
