# はじめに

この半年ほど、Databricks と MLflow で LLM-as-a-Judge を検証する記事を何本か書いてきました。ジャッジを人のラベルと突き合わせる。ジャッジを人の判断に近づける。ジャッジを採点役にしてプロンプトを最適化する。どれも1本ずつ結果は書きましたが、「結局、本番で使う前に何をどの順番で確かめればよいのか」はまとめていませんでした。

この記事では新しい検証はしません。これまでの検証結果を並べて、LLM ジャッジを本番で使う前に私が確認していることを5つにまとめます。数字はすべて過去の記事で実際に出たものです。元にした記事は次の5本です。

- [ジャッジを評価するジャッジ ― LLM-as-a-Judgeの信頼性をメタ評価で保証する](https://qiita.com/taka_yayoi/items/65be4c75b65a6b7363e3)
- [その不一致、悪いのはジャッジ? それとも人間ラベル? ― LLM-as-a-Judgeメタ評価・実践編](https://qiita.com/taka_yayoi/items/45b7e54940183f9b4608)
- [人のラベルと突き合わせて見つけたプロンプトの書き漏れを、MLflow の align() で直せるか試した](https://qiita.com/taka_yayoi/items/8b9cdf2de822bf7c97f6)
- [MLflowのGuidelinesジャッジの判定がぶれるとき、ガイドラインの書き方で直せること](https://qiita.com/taka_yayoi/items/6db8b9fdbbff78d2ef34)
- [Databricks で MLflow の MemAlign と GEPA をつなぐ: MemAlign を飛ばして最適化すると、ジャッジのスコアは1.0、人の基準では0.00だった](https://qiita.com/taka_yayoi/items/28ae7d900463e0f28483)

手順の細かいコードは各記事に譲ります。ここでは、それぞれの確認で何を見て、どう判断しているかを書いていきます。

# 確認していることの全体像

先に5つを並べます。上から順に確認します。

![LLM ジャッジを本番で使う前に確認する5つのこと (fig1_five_checks.png)](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/2c4cfcec-27b5-4d3b-b471-b0aa76a50e50.png)

それぞれの確認を飛ばしたときに実際に起きたことを、表にまとめます。

| 順番 | 確認すること | 飛ばしたときに起きたこと |
| --- | --- | --- |
| 1 | ジャッジに渡る情報だけで判定できる書き方になっているか | 同じ応答でも評価のたびに yes と no が入れ替わる |
| 2 | 人のラベルと突き合わせて、一致率ではなく kappa を見る | 一致率81%のジャッジが、kappa では0.636だった |
| 3 | 食い違いを1件ずつ読み、直す対象を決める | ジャッジではなく人のラベルのほうが甘かった |
| 4 | 同じ採点を複数回行い、ぶれの幅を知る | 同じプロンプトのまま kappa が0.41から0.60まで動いた |
| 5 | ジャッジを直したあと、人の基準でもう一度測る | ジャッジのスコアは1.0、人の基準での合格率は0.00だった |

1は人のラベルがなくてもできる確認です。2から4は、20件ほどの人のラベルがあればできます。5は、ジャッジやプロンプトを直すたびに繰り返します。

# 1. ジャッジに渡る情報だけで判定できるか

最初に見るのは、ジャッジのプロンプトやガイドラインの文面です。人のラベルを集める前にできます。

MLflow 3.16.1 のソースを読んで確かめたところ、`Guidelines` ジャッジに渡っているのは、ガイドラインの文面と、トレースの request と response だけでした。子スパンのツール呼び出しは渡っていません。「チケットを起票したら起票番号を伝えること」というガイドラインでも、実際に起票したかどうかを、ジャッジは応答の文面から読み取ることになります。

この前提でガイドラインを読み直すと、ジャッジが推測で判断するしかない書き方が見つかります。私が確認しているのは次の4つです。

- 判定に必要な情報 (順序、範囲、許可する表現) が文面に書かれているか
- 条件付きのルールに、条件に当てはまらないときの扱いが書かれているか
- 1本のガイドラインに、逆向きの要求が2つ入っていないか
- 列挙が「など」で終わっていないか

もう1つ、特定の語を含むかどうかのように文字列で決まる判定は、LLM ジャッジにせず、コードのスコアラーにします。判定は毎回同じになり、ジャッジのモデルを呼ぶ費用もかかりません。

判定がぶれるとき、ジャッジのモデルや temperature を先に変えたくなります。ただ、判定に必要な情報が文面にないなら、モデルを替えてもジャッジは推測で判断するままです。私は文面を先に直し、モデルを比べるのはその後にしています。

# 2. 一致率ではなく kappa を見る

文面を直したら、人のラベルと突き合わせます。問い合わせと応答の組を20件ほど用意し、人が pass / fail を付け、同じデータをジャッジにも判定させます。

このとき、一致率だけでは判断しません。データの9割が pass なら、ジャッジが中身を見ずに全部 pass と答えても一致率は90%になるからです。Cohen's kappa は、こうした偶然そろう分を差し引いた数字です。1なら完全に一致、0なら当てずっぽうと同じ程度です。

実際に、ベーカリーのレビュー返信を題材にした検証では次の結果でした。

| 指標 | 値 |
| --- | --- |
| 一致率 | 0.812 |
| Cohen's kappa | 0.636 |

一致率の81%は悪くない数字に見えます。kappa にすると、印象は一段下がります。

kappa はジャッジごとに出します。顧客サポートのトリアージを題材にした検証では、同じアプリに付けた3つのジャッジで、結果がはっきり分かれました。

| ジャッジ | 一致率 | Cohen's kappa |
| --- | --- | --- |
| no_hallucination | 1.000 | 1.000 |
| intent_match | 1.000 | 1.000 |
| politeness | 0.167 | 0.016 |

politeness のジャッジは、人が pass とした11件のうち10件を fail にしていました。突き合わせをしていなければ、この fail の多さを応答の品質の問題として受け取っていたはずです。

私が本番で使う目安にしているのは、kappa 0.6以上です。Landis & Koch の基準で「実質的な一致」とされる水準です。下回ったジャッジは、次の確認に進んで原因を調べます。

突き合わせのデータを作るときに気をつけていることが2つあります。

- 判定が分かれそうな微妙なケースを意図して混ぜる。明らかな pass ばかりでは、ジャッジの差が見えない
- ジャッジのモデルは、アプリのモデルと別の系統にする。同じ指示文でも、ジャッジのモデルを Llama 3.3 70B から Claude Sonnet 4.6 に替えると、politeness の fail は3件から11件に変わった

# 3. 食い違いを1件ずつ読み、直す対象を決める

kappa の数字を出して終わりにせず、人とジャッジの判定が分かれたケースを1件ずつ読みます。

食い違いを見つけたとき、直す対象はジャッジとは限りません。これまでの検証で出てきた食い違いは、次の3種類に分かれました。

| 種類 | 実際にあった例 | 直す対象 |
| --- | --- | --- |
| 人のラベルが基準どおりでない | 不満を含むレビューへの返信に謝罪がない。ジャッジは基準の「苦情への謝罪」を当てはめて fail。人は「受け止めているから」と pass にしていた | 人のラベル、または基準そのもの |
| プロンプトに書いていない運用がある | 人は送料込みの20,100円で「引き継ぎが必要」と判定。ジャッジは商品代金の18,900円で判断して pass | ジャッジのプロンプト |
| ジャッジの読み違い | 「今回で2回目」の問い合わせに、「3回以上は引き継ぐ」のルールを当てはめた | プロンプトの書き足しでは直らないことがある |

1つ目の例では、ジャッジの判定理由を読むと筋が通っていました。基準を厳密に守っていなかったのは、ラベルを付けた私のほうです。このときの不一致3件は、すべて「人が pass、ジャッジが fail」でした。

kappa が測っているのは、判定の正しさではなく、人のラベルとどれだけ合うかです。人のラベルに甘さや付け間違いが残ったままジャッジを人に合わせると、ジャッジを人の間違いに合わせることになります。私は、ジャッジを直す前に、人のラベルと基準を先に確定させています。

2つ目の種類は、人のラベルと突き合わせて初めて見つかります。文書になっているルールだけをプロンプトに書くと、現場で使われている運用が抜けます。食い違いの理由を読むと、何を書き足せばよいかが分かります。

# 4. 同じ採点を複数回行い、ぶれの幅を知る

ジャッジを直す前に、もう1つ確認します。同じジャッジで同じデータを複数回採点し、結果がどのくらい動くかを見ます。

返金の問い合わせ20件を題材にした検証では、プロンプトを変えていないのに、kappa が0.41から0.60まで動きました。20件だと、1件の判定が変わるだけで kappa は0.1ほど動きます。同じプロンプトの一致率が、GEPA の中で採点したときは85%、ノートブックで採点したときは75%だったこともあります。

この幅を知らないまま調整前後を1回ずつ比べると、たまたまの差を改善と読んでしまいます。上の検証では、調整前と調整後をそれぞれ3回採点しました。

| | 1回目 | 2回目 | 3回目 | 平均 |
| --- | --- | --- | --- | --- |
| 調整前 | 0.50 | 0.41 | 0.50 | 0.47 |
| 調整後 | 0.49 | 0.49 | 0.49 | 0.49 |

平均の差は0.02で、ぶれの幅に収まります。私はこの結果を「改善した」とは読みませんでした。

私の基準は単純です。調整前後はそれぞれ3回以上採点する。差がぶれの幅より小さければ、改善したとは言わない。件数が20件程度のときは、とくにこの確認を省かないようにしています。

# 5. ジャッジを直したあと、人の基準でもう一度測る

ここまで確認して、ようやくジャッジを直します。手で書き足す方法と、MLflow の `align()` で人のラベルから調整する方法があります。どちらの場合も、直したあとに人の基準でもう一度測ります。

## align() の結果をそのまま採用しない

`align()` は、人がラベルに付けた理由を読み、判断の指針をプロンプトに書き足す案を出します。返金の問い合わせの検証では、MemAlign が送料込みと合計額の運用を正しく拾いました。一方で、人が求めていない条件も1つ足していて、その条件のせいで、もともと正しかった1件の判定が変わりました。正しくなった1件と、誤るようになった1件で、差し引きはゼロでした。

`align()` がはっきり効いた検証もあります。野球の打撃分析エージェントを題材にした検証では、MemAlign にかける前のジャッジは、人の基準と1件も一致していませんでした。MemAlign にかけたあとは、一致率が0.94になりました。

2つの検証を並べると、効いたときと効かなかったときの違いが見えてきます。

| | 効かなかった検証 | 効いた検証 |
| --- | --- | --- |
| 食い違いの形 | 3種類の運用が2〜3件ずつ散らばっていた | 人の基準は2つで、外れ方がそろっていた |
| 調整前後の差 | kappa の平均が0.47から0.49。同じプロンプトでの動き (0.41〜0.60) に収まる | 人の基準との一致率が0.00から0.94 |

食い違いの種類がそろっていて件数が多いほど、`align()` は効きやすい。逆に、数件ずつ散らばった食い違いは、ぶれに埋もれます。3の確認で食い違いを種類に分けておくと、`align()` を使うか、手で書き足すかを決めやすくなります。

## ジャッジを採点役にするなら、人の基準を別に残す

直したジャッジは、プロンプト最適化の採点役にも使えます。ここで、ジャッジを人に合わせる手順を飛ばすとどうなるかを確かめました。同じプロンプトを、採点役のジャッジだけを変えて2通りに最適化した結果です。

| 採点役のジャッジ | ジャッジのスコア (最適化後) | 人の基準での合格率 |
| --- | --- | --- |
| MemAlign で人に合わせたジャッジ | 0.9 | 0.94 |
| 人に合わせていないジャッジ | 1.0 | 0.00 |

人に合わせていないジャッジを採点役にすると、ジャッジのスコアは1.0まで上がりました。人の基準での合格率は0.00で、最適化する前の0.06より下がっています。最適化は、採点役のジャッジに向けて忠実にプロンプトを直します。ジャッジが人とずれていれば、ずれた方向に進みます。

この結果から、私は2つのことを決めています。

- ジャッジを採点役にする前に、人のラベルとの一致を確かめる
- 最適化の成果をジャッジのスコアだけで判断しない。少数でも、人の基準で直接測る手段を残す

2つ目は、ジャッジを人に合わせたあとでも同じです。ジャッジの調整が途中で失敗していても、スコアだけを見ていると気づけません。実際に、ライブラリのバージョンの組み合わせによって、`align()` が例外を出さずに、指示が元のままのジャッジを返したことがありました。人の基準で測る手段があれば、こうした場合にも気づけます。

# まとめ

LLM ジャッジを本番で使う前に確認していることを、これまでの検証結果からまとめました。

- ジャッジに渡っているのは文面だけ。判定に必要な情報、対象外のときの扱いを文面に書く。文字列で決まる判定はコードにする
- 人のラベルと突き合わせるときは、一致率ではなく kappa を見る。本番で使う目安は0.6以上
- **食い違いは1件ずつ読む。直す対象は、人のラベル、プロンプト、ジャッジのモデルのどれかに分かれる**
- 同じプロンプトでも、採点のたびに kappa は0.1ほど動く。調整前後は3回以上採点して比べる
- `align()` は、食い違いの種類がそろっていて件数が多いときに効きやすい。足された指針は読んでから採用する
- **ジャッジを採点役にして最適化するときは、人の基準で直接測る手段を別に残す**

一番の収穫は、5本の記事を並べてみて、どの検証も最後は同じところに戻っていたと分かったことでした。ジャッジは人の代わりに大量の出力を採点してくれます。ただ、そのジャッジが信頼できるかどうかは、人が付けた少数のラベルでしか確かめられません。20件のラベルを付け、食い違いを読み、直したらもう一度測る。手間はかかりますが、ジャッジの数字を根拠に何かを決めるなら、この手順は省けないと考えています。
