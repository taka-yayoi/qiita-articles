# はじめに

2026年11月に発表された第2世代のGenieで、Genie ZeroOpsがベータとして使えるようになりました。ジョブ、パイプライン、テーブルをバックグラウンドで監視し、問題を見つけると原因を調べて修正案まで出してくれるエージェントです。

- [Genie ZeroOps の概要](https://docs.databricks.com/aws/ja/zeroops/)
- [Genie ZeroOps を起動する](https://docs.databricks.com/aws/ja/zeroops/get-started)

Genieファミリー全体の中での位置づけは、以前の記事で整理しました。

https://qiita.com/taka_yayoi/items/49129c0d657364f3bd04

今回は、わざと失敗させたジョブを2つ用意して、ZeroOpsが原因をどこまで特定できるか、修正から解決までがどう流れるかを試しました。新しい機能なので、前半でコンセプトを整理してから実際の動きを見ていきます。

# Genie ZeroOpsとは

## プロンプトなしで動き続けるエージェント

ZeroOpsを理解するうえで一番分かりやすいのは、Genie Codeとの違いです。ドキュメントでは次のように説明されています。

| | Genie Code | Genie ZeroOps |
| --- | --- | --- |
| 動き出すきっかけ | ユーザーがプロンプトを入力する | プロンプトなしで継続的に動く |
| 主な役割 | パイプライン、ノートブック、ダッシュボードを作る | 本番のジョブ、パイプライン、テーブルを見張る |
| 結果の届き方 | チャットの応答 | 受信トレイにインサイトとして届く |

Genie Codeは「頼まれたら作る」エージェントで、ZeroOpsは「頼まれなくても見張る」エージェントです。夜中にジョブが落ちても、朝に受信トレイを開けば、原因と修正案がそろった状態でインサイトが待っている。データエンジニアが毎朝やっている「失敗したジョブのログを開いて原因を追う」作業を、先に済ませておいてくれる位置づけです。

## 検出から修正までの流れ

ZeroOpsの仕事は、検出、根本原因の特定、修正案の提示の3段階に分かれます。ここまでをZeroOpsがプロンプトなしで行い、修正を当てるかどうかは人が判断します。

![zeroops_flow.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/cd5b5ce0-272e-4c46-a659-dd876d472500.png)

修正の適用は、インサイトを開いたスレッドでそのままGenie Codeに頼めます。ZeroOpsとGenie Codeが別々の製品として並んでいるのではなく、見つけて調べるのがZeroOps、直すのがGenie Code、という分担で1つの流れになっています。修正したジョブが次に成功すると、インサイトは自動でクローズされます。

## 何を見つけるのか

ドキュメントに挙がっている検出対象は次の4つです。

- 失敗したジョブやパイプライン
- 成功したものの、古い、または不完全なテーブルを生成したジョブ
- データが古い、または欠落しているテーブル
- 上流のスキーマ変更などで壊れた下流のテーブル

「ジョブが失敗した」だけでなく、「ジョブは成功したのにテーブルがおかしい」まで範囲に入っているのがポイントです。ただし、テーブルのデータ品質の問題を検出するには、別途データ品質モニタリングが必要です。

ベータの現時点では、監視対象はジョブ、パイプライン、テーブルで、モデルやアプリは対象外です。パフォーマンスやコストの劣化も検出の対象には入っていません。

## 人の確認なしに本番を変更しない

運用を任せるエージェントで一番気になるのは、勝手に本番を触らないかどうかだと思います。ZeroOpsは、人によるレビューなしに本番のデータやコードを変更しません。Gitリポジトリからコードを実行するジョブでは、修正を新しいブランチにプッシュしてプルリクエストを開けますが、これもユーザーが明示的に依頼した場合に限られます。

また、インサイトが生成されるのは、設定したユーザーがOWNER、CAN MANAGE、CAN VIEWのいずれかの権限を持つアセットだけです。自分が見られないジョブについて、ZeroOpsが代わりに調べてくることはありません。

# 試すための準備

## プレビューで有効にする

ZeroOpsはベータなので、ワークスペース管理者がプレビューページで有効にします。

![zeroops_preview.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/792664a8-0df9-447d-ad6d-0168849a7b35.png)

有効にすると、ジョブとパイプラインの画面の上部にZeroOpsの入口が表示されます。

![zeroops_jobs_page.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/5fe506c4-6905-4288-a608-d24347745ca4.png)

## 失敗するジョブを2つ用意する

普段のジョブが順調に動いていると、ZeroOpsには見つけるものがありません。そこで、原因の種類が違う2つの失敗を作りました。

| ジョブ | 失敗の原因 |
| --- | --- |
| `zeroops_demo_daily_sales_report` | コードの不具合。設定のキー名が `min_amt` なのに、コードは `min_amount` で読んでいる |
| `zeroops_demo_customer_totals` | 上流のスキーマ変更。上流テーブル `orders` の列 `amount` を `order_amount` に変えて作り直した |

1つ目のジョブで動かすノートブックは次のとおりです。設定の辞書を作るセルと、それを読むセルに分けています。

```python
# セル1: レポートの設定
config = {"min_amt": 1000, "report_table": "daily_sales_report"}
```

```python
# セル2: 一定金額以上の売上だけを日別に集計する
# 設定のキー名が違うので、ここで KeyError になる
min_amount = config["min_amount"]
df = spark.table(f"{catalog}.{schema}.sales").filter(f"amount >= {min_amount}")
(
    df.groupBy("sale_date")
    .sum("amount")
    .withColumnRenamed("sum(amount)", "total_amount")
    .write.mode("overwrite")
    .saveAsTable(f"{catalog}.{schema}.{config['report_table']}")
)
```

2つ目のジョブは、上流の `orders` の列 `amount` を顧客ごとに集計します。

```python
# 顧客ごとの注文金額の合計
df = spark.sql(f"""
    SELECT customer_id, SUM(amount) AS total_amount, COUNT(*) AS order_count
    FROM {catalog}.{schema}.orders
    GROUP BY customer_id
""")
df.write.mode("overwrite").saveAsTable(f"{catalog}.{schema}.customer_totals")
```

こちらは、まず列 `amount` を持つ `orders` で1回成功させます。そのあと `orders` を削除し、列名を `order_amount` に変えて作り直してから、もう一度実行して失敗させます。ジョブの作成と実行はDatabricks SDKでノートブックから行い、どちらもサーバーレスで動かしました。

# 監視対象を設定する

ジョブとパイプラインの画面で「ZeroOpsを開く」をクリックすると、Genie Codeの画面でZeroOpsの受信トレイが開きます。監視対象の設定もGenie Codeのチャットで行います。「all owned jobs」のように自然言語で範囲を伝えると、それが設定に反映されます。

設定の内容は、チャットに表示される「ZeroOps設定」の「ビュー」で確認できます。今回は「すべての所有するジョブ」に加えて、用意した2つのジョブを個別にも指定しました。

![zeroops_config.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/51d49713-2bdc-4b05-aeed-96e284525795.png)

この画面から、設定できる項目がひととおり分かります。

- **範囲**: ジョブに加えて、スキーマ単位でも監視対象を指定できる
- **通知**: Slack、Microsoft Teams、PagerDuty、Webhookから選べる。今回は設定せず、受信トレイで確認した
- **カスタム指示**: 調査で実行すべきことや避けるべきことを書いておける
- **リポジトリの指示**: 調査するジョブのソースがあるフォルダーと、その親フォルダーにあるAGENTS.mdとCLAUDE.mdも読み込む

リポジトリの指示は地味ですが効く仕組みだと思います。コーディングエージェント向けにすでにAGENTS.mdを整備しているチームなら、そのプロジェクトの規約がZeroOpsの調査にもそのまま使われます。

# 受信トレイに2件のインサイトが届く

設定してしばらくすると、受信トレイに2件のインサイトが届きました。スコープを設定すると過去24時間分がさかのぼって調べられるので、設定より前に失敗していたジョブも対象になります。

![zeroops_inbox_open.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/be212533-27d3-4290-ab10-cf8b932fddaa.png)

インサイトのタイトルの時点で、原因の要点が書かれています。1件目は設定のキー名の不一致、2件目は上流の `orders` が列名を変えて作り直されたことです。どちらも、こちらが仕込んだ原因と一致していました。

# コードの不具合を特定し、修正する

## 根本原因と修正案

1件目のインサイトを開くと、失敗の内容、根本原因、証拠、修正案が1つのレポートにまとまっています。

![zeroops_insight_keyerror.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/fb1b78b8-b1fb-4dd9-b0e6-9a1938fa0bf8.png)

根本原因は「セル1で作った設定のキーが `"min_amt"` で、セル2は `config["min_amount"]` で読んでいる」と特定されています。証拠として、実行時の出力と、実際に実行されたソースの両方を挙げているのが良いところです。

ジョブにリトライは設定していませんでしたが、ランには2回の試行が記録されていました。ZeroOpsは「2回とも同じ失敗をしているので、一時的なエラーではない」と判断しています。原因の候補を1つずつ消していく、人が障害を調べるときと同じ手順です。

修正案は、セル1のキー名を `min_amount` に合わせる差分です。そのあとの確認手順として、失敗したランを修復するコマンドも添えられています。

## 同じスレッドで修正を頼む

インサイトの画面はGenie Codeのスレッドになっているので、そのまま修正を頼めます。

```
修正を適用して、失敗したランを修復(repair)してください
```

Genie Codeはノートブックのセルを書き換えたあと、ランの修復に進みます。修復はCLIのコマンドで行われ、実行の前に許可を求められます。

![zeroops_repair_approval.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/45994eca-67c7-4860-a6d1-b212b3a28995.png)

ジョブを再実行する操作なので、ここで一度止まるのは妥当だと思います。許可すると、失敗したタスクだけが再実行されます。

![zeroops_repair_result.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/b938bb4d-e690-4216-946d-132730cc41da.png)

3回目の試行でタスク `main` が成功し、ラン全体の状態が `SUCCESS` になりました。右側にはジョブランの画面が開いていて、結果をその場で確かめられます。書き換えたノートブックは、入力欄の上に変更のあったアセットとして表示され、「すべて承認」と「すべて拒否」で変更を確定するか取り消すかを選べます。

## 次の成功でインサイトがクローズされる

しばらくして受信トレイを開くと、1件目のインサイトは Resolved になっていました。ステータスを手で変える操作はしていません。

![zeroops_inbox_resolved.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/60fc9244-61ee-4192-a3c5-c674254fc0bc.png)

ドキュメントには、次にジョブが成功すると知見が自動でクローズされると書かれています。今回のように修復したランが成功した場合も、これに数えられることが確認できました。直したのに受信トレイに残り続ける、ということがないので、受信トレイを「今まだ対応が必要なもの」の一覧として使えます。

# 上流のスキーマ変更を原因として辿る

2件目は、下流のジョブのコードには問題がなく、上流のテーブルが変わったことで壊れたケースです。ジョブのエラーだけを見ると「列 `amount` が見つからない」としか分からないので、原因を上流まで辿れるかが見どころでした。

![zeroops_insight_schema.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/12bc10ad-dcc5-4ed0-824c-ae8dd0217ce8.png)

ZeroOpsは、次の2つの証拠から原因を特定していました。

- **コードは変わっていない**: 成功した前回のランと失敗したランで、ノートブックのソースのダイジェストが同じであることを確かめている
- **上流のテーブルが作り直された**: `orders` のテーブル履歴を見て、2つのランの間に `CREATE TABLE` が実行されたことを突き止めている

時系列にすると次のとおりです。

![zeroops_scenario2_timeline.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/b78fb0b2-5b04-479b-870c-3ab50ea61613.png)

ここが今回一番感心したところです。ジョブのログだけでなく、ソースの比較とテーブル履歴を組み合わせて「コードの変更ではなく、スキーマの変更」と結論づけています。テーブルを作り直したノートブックのIDまで挙げているので、誰がどこで変えたかを追う手がかりにもなります。

修正案は2通り出ていました。

- **主案**: 下流のセル2を `SUM(order_amount)` に変える。`total_amount` という別名はそのまま残すので、出力テーブル `customer_totals` のスキーマは変わらない
- **代替案**: 列名の変更が意図したものでなければ、上流を作るノートブックを直して `amount` に戻す。その場合、下流のノートブックは変更しない

列名の変更が意図したものかどうかは、ZeroOpsには分かりません。そこで両方の案を出して、どちらを採るかを人に委ねています。上流と下流のどちらを直すべきかは、チームの事情で決まることなので、この作りは理にかなっていると思います。このインサイトは、修正を適用せずに確認だけで終えました。

# まとめ

Genie ZeroOpsを試して分かったことをまとめます。

- ZeroOpsはプロンプトなしで動き続け、ジョブ、パイプライン、テーブルの問題をインサイトとして受信トレイに届ける。Genie Codeが「頼まれたら作る」のに対して、ZeroOpsは「頼まれなくても見張る」
- 監視対象はGenie Codeのチャットで設定する。スコープを設定すると過去24時間分がさかのぼって調べられる
- **コードの不具合では、実行時の出力と実行されたソースを証拠に、原因の行まで特定した**
- **上流のスキーマ変更では、ソースのダイジェストの比較とテーブル履歴から、コードではなく上流のテーブルが原因だと突き止めた**
- 修正は同じスレッドでGenie Codeに頼める。ランの修復のようにジョブを動かす操作は、実行前に許可を求められる
- 修正したジョブが成功すると、インサイトは自動で Resolved になる
- 列名の変更のように意図が分からない原因には、下流を直す案と上流を戻す案の両方が出る

一番の収穫は、2件目のスキーマ変更の調べ方でした。エラーメッセージを見るだけなら誰でもできますが、「前回成功したときとコードは同じか」「その間にテーブルに何が起きたか」を確かめにいくのは、障害対応に慣れた人の手順そのものです。それが朝には受信トレイに届いている、というのがZeroOpsの価値だと思います。まずは自分が所有するジョブだけを監視対象にして、どんなインサイトが届くかを見てみるところから始めるのが良さそうです。
