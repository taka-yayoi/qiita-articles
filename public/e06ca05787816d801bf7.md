# Databricks AI Gateway(ベータ版)とは何か

2025年2月、DatabricksはAI Gateway(ベータ版)をリリースしました。これは従来のModel Servingに同梱されていたAI Gateway機能を大幅に進化させたもので、LLMエンドポイントとコーディングエージェントを一元管理するための**エンタープライズコントロールプレーン**です。

https://docs.databricks.com/aws/ja/ai-gateway/overview-beta

本記事では、従来のAI Gatewayとの違いを中心に、新しいAI Gateway(ベータ版)のアーキテクチャと価値を解説します。

:::note info
**注意**: 2025年2月時点では日本リージョンではまだプレビュー利用ができません。利用するにはアカウント管理者がPreviewsページからAI Gateway(Beta)を有効化する必要がありますが、対応リージョン外ではこのオプションが表示されません。
:::

# 従来のAI Gateway: Model Serving同梱の機能

従来のAI Gatewayは、[Model Serving](https://docs.databricks.com/aws/ja/machine-learning/model-serving/)エンドポイントに**組み込まれた機能**として提供されていました。

利用の流れは以下の通りです。

1. Model Servingエンドポイントを作成する(外部モデル、プロビジョンドスループット、カスタムモデルなど)
2. そのエンドポイント上で「Edit AI Gateway」からゲートウェイ機能を個別に有効化する

つまり、ガバナンス機能(レート制限、使用状況追跡、推論テーブル、フォールバックなど)はModel Servingのリクエスト処理パイプラインの中に存在しており、**Model Servingエンドポイントにリクエストが来たときにのみ発動する**仕組みでした。

![Screenshot 2026-02-13 at 15.07.26.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/beecec29-5009-4d93-974d-78872c06c32a.png)

この設計には根本的な制約がありました。CursorやClaude Codeなどのコーディングエージェントは、ローカルマシンで動くクライアントサイドツールです。これらは自前のSDK/HTTPクライアントで直接OpenAI API、Anthropic API、Google APIなどを叩くため、**Databricks Model Servingを経由しません**。Gatewayの管理対象外だったのです。

![Screenshot 2026-02-13 at 15.18.56.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/5482b5d7-643b-494b-af7b-f469f1af15b9.png)


# 新しいAI Gateway(ベータ版): 独立したコントロールプレーン

## アーキテクチャの根本的な変化

新しいAI Gateway(ベータ版)は、Model Servingから独立した**汎用AIトラフィックプロキシ**として再設計されています。

![Screenshot 2026-02-13 at 15.27.17.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/bd424434-1d40-4c83-87ad-417a18da8af9.png)


「汎用AIトラフィックプロキシ」とは、プロトコルの種類やクライアントの種類を問わず、あらゆるAI関連のHTTPリクエストを受け取り、ガバナンス機能を適用した上で、適切なバックエンドに中継する独立した中間レイヤーのことです。

従来版ではModel Servingパイプラインの内部にGateway機能が存在していたため、クライアントサイドで独自プロトコルを使うツールのトラフィックを捕捉する手段がありませんでした。新しいGatewayはその制約から解放されています。

![Screenshot 2026-02-13 at 15.19.16.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/bec685fc-6555-4bff-ae6c-4f32cf205fcd.png)

## エンドポイントのデプロイが不要

従来は「Model Servingエンドポイントを作成する → Gateway設定を有効化する」という2ステップが必要でした。

新しいAI Gateway(ベータ版)では、**Databricksが一般的なLLM向けのAI Gatewayエンドポイントをあらかじめ提供**しています。開発者がModel Servingエンドポイントを自分でデプロイ・設定する必要はなく、AI GatewayのURLとPATを設定するだけで、裏側の[FMAPI(基盤モデルAPI)](https://docs.databricks.com/aws/ja/machine-learning/foundation-model-apis)に接続されます。

![Screenshot 2026-02-13 at 15.22.04.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/a570a5d2-ae9f-4a22-be01-c7d3fd1ecf8e.png)

## Databricks-hostedモデル

コーディングエージェント統合で使われるモデルはすべて`databricks-`プレフィックスが付いた**Databricksホスティングモデル**です。

- `databricks-gpt-5-2`
- `databricks-claude-opus-4-6`
- `databricks-gemini-2-5-flash`

AI GatewayからOpenAI APIやAnthropic APIに直接リクエストが飛ぶのではなく、DatabricksがFMAPIのpay-per-tokenで自社インフラ上にホスティングしているモデルに接続されます。企業としては、APIキーが各開発者に分散せず、トラフィックもDatabricksのセキュリティ境界内に留まるため、ガバナンス上のメリットがあります。

# コーディングエージェント統合

新しいAI Gateway(ベータ版)の最大の特徴は、コーディングエージェントのガバナンスです。各エージェント固有のプロトコルをネイティブに理解する**専用パス**が用意されています。

| エージェント | base URL パス | モデル例 |
|---|---|---|
| Cursor | `/cursor/v1` | databricks-gpt-5-2 |
| Codex CLI | `/openai/v1` | databricks-gpt-5-2 |
| Gemini CLI | `/gemini` | databricks-gemini-2-5-flash |
| Claude Code | `/anthropic` | databricks-claude-opus-4-6 |

各エージェントのbase URLをAI GatewayのURLに書き換えるだけで、トラフィックがDatabricksを経由するようになります。

## 設定例: Claude Code

Claude Codeの場合、`~/.claude/settings.json`に以下を設定します。

```json
{
  "env": {
    "ANTHROPIC_MODEL": "databricks-claude-opus-4-6",
    "ANTHROPIC_BASE_URL": "https://<ai-gateway-url>/anthropic",
    "ANTHROPIC_AUTH_TOKEN": "<databricks_pat_token>",
    "ANTHROPIC_CUSTOM_HEADERS": "x-databricks-use-coding-agent-mode: true",
    "CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS": "1"
  }
}
```

## 設定例: Cursor

CursorではSettings > Models > API Keysから以下を設定します。

- Override OpenAI Base URLを有効化: `https://<ai-gateway-url>/cursor/v1`
- OpenAI API Keyフィールド: DatabricksのPATを入力
- カスタムモデルとしてAI Gatewayエンドポイント名を追加

## ダッシュボードとOpenTelemetry

AI Gatewayのページから「View Dashboard」を選択すると、コーディングツールの使用状況を可視化するダッシュボードが自動生成されます。

![Screenshot 2026-02-13 at 15.25.44.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/5f1782fb-a19b-4a63-ace6-0d9f5a670cb1.png)

さらにClaude Codeについては、OpenTelemetryを使ったメトリクスとログのエクスポートにも対応しています。Unity CatalogのDeltaテーブルにメトリクスを収集し、より詳細な分析が可能です。

# サポートされている機能一覧

| 機能 | 説明 |
|---|---|
| 権限 | エンドポイントにアクセスできるユーザーを制御 |
| 使用状況の追跡 | システムテーブルを使用して使用状況とコストを監視 |
| 推論テーブル | Unity Catalog Deltaテーブル内のリクエストとレスポンスを監視・監査 |
| 運用メトリクス | 使用状況をリアルタイムで監視 |
| レート制限 | エンドポイント、ユーザー、またはグループレベルで消費制限を適用 |
| フォールバック | 障害時に複数のプロバイダーにルーティングして信頼性を向上 |

ベータ期間中はAI Gateway機能に料金は発生しません。

# 従来版との比較まとめ

| 観点 | 従来のAI Gateway | AI Gateway(ベータ版) |
|---|---|---|
| 位置づけ | Model Servingのオプション機能 | 独立したコントロールプレーン |
| エンドポイント作成 | 必要(自分でデプロイ) | 不要(プリセット提供) |
| 対応プロトコル | Model Serving APIフォーマットのみ | OpenAI/Anthropic/Gemini等をネイティブサポート |
| コーディングエージェント | 対象外 | Cursor、Claude Code、Codex CLI、Gemini CLIをサポート |
| UI | Model Serving画面内の設定項目 | 専用UI + ダッシュボード |
| 利用開始方法 | エンドポイント作成 → Gateway設定の有効化 | base URLとPATを設定するだけ |

# エンタープライズでの価値

管理者の視点で整理すると以下のようになります。

**従来**: 開発者ごとにClaude CodeがAnthropicを直接叩く、CursorがOpenAIを直接叩くなど、AIツールの利用状況が完全に把握不能でした。

**新しいAI Gateway**: AI GatewayのURLとDatabricks PATを開発者に配布するだけで、レート制限、使用状況追跡、ダッシュボードが自動的に適用されます。エンドポイントの作成・管理というオーバーヘッドなしに、ガバナンスレイヤーをすぐに挟めるのが新しい設計の核心です。

特にコーディングエージェントの企業導入が進む中、「誰が、いつ、どのモデルを、どれくらい使っているか」を一元的に把握できるこの機能は、エンタープライズにとって非常に重要な価値を持ちます。
