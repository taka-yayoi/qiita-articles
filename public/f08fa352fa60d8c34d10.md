# その違和感は、正しい

宣言型って、結局なんなのでしょうか。

declarative、宣言型、宣言的。Terraform でも Kubernetes でも、最近の Databricks のパイプラインでも、説明には必ずこの言葉が出てきます。何度も見ているのに、いざ自分の言葉で説明しようとすると、手応えがするりと逃げていく。そういう感覚に、心当たりはないでしょうか。

最初にお伝えしたいのは、その違和感は理解力の問題ではない、ということです。あなたが「宣言型」をうまく掴めないのだとしたら、その原因のかなりの部分は、概念そのものではなく「宣言型」という訳語の側にあります。

この記事は、declarative という概念を解きほぐすための記事です。ただし、新しく難しいことを覚えてもらうための記事ではありません。むしろ逆で、「あなたはとっくにこの概念を使いこなしている」ということに気づいてもらうための記事です。読み終えたとき、宣言型という言葉が、急に当たり前のものに見えていれば成功です。

# なぜ「宣言型」という言葉は伝わらないのか

まず、訳語の話から始めます。

declarative の動詞形は declare です。この語には、大きく二つの顔があります。ひとつは「高らかに言い放つ」という顔。独立宣言、共同宣言、勝利宣言。日本語の「宣言」は、ほぼこちらの意味だけを引き受けています。格式ばっていて、どこか一回性の、重い言葉です。

しかし declare にはもうひとつ、まったく実務的な顔があります。「申告する」です。確定申告、税関申告。あるべき数字や持ち物を、当局に向かって「これが事実です」と差し出す行為。declarative が本当に近いのは、実はこちらの顔のほうです。にもかかわらず、「宣言型」という訳語は、申告のニュアンスをきれいに捨ててしまいました。

もうひとつ、英語と日本語のあいだには構造的な差があります。英語には imperative(命令文)と declarative(平叙文・宣言文)という、文法のカテゴリーがあります。「ドアを閉めろ」と「ドアは閉まっている」の違いです。英語話者は学校文法でこの対比に触れているので、declarative と聞けば「ああ、命令ではなく、事実を述べるほうね」と直感が働きます。

日本語には、この足場がありません。文法用語としての「宣言文」は、ほとんど流通していないからです。つまり日本語話者にとって「宣言型」は、対になるはずの「命令型」と違って、寄りかかれる日常的な感覚を持たない言葉として、宙に浮いてしまっているのです。

ここで訳語を断罪したいわけではありません。「宣言型」はすでに用語として定着していて、いまさら置き換えるのは現実的ではありません。お伝えしたいのは、わかりにくさには明確な理由があり、それはあなたの側の問題ではない、ということだけです。

# declarative が本当に言っている三つのこと

では、declarative という言葉は本当のところ何を指しているのか。三つに分けて整理します。

ひとつめ、手順を書かない。「まずこれをして、次にこれをして」という処理の順番を、書き手は記述しません。

ふたつめ、結果を書く。手順の代わりに、最終的にどうあってほしいか、つまり「あるべき状態」を記述します。

みっつめ、How はランタイムに委ねる。書かれた「あるべき状態」を実際にどう実現するか、その手順の組み立ては、システム側が引き受けます。

対になる命令型(imperative)は、この裏返しです。手順を一歩ずつ書き、状態は手順の結果として副次的に生まれ、How はすべて書き手が握ります。

![Screenshot 2026-05-22 at 20.44.51.JPG](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/8018d0eb-2f4a-4ef3-85d4-83df58d433ff.jpeg)

両者は、同じ結果にたどり着くための、まったく逆の書き方です。書き手が握る範囲とシステムに委ねる範囲が、ちょうど反転しています。

ここで、ひとつ気づいてほしいことがあります。「宣言型」という三文字の漢字は、いま挙げた三つの含意のどれも、直接には表していません。手順を書かないことも、状態を書くことも、委譲することも、「宣言」という言葉からは立ち上がってきません。「宣言型」は declare の語義のひとつを直訳しただけの言葉であって、概念の中身を指し示してはいないのです。だから掴みどころがない。これは、あなたの理解力ではなく、言葉の設計の問題です。

先ほどの「申告」のたとえが、ここで効いてきます。確定申告を思い浮かべてみてください。私たちは税額の計算手順を税務署に提出するわけではありません。「収入はこれだけ、控除はこれだけ」という、あるべき事実を申告するだけです。そこから税額をどう算出するかは、当局の仕事です。declarative とは、まさにこの構図のことです。手順ではなく、あるべき事実を申告する。計算は受け手に委ねる。

# 実は、あなたは毎日「宣言型」を書いている

ここがこの記事のいちばん大事なところです。

declarative は、新しく学ぶべき難解な概念ではありません。日本のエンジニアの多くは、すでに毎日 declarative を書いています。気づいていないのは、概念そのものではなく、「それを宣言型と呼ぶ」というラベルのほうだけなのです。

SQL を考えてみます。`SELECT name FROM users WHERE age > 20` と書くとき、私たちはテーブルをどの順でスキャンし、どのインデックスを使い、どう結合するかを書いていません。「20 歳より上のユーザーの名前」という、欲しい結果の形だけを書いています。どう取ってくるかは、クエリオプティマイザの仕事です。これは完全に declarative です。

Excel の数式も同じです。`=SUM(A1:A10)` は「A1 から A10 までの合計」というあるべき値を宣言しているのであって、加算をどういう順番で実行するかは指示していません。

HTML と CSS もそうです。`color: red` は「この要素は赤い」という状態の記述です。どのタイミングで、どうレンダリングして赤くするかは、ブラウザに委ねています。

そして Terraform や Kubernetes。Terraform の `.tf` ファイルは「サーバーが 3 台ある状態」を宣言し、Kubernetes のマニフェストは「Pod が 3 つ動いている状態」を宣言します。現状がそこからずれていれば、差分を埋めるのはツールの仕事です。Kubernetes の公式ドキュメントでも、命令的な管理と[宣言的なオブジェクト設定](https://kubernetes.io/ja/docs/concepts/overview/working-with-objects/object-management/)が、明確に対比して説明されています。

並べてみると、はっきりします。declarative とは、SQL を書ける人なら、Excel の数式を組める人なら、CSS を書いたことのある人なら、もう体得している考え方です。新しいのは概念ではなく、それらをひとつの名前で括ったという事実だけ。あなたは「宣言型を知らない」のではありません。「自分が宣言型を書いていることを、知らなかった」だけなのです。

# それでも難しく感じる、本当の理由

ここまで読んで、それでもまだ declarative にひっかかりが残るとしたら、その正体を最後に名指ししておきます。

先ほどの三つの含意のうち、ひとつめの「手順を書かない」と、ふたつめの「結果を書く」は、慣れればそれほど難しくありません。本当にひっかかるのは、みっつめの「How はランタイムに委ねる」のほうです。

委ねるとは、信頼するということです。SQL を書くとき、私たちはオプティマイザが妥当な実行計画を選んでくれると信頼しています。Kubernetes に Pod 数を宣言するとき、コントローラーが正しく差分を埋めてくれると信頼しています。declarative が成立するためには、How を受け取る側のシステムへの信頼が、どうしても前提になります。

そして、ここが語彙の問題ではなく、文化の問題に切り替わる地点です。

日本の大企業のシステム開発には、「処理の隅々まで自分たちで制御し、検証したい」「ブラックボックスに重要な判断を任せたくない」という、根強い志向があります。これは丁寧で誠実な姿勢であり、長く品質を支えてきた価値観でもあります。しかし declarative とは、まさにその制御の一部を手放し、システムの判断を信頼する考え方です。両者は、構造的に相性がよくありません。

注意したいのは、これを「日本人はこうだから」と国民性で語ってしまわないことです。それはあやしい一般化です。より正確には、これは長年の調達・検証・責任分界の慣行が育てた組織文化の問題です。誰のものを誰が保証するのか、という積み重ねの結果として、制御志向が形づくられている。だからこそ、これは変えられる種類のものでもあります。

declarative が難しく感じられるとき、ひっかかっているのは多くの場合、漢字三文字の意味ではありません。「How を手放して、システムを信頼できるか」という、もっと手前の問いなのです。

# 実務での橋渡し — 訳語と戦わない

最後に、実務的な提案をひとつ。

「宣言型」という訳語が弱いことは、ここまで見てきた通りです。しかし、だからといって新しい訳語を広めようとするのは、現実的ではありません。用語はすでに固着していますし、置き換えのコストに見合いません。

戦うべきは、訳語そのものではなく、初出の一行です。

記事でも登壇でも、「宣言型」という言葉を出すその瞬間に、補助線を一行添える。たとえばこうです。「宣言型(手順ではなく、あるべき状態を申告する。差分の解消はシステムに委ねる)」。言葉そのものは諦めて、その隣に、毎回きちんとした定義を置く。これだけで、読み手の宙づり感はかなり解消されます。

そして、相手がすでに何かしらの declarative ツールに触れているなら、最強の説明は次の一言です。「Terraform を触ったことがあるなら、あれと同じ考え方です」。SQL でも Kubernetes でも構いません。相手の手の中にすでにある体感を指させば、概念は一瞬で伝わります。新しく教えるのではなく、すでに知っていることを「それが宣言型です」と名指す。それが、いちばん速い橋のかけ方です。

Databricks の文脈で言えば、DAB(Declarative Automation Bundles)や Lakeflow の宣言型パイプラインを説明するときも、同じです。「宣言する」という語を入口にすると損をします。「処理手順を書くのをやめて、あるべき状態を書く。そこへどう到達するかはシステムに任せる」という対比から入り、必要なら「Terraform と同じ発想です」と足す。それだけで、伝わり方がまるで変わります。

declarative という概念は、難しくありません。難しいのは、それを「宣言型」と呼んでしまったこと、そして How を手放す勇気のほうです。前者は補助線で、後者は対話で、どちらも解きほぐすことができます。
