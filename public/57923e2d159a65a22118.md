# [Unity Catalogのシークレットに対する上限の引き上げとBROWSE権限のサポート](https://docs.databricks.com/aws/en/release-notes/product/2026/november#higher-limits-and-browse-support-for-unity-catalog-secrets)
**2026-11-02**
スキーマは最大1,000個のUnity Catalogシークレットを保持できるようになり、メタストアは最大10,000個まで保持できるようになりました（従来の制限はそれぞれ100と1,000）。これらの制限は、Databricksが管理するシークレット、およびAWS Secrets Managerによってバックアップされたシークレットに適用されます。カタログに対する<code>BROWSE</code>権限は、Unity Catalogシークレットに適用されるようになったため、ユーザーは値の読み取りやコード内のシークレットの参照はできませんが、シークレットとそのメタデータを検出できます。詳細は<a href="https://docs.databricks.com/aws/ja/security/secrets/unity-catalog-secrets#privileges-for-uc-secrets">Unity Catalogシークレットの権限</a>を参照してください。

**ユーザーへのインパクト**

Unity Catalogのシークレットに関する変更点とDatabricksユーザーへの影響は以下の通りです：

1. Unity Catalogシークレットの上限が引き上げられました。 
   - スキーマあたりのシークレットの最大数が100から1,000に増加しました。
   - メタストアあたりのシークレットの最大数が1,000から10,000に増加しました。

2. `BROWSE`権限がUnity Catalogシークレットに適用されるようになりました。これにより、ユーザーはシークレットの存在とメタデータを閲覧できますが、シークレットの値の読み取りやコードでの参照はできません。

これらの変更により、Databricksユーザーはより多くのシークレットを管理できるようになり、シークレットの検出が容易になります。ただし、`BROWSE`権限を持つユーザーはシークレットの値を直接アクセスすることはできません。

3. **必要なDatabricks RuntimeまたはSQLウェアハウスのバージョン**: この機能を利用するには、Databricks Runtime 19以降、またはSQLウェアハウスが必要です。古いバージョンを使用しているユーザーは、アップグレードを検討する必要があります。

4. **詳細情報の入手先**: ユーザーは、Databricksのドキュメント（具体的には「メトリックビュー間のリレーションシップ」）を参照することで、この機能に関する詳細な情報を得ることができます。

この新機能により、Databricksユーザーはデータ間の関係をより明確に定義し、分析ツールがより適切なデータ結合を行うことを支援できます。

影響を受ける操作の完全なリストと更新手順については、「Unity Catalog REST API 操作のページ分割」を参照してください。

- Unity Catalog REST APIのリストカタログ、リストスキーマ、リストテーブルなどの操作を直接呼び出しているユーザーは、クライアントを更新してページング処理(`max_results`と`next_page_token`の使用)を実装する必要があります。さもないと、近日中にHTTP `400`エラーを受け取ることになります。
- Databricks SDKまたはDatabricks CLIを使用しているユーザーは、最新リリースにアップグレードすることでデフォルトでページング処理が有効になり、影響を回避できます。

Databricksユーザーは、プレビューチャネルのサーバレスパイプラインにおいて、以下のベータ版機能を利用できます:

1. 単一のパイプラインで複数のリアルタイムモードのフローを実行可能: タスクスロットの競合を気にする必要がなくなります。

2. ソースステージの適応型再パーティショニング: KafkaやKinesisのソースからの読み取りタスク数が自動的に調整されるため、`maxPartitions`や`shardsPerTask`の設定が不要になります。

これらの機能の詳細については、プレビュー・チャネルのサーバーレス・パイプラインに関するドキュメントを参照してください。

# [レイクベースサーチは、中国語、日本語、韓国語の全文検索をサポートしています。](https://docs.databricks.com/aws/en/release-notes/lakebase#lakebase-search-supports-chinese-japanese-and-korean-full-text-search)
**2026-10-15**
`lakebase_tokenizer` 拡張機能が、中国語、日本語、韓国語（CJK）のテキストに対するキーワード検索をサポートするようになりました。これらの言語では単語をスペースで区切らないため、PostgreSQLの標準全文検索では有用な検索キーワードに分割できません。新しい `tokenizer_morph` テンプレートでは、バンドルされた言語辞書を用いた形態素解析によって、CJKテキストを単語に分割します。

* **組み込み設定**: 拡張機能をインストールすると、`tokenizer_chinese`、`tokenizer_japanese`、`tokenizer_korean` が作成されます。これらは、辞書を作成せずに `to_tsvector` で直接使用できます。
* **複合語処理**: 言語に応じて、複合語をそのまま保持するか、より細かい粒度のキーワードに分割するか、あるいは両方を出力するかを選択できます。
* **言語認識フィルタリング**: 日本語の助詞や機能語を除外したり、日本語のキーワードを基本形に変換したり、韓国語の助詞や語尾をフィルタリングしたりすることで、検索結果が意味のあるキーワードに集中するようにします。

`tokenizer_wholeword` と同様に、GIN（一般化反転インデックス）インデックスや、`lakebase_text` および `lakebase_bm25` インデックスでのBM25（Best Match 25）ランキングで動作する標準の `tsvector` 値を生成します。CJKサポートは `lakebase_tokenizer` 0.2.0 で提供されます。すでに拡張機能を使用している場合は、`ALTER EXTENSION lakebase_tokenizer UPDATE` を実行してください。既存の設定やインデックスを変更する必要はありません。詳細については、[lakebase_tokenizer](https://example.com/aws/en/oltp/projects/lakebase-tokenizer) を参照してください。

**ユーザーへのインパクト**

このリリースノートは、Databricksのレイクベースサーチにおける全文検索機能の強化に関するものです。具体的には、中国語、日本語、韓国語（CJK）のテキストに対する検索サポートが追加されました。主な影響と変更点は以下の通りです：

1. **CJKテキストの検索サポート**: `lakebase_tokenizer` 拡張機能がCJKテキストを適切に単語に分割できるようになり、これらの言語でのキーワード検索が改善されました。
2. **組み込み設定の提供**: `tokenizer_chinese`、`tokenizer_japanese`、`tokenizer_korean` という組み込みの設定が利用可能になり、`to_tsvector` で直接使用できます。
3. **複合語処理と言語認識フィルタリング**: 言語に応じた複合語の処理や、不要な語のフィルタリングが可能になり、検索結果の質が向上しました。
4. **互換性**: GINインデックスや、`lakebase_text`、`lakebase_bm25` インデックスでのBM25ランキングで動作する標準の `tsvector` 値を生成します。
5. **アップデート方法**: `lakebase_tokenizer` 0.2.0にアップデートするには、`ALTER EXTENSION lakebase_tokenizer UPDATE` を実行します。既存の設定やインデックスを変更する必要はありません。

Databricksユーザーは、CJK言語のテキストに対する全文検索機能が強化されたことを利用できます。特に、これらの言語のテキストデータを扱っているユーザーにとって、検索の精度と有用性が向上するでしょう。アップデートは簡単で、既存の環境に大きな変更を加える必要はありません。

Lakebaseへの入出力で変更をストリーミングするために、ネイティブのPostgres論理レプリケーションを使用できます。既存のPostgresデータベースをLakebaseに移行し、切り替えるまで同期を保つか、Lakebaseから外部のPostgresデータベースに変更を公開します。詳細は論理レプリケーションをご覧ください。

# [トランザクションは、マネージド Delta Lake テーブルと Apache Iceberg テーブルの両方をサポートします。](https://docs.databricks.com/aws/en/release-notes/product/2026/october#transactions-support-both-managed-delta-lake-and-apache-iceberg-tables)
**2026-10-14**
Unity Catalogが管理するDelta LakeテーブルとUnity Catalogが管理するApache Icebergテーブルの両方で、一般的にトランザクションが利用可能です。1つ以上の管理されたDelta Lakeまたは管理されたApache Icebergテーブルにわたる複数のSQL文を、`BEGIN ATOMIC ... END;`または`BEGIN TRANSACTION; ... COMMIT;`構文を使って、1つの原子的なトランザクションにまとめます。トランザクションには、参加するテーブルで有効になっている<a href="https://docs.databricks.com/aws/ja/tables/features/catalog-commits">カタログコミット</a>が必要です。

詳細については、<a href="https://docs.databricks.com/aws/ja/transactions">トランザクション</a>を参照してください。

**ユーザーへのインパクト**

Unity Catalogが管理するDelta LakeテーブルとApache Icebergテーブルでトランザクションがサポートされるようになりました。`BEGIN ATOMIC ... END;`または`BEGIN TRANSACTION; ... COMMIT;`構文を使用して、複数のSQL文を1つの原子的なトランザクションにまとめることができます。ただし、参加するテーブルでカタログコミットが有効になっている必要があります。これにより、複数のテーブルにわたる操作の原子性が保証され、データの一貫性が向上します。

# [ジェミニ（Genie）のエージェント機能は現在インドで処理されています。](https://docs.databricks.com/aws/en/release-notes/product/2026/october#genie-agentic-capabilities-are-now-processed-in-india)
**2026-10-14**
Genie Codeのエージェント機能、<a href="https://docs.databricks.com/aws/ja/genie-agents">Genie Agents</a>のエージェントモード、および<a href="https://docs.databricks.com/aws/ja/genie-one/chat">Genie One</a>のチャットは、インドリージョンのワークスペースに対して、<a href="https://docs.databricks.com/aws/ja/resources/databricks-geos#cross-geo-processing">クロスGeo処理</a>を行わずに、インド内でデータを処理するようになりました。各AI支援機能がデータを処理する場所については、<a href="https://docs.databricks.com/aws/ja/resources/designated-services">Databricks指定サービス</a>を参照してください。

**ユーザーへのインパクト**

インドリージョンのワークスペースでGenieのエージェント機能やGenie Oneのチャットを利用する場合、これらの機能はインド国内でデータを処理するようになりました。これにより、データが他の地域に送信されることはなくなり、データの主権とプライバシーが強化されます。Databricksの各AI支援機能がデータを処理する場所については、Databricks指定サービスに関するドキュメントを参照してください。

# [データ分類APIが一般提供開始されました。](https://docs.databricks.com/aws/en/release-notes/data-classification#data-classification-api-is-now-generally-available)
**2026-10-14**
データ分類APIとそのTerraformリソースが一般提供開始されました。 自動タグ付け設定 (`auto_tag_configs`) は、引き続きパブリックプレビュー段階にあります。 APIリファレンスを参照してください。

**ユーザーへのインパクト**

データ分類APIが一般提供開始されたことにより、Databricksユーザーはより簡単にデータの分類を行うことができるようになりました。これにより、データの管理とセキュリティが強化されます。具体的には、APIを通じてデータ分類の設定や管理が自動化でき、Terraformリソースを利用したインフラストラクチャのコード化が可能になります。ただし、自動タグ付け設定機能はまだパブリックプレビュー段階にあるため、完全なサポートは今後のリリースを待つ必要があります。
