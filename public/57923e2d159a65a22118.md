# [システムテーブルおよびAPIでクエリテキストはデフォルトでマスクされるようになりました。](https://docs.databricks.com/aws/en/release-notes/product/2026/august#query-text-is-now-masked-by-default-in-system-tables-and-apis)
**2026-08-26**
<p>SQL文には機密情報が含まれる可能性があるため、Databricksは以下の場所でクエリテキストをマスクするようになりました。</p>
<ul>
<li><code>system.query.history</code> の <code>statement_text</code> は <code>&#x3C;REDACTED></code> を返します。</li>
<li>クエリ履歴APIおよびリストクエリAPIの<code>query_text</code>は<code>&#x3C;REDACTED></code>を返します。</li>
<li>SQL定義を含む<code>system.access.audit</code>の<code>request_params</code>内のキーは省略されます。</li>
</ul>
<p>アカウント管理者と<code>databricks_pii_access</code> アカウントグループのメンバーは、マスクされていないクエリテキストを読むことができます。アクセス権を付与するには、アカウント管理者がグループを作成し、メンバーを追加します。<a href="https://docs.databricks.com/aws/ja/admin/system-tables/query-history#statement-text-masking">マスクされたステートメントテキストへのアクセス</a> および <a href="https://docs.databricks.com/aws/ja/admin/system-tables/audit-logs#request-params-masking">マスクされたリクエストパラメータへのアクセス</a> を参照してください。</p>

**ユーザーへのインパクト**

Databricksのリリースにより、システムテーブルおよびAPIでクエリテキストがデフォルトでマスキングされるようになりました。これにより、SQL文に含まれる可能性のある機密情報の漏洩が防止されます。具体的には、`system.query.history`の`statement_text`、`query_history` APIおよび`list_query` APIの`query_text`、`system.access.audit`の`request_params`内のSQL定義を含むキーがマスキングされます。

ただし、アカウント管理者と`databricks_pii_access`アカウントグループのメンバーには、マスキングされていないクエリテキストを読む権限が与えられています。アカウント管理者は、グループを作成し、メンバーを追加することで、このアクセス権を他のユーザーに付与することができます。

この変更により、Databricksユーザーは、機密情報を保護するために、クエリテキストへのアクセスを適切に制御する必要があります。影響を受けるユーザーは、ドキュメントを参照して、マスキングされたステートメントテキストやリクエストパラメータへのアクセス方法について確認する必要があります。

# [Google SheetsからDatabricksにデータを書き戻す方法について説明します。

### 前提条件

* DatabricksアカウントとGoogleアカウントを持っていること
* Databricksのクラスタが起動していること
* Google Sheetsのデータが準備されていること

### 手順

1. **Databricksのセットアップ**
 Databricksで、データを書き込むためのテーブルを作成します。Databricksのノートブックで、以下のコマンドを実行してテーブルを作成します。
```sql
%sql
CREATE TABLE IF NOT EXISTS my_table (
  column1 STRING,
  column2 INTEGER,
  column3 DOUBLE
);
```
2. **Google Sheetsのセットアップ**
 Google SheetsのデータをDatabricksに書き込むために、Google SheetsのAPIを有効にします。Google Cloud Consoleで、APIライブラリページに移動し、「Google Sheets API」を検索して有効にします。
3. **DatabricksからGoogle Sheetsへの接続**
 Databricksのノートブックで、Google Sheetsのデータを読み込むために、以下のコマンドを実行します。
```python
%python
import pandas as pd
from google.oauth2.service_account import Credentials
from googleapiclient.discovery import build

# Google Sheetsの認証情報
SCOPES = ['https://www.googleapis.com/auth/spreadsheets']
SERVICE_ACCOUNT_FILE = '/dbfs/path/to/service_account_key.json'

# Google Sheetsの認証
creds = Credentials.from_service_account_file(SERVICE_ACCOUNT_FILE, scopes=SCOPES)
service = build('sheets', 'v4', credentials=creds)

# Google Sheetsのデータを取得
spreadsheet_id = 'your_spreadsheet_id'
range_name = 'Sheet1!A1:C10'
result = service.spreadsheets().values().get(spreadsheetId=spreadsheet_id, range=range_name).execute()
values = result.get('values', [])

# Pandasデータフレームに変換
df = pd.DataFrame(values[1:], columns=values[0])

# Databricksのデータフレームに変換
df_databricks = spark.createDataFrame(df)
```
4. **データを書き込む**
 Databricksのノートブックで、以下のコマンドを実行してデータを書き込みます。
```python
%python
# データを書き込む
df_databricks.write.format('delta').mode('overwrite').saveAsTable('my_table')
```
### 注意点

* Google Sheetsのデータが大きい場合、データの取得に時間がかかる](https://docs.databricks.com/aws/en/release-notes/product/2026/august#write-data-back-to-databricks-from-google-sheets)
**2026-08-20**
<p>Databricks Connector for Google Sheetsを使用すると、Google SheetsからUnity Catalogテーブルにデータを書き戻すことができるようになりました。Google Sheetsを離れることなく、新しいテーブルの作成や既存のテーブルの上書きを行うことができます。詳細については、<a href="https://docs.databricks.com/aws/ja/integrations/google-sheets/write-back">Google SheetsからDatabricksにデータを書き戻す</a>を参照してください。</p>

**ユーザーへのインパクト**

Databricksユーザーは、Databricks Connector for Google Sheetsを使用して、Google SheetsからUnity Catalogテーブルにデータを直接書き戻すことができるようになりました。これにより、Google Sheetsを離れることなく、新しいテーブルの作成や既存のテーブルの上書きが可能になります。さらに、従来のやり方ではGoogle Sheetsのデータが大きい場合にデータ取得に時間がかかるという問題がありましたが、新機能によりその問題も解消されます。詳細はDatabricksのドキュメントを参照してください。

# [OpenSharing SecureConnect の拡張ネットワーク課金](https://docs.databricks.com/aws/en/release-notes/whats-coming#expanded-networking-billing-for-opensharing-secureconnect)
**2026-08-13**
Databricksは、OpenSharing SecureConnectのネットワーク課金を拡張する予定です。現在、データ提供者は、受信者がSecureConnectを通じて共有データにアクセスする際のデータ転送（egress）に対して課金されます。受信者への課金を含む、追加の課金タイプとアクセスシナリオが計画されています。

以下の表は、計画されている課金、誰に請求されるか、および各アクセスシナリオにどのように適用されるかをまとめたものです。

| 課金タイプ | ステータス | 異なるリージョンまたはクラウド間 | 同一リージョン（クラシックまたはオープンレシーピエント） | 同一リージョン（サーバーレスレシーピエント） |
| --- | --- | --- | --- | --- |
| データ転送 | 現在利用可能 | プロバイダーに請求 | 適用外 ¹ | 適用外 ¹ |
| プライベートコネクティビティ ² | 近日提供予定 | プロバイダーに請求 | プロバイダーに請求 | 受信者に請求 |
| パブリックコネクティビティ | 近日提供予定 | 受信者に請求 | 適用外 ³ | 適用外 ⁴ |

¹ 受信者がプロバイダーと同じリージョンにいる場合、データ転送（egress）は適用されません。
² プロバイダーがネットワークコネクティビティ設定（NCC）をメタストアにアタッチしてプライベートコネクティビティを設定している場合にのみ適用されます。
³ Databricksはこの料金を請求しません。クラシックコンピュートまたはオープンレシーピエントがパブリックネットワーク経由でストレージにアクセスする場合、クラウドプロバイダーが直接ネットワークアドレス変換（NAT）の料金を請求する可能性があります。
⁴ 同一リージョンのサーバーレス受信者は、マネージドプロキシを経由せずに直接ストレージから読み取ります。

料金については、[データ転送とコネクティビティの価格](https://www.databricks.com/product/pricing/data-transfer-connectivity) を参照するか、Databricksアカウントチームにお問い合わせください。

**ユーザーへのインパクト**

DatabricksのOpenSharing SecureConnectのネットワーク課金が拡張されます。主な変更点は以下の通りです。

1. **新しい課金タイプの導入**：プライベートコネクティビティとパブリックコネクティビティの課金が追加されます。
   - プライベートコネクティビティ：プロバイダーがネットワークコネクティビティ設定（NCC）をメタストアにアタッチしている場合に適用されます。異なるリージョンまたはクラウド間のアクセスではプロバイダーに、同一リージョンのサーバーレス受信者の場合には受信者に請求されます。同一リージョンのクラシックまたはオープンレシーピエントの場合にはプロバイダーに請求されます。
   - パブリックコネクティビティ：異なるリージョンまたはクラウド間のアクセスの場合、受信者に請求されます。同一リージョンでは適用されませんが、クラウドプロバイダーが直接ネットワークアドレス変換（NAT）の料金を請求する可能性があります。

2. **既存のデータ転送課金**：データ提供者は引き続き、異なるリージョンまたはクラウド間のデータ転送に対して課金されます。同一リージョン内でのアクセスの場合、データ転送は適用されません。

Databricksユーザーは、特にデータ提供者と受信者の両方として、以下の点に注意する必要があります。

- **コストの増加**：特にサーバーレスレシーピエントの場合、プライベートコネクティビティの料金が新たに発生します。

ソースが列によってキー付けされた一連の部分的なスナップショットである場合に、REPLACE USINGフローを使用します。各更新時に、フローは指定されたキー列に一致するすべての行を置き換え、その他のすべての行は変更されません。`SEQUENCE BY`列は更新を順序付けするため、キーに対する最新のシーケンスが常に優先されます。したがって、更新が順序どおりに到着しなくても、正しく処理されます。REPLACE USINGでは、明示的な挿入、更新、削除操作を含む変更データキャプチャフィードは必要なく、主キーも必要ありません。
詳細については、「<a href="https://docs.databricks.com/aws/ja/ldp/flows-replace-using">REPLACE USINGフローを使用した部分スナップショットの置き換え</a>」を参照してください。

**ユーザーへのインパクト**

REPLACE USING フローが、Lakeflow パイプラインのベータ版で利用できるようになりました。これにより、ソースが列によってキー付けされた一連の部分的なスナップショットである場合に、指定されたキー列に一致する行を置き換えることができます。主な利点は以下の通りです：

1. 明示的な変更データキャプチャフィードや主キーが不要になります。
2. SEQUENCE BY 列で更新を順序付けし、順序が狂っていても正しく処理します。

これにより、部分的なスナップショットの置き換えが容易になり、データパイプラインの管理が簡素化されます。詳細はドキュメントを参照してください。

<p><a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/access-control/permissions-concepts#manage-privilege"><code>MANAGE</code>権限</a>を付与されたオブジェクトに対する<a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/access-control/permissions-concepts#manage-usage-requirements">利用権限</a>（<code>USE CATALOG</code>または<code>USE SCHEMA</code>）の要件がなくなりました。この変更により、<code>MANAGE</code>の動作がオブジェクトの所有権とより一貫したものになります。</p>
<p>以前は、カタログまたはスキーマに対する<code>MANAGE</code>は、そのオブジェクトに対する適切な利用権限も保持している場合にのみ有効でした。親コンテナに対する利用権限は引き続き必要です。</p>
<ul>
<li>カタログに対する<code>MANAGE</code>は利用権限を必要としません。</li>
<li>スキーマに対する<code>MANAGE</code>には親カタログの<code>USE CATALOG</code>が必要ですが、スキーマに対する<code>USE SCHEMA</code>は不要になりました。</li>
<li>テーブル、ビュー、ボリューム、または関数に対する<code>MANAGE</code>は変更されていません。引き続き、親カタログの<code>USE CATALOG</code>と親スキーマの<code>USE SCHEMA</code>が必要です。</li>
</ul>
<p>他のすべての権限は影響を受けず、<code>MANAGE</code>を持つユーザーであっても、利用権限を前提条件として必要とします。たとえば、テーブルをクエリするには、テーブルに対する<code>SELECT</code>、および親カタログとスキーマに対する<code>USE CATALOG</code>と<code>USE SCHEMA</code>が必要です。</p>
<p>対応する利用権限を付与せずに<code>MANAGE</code>を広範に付与していた場合、これらの権限付与が現在有効となり、権限付与者はオブジェクトを管理できるようになります。Databricksでは、既存の<code>MANAGE</code>権限付与を監査して、意図したアクセスを反映していることを確認することをお勧めします。</p>

**ユーザーへのインパクト**

Databricksのリリースノートによると、`MANAGE`権限の動作が変更され、同じオブジェクトに対する`USE CATALOG`や`USE SCHEMA`が不要になりました。つまり、カタログまたはスキーマに対する`MANAGE`権限を持つユーザーは、それらのオブジェクトを管理するために`USE CATALOG`や`USE SCHEMA`権限を別途持つ必要がなくなりました。

この変更は、以下の点でDatabricksユーザーに影響を与えます。

* カタログに対する`MANAGE`権限は、`USE CATALOG`権限を必要としなくなりました。
* スキーマに対する`MANAGE`権限は、親カタログの`USE CATALOG`権限のみ必要で、スキーマに対する`USE SCHEMA`権限は不要になりました。
* テーブル、ビュー、ボリューム、または関数に対する`MANAGE`権限については、従来通り、親カタログの`USE CATALOG`と親スキーマの`USE SCHEMA`が必要です。

他の権限については、引き続き利用権限を前提条件として必要とします。たとえば、テーブルをクエリするには、テーブルに対する`SELECT`、および親カタログとスキーマに対する`USE CATALOG`と`USE SCHEMA`が必要です。

この変更により、`MANAGE`権限を広範に付与していた場合、これらの権限付与が現在有効となり、権限付与者はオブジェクトを管理できるようになります。Databricksでは、既存の`MANAGE`権限付与を監査して、意図したアクセスを反映していることを確認することをお勧めします。

# [マテリアライズドビューとストリーミングテーブルを更新する際に、パイプライン所有者をABACポリシーから免除しない。](https://docs.databricks.com/aws/en/release-notes/product/2026/august#refresh-materialized-views-and-streaming-tables-without-exempting-the-pipeline-owner-from-abac-policies)
**2026-08-03**
パイプラインの所有者または<a href="https://docs.databricks.com/aws/ja/ldp/configure-pipeline#set-run-as">実行ユーザー</a>が属性ベースのアクセス制御（ABAC）ポリシーの対象となっている場合でも、パイプライン管理のマテリアライズドビューまたはストリーミングテーブルを更新できるようになりました。
以前は、パイプラインで管理されているマテリアライズドビューまたはストリーミングテーブルを更新するには、パイプラインの所有者または実行ユーザーを適用可能なABACポリシーから免除する必要がありました。この制限が撤廃されました。
パイプラインがマテリアライズドビューまたはストリーミングテーブルを更新すると、ポリシーはパイプラインの所有者または実行ユーザーを使用して評価されます。保存されたデータがマスクされたりフィルタリングされたりしないようにするには、パイプラインの所有者または実行ユーザーを、パイプラインの更新中に読み取られるすべてのテーブルに関連付けられたABACポリシーの<code>EXCEPT</code>句に追加します。<code>TO</code>句を使用して、マスクされたデータまたはフィルタリングされたデータを受信するユーザーとグループを指定します。
<a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/abac/requirements#materialized-views-and-streaming-tables">マテリアライズドビューとストリーミングテーブルのABACポリシー</a>を参照してください。

**ユーザーへのインパクト**

このリリースノートは、Databricksユーザーがパイプライン所有者または実行ユーザーの属性ベースのアクセス制御（ABAC）ポリシーからの免除が不要になったことを意味します。パイプラインがマテリアライズドビューまたはストリーミングテーブルを更新する際、所有者または実行ユーザーの権限でポリシーが評価されるようになりました。保存されたデータがマスクまたはフィルタリングされないようにするには、パイプライン所有者または実行ユーザーを`EXCEPT`句に追加する必要があります。したがって、ユーザーはパイプラインの権限設定を確認し、必要に応じて`EXCEPT`句を設定する必要があります。

# [サーバーレスジョブの環境変数は現在ベータ版です。](https://docs.databricks.com/aws/en/release-notes/product/2026/august#environment-variables-for-serverless-jobs-are-in-beta)
**2026-08-03**
<p>サーバーレスLakeflow Jobsタスクの環境変数は<a href="https://docs.databricks.com/aws/ja/release-notes/release-types">ベータ版</a>です。ジョブレベルで名前付きの環境変数エントリを定義し、それぞれのタスクに1つずつ選択して、デプロイメント固有の設定をアプリケーションコードに渡すことができます。ワークスペース管理者は、ワークスペースの<strong>プレビュー</strong>ページからプレビューを有効にする必要があります。詳細は<a href="https://docs.databricks.com/aws/ja/jobs/environment-variables">サーバーレスジョブの環境変数の設定</a>を参照してください。</p>

**ユーザーへのインパクト**

サーバーレスジョブの環境変数がベータ版で利用可能になりました。ジョブレベルで環境変数を定義し、タスクごとに選択してアプリケーションコードに渡すことができます。ワークスペース管理者はプレビューを有効にする必要があります。詳細はドキュメントを参照してください。
