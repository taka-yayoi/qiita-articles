<h4>XPathが外部DTDを取得しなくなった</h4>
<p>XMLに対して<a href="https://docs.databricks.com/aws/ja/sql/language-manual/functions/xpath">xpath</a>を評価する際、Databricksはドキュメント内で宣言された外部DTD（Document Type Definitions）をロードしなくなりました。以前は、XMLに不正なURLや到達不能なエンドポイントを指す外部DTD参照が含まれている場合、XPathは失敗する可能性がありました。DTD検証はXPath評価とは別であるため、すでに成功していたクエリは以前と同じ結果を返します。以前は外部DTD取得中にのみ失敗していたクエリが、成功するようになりました。</p>

Databricks SQLバージョン2026.15のプレビューが利用可能になりました。このリリースでは、いくつかの重要な変更と新機能が導入されています。

1. **XPathが外部DTDを取得しなくなる**: XMLに対してXPathを評価する際、Databricksは外部DTD（Document Type Definitions）をロードしなくなりました。これにより、XMLに不正なURLや到達不能なエンドポイントを指す外部DTD参照が含まれている場合に、XPathが失敗する問題が解消されます。DTD検証はXPath評価とは別であるため、すでに成功していたクエリは同じ結果を返します。

Databricksユーザーへの影響: 外部DTD参照を含むXMLデータを扱っている場合、以前は失敗していたクエリが成功するようになります。

2. **スキーマエボリューションを使用したINSERT、MERGE、ストリーミング書き込みにおけるNULL構造体の保持**: スキーマエボリューションを使用する`INSERT`、`MERGE`、ストリーミング書き込みにおいて、ソース内のNULL構造体がターゲットにNULLとして保存されるようになりました。以前は、その値は誤ってすべてのフィールドがNULLの非NULL構造体として具体化されていました。

Databricksユーザーへの影響: すべてのフィールドがNULLの非NULL構造体を受け取ることに依存していたコードがある場合は、代わりにNULL構造体を処理するようにコードを更新する必要があります。

3. **DeltaテーブルにおけるNullType（VOID）のサポート**: Delta Lakeテーブルが`VOID`列をサポートするようになりました。以前は、`VOID`列はパスベースのDataFrame読み取りやタイムトラベルクエリによって黙ってスキップされていました。これらのクエリは、出力に`VOID`列を含むようになりました。

Databricksユーザーへの影響: `VOID`列を含むDeltaテーブルを扱う場合、出力に`VOID`列が含まれるようになります。書き込み操作は影響を受けません。`VOID`型の詳細については、公式ドキュメントを参照してください。

これらの変更は、Databricks SQLのプレビュー版でのみ利用可能です。本番環境にデプロイする前に、テスト環境でこれらの変更の影響を確認することをお勧めします。

# [Databricks Runtime 18: 2026年5月18日](https://docs.databricks.com/aws/en/release-notes/runtime/18#databricks-runtime-18-may-18-2026)
**2026-05-18**
<h3><div></div>動作の変更</h3>
<p>このランタイムでクラスターが再起動したときに有効になる以下の変更を確認します。</p>
<ul>
<li><strong><code>CREATE OR REPLACE TABLE</code></strong>: <a href="https://docs.databricks.com/aws/ja/sql/language-manual/sql-ref-syntax-ddl-create-table"><code>CREATE OR REPLACE TABLE</code></a> は、デフォルトで既存の列およびテーブルのコメントを保持するようになりました。 以前は、テーブルを再作成するとコメントは削除されていました。 マネージドテーブルとビューは、 マテリアライズドビューとストリーミングテーブルの既存の動作と一致するようになりました。 </li>
<li><strong>DataFrame の名前による書き込み</strong>: <code>writeTo().append()</code>、<code>writeTo().overwrite()</code>、<code>writeTo().overwritePartitions()</code>、および <code>write.mode("append").saveAsTable()</code> は、ターゲットの Delta テーブルスキーマに一致するように、型互換の列（たとえば、<code>int</code> から <code>long</code>）を自動的にキャストするようになりました。 以前は、列の型は互換性があるものの同一ではない場合、これらの操作は <code>DELTA_FAILED_TO_MERGE_FIELDS</code> エラーで失敗していました。 この動作は、SQL の <code>INSERT INTO ... BY NAME</code> と一致するようになりました。 上書きモードの <code>save()</code> および <code>saveAsTable()</code> は影響を受けません。 </li>
<li><strong><code>pipelines.pipelineId</code> に対する <code>ALTER TABLE SET TBLPROPERTIES</code></strong>: <code>ALTER TABLE &#x3C;table> SET TBLPROPERTIES('pipelines.pipelineId' = '&#x3C;pipeline-id>')</code> は、指定されたテーブルをパイプラインによる書き込みの対象として設定しようとするようになりました。 以前は、通常のテーブルでこのプロパティを設定しても効果はありませんでした。 テーブルがパイプライン書き込みの対象でない場合、コマンドは <code>SETTING_PIPELINES_PIPELINE_ID_NOT_SUPPORTED</code> をスローします

**ユーザーへのインパクト**

Databricks Runtime 18へのアップデートにより、以下の変更がユーザーのワークフローに影響を及ぼします：

1. **`CREATE OR REPLACE TABLE`の動作変更**: テーブルを再作成する際に、既存の列やテーブルのコメントがデフォルトで保持されるようになりました。これにより、マネージドテーブルやビュー、マテリアライズドビュー、ストリーミングテーブルの動作が一貫します。

2. **DataFrameの名前による書き込みの改善**: `writeTo().append()`や`write.mode("append").saveAsTable()`などの操作で、Deltaテーブルのスキーマに一致するように、型互換の列（例：`int`から`long`）が自動的にキャストされるようになりました。これにより、SQLの`INSERT INTO ... BY NAME`と同様の動作になります。ただし、上書きモードの`save()`や`saveAsTable()`はこの変更の影響を受けません。

3. **`ALTER TABLE SET TBLPROPERTIES`の動作変更**: `pipelines.pipelineId`プロパティを設定する際に、指定されたテーブルをパイプラインによる書き込みの対象として設定するようになりました。テーブルがパイプライン書き込みの対象でない場合、コマンドはエラーをスローします。

これらの変更は、Databricks Runtime 18でクラスターが再起動したときに有効になります。ユーザーは、これらの変更が自分のワークフローに与える影響を確認し、必要に応じてコードの修正やテストを行う必要があります。特に、テーブルのメタデータの保持やDataFrameの書き込み動作に依存する処理がある場合は、注意が必要です。

1. **XPathの変更**：外部DTDのロードがされなくなり、一部のクエリの動作が変わる可能性があります。
2. **NULL structの動作変更**：スキーマ進化を使用する操作で、NULL structが正しくNULLとして格納されるようになりました。コードの更新が必要な場合があります。
3. **NATURAL JOINの修正**：大文字と小文字を区別しないカラムマッチングが正しく動作するようになり、クロスジョインの問題が解消されました。
4. **AWS SDK v1依存関係の削除**：AWS SDK v1ライブラリが直接利用できなくなったため、必要な場合はプロジェクトに明示的な依存関係として追加する必要があります。
5. **Unity CatalogでのSQL UDF依存関係検証の強化**：SQLユーザー定義関数の依存関係検証が強制されるようになりました。

これらの変更は、クラスターの再起動時に有効になります。特に、既存のコードやクエリがこれらの変更の影響を受ける可能性があるため、アップグレード前に十分なテストを行うことをお勧めします。

# [集計SQL関数を、measureの同義語として使用します。](https://docs.databricks.com/aws/en/sql/release-notes/2026#agg-sql-function-as-a-synonym-for-measure)
**2026-04-30**
<p>新しい集計関数<a href="https://docs.databricks.com/aws/ja/sql/language-manual/functions/agg">agg</a>は、<a href="https://docs.databricks.com/aws/ja/sql/language-manual/functions/measure">measure</a>のシノニムです。<a href="https://docs.databricks.com/aws/ja/business-semantics/metric-views">metric view</a>のメジャーを照会するときに、より短い代替手段として<code>agg(measure_column)</code>を使用します。</p>

**ユーザーへのインパクト**

Databricksの新しいリリースにより、`agg`関数が`measure`の同義語として利用可能になりました。これにより、metric viewのメジャーを照会する際に、`agg(measure_column)`というより簡潔な構文を使用できるようになります。つまり、既存のSQLクエリで`measure`の代わりに`agg`を使用することができ、コードの可読性が向上します。具体的には、以下のような変更が期待できます。

```sql
-- 以前の構文
SELECT measure(column_name) FROM metric_view;

-- 新しい構文
SELECT agg(column_name) FROM metric_view;
```

この変更は、下位互換性があり、`measure`を使用した既存のクエリは引き続き動作しますが、新しい`agg`関数を使用することで、より簡潔で読みやすいクエリを書くことができるようになります。

# [属性ベースのアクセスコントロール（ABAC）が一般提供開始されました。](https://docs.databricks.com/aws/en/release-notes/product/2026/april#attribute-based-access-control-abac-is-now-generally-available)
**2026-04-28**
属性ベースのアクセス制御（Attribute-based access control: ABAC）が一般提供（GA）されました。ABACは、Unity Catalogのアクセス制御モデルの1つであり、データアセットに適用された<a href="https://docs.databricks.com/aws/ja/admin/governed-tags">ガバナンスタグ</a>を使用して、テーブル、マテリアライズドビュー、ストリーミングテーブルの行フィルタおよび列マスクポリシーを動的に適用します。ポリシーは、カタログ、スキーマ、またはテーブルのレベルで関連付けられ、一致するタグ属性を持つすべてのセキュリティ保護可能なオブジェクトに自動的に適用されるため、テーブルごとの設定を行わずに大規模な一貫したアクセスルールを実現できます。
このGAリリースの一部として、ユーザーがABACで保護されたテーブルにアクセスするビューまたは関数をクエリする場合、行フィルタと列マスクは、ビューまたは関数の所有者のIDではなく、<strong>セッション・ユーザーのID</strong>（クエリを実行しているユーザーのID）を使用して評価されるようになりました。これにより、ABACの動作は、テーブルレベルの行レベルのセキュリティおよび列マスキングと整合するものとなりました。ビューや関数を介してクエリを実行するユーザーは、依然として基になるテーブルに対する直接的な権限を必要としません。
これは破壊的変更です。Databricksから影響を受ける可能性のあるお客様として連絡を受けた場合、ポリシーを適応させるための3か月の猶予期間が与えられています。連絡を受けていない場合、または新規のお客様の場合は、新しいセッションIDの動作が既にアカウントのデフォルトとなっています。詳細については、<a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/abac/requirements#abac-policies-on-views">ビューに対するABACポリシー</a>を参照してください。
詳細は、<a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/abac">Unity Catalog での属性ベースのアクセス制御</a>を参照してください。

**ユーザーへのインパクト**

このリリースノートは、Databricksユーザーに対して、属性ベースのアクセスコントロール（ABAC）の一般提供開始と、それに伴う変更について通知するものです。

主な影響と変更点は以下の通りです：

1. ABACが一般提供開始され、Unity Catalogのアクセス制御モデルの一つとして利用可能になりました。これにより、ガバナンスタグを使用してテーブル、ビュー、マテリアライズドビュー、ストリーミングテーブルの行フィルタおよび列マスクポリシーを動的に適用できます。

2. ビューまたは関数に対するクエリの実行時に、行フィルタと列マスクの評価に使用されるIDが、ビューまたは関数の所有者のIDから**セッション・ユーザーのID**（クエリを実行しているユーザーのID）に変更されました。

3. この変更は破壊的変更です。影響を受ける可能性があるお客様にはDatabricksから連絡があり、ポリシーを適応させるための3か月の猶予期間が与えられています。連絡を受けていないお客様や新規のお客様の場合、新しいセッションIDの動作が既にアカウントのデフォルトとなっています。

4. ユーザーがビューまたは関数を介してテーブルにアクセスする場合、依然として基になるテーブルに対する直接的な権限は必要ありません。

5. 詳細については、Databricksのドキュメント（「Unity Catalog での属性ベースのアクセス制御」および「ビューに対するABACポリシー」）を参照することが推奨されています。

この変更により、Databricksユーザーは、ABACポリシーの適用方法と、ビューや関数を介したクエリの動作についての理解を深める必要があります。影響を受けるお客様は、与えられた猶予期間内にポリシーの見直しと適応を行うことが求められます。

# [5X-Large SQLウェアハウスのサイズ (パブリックプレビュー)](https://docs.databricks.com/aws/en/release-notes/product/2026/april#5x-large-sql-warehouse-size-public-preview)
