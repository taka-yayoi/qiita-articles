# [オープン・デルタ・シェアリング受信者トークンの変更。](https://docs.databricks.com/aws/en/release-notes/whats-coming#changes-to-open-delta-sharing-recipient-tokens)
**2025-12-09**
オープン受信者向けのDelta Sharingは、Delta Sharingサーバーへの接続に使用される新しい受信者固有のURL形式に移行します。この変更により、ネットワークセキュリティとファイアウォール設定が向上し、共有エンドポイントのベストプラクティスに準拠します。

<p><strong>2026年3月9日以降に作成された受信者トークン:</strong></p>
2026年3月9日から、新しいオープン受信者トークンは、セキュリティとネットワークフィルタリングを改善するために、新しい受信者固有のURL形式を使用します。この変更は、この日以降に発行されたトークンに適用されます。それ以前のトークンは、期限切れになるまで従来のURL形式を使用し続けることができます。次のセクションの<strong>新しいトークン有効期限ポリシー</strong>を参照してください。

AWS GovCloudおよびAWS GovCloud DoDについては、移行は後日発表されます。

OIDCの場合、受信者は<em>2027年3月9日</em>までに新しいURL形式に移行する必要があります。2026年3月9日から、プロバイダーはDelta Sharingページで既存の受信者の新しいURL形式を表示して、受信者と共有できるようになります。

新しいURLは次の形式になります。

<pre><code class="language-text">https://2d4b0370-9d5c-4743-9297-72ba0f5caa8d.delta-sharing.us-west-2.cloud.databricks.com
</code></pre>

<p><strong>新しいトークン有効期限ポリシー:</strong></p>
2025年12月8日から、すべての新しいオープン共有受信者トークンは、作成日から<em>1年</em>の最長有効期限で発行されます。より長い、または無制限の有効性を持つトークンは作成できなくなります。

2025年12月8日から2026年3月9日の間に、従来の受信者URL形式を使用して作成されたトークンについては、各トークンは作成から1年後に自動的に期限切れになります。トークンをローテーションする場合、プロバイダーはダウンタイムウィンドウを設定して、受信者が移行できるようにすることができます。このウィンドウの間、古い受信者URLと新しい受信者URL

Databricksユーザーは、以下の変更に注意する必要があります。

1. **新しい受信者トークン形式**: 2026年3月9日以降に作成されたオープン・デルタ・シェアリング受信者トークンは、新しい受信者固有のURL形式を使用します。形式は `https://<UUID>.delta-sharing.<リージョン>.cloud.databricks.com` になります。

   - 2025年12月8日以降に作成された新しいトークンの最長有効期限は**1年**になります。
   - 2025年12月8日から2026年3月9日の間に従来のURL形式で作成されたトークンは、作成から1年後に自動的に期限切れになります。

3. **移行の必要性**:
   - OIDCを使用している受信者は、**2027年3月9日**までに新しいURL形式に移行する必要があります。
   - プロバイダーは、Delta Sharingページで既存の受信者の新しいURL形式を表示して、受信者と共有できるようになります。

4. **トークンのローテーション**: トークンをローテーションする際には、ダウンタイムウィンドウを設定して、受信者が新しいURLに移行できるようにする必要があります。

# [オープン・デルタ・シェアリングのための新しいトークン有効期限ポリシー](https://docs.databricks.com/aws/en/release-notes/product/2025/december#new-token-expiration-policy-for-open-delta-sharing)
**2025-12-08**
<p>新たに作成されるDelta Sharingのオープンの受信者トークンの有効期限は、作成日から最大1年間となります。1年を超える有効期限や、有効期限なしのトークンは作成できなくなりました。</p>
<p>2025年12月8日より前に発行されたオープンの受信者トークンのうち、2026年12月8日より後に有効期限が設定されているトークン、もしくは有効期限が設定されていないトークンは、自動的に2026年12月8日に失効します。現在、長期間もしくは無期限のトークンをお使いの場合、2026年12月8日以降に不整合が生じないように、インテグレーションを確認し、トークンを更新してください。</p>
<p>「<a href="https://docs.databricks.com/aws/ja/delta-sharing/create-recipient-token">ベアラートークンを使用した非Databricksユーザー用のレシップオブジェクトの作成 (オープンの共有)</a>」を参照してください。</p>

**ユーザーへのインパクト**

Delta Sharingを利用しているDatabricksユーザーは、新しいトークン有効期限ポリシーによる影響を受ける可能性があります。主な影響と対応は以下の通りです：

1. **新しいトークンの最大有効期限が1年に制限**: 作成日から1年を超える有効期限のトークンは作成できなくなりました。新しい受信者トークンは最大1年間有効となります。

2. **既存のトークンの扱い**: 2025年12月8日より前に発行されたトークンのうち、有効期限が2026年12月8日より後、または無期限のトークンは、2026年12月8日に自動的に失効します。

3. **推奨される対応**: 長期または無期限のトークンを使用している場合、2026年12月8日以降に不整合が生じないように、インテグレーションの確認とトークンの更新を行うことを推奨します。

詳細については、Databricksのドキュメント「ベアラートークンを使用した非Databricksユーザー用のレシップオブジェクトの作成 (オープンの共有)」を参照してください。

# [パーソナルアクセストークンの有効期限に関するメール通知](https://docs.databricks.com/aws/en/release-notes/whats-coming#email-notifications-for-expiring-personal-access-tokens)
**2025-12-04**
Databricksは近日、個人用アクセストークンの有効期限が切れる約7日前に、ワークスペースのユーザーに電子メール通知を送信するようになります。通知は、電子メールベースのユーザー名を持つワークスペースユーザー（サービスプリンシパルは含まない）にのみ送信されます。 同じワークスペース内の期限切れのトークンはすべて、1つの電子メールにまとめられます。

詳細は<a href="https://docs.databricks.com/aws/ja/admin/access-control/tokens">個人用アクセストークンの監視と取り消し</a>をご覧ください。

**ユーザーへのインパクト**

Databricksのパーソナルアクセストークンの有効期限に関するメール通知機能が近日導入されます。この変更によるDatabricksユーザーへの影響は以下の通りです：

1. **メール通知の受信**: ワークスペースユーザーのうち、メールアドレスをユーザー名として使用しているユーザーは、パーソナルアクセストークンの有効期限が切れる約7日前にメール通知を受け取ります。
2. **通知対象**: メールベースのユーザー名を持つワークスペースユーザーが対象で、サービスプリンシパルは対象外です。
3. **複数のトークンの通知**: 同じワークスペース内で有効期限が切れるトークンが複数ある場合、それらは1通のメールにまとめられて通知されます。

# [SQL Serverのデータ取り込みパイプラインのフルリフレッシュフローを改善しました。](https://docs.databricks.com/aws/en/release-notes/product/2025/november#improved-full-refresh-flow-for-sql-server-ingestion-pipelines)
**2025-11-14**
<p>SQL Server へのデータ取り込みパイプラインのフルリフレッシュ操作により、スナップショットの完了後にテーブルリフレッシュが遅延するため、ダウンタイムが短縮されるようになりました。スナップショットプロセス中、データ到着先のストリーミングテーブルは既存のデータで利用可能なままです。新しい挿入、削除、更新は蓄積されますが、すぐには適用されません。スナップショットが完了した後、フルリフレッシュおよびその他の蓄積された変更が 1 回の更新で適用されるため、データの可用性の中断が最小限に抑えられます。この改善により、フルリフレッシュ操作中の<code>PENDING_RESET</code>エラーやタイムアウトエラーが軽減されます。「<a href="https://docs.databricks.com/aws/ja/ingestion/lakeflow-connect/sql-server-maintenance#full-refresh">フルリフレッシュの動作</a>」を参照してください。</p>

1. **ダウンタイムの短縮**：SQL Serverへのデータ取り込みパイプラインのフルリフレッシュ操作において、スナップショット完了後にテーブルリフレッシュが遅延するようになり、ダウンタイムが短縮されました。

4. **変更の適用方法の変更**：スナップショット中に蓄積された変更（新規挿入、削除、更新）は、スナップショット完了後に一括で適用されるため、データの可用性の中断が最小限に抑えられます。

# [外部テーブルのUnity Catalogへの変換（パブリックプレビュー）](https://docs.databricks.com/aws/en/release-notes/product/2025/november#convert-foreign-tables-to-unity-catalog-managed-or-external-tables-public-preview)
**2025-11-13**
外部カタログ（Hive MetastoreやAWS Glueなど）の外部テーブルを、テーブルの履歴と設定を保持したまま、Unity Catalogのマネージドテーブルまたは外部テーブルに変換できるようになりました。<code>MOVE</code>（ソースアクセスを無効にする）または<code>COPY</code>（ソースにアクセス可能なままにする）オプションを使用してマネージドテーブルに変換するには<code>ALTER TABLE SET MANAGED</code>を使用し、オプションの<code>DRY RUN</code>検証を使用して外部テーブルに変換するには<code>ALTER TABLE SET EXTERNAL</code>を使用します。さらに、<code>ALTER CATALOG DROP CONNECTION</code>を使用して、外部カタログ全体を標準のUnity Catalogカタログに変換できます。詳しくは、<a href="https://docs.databricks.com/aws/ja/tables/convert-foreign-managed">外部テーブルをUnity Catalogのマネージドテーブルに変換する</a>および<a href="https://docs.databricks.com/aws/ja/tables/convert-foreign-external">外部テーブルをUnity Catalogの外部テーブルに変換する</a>を参照してください。

<ul>
<li><code>ALTER TABLE SET MANAGED</code>: DBR 17.3 LTS以降</li>
<li><code>ALTER TABLE SET EXTERNAL</code>: DBR 17.0 LTS以降</li>
<li><code>ALTER CATALOG DROP CONNECTION</code>: DBR 17.3 LTS以降</li>
<li><code>ALTER SCHEMA SET MANAGED LOCATION</code>: DBR 16.4 LTS以降</li>
</ul>

**ユーザーへのインパクト**

Databricksユーザーは、Unity Catalogへの移行が容易になります。外部テーブルのUnity Catalogへの変換機能（パブリックプレビュー）により、既存の外部テーブルをUnity Catalogのマネージドテーブルまたは外部テーブルに変換できます。これにより、テーブルの履歴と設定を保持したまま、Unity Catalogへの移行が可能です。Databricks Runtime 17.0 LTS以降を使用しているユーザーは、ALTER TABLE SET MANAGEDまたはALTER TABLE SET EXTERNALコマンドを使用して変換を実行できます。さらに、ALTER CATALOG DROP CONNECTIONコマンドを使用して、外部カタログ全体をUnity Catalogカタログに変換することもできます。

**2025-11-03**
属性ベースのアクセス制御（Attribute-based access control: ABAC）がパブリックプレビューで利用できるようになりました。ABACは、データ資産に適用されるガバナンスタグに基づいてポリシーを定義することにより、柔軟でスケーラブルかつ集中化されたアクセス制御を提供するデータガバナンスモデルです。
パブリックプレビューにおけるABACには、ベータ版からの2つの重要な変更点があります。
* 
アカウントレベルでの適用: ABACは、ワークスペースレベルでのプレビューからアカウントレベルでのプレビューに移行しました。ABACポリシーは、デフォルトでアカウントのメタストアに接続されているすべてのワークスペースで適用されるようになりました。詳細については<a href="https://docs.databricks.com/aws/ja/archive/unity-catalog/abac-public-preview-transition">ABAC Beta to Public Preview transition</a>をご覧ください。
* 
カラムマスクの自動型キャスト: Databricksは、ABACポリシーで定義されたカラムマスク関数の出力を、ターゲットカラムのデータ型に自動的にキャストするようになりました。これにより、一貫した型付けとより信頼性の高いクエリ動作が保証されます。既存のカラムマスク関数は、戻り値の型がターゲットカラムの型と互換性がない場合に失敗する可能性があります。詳細については<a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/abac/udf-best-practices#auto-casting"> ABAC column mask type casting</a>をご覧ください。
詳細については<a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/abac">Unity Catalog attribute-based access control (ABAC)</a>をご覧ください。

**ユーザーへのインパクト**

属性ベースのアクセス制御（ABAC）のパブリックプレビューが利用可能になったことによるDatabricksユーザーへの影響は以下の通りです：

1. **アカウントレベルでのABAC適用**：ABACポリシーがアカウントレベルで適用されるようになり、メタストアに接続されたすべてのワークスペースで有効になります。ユーザーは、以前に設定したワークスペースレベルのABACポリシーがアカウントレベルに移行したことに注意する必要があります。

2. **カラムマスクの自動型キャスト**：ABACポリシーで定義されたカラムマスク関数の出力が、ターゲットカラムのデータ型に自動的にキャストされるようになりました。これにより、型の不一致によるエラーが減り、一貫したクエリ動作が保証されます。ただし、既存のカラムマスク関数で、戻り値の型がターゲットカラムの型と互換性がない場合は、失敗する可能性があります。ユーザーは、既存のカラムマスク関数を確認し、必要に応じて修正する必要があります。

これらの変更により、Databricksユーザーは、より柔軟でスケーラブルなデータガバナンスとアクセス制御を利用できるようになりますが、既存のABACポリシーやカラムマスク関数の確認と修正が必要になる場合があります。

# [Databricks JDBC ドライバー 2.7.5](https://docs.databricks.com/aws/en/release-notes/product/2025/october#databricks-jdbc-driver-275)
**2025-10-23**
<p>Databricks JDBC Driver (Simba) バージョン 2.7.5 が利用できるようになりました。このバージョンには以下の改善が含まれています:</p>

<p>コネクターが Kerberos 認証をプロキシ接続とともに使用できるようになりました。Kerberos プロキシを有効化するには、<code>UseProxy=1</code> および <code>ProxyAuth=2</code> を設定してください。プロキシの詳細を設定するには、<code>ProxyHost</code>、<code>ProxyPort</code>、<code>ProxyKrbRealm</code>、<code>ProxyKrbFQDN</code>、<code>ProxyKrbService</code> を使用します。</p>
<p><strong>解決された問題</strong></p>
<ul>

</ul>

**ユーザーへのインパクト**

Databricks JDBC ドライバー 2.7.5 のリリースにより、Databricks ユーザーは以下の影響を受けます：

1. **Kerberos 認証の強化**：プロキシ接続と Kerberos 認証を組み合わせて使用できるようになりました。これにより、より柔軟な認証オプションが提供されます。具体的には、`UseProxy=1` および `ProxyAuth=2` を設定し、必要に応じて `ProxyHost`、`ProxyPort`、`ProxyKrbRealm`、`ProxyKrbFQDN`、`ProxyKrbService` を構成することで、Kerberos プロキシを有効化できます。

2. **複雑なクエリの実行**：以前は、`?` 文字を含む複雑なクエリを実行する際に問題が発生していましたが、このリリースで修正されました。これにより、より複雑なクエリをネイティブモードで正常に実行できるようになりました。

3. **Unity Catalog ボリューム取り込みの安定性向上**：予期しないコネクターの動作によって引き起こされる Unity Catalog ボリューム取り込みの一時的な障害が修正されました。これにより、データ取り込みプロセスの信頼性が向上します。

4. **`getColumns` メソッドの改善**：`java -ea` フラグが有効な場合に、`Void` または `Variant` 型のカラムを含むテーブルに対して `getColumns` を実行するとアサーションエラーが発生する問題が修正されました。これにより、`getColumns` メソッドの堅牢性が向上しました。

これらの改善により、Databricks ユーザーはより安定した、柔軟なデータベース接続と操作を享受できるようになります。
