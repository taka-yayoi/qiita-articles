# [Databricks AI Runtime SDKは、serverless_gpuに代わるものとなります。](https://docs.databricks.com/aws/en/release-notes/product/2026/october#databricks-ai-runtime-sdk-replaces-serverless_gpu)
**2026-10-13**
GPU 環境バージョン 6 から、Databricks AI Runtime SDK (`databricks-sdk-air`) は非推奨の `serverless_gpu` パッケージに置き換わります。 これにより、`databricks.air` 名前空間配下に `@distributed` と `ray_init` API と `databricks.air.data` ユーティリティが提供されます。 `gpus` と `gpu_type` 引数の名前は `num_accelerators` と `accelerator_type` に変更されました。 古い名前は `databricks.air` で引き続き動作しますが、`FutureWarning` が発生します。バージョン 7 でサポートが終了します。

サーバーレス GPU 環境バージョン 6 には、両方のパッケージが含まれています。バージョン 6 は、`serverless_gpu` を含む最後のバージョンです。バージョン 5 以下は、これを引き続き使用します。 [serverless_gpu からの移行](/aws/en/machine-learning/ai-runtime/distributed-training#migrate-serverless-gpu) を参照してください。

**ユーザーへのインパクト**

Databricks AI Runtime SDK (`databricks-sdk-air`) は、`serverless_gpu` に代わる新しいパッケージです。バージョン 6 以降の GPU 環境では、`serverless_gpu` は非推奨となり、`databricks-sdk-air` の使用が推奨されます。主な変更点は以下の通りです。

1. API の変更: `@distributed` と `ray_init` API は `databricks.air` 名前空間に移動しました。
2. 引数の名前変更: `gpus` と `gpu_type` は `num_accelerators` と `accelerator_type` に変更されました。古い名前も引き続き動作しますが、`FutureWarning` が発生します。
3. 移行ガイド: `serverless_gpu` から `databricks-sdk-air` への移行方法については、公式ドキュメントを参照してください。

バージョン 6 では両方のパッケージが利用可能ですが、バージョン 7 以降では `serverless_gpu` のサポートが終了するため、早めに移行することをお勧めします。

# [近日中に、CREATE OR REPLACE VIEW によりデフォルトで権限、コメント、タグが保持されるようになります。](https://docs.databricks.com/aws/en/release-notes/whats-coming#create-or-replace-view-will-soon-preserve-grants-comments-and-tags-by-default)
**2026-10-06**
2026年12月2日から、<code>CREATE OR REPLACE VIEW</code>はビューを削除して再作成するのではなく、その場でビューを更新するようになります。権限付与、タグ、コメントは1つの注意事項つきで保持されます。

*   <code>CREATE OR REPLACE VIEW</code>で列を削除する前に、ビュー列の<a href="https://docs.databricks.com/aws/ja/admin/governed-tags">ガバナンスタグ</a>を削除する必要があります。そうしないと、ステートメントは、それらに依存する<a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/abac">ABAC</a>ポリシーを保護するために<code>CANNOT_DROP_TAGGED_COLUMN</code>エラーで失敗します(<a href="https://docs.databricks.com/aws/ja/database-objects/tags#drop">詳細</a>)。

詳細については、<a href="https://docs.databricks.com/aws/ja/sql/language-manual/sql-ref-syntax-ddl-create-view">CREATE VIEW</a> および <a href="https://docs.databricks.com/https://kb.databricks.com/dbsql/upcoming-change-to-create-or-replace-view-metadata-preservation">CREATE OR REPLACE VIEW メタデータ保存の今後の変更</a>を参照してください。

**ユーザーへのインパクト**

2026年12月2日以降、Databricksの`CREATE OR REPLACE VIEW`文の動作が変更され、デフォルトで権限、コメント、タグが保持されるようになります。この変更により、ビューを再作成するのではなく、その場で更新するようになります。主な影響と注意事項は以下の通りです：

1. **権限、コメント、タグの保持**：`CREATE OR REPLACE VIEW`を使用すると、これらのメタデータが保持されるようになります。
2. **列の削除に関する制約**：ビューから列を削除する前に、その列に付与されたガバナンスタグを削除する必要があります。そうしないと、`CANNOT_DROP_TAGGED_COLUMN`エラーが発生します。これは、そのタグに依存するABACポリシーを保護するためです。
3. **メタデータの明示的な削除**：ビュー上の権限付与、タグ、コメントを明示的に削除するには、`NOCOPY`句を使用します。ただし、ガバナンスタグは保持されることに注意してください。

この変更に対応するため、Databricksユーザーは以下の点に留意する必要があります：

* ビュー定義の更新時に意図しないメタデータの保持を避けるために、`NOCOPY`句の使用を検討する。
* ビューから列を削除する前に、関連するガバナンスタグを削除する。
* 詳細については、Databricksのドキュメント（CREATE VIEWおよびCREATE OR REPLACE VIEWメタデータ保存の今後の変更）を参照する。

# [サービス プリンシパル トークンの OAuth カスタム ID クレームが間もなく利用可能になります](https://docs.databricks.com/aws/en/release-notes/whats-coming#oauth-custom-identity-claims-for-service-principal-tokens-will-soon-be-available)
**2026-10-05**
アプリケーションは、`client_credentials` または `urn:ietf:params:oauth:grant-type:token-exchange` 付与タイプを使用するトークン要求に `custom_claim` パラメータを追加することで、サービスプリンシパルに対して要求する OAuth トークンにカスタム ID クレームを付与することができます。その後、`current_oauth_custom_identity_claim()` 関数を使用して SQL でその値を読み取ることができます。

カスタム ID クレームを使用すると、1 つのサービス プリンシパルを通じて多くのエンドユーザーをサポートしながら、各ユーザーが自分のデータのみを表示できるようになります。動的ビューは、列をクレームと比較することによって行をフィルタリングします。Genie Conversation API、SQL Statement Execution API、および Databricks JDBC ドライバーはクレームを尊重します。

トークンにカスタム ID クレームが含まれていない場合、この関数は `NULL` を返します。クレームが `NULL` の場合に、どの行にも一致しないフィルタを作成してください。

詳細については、「OAuth を使用して Databricks へのサービス プリンシパルのアクセスを認可する」および「Genie Agents API の使用」を参照してください。

**ユーザーへのインパクト**

Databricksユーザーは、サービスプリンシパルのOAuthトークンにカスタムIDクレームを追加できるようになります。これにより、1つのサービスプリンシパルで複数のエンドユーザーをサポートしつつ、ユーザーが自分のデータのみにアクセスできるように動的ビューを実装できます。具体的には、`current_oauth_custom_identity_claim()`関数を使用してSQLでクレーム値を読み取り、行をフィルタリングできます。Genie Conversation API、SQL Statement Execution API、およびDatabricks JDBCドライバーはこれらのクレームを尊重します。トークンにクレームがない場合は`NULL`が返されるため、`NULL`の場合にどの行にも一致しないフィルタを作成する必要があります。

# [Lakebase Searchは、キーワード検索用のテキストトークナイザーを設定可能にします。](https://docs.databricks.com/aws/en/release-notes/lakebase#lakebase-search-adds-a-configurable-text-tokenizer-for-keyword-search)
**2026-09-28**
新しい`lakebase_tokenizer`拡張機能を使用すると、Lakebase Searchがテキストを検索語に変換する方法を制御できます。これにより、キーワード検索が実際のデータとユーザーの読み方に一致するようになります。PostgreSQLのネイティブ全文検索では、このステップを制御する機能が限られています。`lakebase_tokenizer`は、PostgreSQLの標準テキスト検索辞書インターフェースを介して、構成可能な単語トークナイザを追加します。これには、関連性にとって重要な制御機能があります。

* **正規化**: テキストを小文字にし、Unicode正規化を適用してバイト単位で安定した一致を実現し、アクセントを削除して`café`が`cafe`と一致するようにします。
* **ストップワードと同義語**: SQLで独自のストップワードと同義語のリストを管理し、`usa`と`united_states`などの用語が同じ行と一致するようにします。
* **語幹処理と所有格**: ネイティブの英語の語幹処理機能を使用して単語を語根に還元し、末尾の`'s`を削除して、`running`が`run`と一致し、`John's`が`john`と一致するようにします。

この拡張機能は標準の`tsvector`値を生成するため、構成したトークナイザは`to_tsvector`、GIN（一般化された反転インデックス）インデックス、およびBM25（ベストマッチ25）ランキング用の`lakebase_text` `lakebase_bm25`インデックスで動作します。プロジェクト設定でLakebase Searchを有効にした後、この拡張機能をインストールしてください。詳細については、[lakebase_tokenizer](/aws/en/oltp/projects/lakebase-tokenizer)を参照してください。

**ユーザーへのインパクト**

このリリースノートは、DatabricksのLakebase Searchに関するものです。Lakebase Searchは、キーワード検索用のテキストトークナイザーを設定可能にする新機能`lakebase_tokenizer`拡張機能を導入しました。これにより、ユーザーはLakebase Searchがテキストを検索語に変換する方法を制御できます。主な影響は以下の通りです：

1. **検索の精度向上**：テキストの正規化、ストップワードと同義語の管理、語幹処理と所有格の処理により、検索結果の関連性が向上します。
2. **カスタマイズ性の向上**：ユーザーはSQLで独自のストップワードと同義語のリストを管理できます。
3. **互換性**：`lakebase_tokenizer`は標準の`tsvector`値を生成するため、既存のPostgreSQLの機能（`to_tsvector`、GINインデックス、`lakebase_text` `lakebase_bm25`インデックス）と互換性があります。

Databricksユーザーは、Lakebase Searchを有効にし、`lakebase_tokenizer`拡張機能をインストールすることで、これらの新機能を利用できます。

Unity Catalog Python UDF（ユーザー定義関数）が一般提供されました。これにより、Databricksユーザーはより柔軟にデータ処理を行うことができます。主な変更点は以下の通りです：

* スカラーUDF（1行ずつ処理する関数）の名前付きハンドラが追加されました。
* クエリあたり5つのUDF呼び出しの制限が撤廃されました。
* スカラー`TIMESTAMP`入力がPySparkの動作に合わせられました。
* カスタム依存関係のインストールや、Unity Catalogサービス資格情報やシークレットへのアクセスが可能になりました。
* 一部の機能では、`environment_version`を`6`以上に設定する必要があります。

これらの変更により、ユーザーはより複雑なデータ処理を行うことができますが、一部の機能には特定の要件があります。要件については、[Python UDF feature requirements](https://docs.databricks.com/aws/ja/udf/unity-catalog#ga-feature-requirements)を参照してください。また、コンプライアンスセキュリティプロファイルが有効になっているワークスペースについては、[近日公開予定](https://docs.databricks.com/aws/ja/release-notes/whats-coming#uc-udfs-csp-default)の変更を確認してください。

# [ScalaのUDFは、Unity Catalogのシークレットにアクセスできます。](https://docs.databricks.com/aws/en/release-notes/product/2026/september#scala-udfs-can-access-unity-catalog-secrets)
**2026-09-23**
Unity CatalogのScala UDFでセッションスコープとUnity Catalogのものは、Unity Catalogで管理されているシークレットにアクセスできるようになりました。セッションスコープのUDFは、呼び出し元の権限を使用します。 Unity CatalogのScala UDFは<code>SECRETS</code>句でシークレットを宣言し、関数所有者の権限を使用するため、呼び出し元はシークレットへの直接アクセスを必要としません。 サーバーレスコンピューティングでは、セッションスコープのScala UDFからのシークレットアクセスには、環境バージョン6以降が必要です。 シークレットにアクセスするUnity Catalog Scala UDFは、<code>environment_version</code>を<code>6</code>以降に設定する必要があります。 クラシックコンピュートでは、シークレットアクセスには、標準アクセスモードのDatabricks Runtime 19以降が必要です。 SQLウェアハウスタイプの中で、サーバーレスSQLウェアハウスのみが、シークレットにアクセスするUnity Catalog Scala UDFをサポートします。 専用アクセスモードのコンピュートでの直接呼び出しはサポートされていません。 詳しくは<a href="https://docs.databricks.com/aws/ja/security/secrets/unity-catalog-secrets">Unity Catalogのシークレット</a>をご参照ください。

**ユーザーへのインパクト**

このリリースノートは、DatabricksのScalaユーザー定義関数（UDF）がUnity Catalogで管理されているシークレットにアクセスできるようになったことを示しています。主な影響は以下の通りです：

1. **セッションスコープのUDF**：呼び出し元の権限でシークレットにアクセスします。サーバーレスコンピューティングでは環境バージョン6以降、クラシックコンピュートではDatabricks Runtime 19以降（標準アクセスモード）が必要です。

2. **Unity CatalogのScala UDF**：`SECRETS`句でシークレットを宣言し、関数所有者の権限でシークレットにアクセスします。呼び出し元はシークレットへの直接アクセスを必要としませんが、環境バージョン6以降が必要です。

3. **サポートされる環境**：サーバーレスSQLウェアハウスはサポートされていますが、専用アクセスモードでの直接呼び出しはサポートされていません。

つまり、Scala UDFを使用するDatabricksユーザーは、Unity Catalogで管理されるシークレットへのアクセスが可能になり、より安全なデータ管理が実現します。ただし、適切な環境設定とアクセスモードの選択が重要になります。詳細は、リンク先のドキュメントを参照してください。

# [新しいバリアントテーブルでは、バリアント シャッディングが間もなくデフォルトで有効になります。](https://docs.databricks.com/aws/en/release-notes/whats-coming#variant-shredding-will-soon-be-enabled-by-default-on-new-variant-tables)
**2026-09-22**
2026年11月18日から、Databricksは、Databricks Runtime 17.3以降で作成された<code>VARIANT</code>型の列を含む新しいテーブルに、<code>variantShredding</code>テーブル機能を自動的に追加するようになります。Variant shreddingは、頻繁にアクセスされるフィールドを型付きのカラム形式で保存することで、クエリのパフォーマンスを向上させます。

これは、Databricks Runtime 15.4に対する破壊的変更です。Databricks Runtime 15.4が動作しているクラスターは、variant shreddingが有効になっているテーブルからの読み取りおよび書き込みができません。この変更が有効になる前に、影響を受けるクラスターをDatabricks Runtime 16.4以降にアップグレードしてください。

詳細については、<a href="https://docs.databricks.com/aws/ja/tables/features/variant-shredding">variant shreddingを使用してパフォーマンスを最適化する</a>を参照してください。

**ユーザーへのインパクト**

2026年11月18日以降、Databricks Runtime 17.3以降で作成されたVARIANT型の列を含む新しいテーブルでは、variant shreddingがデフォルトで有効になります。これにより、クエリのパフォーマンスが向上しますが、Databricks Runtime 15.4以下のクラスターでは、これらのテーブルへの読み書きができなくなります。影響を受けるクラスターは、Databricks Runtime 16.4以降にアップグレードする必要があります。

# [Databricks Runtime 20におけるバンドルBigQuery JDBCドライバの削除](https://docs.databricks.com/aws/en/release-notes/whats-coming#bundled-bigquery-jdbc-driver-removal-in-databricks-runtime-20)
**2026-09-22**
Databricks Runtime 20以降では、Databricks RuntimeにバンドルされているBigQuery JDBCドライバーは含まれなくなりました。一方、Databricks Runtime 19以前では、引き続きBigQuery JDBCドライバーが含まれます。
<code>jdbc:bigquery:</code> URLでSpark JDBCを使用する従来のコンピュートワークロードは、BigQuery JDBCドライバーがインストールされていない限り、ドライバーが見つからない旨のエラーで失敗します。影響を受けるワークロードをアップグレードする前に、ワークロードを移行してください。

**ユーザーへのインパクト**

Databricks Runtime 20以降にアップグレードする場合、これまでBigQuery JDBCドライバーを利用していたワークロードは、ドライバーが見つからないエラーで失敗します。そのため、BigQuery JDBCドライバーを別途インストールする必要があります。影響を受けるワークロードを事前に移行しておくことを推奨します。Databricks Runtime 19以前を利用している場合は、引き続きBigQuery JDBCドライバーが利用可能です。
