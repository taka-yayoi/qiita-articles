# [近日予定されている挙動の変更: MANAGE は同一オブジェクトに対する USE CATALOG や USE SCHEMA を必要としなくなる

(注: これは、データベース管理システム、特に Databricks などのプラットフォームにおけるアクセス制御に関する変更についての記述と思われます。)

原文の "Upcoming behavior change" は、「近日予定されている挙動の変更」や「今後の挙動変更」などと訳しました。

"MANAGE" "USE CATALOG" "USE SCHEMA" は、データベースやそのオブジェクトに対する権限や操作に関連するコマンドや権限名と思われます。これらは特定のデータベースシステム（おそらくDatabricks）に特有の用語であるため、訳文では英語のまま残しました。ただし、一般的な理解を助けるために簡単に説明すると、

- MANAGE: オブジェクトを管理する権限または操作
- USE CATALOG: カタログ（データベースやスキーマの集まり）を使用する権限
- USE SCHEMA: スキーマ（データベース内の論理的な構造）を使用する権限

をそれぞれ指しています。

したがって、この変更は、これらの権限の要件に関する挙動が変更されることを示しています。具体的には、あるオブジェクトに対して `MANAGE` 権限を行使するために、同じオブジェクトに対して `USE CATALOG` や `USE SCHEMA` が必要なくなる、という変更です。](https://docs.databricks.com/aws/en/release-notes/whats-coming#upcoming-behavior-change-manage-no-longer-requires-use-catalog-or-use-schema-on-the-same-object)
**2026-07-15**
<p><a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/access-control/permissions-concepts#the-manage-privilege">MANAGE権限</a> があると、ユーザーは、オブジェクトの所有者でなくても、そのオブジェクトに対する権限を管理したり、所有権を移譲したり、オブジェクトを削除したりできます。</p>
<p>一般に、<a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/access-control/permissions-concepts#usage-privileges">使用権限</a>（<code>USE CATALOG</code> および <code>USE SCHEMA</code>）は、Unity Catalogオブジェクトを操作するための前提条件です。現在、カタログまたはスキーマに対する <code>MANAGE</code> 権限は、適切な使用権限も保持している場合にのみ有効になります。</p>
<p>2026年8月3日から、<code>MANAGE</code> を付与された特定のオブジェクトに対する使用権限が <code>MANAGE</code> に不要になります。この変更により、<code>MANAGE</code> の動作がオブジェクトの所有権とより一貫したものになります。引き続き、親コンテナに対する使用権限が必要になります。例えば、以下のようなケースが考えられます。</p>
<ul>
<li>現時点では、スキーマを管理するには、当該スキーマに対する<code>USE CATALOG</code> + <code>USE SCHEMA</code> + <code>MANAGE</code> が必要です。</li>
<li>変更後は、スキーマを管理するために必要な権限は、当該スキーマに対する <code>USE CATALOG</code> + <code>MANAGE</code> のみになります。</li>
</ul>
<p>次の表は、オブジェクトを管理するために新たに必要となる権限をまとめたものです。</p>

<li>
<ul>

<li>必要な権限</li>
</ul>
</li>
<li>
<ul>
<li>カタログ</li>
<li>カタログに対する<code>MANAGE</code> のみ</li>
</ul>
</li>
<li>
<ul>
<li>スキーマ</li>
<li>スキーマに対する<code>MANAGE</code> 、および親カタログに対する<code>USE CATALOG</code></li>
</ul>

## Databricksユーザーへの影響

2026年8月3日から、DatabricksのUnity Catalogにおいて、`MANAGE`権限の挙動が変更されます。具体的には、あるオブジェクト（カタログやスキーマなど）に対して`MANAGE`権限を持つユーザーは、そのオブジェクトに対する`USE CATALOG`や`USE SCHEMA`権限がなくても、そのオブジェクトを管理できるようになります。ただし、親コンテナ（例えば、スキーマの場合はカタログ）に対する`USE CATALOG`権限は引き続き必要です。

### 主な変更点

- スキーマを管理する場合、これまでは`USE CATALOG` + `USE SCHEMA` + `MANAGE`が必要でしたが、変更後は`USE CATALOG` + `MANAGE`のみでよくなります。
- カタログを管理する場合、`MANAGE`権限のみでよくなります。

### ユーザーへの影響

- オブジェクトの管理に関する権限管理が簡素化されます。
- 既存の権限設定を見直し、必要に応じて調整する必要があります。

### 推奨事項

- 2026年8月3日より前に、Databricks環境における権限設定の見直しを行ってください。
- オブジェクトの管理に必要な権限が変更になることをユーザーに周知し、必要なトレーニングやサポートを提供してください。

# [継続ジョブおよびパイプラインの動作変更点](https://docs.databricks.com/aws/en/release-notes/whats-coming#behavior-changes-for-continuous-jobs-and-pipelines)
**2026-07-08**
2026年8月初旬に、Lakeflow Spark 宣言型パイプラインとジョブの継続的な更新が行われ、構成と状態管理が簡素化されます。

<strong>継続的パイプライン</strong>

パイプライン ページから、<a href="https://docs.databricks.com/aws/ja/ldp/serverless#performance">パフォーマンス モード</a>などのジョブ レベルの設定を含め、継続的なスケジュールを直接構成できるようになります。この方法で継続的なスケジュールを構成すると、パイプラインが継続的ジョブにラップされます。

Databricks では、パイプラインの組み込みの継続的設定ではなく、継続的ジョブを使用して継続的パイプラインを実行することをお勧めします。継続的ジョブがパイプラインをラップする場合、ジョブはパイプラインの実行ライフサイクルを管理します。組み込みの継続的設定は削除されませんが、新しい継続的パイプラインでは継続的ジョブ パターンを使用する必要があります。

<strong>継続的ジョブ</strong>

継続的ジョブの状態管理が簡素化されます。次の破壊的変更が有効になります。

* ジョブに継続的なスケジュールを追加すると、スケジュールが一時停止しているか、一時停止していないかに関係なく、アクティブな実行がキャンセルされます。
* ジョブから継続的なスケジュールを削除すると、アクティブな実行がキャンセルされます。
* 一時停止した継続的ジョブを実行すると、一時停止が解除されます。
* 継続的ジョブを一時停止すると、アクティブな実行もキャンセルされます。
* 継続的ジョブのアクティブな実行を停止すると、ジョブも一時停止します。

新しい読み取り専用 API フィールドは、継続的ジョブの状態を追跡します。

現在の継続的ジョブの動作に依存する自動化またはワークフローを、このリリースの前に確認して更新してください。

**ユーザーへのインパクト**

Databricksユーザーに対する影響：

2026年8月初旬に予定されているLakeflow Spark宣言型パイプラインとジョブの更新により、継続ジョブとパイプラインの動作にいくつかの変更が生じます。

1. **継続的パイプライン**：
   - パイプライン ページから直接、ジョブ レベルの設定（例：パフォーマンス モード）を含む継続的なスケジュールを構成できるようになります。
   - この構成により、パイプラインが継続的ジョブにラップされます。
   - Databricks は、パイプラインの組み込みの継続的設定ではなく、継続的ジョブを使用することを推奨しています。新しい継続的パイプラインでは継続的ジョブ パターンを使用する必要があります。

2. **継続的ジョブ**：
   - 状態管理が簡素化され、いくつかの破壊的変更が導入されます：
     - 継続的なスケジュールを追加すると、アクティブな実行がキャンセルされます。
     - 継続的なスケジュールを削除すると、アクティブな実行がキャンセルされます。
     - 一時停止した継続的ジョブを実行すると、一時停止が解除されます。
     - 継続的ジョブを一時停止すると、アクティブな実行がキャンセルされます。
     - 継続的ジョブのアクティブな実行を停止すると、ジョブも一時停止します。
   - 新しい読み取り専用 API フィールドが、継続的ジョブの状態を追跡するために使用されます。

**推奨事項**：

現在の継続的ジョブの動作に依存する自動化またはワークフローがある場合、このリリース前にそれらを確認して更新する必要があります。これらの変更は、既存のジョブやパイプラインの運用に影響を及ぼす可能性があるため、事前に準備しておくことが重要です。

# [ジョブタスクのサブセットをその依存関係とともに実行する](https://docs.databricks.com/aws/en/release-notes/product/2026/june#run-a-subset-of-job-tasks-with-their-dependencies)
**2026-06-30**
<p>ジョブのタスクのサブセットを実行するときに、選択範囲を拡張して各タスクの依存関係を含めることができるようになりました。タスクキーに<code>+</code>修飾子を追加して、上流タスク(<code>+my_task</code>)、下流タスク(<code>my_task+</code>)、またはその両方(<code>+my_task+</code>)を実行します。UI、REST API、Databricks CLI、SDK、またはDeclarative Automation Bundlesから部分実行を開始します。 <a href="https://docs.databricks.com/aws/ja/jobs/run-now#run-task-subset">タスクのサブセットとその依存関係を実行する</a>を参照してください。</p>

**ユーザーへのインパクト**

このリリースにより、Databricksユーザーはジョブの実行時に特定のタスクとその依存関係（上流または下流タスク）を選択して実行できるようになります。具体的な変更点とその影響は以下の通りです：

1. **タスクの部分実行の柔軟性向上**：ジョブ内の特定のタスクを実行する際に、`+` 修飾子を使用して上流タスク (`+my_task`)、下流タスク (`my_task+`)、またはその両方 (`+my_task+`) を含めることができます。これにより、必要なタスクとその依存関係だけを実行でき、リソースの効率的な使用が可能になります。

# [Databricks Runtime 19 (Beta): 2026 年 6 月 26 日](https://docs.databricks.com/aws/en/release-notes/runtime/19#databricks-runtime-19-beta-june-26-2026)
**2026-06-26**
<h3>動作の変更</h3>
<ul>
<li><strong>標準アクセスモードでの環境変数の利用制限</strong>: <a href="https://docs.databricks.com/aws/ja/compute/standard-limitations">標準アクセスモード</a>では、事前定義された一部の環境変数のみがSparkエンジンとinitスクリプトで利用できます。このセットには、プロキシ設定（<code>HTTP_PROXY</code>）、クラウド認証情報（<code>AWS_ACCESS_KEY_ID</code>、<code>AZURE_CLIENT_ID</code>）、カタログ変数（<code>CATALOG</code>）などの一般的な設定変数が含まれます。クラスタで設定したその他の変数は、UDFを含むユーザーコードでは利用できますが、Sparkエンジンやinitスクリプトでは利用できません。以前は、すべてのクラスタ環境変数がSparkエンジンとinitスクリプトで利用できました。 <a href="https://docs.databricks.com/aws/ja/compute/standard-limitations#environment-variable-limitations">環境変数の制限</a>を参照してください。</li>
<li><strong>標準アクセスモードでの制限付きSpark設定</strong>: <a href="https://docs.databricks.com/aws/ja/compute/standard-limitations">標準アクセスモード</a>では、特定のSpark設定プロパティを設定できなくなりました。制限されたプロパティ（プレフィックスで一致）を設定するクラスタの作成または編集は、エラーで失敗します。制限されたプロパティには、<code>spark.driver.extraJavaOptions</code>、<code>spark.executor.extraJavaOptions</code>、<code>spark.jars</code>、<code>spark.files</code>、<code>spark.executorEnv.*</code>、<code>spark.kubernetes.*</code>などがあります。以前は、標準アクセスモードでこれらのプロパティを設定できました。アップグレード前にクラスタ設定から削除してください。完全なリストについては、<a href="https://docs.databricks.com/aws/ja/compute/standard-limitations#spark-configuration-limitations">Spark設定の制限</a>を参照してください。</li>
</ul>

**ユーザーへのインパクト**

Databricks Runtime 19へのアップグレードにより、標準アクセスモードのクラスタで以下の変更が発生します：

1. 環境変数の利用制限: ユーザー定義の環境変数はSparkエンジンとinitスクリプトで利用できなくなり、代わりに事前定義された一部の変数（例：プロキシ設定、クラウド認証情報、カタログ変数）のみが利用できるようになります。ユーザーコードでは引き続き利用可能です。

2. 制限付きSpark設定: 特定のSpark設定プロパティ（例：`spark.driver.extraJavaOptions`、`spark.executor.extraJavaOptions`）を設定できなくなります。これらのプロパティを設定しているクラスタは、作成または編集時にエラーで失敗します。

これらの変更により、既存のクラスタ設定やコードの修正が必要になる場合があります。特に、標準アクセスモードで環境変数や制限付きSpark設定を使用している場合は、Databricksドキュメントの「環境変数の制限」と「Spark設定の制限」を参照し、必要な調整を行ってください。

# [Genieコードシステムテーブルは、現在ユーザーが送信したインタラクションのみをカウントします。](https://docs.databricks.com/aws/en/release-notes/product/2026/june#genie-code-system-table-now-counts-only-user-submitted-interactions)
**2026-06-22**
<p><a href="https://docs.databricks.com/aws/ja/admin/system-tables/assistant">Genie Code システムテーブル</a>（<code>system.access.assistant_events</code>）は、サイドパネルのチャットやエージェントモード、インラインアシスタント（<code>%assistant</code>）など、ユーザーが送信したGenie Codeインタラクションのみを記録するようになりました。オートコンプリート（ゴーストテキスト）、クイックフィックスの提案、自動リネームなどのバックグラウンドおよび自動化されたリクエストは、イベントとして記録されなくなりました。</p>
<p>この変更は2026年5月7日に有効となり、これらのバックグラウンドリクエストをカウントしていた以前の動作が修正されました。この日付より前に記録されたイベント数は、実際のユーザーアクティビティよりも多く表示される可能性があるため、この時点前後での1日のイベントの減少は予想され、利用状況の低下を示すものではありません。</p>

**ユーザーへのインパクト**

Genieコードシステムテーブル（`system.access.assistant_events`）の変更について、Databricksユーザーへの影響を簡潔に説明します。

2026年5月7日以降、Genieコードシステムテーブルは、ユーザーが送信したインタラクション（サイドパネルのチャット、エージェントモード、インラインアシスタントなど）のみを記録し、自動化されたリクエスト（オートコンプリート、クイックフィックスの提案、自動リネームなど）は記録しなくなります。これにより、それ以前のデータと比較して1日のイベント数が減少する可能性がありますが、これは利用状況の低下を示すものではありません。

# [Discover ページがパブリックプレビューになりました](https://docs.databricks.com/aws/en/release-notes/product/2026/june#the-discover-page-is-now-in-public-preview)
**2026-06-22**
<p>Discoverページがパブリックプレビューになりました。Discoverはキュレーションされた閲覧エクスペリエンスであり、ユーザーがカタログ階層に関する深い知識がなくても、Unity Catalogによって管理されるデータアセットを見つけられるようサポートします。*ドメイン*や*サブドメイン*を使って、テーブルやダッシュボード、Genie Spacesをビジネス領域ごとに整理し、カスタムキュレーションで主要なアセットをハイライトし、AIが推奨するアセットを参照することができます。</p>

**ユーザーへのインパクト**

Discoverページがパブリックプレビューになったことで、DatabricksユーザーはUnity Catalogで管理されるデータアセットをより簡単に発見できるようになります。具体的には、ドメインやサブドメインを使ってアセットを整理し、カスタムキュレーションやAI推奨により、関連するテーブル、ダッシュボード、Genie Spacesを簡単に見つけることができます。これにより、カタログ階層に関する深い知識がなくても、必要なデータにアクセスしやすくなります。

# [以前のコンピューティングプレビューシステムのスキーマは廃止予定です。](https://docs.databricks.com/aws/en/release-notes/product/2026/june#legacy-compute_preview-system-schema-deprecated)
**2026-06-22**
<p>レガシーな<code>compute_preview</code> システムスキーマは非推奨となり、<code>system</code>カタログから削除されます。代わりに<code>system.compute</code>スキーマを使用してください。現在のシステムスキーマとテーブル一覧については、<a href="https://docs.databricks.com/aws/ja/admin/system-tables">システムテーブルリファレンス</a>を参照してください。</p>

**ユーザーへのインパクト**

Databricksユーザーは、従来の`compute_preview`システムスキーマが非推奨となり、`system`カタログから削除されるため、今後は`system.compute`スキーマを使用する必要があります。影響を受けるユーザーは、システムテーブルリファレンスを参照して、現在のシステムスキーマとテーブル一覧を確認し、必要な変更を加える必要があります。
