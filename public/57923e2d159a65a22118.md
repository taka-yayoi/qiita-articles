# [同じオブジェクトに対して、MANAGEでUSE CATALOGやUSE SCHEMAが不要になりました。](https://docs.databricks.com/aws/en/release-notes/product/2026/august#manage-no-longer-requires-use-catalog-or-use-schema-on-the-same-object)

<p>以前は、カタログまたはスキーマに対する<code>MANAGE</code>は、そのオブジェクトに対する適切な利用権限も保持している場合にのみ有効でした。親コンテナに対する利用権限は引き続き必要です。</p>

<li>スキーマに対する<code>MANAGE</code>には親カタログの<code>USE CATALOG</code>が必要ですが、スキーマに対する<code>USE SCHEMA</code>は不要になりました。</li>
<li>テーブル、ビュー、ボリューム、または関数に対する<code>MANAGE</code>は変更されていません。引き続き、親カタログの<code>USE CATALOG</code>と親スキーマの<code>USE SCHEMA</code>が必要です。</li>
</ul>
<p>他のすべての権限は影響を受けず、<code>MANAGE</code>を持つユーザーであっても、利用権限を前提条件として必要とします。たとえば、テーブルをクエリするには、テーブルに対する<code>SELECT</code>、および親カタログとスキーマに対する<code>USE CATALOG</code>と<code>USE SCHEMA</code>が必要です。</p>
<p>対応する利用権限を付与せずに<code>MANAGE</code>を広範に付与していた場合、これらの権限付与が現在有効となり、権限付与者はオブジェクトを管理できるようになります。Databricksでは、既存の<code>MANAGE</code>権限付与を監査して、意図したアクセスを反映していることを確認することをお勧めします。</p>

**ユーザーへのインパクト**

Databricksのリリースノートによると、`MANAGE`権限の動作が変更され、同じオブジェクトに対する`USE CATALOG`や`USE SCHEMA`が不要になりました。つまり、カタログまたはスキーマに対する`MANAGE`権限を持つユーザーは、それらのオブジェクトを管理するために`USE CATALOG`や`USE SCHEMA`権限を別途持つ必要がなくなりました。

この変更は、以下の点でDatabricksユーザーに影響を与えます。

* カタログに対する`MANAGE`権限は、`USE CATALOG`権限を必要としなくなりました。
* スキーマに対する`MANAGE`権限は、親カタログの`USE CATALOG`権限のみ必要で、スキーマに対する`USE SCHEMA`権限は不要になりました。
* テーブル、ビュー、ボリューム、または関数に対する`MANAGE`権限については、従来通り、親カタログの`USE CATALOG`と親スキーマの`USE SCHEMA`が必要です。

他の権限については、引き続き利用権限を前提条件として必要とします。たとえば、テーブルをクエリするには、テーブルに対する`SELECT`、および親カタログとスキーマに対する`USE CATALOG`と`USE SCHEMA`が必要です。

この変更により、`MANAGE`権限を広範に付与していた場合、これらの権限付与が現在有効となり、権限付与者はオブジェクトを管理できるようになります。Databricksでは、既存の`MANAGE`権限付与を監査して、意図したアクセスを反映していることを確認することをお勧めします。

これらの変更は、Databricksユーザーが既存のワークロードやアプリケーションの動作を確認し、必要に応じて設定やコードの調整を行う必要があることを意味します。特に、Python UDFを使用している場合は、型強制の動作の変更に注意する必要があります。

**ユーザーへのインパクト**

* これにより、機密データへのアクセスがより厳密に制御され、ユーザーが自分のIDとしてアクセスしたり、異なるユースケースやプロジェクト間でデータを混在させたりすることがなくなります。
* アカウント管理者とワークスペース管理者は、RBACを有効にするために必要なアクションを実行する必要があります。アカウントレベルとワークスペースレベルの両方でプレビューを有効にする必要があります。
* 詳細については、Databricksのドキュメント（ロールベースアクセス制御 (RBAC)）を参照してください。

# [近日予定されている挙動の変更: MANAGE は同一オブジェクトに対する USE CATALOG や USE SCHEMA を必要としなくなる

(注: これは、データベース管理システム、特に Databricks などのプラットフォームにおけるアクセス制御に関する変更についての記述と思われます。)

原文の "Upcoming behavior change" は、「近日予定されている挙動の変更」や「今後の挙動変更」などと訳しました。

"MANAGE" "USE CATALOG" "USE SCHEMA" は、データベースやそのオブジェクトに対する権限や操作に関連するコマンドや権限名と思われます。これらは特定のデータベースシステム（おそらくDatabricks）に特有の用語であるため、訳文では英語のまま残しました。ただし、一般的な理解を助けるために簡単に説明すると、

- MANAGE: オブジェクトを管理する権限または操作
- USE CATALOG: カタログ（データベースやスキーマの集まり）を使用する権限
- USE SCHEMA: スキーマ（データベース内の論理的な構造）を使用する権限

をそれぞれ指しています。

したがって、この変更は、これらの権限の要件に関する挙動が変更されることを示しています。具体的には、あるオブジェクトに対して `MANAGE` 権限を行使するために、同じオブジェクトに対して `USE CATALOG` や `USE SCHEMA` が必要なくなる、という変更です。](https://docs.databricks.com/aws/en/release-notes/whats-coming#upcoming-behavior-change-manage-no-longer-requires-use-catalog-or-use-schema-on-the-same-object)
**2026-07-15**
<p><a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/access-control/permissions-concepts#the-manage-privilege">MANAGE権限</a> があると、ユーザーは、オブジェクトの所有者でなくても、そのオブジェクトに対する権限を管理したり、所有権を移譲したり、オブジェクトを削除したりできます。</p>
<p>一般に、<a href="https://docs.databricks.com/aws/ja/data-governance/unity-catalog/access-control/permissions-concepts#usage-privileges">使用権限</a>（<code>USE CATALOG</code> および <code>USE SCHEMA</code>）は、Unity Catalogオブジェクトを操作するための前提条件です。現在、カタログまたはスキーマに対する <code>MANAGE</code> 権限は、適切な使用権限も保持している場合にのみ有効になります。</p>
<p>2026年8月3日から、<code>MANAGE</code> を付与された特定のオブジェクトに対する使用権限が <code>MANAGE</code> に不要になります。この変更により、<code>MANAGE</code> の動作がオブジェクトの所有権とより一貫したものになります。引き続き、親コンテナに対する使用権限が必要になります。例えば、以下のようなケースが考えられます。</p>
<ul>
<li>現時点では、スキーマを管理するには、当該スキーマに対する<code>USE CATALOG</code> + <code>USE SCHEMA</code> + <code>MANAGE</code> が必要です。</li>
<li>変更後は、スキーマを管理するために必要な権限は、当該スキーマに対する <code>USE CATALOG</code> + <code>MANAGE</code> のみになります。</li>
</ul>

## Databricksユーザーへの影響

2026年8月3日から、DatabricksのUnity Catalogにおいて、`MANAGE`権限の挙動が変更されます。具体的には、あるオブジェクト（カタログやスキーマなど）に対して`MANAGE`権限を持つユーザーは、そのオブジェクトに対する`USE CATALOG`や`USE SCHEMA`権限がなくても、そのオブジェクトを管理できるようになります。ただし、親コンテナ（例えば、スキーマの場合はカタログ）に対する`USE CATALOG`権限は引き続き必要です。

### 主な変更点

- スキーマを管理する場合、これまでは`USE CATALOG` + `USE SCHEMA` + `MANAGE`が必要でしたが、変更後は`USE CATALOG` + `MANAGE`のみでよくなります。
- カタログを管理する場合、`MANAGE`権限のみでよくなります。

### ユーザーへの影響

- オブジェクトの管理に関する権限管理が簡素化されます。
- 既存の権限設定を見直し、必要に応じて調整する必要があります。

### 推奨事項

- 2026年8月3日より前に、Databricks環境における権限設定の見直しを行ってください。
- オブジェクトの管理に必要な権限が変更になることをユーザーに周知し、必要なトレーニングやサポートを提供してください。

カスタムモデルサービングエンドポイントのうち、テンソルベースの入力シグネチャを持つものについては、リクエストボディを JSON ではなく、シリアライズされた <a href="https://docs.databricks.com/https://github.com/kserve/open-inference-protocol">KServe v2</a> の <code>ModelInferRequest</code> (<code>Content-Type: application/x-protobuf</code>) として送信できるようになりました。

この変更は、モデルの提供方法に影響を与える可能性があります。Protobufテンソル入力を使用することで、モデルの推論リクエストの効率化が期待できます。ただし、リクエストの送信方法を変更する必要があります。詳細については、Databricksのドキュメントを参照してください。

これらの変更により、ユーザーはGenie Agentsをより使いやすく、管理しやすくなります。また、権限に応じたアクセス方法が統一されるため、ユーザーエクスペリエンスが向上します。

**2026-07-09**
<p>これで、AWS PrivateLinkを使用して、SAP Business Data Cloud（BDC）にプライベートに接続できます。組織でプライベートネットワーク接続が必要な場合は、接続を作成する前に、SAP BDC共有のバックエンドにあるS3バケットにAWS PrivateLinkを設定してください。詳細は、「<a href="https://docs.databricks.com/aws/ja/opensharing/sap-bdc/create-connection#private-connectivity">SAP BDCへのプライベート接続を設定する</a>」を参照してください。</p>

**ユーザーへのインパクト**

AWS PrivateLinkを使用することで、SAP Business Data Cloud（BDC）へのプライベート接続が可能になりました。これにより、組織のセキュリティとコンプライアンスが向上します。プライベートネットワーク接続を必要とする組織は、SAP BDC共有のバックエンドにあるS3バケットにAWS PrivateLinkを設定する必要があります。具体的な手順については、提供されたドキュメントリンクを参照してください。

# [Genieエージェントの強化](https://docs.databricks.com/aws/en/ai-bi/release-notes/2026#genie-agents-enhancements)
**2026-07-09**
<ul>
<li><strong>Genie SpacesがGenie Agentsに名称変更</strong>: Genie SpacesはGenie Agentsと呼ばれるようになりました。</li>
<li><strong>SQL式が例示SQLとともにグループ化</strong>: 作成エクスペリエンスにおいて、SQL式が例示SQLクエリとともにグループ化されるようになったため、両者を一か所で定義および管理できるようになりました。<a href="https://docs.databricks.com/aws/ja/genie/tune-quality#sql-expressions">SQL式の定義</a>を参照してください。</li>
<li><strong>Genie Oneにおける一貫したGenie Agentエクスペリエンス</strong>: Genie Oneにおいて、Genie Agentは、閲覧権限のみがある場合はチャットとして開き、作成権限がある場合はAnalytics and AI workspace UIで開くようになりました。<a href="https://docs.databricks.com/aws/ja/genie-one/genie">Genie Oneの使用</a>を参照してください。</li>
</ul>

**ユーザーへのインパクト**

Genieエージェントの強化に関するリリースノートの内容は、以下のとおりDatabricksユーザーに影響を及ぼします。

1. **Genie SpacesがGenie Agentsに名称変更**: ユーザーは、従来「Genie Spaces」と呼ばれていた機能が「Genie Agents」に名称変更されたことを認識する必要があります。これにより、UIやドキュメントでの参照が変更される可能性があります。

2. **SQL式が例示SQLとともにグループ化**: Genie Agentsの作成時に、SQL式と例示SQLクエリが一つの場所で定義および管理できるようになりました。これにより、ユーザーはSQL式と例示SQLをより効率的に管理できます。具体的な操作方法については、[SQL式の定義](https://docs.databricks.com/aws/ja/genie/tune-quality#sql-expressions)を参照してください。

3. **Genie Oneにおける一貫したGenie Agentエクスペリエンス**: Genie OneでGenie Agentにアクセスする際、ユーザーの権限に応じてUIが異なるようになりました。閲覧権限のみのユーザーはチャットとして開き、作成権限があるユーザーはAnalytics and AI workspace UIで開きます。詳細は、[Genie Oneの使用](https://docs.databricks.com/aws/ja/genie-one/genie)を参照してください。

これらの変更により、ユーザーはGenie Agentsをより効率的に利用し、管理できるようになります。特に、権限に応じたアクセス方法の変更とSQL式の管理方法の改善は、日々の作業フローに影響を及ぼす可能性があります。

# [Databricks SQL アラートは、コンプライアンスセキュリティプロファイルが有効になっているワークスペースでデフォルトで利用できるようになりました。](https://docs.databricks.com/aws/en/release-notes/product/2026/july#databricks-sql-alerts-are-now-available-by-default-for-workspaces-with-the-compliance-security-profile-enabled)
**2026-07-09**
<p>Databricks SQL アラートは、Databricksがサポートするすべてのコンプライアンスセキュリティプロファイル標準をサポートし、<a href="https://docs.databricks.com/aws/ja/security/privacy/security-profile">コンプライアンスセキュリティプロファイル</a>が有効になっているワークスペースでデフォルトで利用できるようになりました。</p>
<p>Databricks SQL アラートを使用すると、スケジュールに従ってクエリを実行し、条件を評価し、条件が満たされたときに受信者に通知することで、データと KPI を監視できます。</p>
<p><a href="https://docs.databricks.com/aws/ja/sql/user/alerts">Databricks SQL アラート</a>を参照してください。</p>

**ユーザーへのインパクト**

Databricks SQLアラートが、コンプライアンスセキュリティプロファイルが有効なワークスペースでデフォルトで利用できるようになりました。これにより、ユーザーはスケジュールに従ってクエリを実行し、条件が満たされたときに通知を受け取ることで、データとKPIを監視できます。Databricksがサポートするすべてのコンプライアンスセキュリティプロファイル標準に準拠しています。
