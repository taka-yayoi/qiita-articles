https://openai.com/index/gpt-4-1/

> 本日、APIで3つの新しいモデルをリリースします：GPT-4.1、GPT-4.1 mini、GPT-4.1 nanoです。これらのモデルは、全体的にGPT-4oおよびGPT-4o miniを上回っており、特にコーディングと指示の遵守において大きな進歩を遂げています。さらに、最大100万トークンのコンテキストウィンドウをサポートし、長いコンテキストをより効果的に活用できるよう改良されています。知識カットオフも更新され、2024年6月時点の情報まで対応しています。

いろいろ試してみると、結構な確率でMarkdownを返すので、それをレンダリングするような関数を作成します。

```py
import time
import openai
from IPython.display import Markdown

def compare_models(prompt_text):

  # 比較するモデル
  models = {
    "gpt-4.1": "GPT-4.1",
    "gpt-4o": "GPT-4o"
  }

  # 結果格納用
  results = {}
  both_result_content = ""

  for model_name, description in models.items():
    #print(f"\n=== {description} ({model_name}) ===")
    both_result_content = both_result_content + f"\\\n**=== {description} ({model_name}) ===** \\\n\\\n"

    start_time = time.time()

    response = client.chat.completions.create(
        model=model_name,
        messages=[
            {"role": "system", "content": "あなたは有能なアシスタントです。"},
            {"role": "user", "content": prompt_text}
        ],
        temperature=0.7
    )

    end_time = time.time()

    elapsed_time = end_time - start_time
    content = response.choices[0].message.content
    both_result_content = both_result_content + content + f"\\\n\\\n反応時間: {elapsed_time:.2f} 秒"

  return both_result_content
```

プロンプトに関しては、GPT-4oに`これらのモデルの良し悪しを比較できるプロンプトの例`とお願いしました。

## GPT-4.1

```py
import re

def validate_email(email):
    """
    メールアドレスがRFC5322にできる限り準拠しているかを検証します。
    :param email: チェックするメールアドレス（str）
    :return: 正しい場合True、不正な場合False
    """
    try:
        # RFC5322の仕様にできる限り近い正規表現
        regex = r"^(?P<local>[a-zA-Z0-9!#$%&'*+/=?^_`{|}~.-]+)@(?P<domain>[a-zA-Z0-9-]+(?:\.[a-zA-Z0-9-]+)*\.[a-zA-Z]{2,})$"
        if not isinstance(email, str):
            return False
        if re.fullmatch(regex, email):
            return True
        else:
            return False
    except Exception:
        return False

# テスト
print(validate_email("example@example.com"))  # True
print(validate_email("invalid-email"))        # False
```

きちんと動いています。正規表現もシンプルでぱっと見何をやっているのかが把握できます。

## GPT-4o

```py
import re

def validate_email(email):
    try:
        # RFC 5322に基づく一般的な正規表現パターン
        email_regex = re.compile(
            r"(?i)^(?:(?:[a-z0-9!#$%&'*+/=?^_`{|}~-]+(?:\.[a-z0-9!#$%&'*+/=?^_`{|}~-]+)*)|(?:\"(?:[\x01-\x08\x0b\x0c\x0e-\x1f\x21\x23-\x5b\x5d-\x7f]|\\[\x01-\x09\x0b\x0c\x0e-\x7f])*\"))
            @(?:(?:[a-z0-9](?:[a-z0-9-]*[a-z0-9])?\.)+[a-z0-9](?:[a-z0-9-]*[a-z0-9])?|\[(?:(?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)\.){3}
            (?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)\])$"
        )
        
        if email_regex.match(email):
            return True
        else:
            return False
    except Exception as e:
        print(f"An error occurred: {e}")
        return False

# テスト
print(validate_email("example@example.com"))  # True
print(validate_email("invalid-email"))        # False
```

こちらはエラーになりました。しかも、正規表現が複雑怪奇すぎて読み解けません。

# 曖昧な指示から構造化した出力の生成

```py
# テストするプロンプト
prompt_text = """
以下の曖昧な要求仕様を整理して、要件定義書の構成に分類してください。

【曖昧な仕様】
ユーザーは簡単にログインできるようにしたい。
セキュリティは万全にしたい。
スマホでも使いやすくしたい。
バックエンドにはAPIを作る必要がある。
管理者画面も必要。
...

→ 分類対象：
- 機能要件
- 非機能要件
- システム要件
- 運用要件
"""
result = compare_models(prompt_text)
Markdown(result)
```

これは結構出力が違ったので、マークダウンを直接貼り付けます。GPT-4.1の方が粒度の細かい仕様書になっています。

## GPT-4.1

以下に、いただいた曖昧な仕様を要件定義書の構成（機能要件、非機能要件、システム要件、運用要件）に分類して整理します。

---

### 1. ユーザーは簡単にログインできるようにしたい。

- **分類：機能要件／非機能要件**
  - **機能要件**：ユーザーログイン機能の提供。
  - **非機能要件**：ログインの手順が簡便であること（例：ワンタイムパス、ソーシャルログイン対応など）。

---

### 2. セキュリティは万全にしたい。

- **分類：非機能要件**
  - システム全体のセキュリティ要件（例：通信の暗号化、不正アクセス防止、パスワードポリシー、監査ログなど）。

---

### 3. スマホでも使いやすくしたい。

- **分類：非機能要件**
  - ユーザーインターフェースのモバイル対応（レスポンシブデザイン、タッチ操作対応など）。

---

### 4. バックエンドにはAPIを作る必要がある。

- **分類：システム要件／機能要件**
  - **システム要件**：API基盤の構築。
  - **機能要件**：APIが提供する具体的な機能（例：ユーザー情報取得、データ登録など）。

---

### 5. 管理者画面も必要。

- **分類：機能要件**
  - 管理者向け画面の提供（例：利用者管理、データ閲覧・編集など）。

---

### まとめ表

| 仕様内容                   | 機能要件 | 非機能要件 | システム要件 | 運用要件 |
|----------------------------|----------|------------|--------------|----------|
| 簡単にログイン              | 〇       | 〇         |              |          |
| セキュリティ万全            |          | 〇         |              |          |
| スマホでも使いやすい        |          | 〇         |              |          |
| バックエンドAPIの必要性     | 〇       |            | 〇           |          |
| 管理者画面                  | 〇       |            |              |          |

---

ご不明な点や、さらに詳細な要件定義への落とし込みが必要な場合はご指示ください。

## GPT-4o

曖昧な仕様を要件定義書の構成に分類すると、以下のようになります。

1. **機能要件**
   - ユーザーは簡単にログインできるようにしたい。
   - 管理者画面も必要。
   - バックエンドにはAPIを作る必要がある。

2. **非機能要件**
   - セキュリティは万全にしたい。
   - スマホでも使いやすくしたい。

3. **システム要件**
   - バックエンドにはAPIを作る必要がある。（APIの具体的な仕様や技術スタックの選定も含まれる場合はシステム要件に該当することがあります）

4. **運用要件**
   - 現時点では具体的な運用要件に該当する内容が提示されていませんが、運用に関する要件が出てきた場合にこの分類に含まれます。

曖昧な仕様を具体的な要件に落とし込むためには、さらに詳細な検討と具体化が必要です。特に、セキュリティやユーザーの使いやすさをどのように実現するかについては、技術的な詳細や運用上のプロセスを定義する必要があります。

# まとめ

指示を忠実かつ高精度に実行する能力という観点ではGPT-4.1の方が優れているようです。今回は試していませんでしたが、コンテキスト長も100万トークンと非常に長いので、コーディングのシーンでは威力を発揮しそうです。

GPT-4oはその柔軟性とクリエイティブ性が役立つシーンが別にあるので、ユースケースに応じて使い分けるのが良さそうです。
