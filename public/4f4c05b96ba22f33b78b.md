# イントロダクション

ある小売分析企業のシニアデータエンジニアであるAmiraに会いました。毎日彼女は、ダッシュボード、予測モデル、顧客行動の洞察を支援するいくつかのDelta Lakeテーブルを管理しています。彼女のチームは、Delta Lakeの信頼性とスケーラビリティを頼りにしていますが、頻繁な更新や削除、ストリーミングジョブのため、Amiraはテーブルが定常的に最適化され、コンプライアンスに準拠し、リカバリー可能にしておく必要があります。

多くの実践者同様、彼女は以下のような疑問に直面しています:

- 「私のクラウドストレージ料金はなぜ増加しているのか？」
- 「このデータセットでどこまでタイムトラベルで戻れるのか？」
- 「不慮の上書きをどのように元に戻せるのか？」

これらの課題は最終的には、Delta LakeがDeltaテーブルの根幹を形成するファイルとトランザクションログをどのように管理するのかの理解に帰着します。

Delta LakeはACIDトランザクション、スケーラブルなメタデータ操作、データレイクの統合ガバナンスを提供するオープンソースストレージレイヤーです。本書では、データファイルとトランザクションログがどのようにして**タイムトラベル、バキューム、リストア、変更追跡**のようなオペレーションを可能にするのかにフォーカスし、**Delta Lakeの解剖学**を探索します。

外部テーブルではなくマネージドテーブルを使っている場合には、これらのオペレーションの多くは自動化されます。最後にはこのメリットをカバーします。だとしても、これらがどのようん動作するのかを理解することは、Amiraのような実践者がパフォーマンスをファインチューンし、問題をトラブルシュートし、履歴的なアクセスを維持する助けとなります。

AmiraはこれらのキーとなるDelta Lakeのオペレーションに取り組んでいるので、彼女のジャーニーに従います:

- **履歴**と**チェンジデータフィード(CDF)**: **タイムトラベル**、監査、行レベルでのテーブル変更の追跡。
- **VACUUM**: ストレージの最適化、ファイル保持の管理。
- **DROP**、**RESTORE**、**UNDROP**: データ損失から復旧。

Amiraのユースケースの探索を始める前に、彼女が覚えておくべきDeltaの設定を見てみましょう:

| Delta設定 | 説明 | デフォルト値 |
|:--|:--|:--|
| delta.logRetentionDuration = "interval <interval>"  | テーブルの履歴をどれだけの期間保持するのかを制御。  | 30日  |
| delta.deletedFileRetentionDuration = "interval <interval>"  | 現在のテーブルバージョンにおいて参照されていないデータファイルを削除するために、VACUUMが使用する閾値を決定。  |  7日 |
| delta.enableChangeDataFeed=true  | チェンジデータフィード(CDF)を用いてDeltaテーブルのバージョン間での行レベルの変更をDatabricksが追跡可能に。  | False  |

# Delta Lakeテーブルの解剖学

Amiraは彼女のテーブルの一つである`sales_transactions`のサイズが激増した理由の調査から１日をスタートします。最適化に飛びつく前に、Deltaテーブルの構成要素を確認します。

Deltaテーブルのフォルダ構造には以下が含まれます:

- テーブルそのものを表現する**トップレベルのディレクトリ**
- トランザクションログファイルを格納する **_delta_log** ディレクトリ

実際の**データファイル(file1.parquet、file2.parquetなど)**

![](https://community.databricks.com/t5/image/serverpage/image-id/21599i681EA909AE7A61A6/image-size/large?v=v2&px=999)
*Delta Lakeテーブルの解剖学。ソース [dennyglee](https://dennyglee.com/2023/11/26/understanding-the-delta-lake-transaction-log-at-the-file-level/)*

この構造を理解することは、AmiraにとってDelta Lakeがどのファイルを自動的に管理し、どのファイルが更新や削除の後に残り続ける場合があるかを特定する助けとなります。

# タイムトラベルと監査 - 履歴

**シナリオ:** ある朝、Amiraはコンプライアンスからのリクエストを受け取ります:

- 「先週の月曜日に***sales_transactions***テーブルがどのようなものだったかを見せてくれませんか？」

Delta Lakeの**履歴**と**タイムトラベル**機能によって、彼女は容易に過去のバージョンにクエリーすることができます。

それぞれのテーブル変更は新たなバージョンを作成され、これらはトランザクションログに記録されます。以下のコマンドはAmiraが全ての変更を調査することを助けてくれます:

```sql
DESCRIBE HISTORY sales_transactions;
```
![](https://community.databricks.com/t5/image/serverpage/image-id/21600i77F8E34DA2CF7875/image-size/medium?v=v2&px=400)

これは、いつデータが誰によってどのように更新されたのかを表示しており、これらは監査において重要なものとなります。

デフォルトでは、Deltaは**30日**(`delta.logRetentionDuration = '30 days'`)のログを保持しますが、監査が頼長保持期間を必要とした場合にAmiraはこれを延長することができます。

時間を遡るために、彼女は古いバージョンを直接クエリーすることができます:

```sql
SELECT * FROM sales_transactions VERSION AS OF 10;
```

この**トランザクションログ**がこれらすべてにおける中心的存在です。全ての変更、インサートからスキーマ変更まで全ての変更を記録し、**データリネージ**と**リカバリー**を可能とします。

## 増分変更の追跡 - チェンジデータフィード(CDF)

**シナリオ:** その日の遅く、Amiraの下流のシステムではリアルタイムで分析ダッシュボードを更新するために、毎時の売上トランザクションでどのような変更があったのかを正確に知る必要がありました。

Delta Lakeの**チェンジデータフィード(CDF)** がこれを可能にします。これによって、Amiraはテーブルの二つのバージョン間で生じたインサート、更新、削除を含む行レベルの変更をクエリーできるようになります。

偶然にも、彼女はすでに当該テーブルに対してCDFを有効化していましたので、これらの変更に対する記録が可能となっています:

```sql
ALTER TABLE table_name SET TBLPROPERTIES
(delta.enableChangeDataFeed=true)
```

これによって、Deltaテーブルのバージョン間での行レベルの変更を追跡することができます。

```sql
SELECT * FROM table_changes('sales_transactions', 100, 110);
```

CDFは、トランザクションログとバージョン履歴と連携して、テーブルディレクトリの配下の`_change_data`フォルダにこれらの変更を格納します。

![](https://community.databricks.com/t5/image/serverpage/image-id/21601i3C33C8A7B79F12BB/image-size/large?v=v2&px=999)
*CDFを有効化したDelta Lakeテーブルの解剖学*

しかし、AmiraはCDFデータが**一時的**なものであることを知っています。保持ポリシーやVACUUMによって古いバージョンが削除されると、関連するCDFデータも消失します。

重要な変更データを保存するために、クリーンアップジョブを実行する前に恒久的な監査テーブルにCDFの出力を書き込むインクリメンタルなプロセスを作成します(詳細は[こちら](https://docs.databricks.com/aws/ja/delta/delta-change-data-feed#%E3%83%81%E3%82%A7%E3%83%B3%E3%82%B8%E3%83%87%E3%83%BC%E3%82%BF%E3%83%95%E3%82%A3%E3%83%BC%E3%83%89%E3%82%92%E4%BD%BF%E7%94%A8%E3%81%97%E3%81%A6%E3%83%86%E3%83%BC%E3%83%96%E3%83%AB%E3%81%AE%E5%B1%A5%E6%AD%B4%E5%85%A8%E4%BD%93%E3%82%92%E5%86%8D%E7%94%9F%E3%81%A7%E3%81%8D%E3%81%BE%E3%81%99%E3%81%8B))。

また、ストリーミングジョブのラグに保持期間の設定が適合していることを確実にします:

```sql
ALTER TABLE sales_transactions 
SET TBLPROPERTIES ('delta.deletedFileRetentionDuration' = '30 days');
```

これによって、ストリーミングが遅延したとしても、下流のコンシューマーが更新を処理できるのに十分な期間`_change_data`ファイルが保持されることを確実なものにします。

# ストレージの最適化 - VACUUM

**シナリオ:** データ取り込みの数ヶ月後、Amiraはクラウドストレージのコストが上昇していることに気づきます。古いデータファイルが論理的に削除された後であっても残り続けているのではないかと疑います。

ここで[VACUUM](https://docs.databricks.com/aws/ja/sql/language-manual/delta-vacuum)コマンドが助けとなります。

## VACUUMは何をするのか

- 現在のDeltaテーブルの状態で**参照されていない**ファイルを削除します。
- **保持期間の閾値**(デフォルト7日)を超えた古くて参照されていないファイルを物理的に削除します。

Amiraが***VACUUM sales_transactions;*** を実行すると、Deltaは以前の更新や削除で古いものとなったParquetファイルのような必要とされないファイルを削除します。

しかし、彼女は注意しなくてはなりません: 保持期間の閾値が短すぎると、意図せずして**タイムトラベル**や**ストリーミングジョブ**で必要とされる亜フィルを削除してしまう場合があります。

### 保持期間の調整

彼女のチームのデータリカバリー要件に合わせて、Amiraはより長い保持期間を設定します:

```sql
ALTER TABLE sales_transactions 

SET TBLPROPERTIES ('delta.deletedFileRetentionDuration' = '30 days');
```

これによって、削除されたファイルは1ヶ月間アクセス可能になり、取り込みエラーや処理の遅延からのリカバリーに必要な十分な時間を確保することができます。

# 間違いをやり直す - RESTORE

**シナリオ:** あるジュニアデータエンジニアが誤ってAmiraのテーブルを不正なデータで上書きしてしまいました。

![](https://community.databricks.com/t5/image/serverpage/image-id/21602i09164C3C62328979/image-size/large?v=v2&px=999)
*以前のテーブルのコンテンツを上書きするCREATE OR REPLACEオペレーションを表示しているテーブル履歴*

最初から再構築するのではなく、Amiraはシンプルに以下を実行します:

```sql
RESTORE TABLE sales_transactions TO VERSION AS OF 6;
```

[RESTORE](https://docs.databricks.com/aws/ja/sql/language-manual/delta-restore)オペレーションは、保持されているログとデータファイルを用いてエラー以前の状態であるバージョン6に即座にロールバックします。

![](https://community.databricks.com/t5/image/serverpage/image-id/21603i687FE32BD063A1C5/image-size/large?v=v2&px=999)
*RESTOREオペレーションを示すテーブル履歴*

しかし、彼女はVACUUMが古いデータファイルを削除していないことを確認する必要があります。さもないと、これらのバージョンへのリストアは不可能となります。

## 不意の削除への対応 - DROPとUNDROP

**シナリオ:** 彼女のチームのルーチンクリーンアップの際に、誰かが間違ってUnity Catalogのマネージドテーブルを削除してしまいました。

```sql
DROP TABLE analytics.sales_transactions;
```

幸運なことに、Delta Lakeはセーフティネットを用意しています。**7日**以内であれば、Amiraはテーブルを復旧できます:

```sql
UNDROP TABLE analytics.sales_transactions;
```

この機能は復旧作業の数時間を削減し、チームにおけるデータ損失を防ぎます。

# Unity Catalogマネージドテーブルのメリット

Amiraの非常に重要なゴールは、オペレーション作業を最小化しつつも、パフォーマンス、ガバナンス、回復可能性を最大化することです。Unity Catalogのマネージドテーブルは完全に管理され、自動的に最適化され、外部テーブルと比較してストレージやコンピュートのコストを引き下げるため、Databricksにおけるデフォルトかつ推奨されるテーブルタイプとなっています。

- **予測最適化による自動メンテナンスと最適化:** マネージドテーブルは、読み取り/書き込みパターンから学習して、手動による介入なしにデータレイアウトと統計を最適な状態に保つために、OPTIMIZE、VACUUM、ANALYZEのようなオペレーションを自動で実行します。
![](https://community.databricks.com/t5/image/serverpage/image-id/21604i5695B84C17E61DE1/image-size/large?v=v2&px=999)
- **コストの削減、クエリーの高速化:** マネージドテーブルは、お客様におけるコンピュートコストを削減し、クエリーのレイテンシーを改善するために、(クラスタリングとコンパクションを含む)AI駆動の最適化とインテリジェントな統計情報収集処理を活用します。
- **常時稼働のメタデータキャッシュ:** マネージドテーブルでは、トランザクションログの読み込みを削減し、クエリー計画を高速化するためのインメモリメタデータキャッシュを有効化します。マネージドテーブルではデフォルトで有効化されます。
- **ライフサイクル自動化とセイフティネット:** マネージドテーブルをDROP TABLEした後、Databricksは8日後にクラウドストレージから背後にあるデータを自動で削除します。また、同じ期間で削除されたマネージドテーブルを回復するためのUNDROP TABLEをサポートしています。
- **一貫性のあるストレージロケーションと名前ベースのアクセス:** マネージドテーブルのデータファイルは、親のスキーマやカタログのマネージドロケーションに格納され、Databricksではガバナンスやマネージドの機能を保持するために、パスベースのアクセスではなく名前ベースのアクセス(catalog.schema.table)を推奨しています。

Amiraが既存データの登録に直接的なパスベースのアクセスを必要とし、ライフサイクルが完全にセルフマネージドである必要がある場合、外部テーブルが適切なソリューションとなる場合があります。外部テーブルを削除した際には背後のファイルは削除されないことを覚えておいてください。Unity Catalogはあなたのために外部テーブルのライフサイクルを管理しません。

# まとめ

AmiraやDeltaテーブルを日々管理するすべてのデータ実践者にとって、Delta Lakeがどのようにデータとログの保持を管理するのかを理解することは重要です。

**HISTORY**、**CDF**、**VACUUM**、**RESTORE**のようなコマンドをマスターすることで、彼女のテーブルは以下の状態を保ちます:

- **クリーン** (ストレージを消費する古いファイルは存在しません)
- **回復可能** (不意の上書きや削除から)
- **監査可能** (コンプライアンスやデバッグ目的)
- **ストリームフレンドリー** (継続的データパイプライン)

彼女の日々の体験を通じて、AmiraはDelta Lakeのオペレーション上のコンセプトが理論のみのものではなく、信頼できスケーラブルで効率的なデータエコシステムを維持するための重要なツールであることを示しました。
