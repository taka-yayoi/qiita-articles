# はじめに

2026年9月17日に公開されたMLflow 3.16.1で、記録先がUnity Catalogのトレースでもspan linkが記録されるようになりました。

- [MLflow 3.16.1 リリースノート](https://github.com/mlflow/mlflow/releases/tag/v3.16.1)
- [OpenTelemetry トレースを Unity Catalog に保存する | Databricks](https://docs.databricks.com/aws/ja/mlflow3/genai/tracing/trace-unity-catalog)

前回の記事では、MLflow SDKでspan linkを張る方法を試しました。

- [MLflowのspan linkを試してみた](https://qiita.com/taka_yayoi/items/9f5885bf98b38484a05b)

今回はその続きで、MLflowを使わずにOpenTelemetry SDKだけで計装したアプリケーションから、span link付きのトレースをOTLPでDatabricksに送ってみます。既存のアプリケーションがすでにOpenTelemetryで計装されていて、トレースの保存先としてUnity Catalogを使う、という構成を想定しています。送る側にMLflowのバージョンが関係するのか、読む側はどうか、というあたりも含めて書いていきます。

# OTLPでUnity Catalogに送る経路は2つある

OpenTelemetryのトレースをOTLPでUnity Catalogのテーブルに書き込む方法は2つあります。宛先のテーブルを指定するHTTPヘッダーの名前が違います。

| | MLflowのOTLPコレクター | Zerobus Ingest |
| --- | --- | --- |
| エンドポイント | `https://<workspace-host>/api/2.0/otel/v1/traces` | `https://<workspace-id>.zerobus.<region>.cloud.databricks.com/v1/traces` |
| テーブル指定ヘッダー | `X-Databricks-UC-Table-Name` | `x-databricks-zerobus-table-name` |
| テーブル | エクスペリメントの設定時に作られる | 事前に作成する |
| 認証 | ワークスペースのトークン | サービスプリンシパルで発行した専用トークン |

- [OpenTelemetry (OTLP) クライアントを設定してデータを Unity Catalog に送信する | Databricks](https://docs.databricks.com/aws/ja/ingestion/opentelemetry/configure)

今回は両方で試しましたが、span linkの扱いは同じでした。この記事では、手順の少ないMLflowのOTLPコレクターを使って書きます。

# 送信先のエクスペリメントとテーブルを用意する

送る側はMLflowを使いませんが、トレースの記録先となるエクスペリメントとUnity Catalogのテーブルは、MLflowで用意します。ここだけMLflow SDKを使います。

```bash
pip install "mlflow[databricks]>=3.16.1" opentelemetry-sdk opentelemetry-exporter-otlp-proto-http
```

```python
import os
import mlflow
from mlflow.entities.trace_location import UnityCatalog

mlflow.set_tracking_uri("databricks")
# Unity Catalogへの書き込みに使うSQLウェアハウス。未設定だとテーブルの作成に失敗します
os.environ["MLFLOW_TRACING_SQL_WAREHOUSE_ID"] = "<sql_warehouse_id>"

mlflow.set_experiment(
    experiment_name="/Users/<you>/span-link-otlp",
    trace_location=UnityCatalog(
        catalog_name="<catalog>",
        schema_name="<schema>",
        table_prefix="collector",  # collector_otel_spans などのテーブルが作られます
    ),
)
```

これで `<catalog>.<schema>.collector_otel_spans` などのテーブルが作られ、エクスペリメントのトレースの記録先になります。

# OpenTelemetry SDKでspan link付きのトレースを送る

ここからはOpenTelemetry SDKだけを使います。トークンは個人アクセストークンを作らず、Databricks CLIのOAuthから取ります。

```python
import json
import subprocess

from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.resources import Resource
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import SimpleSpanProcessor
from opentelemetry.trace import Link

HOST = "https://<workspace-host>"
TABLE = "<catalog>.<schema>.collector_otel_spans"

# Databricks CLI でログイン済みのプロファイルからトークンを取ります
token = json.loads(subprocess.check_output(
    ["databricks", "auth", "token", "--profile", "<profile>"]))["access_token"]

exporter = OTLPSpanExporter(
    endpoint=f"{HOST}/api/2.0/otel/v1/traces",
    headers={
        "authorization": f"Bearer {token}",
        "X-Databricks-UC-Table-Name": TABLE,  # MLflowのOTLPコレクター側のヘッダー名
    },
)
provider = TracerProvider(resource=Resource.create({"service.name": "span-link-otlp"}))
provider.add_span_processor(SimpleSpanProcessor(exporter))
tracer = provider.get_tracer("span-link-otlp")
```

上流の処理を1本のトレースとして送ります。

```python
with tracer.start_as_current_span("collector_A_producer") as producer:
    producer.set_attribute("gen_ai.input.messages", json.dumps([{"role": "user", "content": "A"}]))
producer_ctx = producer.get_span_context()
```

下流のトレースから、上流のスパンへリンクを張ります。OpenTelemetryでは、スパンを開始するときに `links` で渡します。同じトレースの中のスパン同士のリンクも1本張っておきます。

```python
with tracer.start_as_current_span(
    "collector_B_consumer",
    # 別トレースのスパンへのリンク。親子関係にはなりません
    links=[Link(producer_ctx, {"link.kind": "cross_trace"})],
) as consumer:
    with tracer.start_as_current_span("collector_B_step1") as step1:
        pass
    with tracer.start_as_current_span(
        "collector_B_step2",
        # 同じトレース内のスパンへのリンク
        links=[Link(step1.get_span_context(), {"link.kind": "same_trace"})],
    ):
        pass

provider.force_flush()
provider.shutdown()  # プロセス終了前に残りのスパンを送り切ります
```

これで送信は完了です。エラーは返ってきません。

# Unity Catalogのテーブルにリンクが入っている

まずSQLで、テーブルの `links` 列を見ます。

```sql
SELECT name, trace_id, to_json(links) AS links
FROM <catalog>.<schema>.collector_otel_spans
ORDER BY start_time_unix_nano
```

```
collector_A_producer  52601748...  []
collector_B_consumer  5e089dee...  [{"trace_id":"52601748...","span_id":"a212770673e28392","attributes":{"link.kind":"cross_trace"},"flags":256}]
collector_B_step1     5e089dee...  []
collector_B_step2     5e089dee...  [{"trace_id":"5e089dee...","span_id":"fd6cc176f17f5130","attributes":{"link.kind":"same_trace"},"flags":256}]
```

別トレースへのリンクも、同じトレース内のリンクも、属性ごと記録されていました。OTLPのスパンをそのまま行にしたテーブルなので、ここまではMLflowのバージョンに関係なく入ります。

# Databricksのトレース画面にもリンクが表示される

エクスペリメントのトレース画面で `collector_B_consumer` のトレースを開くと、リンクを持つ `collector_B_consumer` と `collector_B_step2` に鎖のアイコンと件数のバッジが付いています。スパンを選ぶと「リンク」タブがあり、リンク先のトレースID・スパンID・属性が表示されます。

![v2_otlp_links_tab.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/ed23c19d-7cc0-4b5f-b731-3ade3f521712.png)

MLflowを一切使わずに送ったトレースでも、MLflow SDKでリンクを張ったときと同じように表示されます。トレースIDとスパンIDはコピーボタンになっていて、リンク先を開くときはコピーしたトレースIDで検索します。

# SDKで読み出すなら3.16.1以降が必要

ここがハマりどころです。テーブルにリンクが入っていても、**MLflow SDKで読み出すときは、SDK側が3.16.1以降でないとリンクが返ってきません。**

```python
traces = mlflow.search_traces(
    locations=["<catalog>.<schema>.collector"],
    return_type="list",
)
for t in traces:
    for s in t.data.spans:
        print(s.name, [(l.trace_id, l.span_id, l.attributes) for l in s.links])
```

3.17.2では、リンクがそのまま返ってきます。

```
collector_B_consumer [('trace:/<catalog>.<schema>.collector/tr-52601748...', 'a212770673e28392', {'link.kind': 'cross_trace'})]
collector_B_step1 []
collector_B_step2 [('trace:/<catalog>.<schema>.collector/tr-5e089dee...', 'fd6cc176f17f5130', {'link.kind': 'same_trace'})]
```

同じトレースを3.16.0で読むと、警告が出てリンクは空になります。

```
Span links are not currently supported for Unity Catalog traces.
1 link(s) on span 'collector_B_consumer' will be dropped.
```

3.16.0までのSDKは、Unity Catalogのトレースのリンクを読み込むときにも外していたためです。送る側はOpenTelemetry SDKなのでMLflowのバージョンは関係ありませんが、評価ジョブやノートブックなど、トレースを読む側の環境のMLflowは3.16.1以降に揃えておく必要があります。

# Zerobus Ingestで送っても同じだった

Zerobus Ingestの経路でも、同じ構成のトレースを送って確かめました。違うのは、エンドポイントとヘッダー名と、サービスプリンシパルで発行する専用トークンです。

```python
exporter = OTLPSpanExporter(
    endpoint=f"https://{WORKSPACE_ID}.zerobus.{REGION}.cloud.databricks.com:443/v1/traces",
    headers={
        "authorization": f"Bearer {zerobus_token}",  # zerobusDirectWriteApi 向けに発行したトークン
        "x-databricks-zerobus-table-name": TABLE,    # Zerobus Ingest側のヘッダー名
    },
)
```

テーブルの事前作成とトークンの発行手順は、上の「OpenTelemetry (OTLP) クライアントを設定してデータを Unity Catalog に送信する」に沿って進めました。送ったあとでテーブルをエクスペリメントの記録先に紐づけると、テーブルの `links` 列、トレース画面の「リンク」タブ、SDKでの読み出しの結果は、MLflowのOTLPコレクターのときとすべて同じでした。

# まとめ

OpenTelemetry SDKだけでspan link付きのトレースをDatabricksに送って分かったことをまとめます。

- **MLflow 3.16.1から、記録先がUnity Catalogのトレースでもspan linkが扱えるようになった**
- OpenTelemetry SDKで `links` を付けて送ったリンクは、Unity Catalogのテーブルの `links` 列に属性ごと記録される。MLflowのOTLPコレクター、Zerobus Ingestのどちらでも同じ
- Databricksのトレース画面では、スパンの「リンク」タブにリンク先のトレースID・スパンID・属性が表示される
- **MLflow SDKで読み出す側は3.16.1以降が必要。3.16.0では、テーブルに入っていても読み出すときにリンクが外れる**
- 送る側はOpenTelemetry SDKなので、MLflowのバージョンは関係ない

一番の収穫は、記録と読み出しを分けて確かめられたことでした。テーブルにはリンクが入っているのに、古いSDKで読むと空になる、という状況は、SDKの結果だけを見ていると「まだ対応していない」と判断してしまいかねません。OTLPで送る構成では、まずテーブルを直接見て、どこで情報が落ちているのかを切り分けると早いと思います。
