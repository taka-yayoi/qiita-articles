# はじめに

前回の記事では、Claude Code を題材にハーネスとは何かを整理しました。

https://qiita.com/taka_yayoi/items/3efc82120727a012c036

その中で、Claude Code や Codex を自分の仕事を楽にするために使うだけなら、ハーネスという用語を知らなくても十分に成果を出せる、と書きました。ハーネスを理解する必要があるのは、期待した結果が出ないときに原因を探す立場の人、エージェントを管理する基盤チーム、自分でエージェントを作る開発者だ、という整理です。

ところが、ここ数か月に出てきたハーネスを並べてみると、この線引きが少し変わってきていると感じます。コーディングの道具ではなく、誰でも使う個人用のエージェントとしてハーネスが届き始めたからです。

この記事では、最近出てきたハーネスを紹介しながら、なぜ今これだけ次々に出てくるのかを推察します。そのうえで今後の方向性を予測し、メタハーネスの話につなげます。推察と予測の部分は、公開されている情報をもとにした私の推察です。

# 前回の整理のおさらい

前回の記事の要点を3つだけ振り返ります。

- モデルは文章を受け取って文章を返すだけで、ファイルを開いたり作業を終えると判断したりするのは外側のプログラム。この外側のプログラムをハーネスと呼ぶ
- ハーネスは、ループ、ツール、コンテキスト、権限、停止条件の5つの部品でできている
- ハーネスの動き方は作り手が設計している。用途に合わない設計は、モデルを替えても変わらない

この記事でも、この5つの部品を手がかりに新しいハーネスを見ていきます。

# 最近出てきたハーネス

## DeepSeek Harness: モデルの会社が自分のハーネスを出す

2026年8月13日、DeepSeek は DeepSeek-V4-Pro の正式版と同時に、DeepSeek Harness を開発者プレビューとして公開しました。MITライセンスのオープンソースで、ループ、ツール、モデルの接続など、ハーネスのほとんどの部品をプラグインとして差し替えられる作りです。

注目したいのは、モデルの性能の示し方です。DeepSeek は、公開ベンチマークのうちコーディングエージェントのタスクを、DeepSeek Harness の minimal mode で測ったと明記しています。ほかのハーネスでは結果が多少変わる可能性がある、という注記付きです。モデルの成績表に、どのハーネスで測ったかが書かれるようになりました。

同じ8月には、Meta もコーディング用のハーネス Muse Code を、モデルの Muse Spark 1.2 と同時にベータで出しています。こちらはさらに踏み込んで、Muse Code を最初から訓練の中に組み込み、モデルをハーネスと一緒に訓練したと説明しています。ただし、訓練には複数のハーネスを使っていて、Muse Code で最もよく動く一方で、ほかのコーディングエージェントでも使えるとも書いています。

## Muse: 誰でも使う個人用のハーネス

2026年9月8日、Meta は個人用のAIエージェント Muse を発表しました。現時点では米国向けで、iOS、Android、Web から使えます。メッセージを送る感覚で頼みごとを伝えると、メールの送信や旅行の予約、フォームの入力などを代わりに進めます。

Muse は製品としてはエージェントですが、発表の中身を読むと、説明の大半はハーネスの部品の話です。前回の5つの部品に当てはめると次のようになります。

| 部品 | Muse での作り |
| --- | --- |
| ループ | 時間のかかるタスクは、アプリを閉じたあとも作業を続ける |
| ツール | 専用の仮想マシンに自分のブラウザを持ち、フォームの入力や交渉もできる |
| コンテキスト | 大切なことを覚えておき、一度聞いただけの詳細も後で使う。「忘れて」と言えば忘れる |
| 権限 | 接続するアプリと、そのアプリで何をしてよいかを利用者が選ぶ。インターネットへの通信は、Muse とは別の Sentinel というエージェントが承認したものだけが通る |
| 停止条件 | メールの送信や購入の前に止まり、利用者の承認を待つ。状況が変わったときにも戻ってくる |

モデルの Muse Spark の話は、発表ではほとんど出てきません。代わりに、専用の仮想マシン、Sentinel による通信の承認、実行済みと予定の操作をすべて見られる監査証跡など、権限と停止条件の作り込みが前面に出ています。個人のメールやお金を扱う以上、安心して任せられるかどうかはハーネスで決まる、ということだと思います。

## Genie ZeroOps: 業務の内側に置かれたハーネス

2026年11月には、Databricks の Genie ZeroOps がベータになりました。ジョブ、パイプライン、テーブルをプロンプトなしで監視し、問題を見つけると原因を調べて修正案を受信トレイに届けるエージェントです。実際に試した結果は別の記事に書きました。

https://qiita.com/taka_yayoi/items/1f1219cd56116755dd19

試していて印象に残ったのは、上流テーブルの列名変更が原因の失敗を特定した場面です。成功したランと失敗したランでノートブックのソースが同じことを確かめ、テーブル履歴から2つのランの間に上流テーブルが作り直されたことを突き止めていました。これはモデルの賢さだけでは説明できません。ランの履歴やテーブル履歴に手が届く場所にハーネスが置かれているから、できることです。

## 並べてみると

3つのハーネスを並べると、使う人も動き出すきっかけも違います。

| ハーネス | 使う人 | 動き出すきっかけ | 作り込んでいるところ |
| --- | --- | --- | --- |
| DeepSeek Harness | 開発者 | 人のプロンプト | 部品の差し替えやすさ。自社モデルの性能を引き出す |
| Muse | 一般の利用者 | 人が渡した目標。その後は自分で進める | 権限と停止条件。専用の仮想マシンと承認の仕組み |
| Genie ZeroOps | データチーム | プロンプトなし。監視の範囲だけを設定する | データ基盤の内側の情報に手が届くこと |

前回取り上げた Claude Code は、開発者がプロンプトを入力して動かすハーネスでした。この3つを見ると、ハーネスが使われる場所と動き方が、ここ数か月で一気に広がったことが分かります。

# なぜ今ハーネスが次々に出てくるのか

ここからは私の推察です。理由は3つあると考えています。

## 性能がモデルとハーネスの組み合わせで測られるようになった

DeepSeek がベンチマークを自社のハーネスで測ったことと、Meta がモデルをハーネスと一緒に訓練したことは、同じ方向を向いています。エージェントとしての性能は、モデル単体ではなく、モデルとハーネスの組み合わせで決まる。前回の記事の最後に書いたことを、モデルを作る側が認めて行動に移した形です。

そうなると、モデルの会社にとってハーネスは手放せないものになります。自社のモデルの性能を一番引き出せるハーネスを自分で用意しておかないと、他社のハーネスの上で、本来より低い成績で比べられてしまうからです。

## 「頼まれたら答える」から「任せたら動き続ける」へ

Muse はアプリを閉じても作業を続け、Genie ZeroOps はプロンプトなしで動き続けます。どちらも、人が画面の前にいない時間に仕事をするエージェントです。

![harness_shift.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/88f1c1cc-ac20-4bce-9f1a-d2e1aa7e3a8e.png)

人が見ていない時間に動くなら、ハーネスの部品のうち、とくに権限と停止条件の重みが増えます。どこまでなら黙って進めてよいか、どこで止まって人に聞くか、止まったことをどうやって人に知らせるか。これはモデルの性能では決まらず、ハーネスの設計で決まります。Muse の承認の仕組みと、Genie ZeroOps の受信トレイは、どちらもこの問いへの答えです。動き続けるエージェントを作ろうとすると、ハーネスを作り込まざるをえません。

## 層を握るほど乗り換えられにくくなる

Drew Breunig は、ハーネスを「状況に置かれたエージェント」と定義しています。ハーネスは、モデルの外側にある環境、つまりセッション、実行環境、リポジトリ、記憶、スキル、チーム、組織のポリシーを管理する、という見方です。そして、外側の層まで設定が積み上がるほど、別のハーネスに乗り換えにくくなると指摘しています。

Muse で考えると分かりやすいと思います。自分のことを覚えてもらい、メールや決済をつなぎ、どこで承認を求めるかを決めた個人用エージェントは、簡単には別の製品に移れません。ハーネスを握ることは、利用者との長い付き合いを握ることでもあります。各社がハーネスを出してくる動機として、これも大きいはずです。

# ハーネスは「普通の人」にも関係してくる

前回の線引きに戻ります。仕事を楽にするために使うだけなら用語は知らなくてよい、という点は今も変わらないと思います。Muse を使う人が「ハーネス」という言葉を知る必要はありません。

ただ、Muse を使い始めるときに利用者が決めることを見ると、どのアプリにつなぐか、メールを読むだけにするか送信までさせるか、という設定が並びます。これは前回の記事でいう権限の部品です。どこで止まって承認を求めるかは停止条件です。用語を知らなくても、ハーネスの部品のうち少なくとも権限と停止条件は、誰もが自分で決める場面が出てきます。

前回は、ハーネスを理解する必要がある人として、原因を探す人、基盤チーム、開発者を挙げました。エージェントが自分の代わりにメールを送り、お金を払うようになると、ここに「エージェントに仕事を任せるすべての人」が加わります。理解が必要になるのは用語ではなく、何を任せて、どこで止めるかという判断のほうです。

# 今後の方向性の予測

ここからは予測です。

## ハーネスは用途ごとに分かれていく

コーディング、個人の生活、データ基盤の運用と、ハーネスはすでに用途ごとに違う形をとり始めています。Genie ZeroOps が示したように、特定の業務のデータに手が届くことがハーネスの強みになるなら、業務ごとに専用のハーネスが増えていくはずです。汎用のハーネスが1つですべてを担う方向には進まないと考えています。

## 受信トレイと承認が共通の画面になる

動き続けるエージェントが増えるほど、人がエージェントと接する場面は、チャットで頼むことから、受信トレイで結果を確かめて承認することに移っていきます。Muse の承認、Genie ZeroOps の受信トレイは、どちらもこの形です。

## 1人が複数のハーネスを使い、束ねる層が必要になる

ハーネスが用途ごとに分かれると、1人が複数のハーネスを使うのが普通になります。仕事ではコーディング用のハーネスを2つ、運用には Genie ZeroOps、という具合です。

そうなると、ハーネスをまたいだ管理が必要になります。どのハーネスにどこまで権限を与えるか、全体でいくら使っているか、何をしたかの記録をどう残すか。個々のハーネスは自分の範囲しか管理しないので、これはハーネスの外側に置くしかありません。前回の記事の最後で触れた、メタハーネスの出番です。

# メタハーネス Omnigent の最近の動き

Databricks がオープンソースで公開しているメタハーネス Omnigent は、2026年11月12日に v0.22.0 が出ています。今回の文脈に関係する点が2つあります。

## 束ねるハーネスの数が増えた

6月の公開時には、Claude Code、Codex、Pi などを束ねると紹介されていました。v0.22.0 の README では、束ねる対象として次のハーネスが並んでいます。

- Claude Code、Codex、Cursor、OpenCode、Goose
- Antigravity、GitHub Copilot、Devin、Kiro
- Qwen Code、Kimi Code、Grok Build、Jcode、Hermes、Pi
- OpenAI Agents / Open Responses、自作のエージェント

ハーネスが次々に出てくる状況が、そのまま束ねる側の一覧に表れています。

## 任せたら動き続ける方向に広がっている

v0.22.0 の変更履歴には、自動化 (Automations) の機能が多く並んでいます。

- スケジュールに加えて、Jira、Slack、GitHub、Linear を起点にセッションを始められる
- PagerDuty のインシデントを起点にするテンプレートがある
- 新しい自動化は、サーバー側のサンドボックスで動くのが既定になった。自分のマシンが起動していなくても動く
- 承認待ちや質問、失敗した自動化が受信トレイ (Inbox) に集まる

これは、Muse や Genie ZeroOps と同じ「任せたら動き続ける」方向です。違いは、特定のハーネスの中ではなく、束ねたハーネスの上でそれを実現している点です。自動化ごとに1回あたりの予算の上限を設定でき、承認を飛ばすモードは明示的に選んだときだけ使える、という作りにもなっています。人が見ていない時間に動かすなら、どのハーネスで動かすかにかかわらず、権限と停止条件をそろえて管理したい。その要求に、メタハーネスの側から応えようとしているように見えます。

# まとめ

- 2026年8月以降、DeepSeek Harness、Muse Code、Muse、Genie ZeroOps と、性格の違うハーネスが続けて登場した
- **DeepSeek はベンチマークを自社のハーネスで測り、Meta はモデルをハーネスと一緒に訓練した。性能はモデルとハーネスの組み合わせで示されるようになっている**
- Muse の発表の中心は、専用の仮想マシン、通信の承認、監査証跡といった、ハーネスの権限と停止条件の作り込みだった
- **Muse や Genie ZeroOps のように、人が見ていない時間に動き続けるエージェントが増えている。そのぶんハーネスの権限と停止条件の重みが増す**
- 用語を知る必要はないが、何を任せてどこで止めるかは、エージェントを使うすべての人が決める場面が出てくる
- ハーネスが用途ごとに分かれていくと、1人が複数のハーネスを使うようになり、それらを束ねて管理する層が必要になる
- Omnigent v0.22.0 は、束ねるハーネスが16種類と自作のエージェントに広がり、自動化と受信トレイで「任せたら動き続ける」方向にも進んでいる

前回は「ハーネスを理解しておく必要がある人」を絞り込む記事でしたが、今回はその範囲が広がっていく話になりました。一番の変化は、ハーネスの話題の中心がループやツールから、権限と停止条件に移ってきたことだと思います。エージェントに仕事を任せる時間が長くなるほど、問われるのは賢さよりも、どこまで任せて、どこで止まるかです。それを1つのハーネスの中で決めるのか、ハーネスをまたいで決めるのか。次の数か月は、その分かれ目を見ていくことになりそうです。
