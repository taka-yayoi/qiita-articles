# メトリクスビューを一言で言うと

**集計結果ではなく、指標の計算方法を登録しておくビューです。**

数字そのものは持ちません。持っているのは求め方だけです。日ごとか、カテゴリごとか、県ごとか。どの単位で計算するかは、使う人がクエリのときに決めます。

この一行だけ読んでも、たぶんピンと来ないと思います。私も来ませんでした。なので、何が困っていたのかから書きます。

# 題材

架空のECショップ「もくもく商店」の注文データを使います。6,000件の注文と、顧客マスタです。

```sql
SELECT * FROM orders LIMIT 10;
```

`orders` は注文1件が1行で、注文日、顧客ID、商品カテゴリ、金額、ステータスを持っています。`customers` には都道府県と会員ランクが入っています。生成するコードはノートブックにあります。乱数シードを固定してあるので、手元で実行しても同じ数字になります。

この記事では、あなたはこのデータを預かっている人です。社内から「この数字が見たい」と依頼される側です。依頼してくる人を、この先「使う人」と呼びます。

# 標準ビューで集計結果を渡すと何が起きるか

## 標準ビューに名前を付けて渡す

「日ごとの売上が見たい」と言われたとします。毎回SQLを書いてもらうわけにもいかないので、ビューにして渡します。メトリクスビューと区別するため、この記事では普通のビューを標準ビューと呼びます。公式ドキュメントの呼び方です。

```sql
CREATE OR REPLACE VIEW v_sales_daily AS
SELECT
  order_date,
  SUM(amount)                 AS total_sales,
  COUNT(*)                    AS order_count,
  COUNT(DISTINCT customer_id) AS unique_customers
FROM orders
WHERE status = '完了'
GROUP BY order_date;
```

使う人は `SELECT * FROM v_sales_daily` と書くだけで、日ごとの売上合計、注文数、購入顧客数を見られます。この標準ビューを、この先「日次サマリ」と呼びます。

中に `GROUP BY order_date` が書いてあるので、返ってくるのは日ごとの集計結果だけです。ここで言う集計結果は、`GROUP BY` で集計し終えたもののことです。ビューでもテーブルでも同じです。

## 症状1 切り口ごとに標準ビューが増える

次に「カテゴリごとにも見たい」と言われます。日次サマリの単位は日なので、カテゴリでは出せません。2つ目の標準ビューを作ります。

```sql
CREATE OR REPLACE VIEW v_sales_category AS
SELECT
  category,
  SUM(amount)                 AS total_sales,
  COUNT(*)                    AS order_count,
  COUNT(DISTINCT customer_id) AS unique_customers
FROM orders
WHERE status = '完了'
GROUP BY category;
```

続いて都道府県で聞かれて3つ目です。売上合計、注文数、購入顧客数の同じ式が、3つの標準ビューに書かれることになります。式を変えたくなったら、3つとも直します。月ごと、会員ランク別と依頼が来るたびに、さらに増えます。

ここまでは手間の話です。面倒ではありますが、作れば済みます。

## 症状2 集計結果を合計すると、数字が変わる

ここで「2026年3月は何人のお客さんが買ってくれましたか」と聞かれます。月ごとの標準ビューはありません。使う人の手元にあるのは日次サマリです。売上合計と注文数は、いつも31日ぶんを足して3月の値を出していて、それで合っていました。購入顧客数も同じように足します。

```sql
SELECT
  SUM(total_sales)      AS `売上合計`,
  SUM(order_count)      AS `注文数`,
  SUM(unique_customers) AS `購入顧客数`
FROM v_sales_daily
WHERE order_date BETWEEN '2026-03-01' AND '2026-03-31';
```

売上合計 1,721,180円、注文数 339件、購入顧客数 335人。

元のテーブルを持っているあなたが `orders` から直接数えると、こうなります。

```sql
SELECT
  SUM(amount)                 AS `売上合計`,
  COUNT(*)                    AS `注文数`,
  COUNT(DISTINCT customer_id) AS `購入顧客数`
FROM orders
WHERE status = '完了'
  AND order_date BETWEEN '2026-03-01' AND '2026-03-31';
```

売上合計と注文数は一致します。購入顧客数だけが **335人と246人** で合いません。使う人は、売上と同じように足しただけです。エラーも出ていません。

## なぜ購入顧客数だけが合わないのか

聞かれているのは「3月に1回でも買った人の数」です。同じ人が何回買っても1人です。日次サマリの `unique_customers` も同じ定義で、その日に買った人の数です。

日次サマリの行に残っているのは、その日に買った人の数だけです。3月1日は7人、3月2日は10人。この7人と10人に同じ人がいるかどうかは、日次サマリからは分かりません。誰が買ったのかは、集計した時点で消えているからです。

内訳を見てみます。

```sql
-- まず、お客さんごとに「3月に何日買ったか」を数える
WITH `顧客ごとの購入日数` AS (
  SELECT
    customer_id,
    COUNT(DISTINCT order_date) AS `購入日数`
  FROM orders
  WHERE status = '完了'
    AND order_date BETWEEN '2026-03-01' AND '2026-03-31'
  GROUP BY customer_id
)
-- 次に、購入日数ごとに人数を数える
SELECT
  `購入日数`,
  COUNT(*) AS `人数`
FROM `顧客ごとの購入日数`
GROUP BY `購入日数`
ORDER BY `購入日数`;
```

1日だけ買った人が173人、2日買った人が59人、3日が12人、4日が2人でした。2日以上買った73人が、買った日数ぶん重複して数えられています。59 + 12×2 + 2×3 = 89 で、335と246の差にぴったり一致します。

## 足せるかどうかは集計関数で決まる

日次サマリから3月の値を出せるかどうかは、指標の名前ではなく、集計関数で決まります。

| 指標 | 集計関数 | 日次サマリから3月の値を出せるか |
|---|---|---|
| 売上合計 | `SUM(amount)` | 出せる。1日の売上と2日の売上は別のお金で、重ならない |
| 注文数 | `COUNT(*)` | 出せる。1件の注文は、どれか1日にしか入っていない |
| 購入顧客数 | `COUNT(DISTINCT customer_id)` | 出せない。同じ人が何日も買うと、その日数だけ数えられる |

`COUNT(DISTINCT)` のほか、中央値も足して出すことはできません。これは日次サマリに限った話ではありません。ダッシュボードの合計行や、Excelに落として足したときも同じことが起きます。

## 原因は GROUP BY を書く場所

症状1と症状2は別々の困りごとに見えますが、原因は同じです。標準ビューは、定義の中に `GROUP BY` を書きます。

| | 標準ビュー | メトリクスビュー |
|---|---|---|
| `GROUP BY` を書く場所 | ビューの定義の中 | 使う人のクエリ |
| 書く人 | あなた (作る人) | 使う人 |
| 単位が決まるとき | 標準ビューを作ったとき | クエリを実行したとき |

標準ビューは作った時点で単位が決まるので、別の単位が欲しければ、もう1つ作るしかありません。これが症状1です。

そして使う人には、定義の中の `GROUP BY` が見えません。`unique_customers` という列を見ても、それが日ごとに数えた人数だとは分かりません。`SUM(unique_customers)` は構文として正しく、エラーも出ません。これが症状2です。

公式ドキュメントにも「標準ビューは、作成時に集計とグループ化を固定します」と書かれています。

メトリクスビューは、定義に `GROUP BY` を書きません。計算方法だけを1か所に書いておき、どの単位で集計するかは使う人が選びます。

# メトリクスビューを作る

## 書くのはメジャーとフィールドの2種類

定義に書くものは2つだけです。ここを押さえると、あとは書き写すだけになります。

**メジャー** は計算方法です。売上合計なら `SUM(amount)`、注文数なら `COUNT(*)`、購入顧客数なら `COUNT(DISTINCT customer_id)`。式に集計関数が入ります。YAMLでは `measures` に書きます。決めるのは、データを預かっているあなたです。

**フィールド** は、使う人が選べる単位です。注文日、注文月、商品カテゴリ、都道府県、会員ランク。注文1件ごとに値が決まる列で、集計関数は入りません。ドキュメントには「ディメンションとも呼ばれます」という言い添えがあるので、他のBIツールを触ってきた方はそちらの言い方のほうが馴染みがあるかもしれません。YAMLでは `fields` に書きます。

| | メジャー | フィールド |
|---|---|---|
| 中身 | 計算方法 (集計関数が入る) | 使う人が選べる単位 (集計関数は入らない) |
| 例 | 売上合計、注文数、購入顧客数 | 注文日、注文月、カテゴリ、都道府県、会員ランク |
| クエリでの使い方 | `MEASURE()` で囲んで呼び出す | `SELECT` と `GROUP BY` に書く |

## YAMLで定義する

`CREATE VIEW ... WITH METRICS LANGUAGE YAML AS $$ ... $$` の中にYAMLを書きます。

```sql
CREATE OR REPLACE VIEW sales_metrics
WITH METRICS
LANGUAGE YAML
AS $$
version: 1.1
comment: "もくもく商店の売上指標"
source: orders
filter: status = '完了'

joins:
  - name: customer
    source: customers
    'on': source.customer_id = customer.customer_id

fields:
  - name: order_date
    expr: order_date
    comment: "注文日"
  - name: order_month
    expr: DATE_TRUNC('MONTH', order_date)
    comment: "注文月"
  - name: category
    expr: category
    comment: "商品カテゴリ"
  - name: prefecture
    expr: customer.prefecture
    comment: "顧客の都道府県"
  - name: member_rank
    expr: customer.member_rank
    comment: "会員ランク"

measures:
  - name: total_sales
    expr: SUM(amount)
    comment: "売上合計 (円)"
  - name: order_count
    expr: COUNT(*)
    comment: "注文数"
  - name: unique_customers
    expr: COUNT(DISTINCT customer_id)
    comment: "購入顧客数"
$$;
```

読みどころは3つです。

`filter` は、誰がクエリしても必ずかかる条件です。完了した注文だけを対象にする、という決めごとを定義側に置けます。使う人が `WHERE status = '完了'` を書き忘れて数字がずれる、ということが起きません。

`joins` に結合を書いておくと、使う人は `JOIN` を書かずに `prefecture` や `member_rank` をほかのフィールドと同じように扱えます。`on` をクォートしているのは、YAMLが `on` を真偽値のtrueとして解釈するためです。ここは最初に引っかかったところでした。

そして、**`GROUP BY` が一度も出てきません。** どの単位で集計するかを、このメトリクスビューは決めていません。

# 切り口を変えて聞く

## GROUP BYは使う人が書く

書き方のきまりは2つです。集計する単位は `GROUP BY` にフィールドを書き、メジャーは `MEASURE()` で囲みます。

```sql
-- 月ごと
SELECT
  order_month,
  MEASURE(total_sales)      AS `売上合計`,
  MEASURE(unique_customers) AS `購入顧客数`
FROM sales_metrics
WHERE order_month >= '2026-01-01'
GROUP BY order_month
ORDER BY order_month;
```

```sql
-- カテゴリごと。メトリクスビューは作り直していない
SELECT
  category,
  MEASURE(total_sales) AS `売上合計`,
  MEASURE(order_count) AS `注文数`
FROM sales_metrics
GROUP BY category
ORDER BY `売上合計` DESC;
```

```sql
-- 都道府県ごと。JOINを書いていない
SELECT
  prefecture,
  MEASURE(total_sales)      AS `売上合計`,
  MEASURE(unique_customers) AS `購入顧客数`
FROM sales_metrics
GROUP BY prefecture
ORDER BY `売上合計` DESC;
```

さきほどは切り口ごとに標準ビューを作りましたが、こちらはメトリクスビュー1つのままです。`GROUP BY` に書くフィールドを変えているだけです。

最初の問いにも戻ってみます。`GROUP BY` を書かなければ、`WHERE` で絞った範囲の全体が1行で返ります。

```sql
SELECT
  MEASURE(total_sales)      AS `売上合計`,
  MEASURE(order_count)      AS `注文数`,
  MEASURE(unique_customers) AS `購入顧客数`
FROM sales_metrics
WHERE order_date BETWEEN '2026-03-01' AND '2026-03-31';
```

246人が返ります。集計結果を持っておらず、聞かれた範囲をそのつど `orders` から数えるので、日ごとの人数を足すことによる重複が起きません。

## SELECT * は使えない

```sql
SELECT * FROM sales_metrics;
```

これはエラーになります。

```
[METRIC_VIEW_MISSING_MEASURE_FUNCTION] The usage of measure column
[total_sales,order_count,unique_customers] of a metric view
requires a MEASURE() (or AGG()) function to produce results.
```

エラーの文に並んでいるのは、すべてメジャーです。メジャーは計算方法なので、どの単位で計算するかが決まらないと値が決まりません。単位を指定していない `SELECT *` では値を作れない、ということです。当然といえば当然なのですが、テーブルと同じ感覚で中身を覗こうとして最初にここで止まりました。欲しい列を明示して、メジャーは `MEASURE()` で囲む。これがメトリクスビューへの聞き方です。

## フィールドに書いていない列では集計できない

`status` は `orders` の列ですが、フィールドには定義していません。これで集計しようとすると、`UNRESOLVED_COLUMN` エラーになります。

```sql
SELECT status, MEASURE(total_sales)
FROM sales_metrics
GROUP BY status;
```

エラーで候補として挙がるのも、フィールドとメジャーの名前だけでした。使う人が選べる単位は、あなたがフィールドに書いたものに限られます。その列で集計したくなったら、`fields` に足します。

一方、`customers` テーブルの `prefecture` は、`joins` で結合したうえでフィールドに定義してあるので、そのまま使えます。元がどのテーブルの列かではなく、フィールドに書いたかどうかで決まります。

## クエリのときにJOINはできない

メトリクスビューは、クエリのときにほかのテーブルと直接 `JOIN` できません。組み合わせたいときは、いったん `WITH` 句で結果を受けてから結合します。

結合を定義側の `joins` に書いておくのは、そのためでもあります。使う人が結合の条件を間違えて数字がずれる余地を、定義の中で消しておけます。

# 定義が1か所にあるということ

カタログエクスプローラーから開くと、「メジャー」と「フィールド」という2つの見出しで、登録したものが一覧になります。元になっているテーブルと `filter` の条件も表示されます。

![カタログエクスプローラーで見たメトリクスビュー](スクリーンショット挿入)

購入顧客数の計算式は、ここにしかありません。変えたいときはここだけ直せば、使う人全員に同時に反映されます。Unity Catalogのオブジェクトなので、権限の管理もテーブルと同じです。計算方法を決めるのはあなた、単位を選ぶのは使う人、という分け方ができます。

そして、SQLを書かない人も同じ定義を使えます。

AI/BIダッシュボードにデータとして `sales_metrics` を追加し、X軸に `category`、Y軸に `total_sales` を選ぶと、`MEASURE()` は自動で付きます。Genieスペースに追加して「2026年3月は何人のお客さんが買いましたか」と日本語で聞けば、生成されるSQLに `MEASURE()` が入り、SQLで聞いたときと同じ246人が返ります。

同じ定義は、アラートからも、Power BIやTableauのような外部BIツール、Excelからも参照できます。どこから見ても、購入顧客数の計算式はひとつです。

# Genieオントロジーの中での位置づけ

メトリクスビューは、SQLを書く人のための仕組みであると同時に、AIに正しい数字を答えさせるための土台でもあります。

Databricksは、社内で使う言葉や指標の意味をまとめる仕組みを「Genieオントロジー」として整理しています。現時点ではプレビューです。中身は2階建てになっています。

| 誰が用意するか | 中身 |
|---|---|
| 人が定義する | メトリクスビュー (指標)、ドメイン (データのまとまり)、ページ (業務の言葉の説明) |
| Databricksが集める | 既存のノートブックやクエリから拾った定義、よく使われている情報 |

- [Genieオントロジー](https://docs.databricks.com/aws/ja/genie/genie-ontology)

メトリクスビューは、このうち「人が定義する」側の中心にあります。購入顧客数の定義を1か所に置いておけば、人がSQLで聞いても、ダッシュボードで見ても、Genieに日本語で聞いても、返ってくる数字が揃います。

Genieに正しく答えさせるために例題を大量に登録する、という運用をしている方もいると思います。指標の定義そのものを先に置けるなら、そちらのほうが筋がいい場面は多そうです。

# 今回扱わなかったこと

定義に書けることはほかにもあります。もくもく会でも時間の都合で扱いませんが、名前だけ挙げておきます。ノートブックの末尾に読み物として入れてあるので、持ち帰って試してみてください。

- `display_name` と `synonyms` と `format`。画面に出す名前、別名、通貨や小数点の書式を付けられます。英語の列名に日本語の表示名と同義語を付けておくと、「売上」「売り上げ」「売上高」のような言い方の揺れにも対応しやすくなります
- ウィンドウメジャー。「過去7日間の購入顧客数」「前年同月の売上」のように、期間をずらしたり広げたりする指標を定義できます
- [パラメーター](https://docs.databricks.com/aws/ja/uc-semantics/metric-views/use-parameters)。クエリ時に値を渡して計算を変えられます
- [マテリアライズ](https://docs.databricks.com/aws/ja/uc-semantics/metric-views/materialization)。よく使う集計を事前計算しておき、クエリを自動で速いほうに振り分けます

# まとめ

メトリクスビューを作ってみて分かったことをまとめます。

- **集計結果ではなく、指標の計算方法を登録しておくビュー。** 数字は持たず、どの単位で集計するかは使う人が `GROUP BY` で決める
- 標準ビューは定義の中に `GROUP BY` を書くので、作った時点で単位が決まる。切り口ごとに標準ビューが増え (症状1)、集計結果を合計すると購入顧客数のような指標は正しく出ない (症状2)
- 足せるかどうかは集計関数で決まる。`SUM` と `COUNT(*)` は日ごとの値を足せるが、**`COUNT(DISTINCT)` は足せない**
- 書くのはメジャーとフィールドの2種類。メジャーは計算方法、フィールドは使う人が選べる単位
- **定義に `GROUP BY` は出てこない。** 切り口を変えてもメトリクスビューは1つのまま
- **`SELECT *` はエラーになる。** 単位が決まらないとメジャーの値が決まらないため
- フィールドに書いていない列では集計できない。`UNRESOLVED_COLUMN` エラーになる
- `filter` と `joins` を定義側に置けるので、使う人の書き忘れや結合ミスで数字がずれる余地を減らせる
- YAMLの `on` はクォートが要る。YAMLが真偽値のtrueとして解釈するため
- 定義は1か所。SQL、ダッシュボード、Genie、外部BIツールのどこから見ても同じ数字になる

一番の収穫は、「集計済みのビューを配る」という当たり前にやっていたことが、何を失っているのかを言葉にできたことでした。集計した瞬間に、誰が買ったのかという情報が消えます。消えたあとで人数を足すと、静かに間違った数字が出ます。エラーは出ません。

購入顧客数のような指標を日次サマリから足している構成は、おそらく珍しくありません。もし心当たりがあれば、注文データから直接数えた値と突き合わせてみると、面白いことになるかもしれません。

もくもく会では、ここに書いたことを手元で動かしてもらいます。読んで分かった気になるのと、`SELECT *` を実行してエラーを出してみるのとでは、残り方が違うと思っています。当日お待ちしています。
