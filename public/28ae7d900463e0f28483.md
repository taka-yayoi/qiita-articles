# はじめに

MLflow の Cookbook に、エージェントの品質を上げるためのレシピ「Agent Alignment Optimization」が載っています。

- [Agent Alignment Optimization (MLflow Cookbook)](https://mlflow.org/cookbook/agent-alignment-optimization)

このレシピでは、まず LLM ジャッジを MemAlign で人の評価に合わせます。そのあと、そのジャッジを採点役にして、GEPA でエージェントのシステムプロンプトを最適化します。

ジャッジを人に合わせる MemAlign と、プロンプトを最適化する GEPA は、これまで別々に試してきました。

- [MemAlignとは? 人間のフィードバックでLLMジャッジを改善する](https://qiita.com/taka_yayoi/items/a4fb3c5bf494d75b7376)
- [人のラベルと突き合わせて見つけたプロンプトの書き漏れを、MLflow の align() で直せるか試した](https://qiita.com/taka_yayoi/items/8b9cdf2de822bf7c97f6)
- [DatabricksにおけるGEPAを用いたプロンプト最適化のチュートリアル](https://qiita.com/taka_yayoi/items/ab5873b4d9b4d633c715)

今回はこの2つをつないで、Databricks で動かしました。確かめたかったのは、**最適化の前にジャッジを人に合わせる手順は本当に要るのか** です。そこで、Cookbook どおりの流れに加えて、MemAlign を飛ばしてそのまま最適化した場合も試し、結果を人の基準で比べました。

結果を先に書くと、MemAlign を飛ばした場合は、ジャッジのスコアが1.0まで上がったのに、人の基準での合格率は0.00でした。最初のプロンプトの0.06より悪くなっています。Cookbook どおりの場合は0.94でした。そのあたりも含めて書いていきます。

# 確かめ方

## 同じプロンプトを、採点役だけ変えて2通りに最適化する

同じ最初のプロンプトを、GEPA で2通りに最適化しました。違うのは、GEPA が候補のプロンプトを採点するときに使うジャッジだけです。

- **Cookbook どおり:** MemAlign で人に合わせたジャッジで採点する
- **MemAlign を飛ばした場合:** `make_judge` で作ったジャッジのまま採点する

`make_judge` で作ったジャッジを MemAlign にかけたものが、人に合わせたジャッジです。2つは別々に用意したジャッジではなく、MemAlign にかける前と後の関係にあります。

![fig1_flow.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/473523b8-d825-4bd6-b44b-d9430031557c.png)

図の実線は、入力から何かを作る流れです。破線は、ジャッジや基準を採点役として使う関係です。ジャッジは GEPA の材料ではなく、GEPA が候補のプロンプトを採点するときに呼ぶものです。

## 結果は人の基準で測る

最適化したプロンプトの良し悪しは、ジャッジではなく人の基準で測ります。ジャッジで測ると、どちらのプロンプトも自分の採点役のジャッジから見て良いプロンプトになっているので、差が見えないからです。

Cookbook では、最適化前後の比較にも、採点役に使った人に合わせたジャッジを使っています。今回は人の基準をコードで書いて、比較にはそれを使いました。基準は次の2つで、ベンチでコーチが読む想定です。

- 数字を出すときは母数を添える (`N=847球` や `38打数` など)
- 回答を300字以内に収める

コードで書いたこの基準は、専門家のラベルを付けるときにも使います。つまり、MemAlign に渡すラベルと最後の採点は、同じ基準から出ています。

# Cookbook の手順を Databricks で動かす

ここからは Cookbook の手順に沿って進めます。Databricks で動かすために変えたところは、その都度書きます。

## エージェントを作り、プロンプトを登録する

最初のプロンプトは、Cookbook のものを日本語にしました。回答の長さや母数については何も書いていません。プロンプトは Unity Catalog の Prompt Registry に `カタログ.スキーマ.名前` の3階層の名前で登録します。

```python
SYSTEM_PROMPT_V1 = (
    "あなたは野球の打撃分析アシスタントです。"
    "利用できるツールを使って、投手の傾向、対戦成績、打撃戦略に関する質問に答えてください。"
    "実行可能な推奨を示してください。"
)

prompt_v1 = mlflow.genai.register_prompt(
    name=f"{CATALOG}.{SCHEMA}.baseball_agent_prompt",
    template=SYSTEM_PROMPT_V1,
    commit_message="最初のプロンプト",
)
```

エージェントを呼ぶ予測関数では、毎回 `format()` でプロンプトを読み込みます。`optimize_prompts` は、`PromptVersion` のテンプレートを候補のプロンプトに差し替えながら評価します。差し替えが効くのは `format()` を呼んだときです。

```python
from databricks_langchain import ChatDatabricks
from langgraph.prebuilt import create_react_agent

llm = ChatDatabricks(endpoint="databricks-claude-haiku-4-5")


def run_agent(system_prompt: str, question: str) -> str:
    agent = create_react_agent(model=llm, tools=TOOLS, prompt=system_prompt)
    result = agent.invoke({"messages": [{"role": "user", "content": question}]})
    return to_text(result["messages"][-1].content)


def make_predict(prompt_version):
    def predict_fn(question: str) -> str:
        # 毎回 format() を呼ぶ。最適化中はここで候補のプロンプトに差し替わる
        return run_agent(prompt_version.format(), question)
    return predict_fn
```

ここは Cookbook のコードから変えたところです。Cookbook の最適化のステップでは、予測関数が最初に作ったエージェントをそのまま呼んでいて、`format()` を呼んでいません。この形だと、候補のプロンプトがエージェントに渡りません。今回は Cookbook のコードをそのままの形では動かしていませんが、自分のエージェントで試すときは、予測関数がプロンプトをどこで読み込んでいるかを確認しておくとよさそうです。

`to_text` は、モデルによって `content` が文字列ではなくブロックのリストで返ってくるので、テキストだけを取り出すヘルパーです。

## ドメイン用のジャッジを作る

Cookbook のジャッジを日本語にし、サンプルサイズの条件を外しました。人の基準 (母数と字数) は書いていません。MemAlign で、この2つを人のラベルから学ばせるためです。

```python
from mlflow.genai.judges import make_judge

base_judge = make_judge(
    name="baseball_analysis",
    instructions=(
        "{{ inputs }} にあるユーザーの質問と、{{ outputs }} にあるエージェントの回答を読み、"
        "回答がデータを適切に分析し、打者またはコーチ陣が実行できる推奨を示しているかを判定してください。\n\n"
        "回答がツールで得たデータに触れ、明確で実行可能な推奨を示していれば合格 (true)。"
        "データがない、誤っている、推奨があいまいな場合は不合格 (false)。"
    ),
    # Claude を日本語のジャッジに使うと JSON のパースで失敗したことがあるため GPT 系にする
    model="databricks:/databricks-gpt-oss-120b",
    feedback_value_type=bool,
)
```

これが「`make_judge` で作ったジャッジ」です。MemAlign を飛ばした場合は、このジャッジをそのまま GEPA の採点役にします。

## 回答に専門家のラベルを付ける

Cookbook では、専門家のフィードバックをモックで用意しています。今回は、人の基準をコードで書いた関数でラベルを付けました。ジャッジがラベルから学べるように、合否と一緒に理由の文も返します。

```python
import re

# 母数の書き方は「N=847」「38打数」「打数：38」「847球」のどれでも拾う
SAMPLE_SIZE_PATTERN = re.compile(r"N\s*=\s*\d+|\d+\s*打数|打数\**\s*[:：]\s*\d+|\d+\s*球")
MAX_CHARS = 300


def expert_label(answer: str):
    """人の基準。合否と理由を返す"""
    has_sample_size = bool(SAMPLE_SIZE_PATTERN.search(answer))
    has_numbers = bool(re.search(r"\d", answer))
    within_length = len(answer.strip()) <= MAX_CHARS
    reasons = []
    if not has_numbers:
        reasons.append("ツールで調べたデータを示していない。聞き返すのではなく、データを調べて推奨まで答えるべき")
    elif not has_sample_size:
        reasons.append("割合や打率を出しているのに、母数 (N=847球や38打数のような件数) を書いていない。母数がないと数字の重みが判断できない")
    if not within_length:
        reasons.append(f"回答が{len(answer.strip())}字あり、ベンチで読むには長すぎる。300字以内に収めるべき")
    if reasons:
        return False, "。".join(reasons) + "。"
    return True, "母数を添えて数字を示し、300字以内で推奨まで書けている。"
```

正規表現は、エージェントが実際に出した書き方を見て直しました。最初は「38打数」のように数字が先に来る書き方しか拾えず、「打数：38」と書いた回答を不合格にしていました。基準をコードで書くときは、実際の出力に当ててから使うのが確実です。

学習用の10問にエージェントで答え、トレースにラベルを記録します。ラベルの名前はジャッジと同じ `baseball_analysis` にします。`align()` はこの名前で、ラベルとジャッジをひも付けます。

ここがハマりどころでした。最初のプロンプトだけで回答を作ると、10件すべてが不合格になりました。回答が300字を超えるためです。不合格の例しかないと、MemAlign は「どんな回答なら合格か」を学べません。そこで、「簡潔に答えてください」とだけ書いた別のプロンプトでも同じ10問に答えさせ、合計20件にラベルを付けました。このプロンプトには、母数のことも字数のことも書いていません。

```python
from mlflow.entities import AssessmentSource, AssessmentSourceType

# ラベルの合格・不合格を混ぜるために使う、もう1つのプロンプト (登録はしない)
SYSTEM_PROMPT_SHORT = (
    "あなたは野球の打撃分析アシスタントです。"
    "ツールで調べたデータを使って、質問に簡潔に答えてください。"
)


@mlflow.trace(name="baseball_agent")
def traced_agent(system_prompt: str, question: str) -> str:
    return run_agent(system_prompt, question)


train_rows = []
for system_prompt in [prompt_v1.format(), SYSTEM_PROMPT_SHORT]:
    for q in TRAIN_QUESTIONS:
        answer = traced_agent(system_prompt, q)
        train_rows.append({"answer": answer, "trace_id": mlflow.get_last_active_trace_id()})

# トレースは非同期で保存される。ラベルを付ける前に保存を待つ
mlflow.flush_trace_async_logging()

for row in train_rows:
    passed, rationale = expert_label(row["answer"])
    mlflow.log_feedback(
        trace_id=row["trace_id"],
        name="baseball_analysis",  # ジャッジと同じ名前にする
        value=passed,
        rationale=rationale,
        source=AssessmentSource(source_type=AssessmentSourceType.HUMAN, source_id="expert-rule"),
    )
```

ラベルの内訳は、最初のプロンプトの回答が不合格10件、簡潔なプロンプトの回答が合格4件・不合格6件でした。不合格の理由は「300字を超えただけ」「母数がないだけ」「両方」に分かれていて、2つの基準をそれぞれ学べるデータになっています。

## MemAlign でジャッジを人に合わせる

```python
from mlflow.genai.judges.optimizers import MemAlignOptimizer

traces = [mlflow.get_trace(row["trace_id"]) for row in train_rows]
optimizer = MemAlignOptimizer(
    reflection_lm="databricks:/databricks-gpt-oss-120b",
    # 既定は OpenAI のモデルなので、Databricks の埋め込みモデルを指定する
    embedding_model="databricks:/databricks-qwen3-embedding-0-6b",
    retrieval_k=3,
)
aligned_judge = base_judge.align(traces=traces, optimizer=optimizer)
print(aligned_judge.instructions)
```

元の指示の後ろに、4つの指針が書き足されました。これが「MemAlign で人に合わせたジャッジ」です。

```text
Distilled Guidelines (4):
  - When presenting percentages, rates, or averages, always include the sample size (e.g., N=847 pitches or 38 at‑bats) so the weight of the numbers is clear.
  - Keep the entire response concise – no more than roughly 300 Japanese characters (including punctuation and spaces).
  - Provide a clear, actionable recommendation for the batter or coach that is directly derived from the presented data.
  - When reporting a batting average or similar performance metric, also state the raw count (e.g., 打数 38) alongside the rate.
```

人の基準の2つ (母数と300字) が、どちらも指針になっています。3つ目の「データから導いた推奨を書く」は、理由の文の「推奨まで書けている」「推奨まで答えるべき」から拾われたものです。以前の記事と同じく、指針は英語で出力されました。

人に合わせられたかも確かめました。最適化に使わないホールドアウトの8問に最初のプロンプトで2回ずつ答え、その16件を2つのジャッジで判定して、人の基準と一致した割合を出しています。

| ジャッジ | 人の基準との一致率 |
|---|---|
| `make_judge` で作ったジャッジ | 0.00 |
| MemAlign で人に合わせたジャッジ | 0.94 |

`make_judge` で作ったジャッジは、人の基準で不合格の15件をすべて合格にし、合格の1件だけを不合格にしていました。このジャッジは「データに触れて、推奨がはっきりしているか」を見ています。最初のプロンプトの回答は長く、推奨も丁寧に書いてあるので、このジャッジから見ると良い回答です。人の基準とは、ほぼ真逆を向いていたことになります。

## GEPA でプロンプトを最適化する

ここで、採点役だけを変えて2回最適化します。学習用の10問と設定は同じです。

```python
from mlflow.genai.optimize import GepaPromptOptimizer

# optimize_prompts の学習データには inputs と expectations の両方が必要
train_data = [
    {
        "inputs": {"question": q},
        "expectations": {"expected_facts": ["ツールで得たデータに基づいて推奨を示している"]},
    }
    for q in TRAIN_QUESTIONS
]


def optimize_with(judge):
    result = mlflow.genai.optimize_prompts(
        predict_fn=make_predict(prompt_v1),
        train_data=train_data,
        prompt_uris=[prompt_v1.uri],
        optimizer=GepaPromptOptimizer(
            reflection_model="databricks:/databricks-claude-sonnet-4-5",
            max_metric_calls=60,  # スコアラーを呼ぶ回数の上限
        ),
        scorers=[judge],
    )
    print(f"ジャッジのスコア: {result.initial_eval_score} -> {result.final_eval_score}")
    return result.optimized_prompts[0]


prompt_cookbook = optimize_with(aligned_judge)  # Cookbook どおり
prompt_skipped = optimize_with(base_judge)      # MemAlign を飛ばした場合
```

`optimize_prompts` は、最適化したプロンプトを Prompt Registry に新しいバージョンとして登録します。

GEPA が報告したジャッジのスコアは、どちらも上がりました。

| | 最適化前 | 最適化後 |
|---|---|---|
| Cookbook どおり | 0.0 | 0.9 |
| MemAlign を飛ばした場合 | 0.9 | 1.0 |

ジャッジのスコアだけを見れば、どちらも成功です。MemAlign を飛ばした場合は、最適化前から0.9あります。採点役のジャッジが、最初のプロンプトの長い回答をすでに良い回答と見ていたためです。

できたプロンプトの中身は、大きく違いました。Cookbook どおりのプロンプトには、MemAlign の指針がほぼそのまま入っています。抜粋します。

```text
**回答の要件：**
1. **データの完全性**: ツールから得た数値には必ずサンプルサイズ（例：N=847球、38打数など）を明記し、データの重みを示してください
2. **簡潔性**: 回答は300文字以内に収めてください。ベンチで素早く読めることが重要です
```

この後に「悪い例」と「良い例」も続きます。「良い例」には学習用の質問 (小林投手、3-1のカウント) がそのまま使われていました。ホールドアウトの質問とは別の質問なので、評価への影響はありません。

MemAlign を飛ばした場合のプロンプトには、`make_judge` で作ったジャッジが求める「実行可能な推奨」が、要素として細かく書き込まれました。

```text
**回答に含めるべき要素:**
- データに基づく分析結果
- 具体的な推奨戦略（例：「ストレート待ちで構える」「変化球への対応準備も必要」など）
- 注意点やリスク要因
- 実行可能なアクションプラン
```

母数と字数については、何も書かれていません。

# 人の基準で比べる

最初のプロンプトと、最適化した2つのプロンプトで、ホールドアウトの8問に2回ずつ答えさせました。その16件を、人の基準で採点しています。

| プロンプト | 人の基準での合格率 | 母数あり | 300字以内 | 平均字数 |
|---|---|---|---|---|
| 最初のプロンプト | 0.06 | 0.81 | 0.06 | 501 |
| Cookbook どおり | 0.94 | 1.00 | 0.94 | 226 |
| MemAlign を飛ばした場合 | 0.00 | 0.50 | 0.12 | 777 |

![fig2_scores.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/9cf02281-b947-4dea-9940-0c3bd1a36c7e.png)

Cookbook どおりの場合は、人の基準での合格率が0.06から0.94に上がりました。ジャッジのスコア (0.9) と、人の基準での合格率がそろっています。

MemAlign を飛ばした場合は、ジャッジのスコアが1.0になったのに、人の基準での合格率は0.00でした。最初のプロンプトより下がっています。採点役のジャッジが人とずれていたため、そのずれた基準に向けて最適化されました。プロンプトが「分析結果」「注意点」「アクションプラン」を求めたので回答が平均777字に伸び、母数を書く割合も0.81から0.50に下がりました。

繰り返しごとの合格率は、Cookbook どおりが1.00と0.88、MemAlign を飛ばした場合が2回とも0.00で、2回とも同じ傾向でした。

同じ質問への回答を並べます。「木村投手に対して、右打者は初球を打つべきですか？」への回答です。MemAlign を飛ばした場合の回答は744字で、球種配分の表、理由3つ、「具体的な打撃アクションプラン」、注意点、結論まで書いていて、母数はありませんでした。Cookbook どおりの回答は230字で、全文は次のとおりです。

```text
**推奨：初球は慎重に対応し、積極的には打たない**

木村投手の初球（0-0）対右打者：ストレート45%、スライダー30%、チェンジアップ25%（N=847球）

初球は変化球が55%を占めており、ストレートのみが確実な狙い球です。初球から積極的に打つと変化球に引っかかるリスクが高い。**戦略：初球はボール球を見極め、ストライクゾーンのストレートに絞って狙う。1ボール以上にしてから攻略するカウント（2-0、3-1など）で打者有利を作る方が効果的です。**
```

推奨が先頭にあり、母数も付いています。ベンチで読む回答としては、こちらが望ましい形です。

## 結果を読むときの注意

- 人の基準は、コードで判定できる単純な2つの条件です。そのため、MemAlign の指針がそのまま GEPA のプロンプトに移りやすい条件になっています。人の判断がもっと曖昧な基準では、ここまできれいに分かれない可能性があります
- ホールドアウトは8問を2回ずつの16件で、1件の違いで率が0.06動きます。ただ、今回は0.00と0.94の差なので、件数の少なさで結論は変わりません
- エージェントの回答は、実行のたびに変わります。数字は今回の実行でのものです

# DSPy は 3.4.0 に固定する

MemAlign は内部で DSPy を使います。今回、最初は DSPy のバージョンを固定せずにインストールしていて、DSPy 3.5 が入りました。この組み合わせでは、MemAlign が2か所で止まりました。

1つ目は埋め込みです。エラーメッセージによると、DSPy 3.5 の埋め込みは、モデル名として `openai/<model>` か `azure/<deployment>` の形式を受け付けます。`databricks:/databricks-qwen3-embedding-0-6b` の指定はここで止まりました。

2つ目は指針の生成です。DSPy 3.5 で `lm(messages=[...])` の呼び出し方が新しい API に置き換わったため、MemAlign の指針の生成がエラーになりました。ここでは、MemAlign はエラーをログに出したうえで処理を続けます。そのため `align()` は例外を投げずに終わり、指示は元のままのジャッジが返ってきます。

このまま最適化に進むと、Cookbook どおりのつもりで、実際には MemAlign を飛ばした場合と同じことをしてしまいます。今回のノートブックでは、指示が元のままなら失敗として扱うようにしました。

```python
aligned_judge = base_judge.align(traces=traces, optimizer=optimizer)
# MemAlign は指針の生成に失敗しても例外を投げない。指示が元のままなら失敗として扱う
if aligned_judge.instructions.strip() == base_judge.instructions.strip():
    raise RuntimeError("指針が1つも書き足されていない。上のログに MemAlign のエラーが出ていないか確認する")
```

DSPy を 3.4.0 に固定すると、MLflow 3.18.0 でも MemAlign は最後まで動きました。DSPy はすでに読み込んだプロセスではバージョンを戻せないので、固定するならインストールのセルで最初から固定しておくのが確実です。

# まとめ

MLflow Cookbook の Agent Alignment Optimization を Databricks で動かし、MemAlign を飛ばした場合と比べて分かったことをまとめます。

- Cookbook の流れは、MemAlign でジャッジを人に合わせてから、そのジャッジを採点役にして GEPA でプロンプトを最適化する
- **MemAlign を飛ばして最適化すると、ジャッジのスコアは1.0まで上がったのに、人の基準での合格率は0.00だった。** 最初のプロンプト (0.06) より下がった
- Cookbook どおりに最適化すると、人の基準での合格率は0.94まで上がった。MemAlign の指針が、ほぼそのまま GEPA のプロンプトに入った
- `make_judge` で作ったジャッジは、ホールドアウトで人の基準と1件も一致していなかった。MemAlign で人に合わせたあとは0.94
- ラベルに合格の例がないと、MemAlign は合格の形を学べない。最初のプロンプトだけでは全件が不合格になった
- `optimize_prompts` の予測関数では、毎回 `format()` を呼んでプロンプトを読み込む。候補のプロンプトはここで差し替わる
- **DSPy 3.5 では、MemAlign の埋め込みと指針の生成が止まる。指針の生成の失敗では例外が出ないので、DSPy は 3.4.0 に固定し、指示が変わったかを確認する**

一番の収穫は、Cookbook に MemAlign の手順がある理由を、数字で確かめられたことでした。GEPA は採点役のジャッジに向けて忠実にプロンプトを直すので、ジャッジが人とずれていると、スコアが上がっても人の基準では悪くなります。最適化の成果をジャッジのスコアだけで判断せず、少数でも人の基準で直接測る仕組みを残しておくと、このずれに早く気づけそうです。
