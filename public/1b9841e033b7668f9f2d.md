データのランドスケープが急激に成長することで、複雑で従来のロールベースのアクセス制御(RBAC)は自身の制限に直面するようになっています。データエンジニアは、数千のテーブルに対する数百のロールを管理すことが悪夢となる「ロール爆発」のシナリオに直面しています。現在ベータ版のゲームチェンジをするアプローチであり、データバナンスの考え方に革命をもたらすDatabricks Unity Catalogの**属性ベースアクセス制御(ABAC)** にようこそ。

お使いのレイクハウスでのきめ細かいアクセスの管理に苦戦したり、さまざまなアクセスパターンに対応するためだけに数えきれないロールを作成していることに気づいたのであれば、ABACはあなたが待ち続けたソリューションなのかもしれません。

# ABACとは？なぜデータエンジニアは注意すべきなのか？

**属性ベースアクセス制御(ABAC)** は、静的なロール割り当てではなく、ユーザー、リソース、アクション、環境条件の属性に基づいて認証の意思決定を行う動的なアクセス制御モデルです。DatabricksのUnity Catalogの文脈ではABACによって、定常的なポリシーのアップデートを必要とすることなしに、変化し続ける状況に自動で適応する洗練されたタグドリブンのポリシーを作成することができます。

このように考えてみましょう: 「US_Sales_Manager」、「EU_Sales_Manager」、「APAC_Sales_Manager」のように個別のロールを作成するのではなく、ユーザーの位置属性とデータ分類タグに基づいてアクセスを許可する単一のポリシーを作成するのです。システムはクエリーの際にこれらの属性を動的に評価します。

# 従来のRBACの問題

従来のRBACはシンプルなシナリオではうまく動作しますが、複雑性が増すとすぐに破綻してしまいます。これらの一般的な課題を考えてみます:

- **ロール爆発:** 組織がスケールすると、さまざまな権限の組み合わせに対応するために指数関数的に多くのロールが必要となります。
- **メンテナンスのオーバーヘッド:** 全ての組織上の変更は複数のロール定義の更新を必要とします。
- **限定的な粒度:** 通常RBACはテーブルやスキーマレベルで動作するものであり、行・列レベルのアクセスコントロールを面倒なものにします。
- **静的な性質:** ロールはビジネスコンテキストや時間に敏感なアクセス要件に適応しません。

# Unity CatalogにおけるABACの動作原理

Unity CatalogのABACは、動的なアクセス制御を強制するために協働する3つのコアコンポーネントを通じて動作します:

![](https://community.databricks.com/t5/image/serverpage/image-id/18383i9657120AAD4068DC/image-size/large?v=v2&px=999)
Databricks ABACアーキテクチャとワークフロー図

## 1. 管理タグ

管理タグは、Unity CatalogにおけるABACの基盤です。これらは、カタログ、スキーマ、テーブル、個々のカラムのようなデータ資産に適用するメタデータ属性であり、集中管理されます。通常のタグとは異なり、統制タグは:

- **定義を集中管理:** タグポリシーを通じてアカウントレベルで作成
- **値の制限あり:** 定義済みの値のみを割り当て可能
- **権限管理可能:** 承認されたユーザーのみが割り当て、変更可能

タグポリシー作成の例:

```
-- Tag policy defines allowed values
-- Tag key: "data_classification" 
-- Allowed values: "public", "internal", "confidential", "restricted"
```

## 2. ポリシー

ポリシーは、タグの値とユーザーの属性に基づいてアクセスを決定するルールです。Unity Catalogでは2つのタイプのABACポリシーをサポートしています:

- **行フィルターポリシー:** データのコンテンツやユーザー属性に基づいてユーザーがどの行を参照できるのかを制御します
- **列マスクポリシー:** ユーザーが特定カラムで参照する値を制御し、機微情報をマスキング、検閲することができます

## 3. ユーザー定義関数(UDF)

UDFには、あなたのアクセスコントロールポリシーのためのビジネスロジックが含まれます。これらは、複雑な条件、ユーザーの文脈、環境要件を組み込みます。これらの関数は、リアルタイムのアクセス決定を行うためにクエリーの際に評価されます。

# データエンジニアにとっての主要なメリット

ABACは、すべてのアクセスパターンに対する個別のロールを作成するのではなく、属性を用いることでロール爆発を排除します。単一のポリシーで数百のテーブルに対するアクセスを統治し、タグとユーザーの文脈に基づいて適切なコントロールを自動で適用します。

## 複雑性なしのスケーラビリティ

静的なロールと違い、ABACポリシーは変化する状況に自動で適応します。新規テーブルにタグをつけたり、ユーザーの属性を変更すると、アクセスコントロールはポリシーの変更なしに調整されます。

## 集中管理のガバナンス

すべてのアクセスロジックは、タグポリシーとUDFを通じて集中管理されるので、あなたのガバナンスモデルの監査、修正、メンテナンスが容易になります。ビジネスルールの変更の際には、複数のロール定義ではなく一箇所の更新で対応できます。

## きめ細かいコントロール

ABACは、複雑なビジネスロジックに基づいた行レベルのフィルタリングと列レベルのマスキングをサポートしています。時間、位置、ユーザー属性、データの機密度を同時に考慮する条件付きのアクセスを実装することができます。

# 使い始める: ベストプラクティス

## 1. 小さく始めて大きく考えましょう

ワークフローを理解するために、クリティカルではないデータに対するパイロット実装からスタートしましょう。PIIのマスキングや地域的なデータ制限のような特殊なユースケースを特定しましょう。

## 2. あなたのタグの分類体系を設計しましょう

ポリシーを実装する前に、あなたのタグの分類体系(taxonomy)を注意深く設計しましょう。以下を検討しましょう:

- データ分類レベル(公開、内部、機密、制限)
- 地理的リージョン
- ビジネスドメイン
- 規制の要件

## 3. 階層継承を活用しましょう

効率性を最大化し、管理のオーバーヘッドを削減するために、最も高位の適用可能なレベル(カタログ > スキーマ > テーブル)でポリシーを適用しましょう。

## 4. 監視して監査しましょう

ポリシーの効用を監視し、コンプライアンスを保証するために、Unity Catalogの包括的な監査ロギングを活用しましょう。
