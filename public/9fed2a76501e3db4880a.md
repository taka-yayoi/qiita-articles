結構心待ちにしていた機能です。

https://qiita.com/taka_yayoi/items/8ec6ec967d6d9fdae0e6

これまでもダイナミックビューで同様のことは実現できていましたが、テーブルに対するビューを定義するので若干取り回しが大変だったのですが、テーブルにフィルターをアタッチする形になるのでフィルターの再利用もしやすくなります。

こちらでは行フィルター(row filter)を試します。

# 準備

事前に`DS`というグループを作成しておき、ユーザーAのみを追加しておきます。

対象のテーブルは`target`とします。以下のように`pickup_zip`などの郵便番号が含まれているテーブルです。ちなみにこちらはNYのタクシーの乗降記録です。
![Screenshot 2023-09-13 at 10.56.05.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/d36e13bc-a4e5-3ee4-ce0e-7d73e97960a1.png)

Sharedクラスターを作成して起動します。シングルユーザークラスターでは本機能は動作しません。

# ユーザーAの作業

```sql
USE main.default;
```

行フィルターの関数を定義します。このフィルターは、テーブルにアクセスするユーザーがグループ`DS`に所属している場合には前レコードを返却しますが、そうではない場合にはzipコードが`10153`のレコードのみを返却します。

```sql
CREATE FUNCTION zip_filter(zip STRING)
RETURN IF(IS_ACCOUNT_GROUP_MEMBER('DS'), true, zip='10153');
```

カタログエクスプローラで関数を確認することができます。
![Screenshot 2023-09-13 at 10.57.42.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/71ba5575-a30a-6368-bbbb-20d292d6565a.png)

テーブルにフィルターを適用します。

```sql
ALTER TABLE target SET ROW FILTER zip_filter ON (pickup_zip);
```

なお、フィルター適用されているかどうかを確認するにはテーブルに`DESCRIBE EXTENDED`を実行します。

```sql
DESCRIBE EXTENDED target;
```

`Row filter`にどのテーブルのどの列にどのフィルターが適用されているのかが表示されます。
![Screenshot 2023-09-13 at 11.07.58.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/d9f1f86b-47e8-7671-1311-d0630de691d9.png)

テーブル`target`にクエリーを発行するとすべてのレコードが返却されます。
![Screenshot 2023-09-13 at 11.11.06.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/275b8337-60a2-edb9-6ade-f2ec06f3f2cb.png)


# ユーザーBの作業

ユーザーBはグループ`DS`には属していません。

```sql
SELECT * FROM target;
```

行フィルターが動作して、`pickup_zip`が`10153`のレコードしか返却されなくなっています。
