# イントロダクション

Lakeflow Spark宣言型パイプライン(SDP)は、スケーラブルかつメンテナンス可能なETLパイプラインの構築のために設計されたフレームワークです。全ての人は、時間や工数を削減し、頭痛の種を取り除くために、標準的なSparkやPandasのような従来の命令型ETLから宣言型アプローチへの移行を望むべきです。このブログ記事シリーズは、使い始める際に必要となるソリューションやベストプラクティスを提供することで簡単に取り組めるようにするためのものです。

宣言型アプローチを導入することで、あなたは**ビジネスロジック**のみにフォーカスすることになります。SDPは自動で、再計算、リトライ、永続化、状態管理のような面倒な作業に対応し、無駄な提携コードを排除します。

例をウォークスルーしていきましょう。

一般的なタスクを考えてみます: lowly Changing Dimension (SCD) Type 1テーブルを維持するために、Change Data Capture (CDC)のログを取り込みます。この際、あなたはキーに基づくレコードのupsert、削除の対応、最新バージョンのレコードのみが保持されることを確実にする必要があります。

**Spark命令型コード**

 ```py
from pyspark.sql import DataFrame
from pyspark.sql.functions import col, struct, max_by

def upsert_to_delta(micro_batch_df, batch_id):
    # Deduplicate within the micro-batch to get the latest record per key
    (micro_batch_df
     .groupBy("key")
     .agg(max_by(struct("*"), col("ts")).alias("row"))
     .select("row.*")
     .createOrReplaceTempView("updates"))

    # Execute the MERGE logic
    # Note: Replace the ellipses with your actual column mapping
    micro_batch_df.spark_session.sql("""
        MERGE INTO cdc_data_raw t
        USING updates s
        ON s.key = t.key
        WHEN MATCHED AND s.is_delete = true THEN 
            UPDATE SET DELETED_AT = now()
        WHEN MATCHED THEN UPDATE SET 
            A = CASE WHEN s.ts > t.ts THEN s.a ELSE t.a END,
            B = CASE WHEN s.ts > t.ts THEN s.b ELSE t.b END,
            -- ... for every column ...
            ts = CASE WHEN s.ts > t.ts THEN s.ts ELSE t.ts END
        WHEN NOT MATCHED THEN INSERT *
    """)

# Start the stream
(cdcData.writeStream
    .foreachBatch(upsert_to_delta)
    .outputMode("append")
    .start()
)
```

**Spark宣言型コード**

```py
from pyspark import pipelines as dp
from pyspark.sql.functions import col, expr

@dp.view
def users():
    return spark.readStream.table("cdc_data.users")

dp.create_streaming_table("target")

dp.create_auto_cdc_flow(
    target = "target",
    source = "users",
    keys = ["key"],
    sequence_by = col("ts"),
    apply_as_deletes = expr("is_deleted = True")
)
```

命令型のアプローチでは、複雑かつ複数行の`MERGE`ステートメントと、手動による状態管理が必要となります。SDPでは、`AUTO CDC`フローが仕組みに自動で対応します。あなたはビジネスロジック飲みにフォーカスするのです。**ビンゴ！**

もちろん、`AUTO CDC`はこのフレームワークの単なるビルディングブロックの一つにすぎません。あなたのパイプラインのほとんどに対応できることを念頭に置いた他のいくつかのシンプルなパターンが存在します。基礎からスタートしましょう: **SDPでテーブルに結果を保存する方法**です。

# Part 1. Spark宣言型パイプラインでテーブルに結果を保存する方法

従来のSparkの世界では、我々は通常全てのスクリプトを「コマンド」で終了します。データを変換し、Sparkに正確に何をすべきかを伝えます: `df.write.saveAsTable("sales")`などです。

あなたが初めてLakeflow SDPに切り替えた際、つまづくかもしれません。あなたはあなたのトランスフォーメーションを記述し、データを永続化する準備ができ、あなたの信頼する`.write.save()`に辿り着きます。**しかし、そこにそれはありません。** 手元にデータがある際、実際にはどのようにテーブルに着地させるのでしょうか？

実際のところ、<ins>SDPでは明示的に「write」アクションを呼び出す必要がありません。</ins>

# シフト: アクションから宣言へ

このシフトはシンプルです: 命令型の世界では、あなたはテーブルにデータを**送信します**。宣言型の世界では、あなたは関数やSQLクエリー(SDPではPythonとSQLの両方をサポートします)の結果としてテーブルを**定義します**。

従うべき手動のコーディングステップではなく、シンプルにデコレーターを使用します。Python SDPでは、全てのテーブルの宣言はSparkデータフレームを返却するPython関数であることに注意してください。

**命令型の方法**

```py
(spark.readStream.table("raw_sales")
    .filter("amount > 0")
    .writeStream .option("checkpointLocation","s3://bucket/checkpoints/sales_report")
    .outputMode("append")
    .toTable("sales_report")
)
```

**SDPの方法**

```py
from pyspark import pipelines as dp

@dp.table
def sales_report():
    return (spark.readStream
             .table("raw_sales")
             .filter("amount > 0")
            )
```

売り上げデータに対する日次集計を説明するより複雑な例を考えてみましょう。

**命令型の方法**

このアプローチはあなたに対して、メインのロジックフローだけでなく、「ヘルパー」関数、手動でのシンク、チェックポイントの管理を要求します。

```py
# The foreachbatch function
def process_daily_chunk(batch_df, batch_id):
    # Perform aggregation within the batch.
    # Note: this would NOT handle late data.
    daily_summary = (batch_df
        .groupBy("store_id", "processing_date")
        .agg({"sales_amount": "sum"})
    )

    # Manually append to the target table
    (daily_summary.write.mode("append")
         .saveAsTable("daily_sales_stats"))

# The main stream management
(spark.readStream
    .table("raw_transactions")
    .writeStream
    .foreachBatch(process_daily_chunk)
    .option("checkpointLocation", "s3://bucket/checkpoints/daily_stats")
    .start()
)
```

**SDPの方法**

このフレームワークは「how」に対応します。あなたは「what」のみを定義します。`@​dp.materialized_view`を使っているので、SDPは状態およびインクリメンタル更新に自動で対応します。

```py
from pyspark import pipelines as dp
from pyspark.sql import functions as F

@dp.materialized_view
def daily_sales_stats():
    # You define the transformation; 
    # SDP handles the execution under the hood.
    # Note: late data is handled automatically.
    return (
        spark.read.table("raw_transactions")
        .groupBy("store_id", "processing_date")
        .agg(F.sum("sales_amount").alias("total_sales"))
    )
```

`@​dp.table`や`@​dp.materialized_view`を追加することで、あなたはフレームワークに以下を支持することになります: *「この関数は物理テーブルを表現します。そのようにしてください」* デフォルトでは、テーブル名は関数名から導出されることに注意してください。

*「待って、`@​dp.materialized_view`ではなく`@​dp.table`を使うのはどんな時？」* と不思議に思うかもしれません。安心してください！私は上の例で両方使いましたが、現時点では区別が曖昧だと感じても全く問題ありません。これらは似たものに見えますが、内部ではデータを全く異なる方法で取り扱います。次の記事でこの違いに踏み込みます。

# 重要なポイント

SDPの旅を始めるに際して、あなたのコードをに対する定期的な「セルフチェック」を行いましょう:

**「ビジネスロジックにフォーカスしているか？あるいは実装の詳細に踏み込んでいるのか？」**

ご自身で保存モードや`foreachbatch`のセマンティクスを考えていることに気づいた場合には、依然として命令型で考えている可能性があります。フレームワークに「how」を対応させている場合には、SDPを正しく使っていると言えます。

# まとめ

SDPは、ETLパイプラインのために標準化されたマネージドのフレームワークを提供します。自動で**チェックポイント**、**ストレージのパス**、**定型コード**に対応し、ビジネスロジックや成果にフォーカスする余地を広げます。

次の記事では、**ストリーミングテーブルとマテリアライズドビューの違い**に踏み込み、あなたのパイプラインを効率的な状態に保つためには、どちらを使うのかに関して正確にブレークダウンします。お楽しみに！
