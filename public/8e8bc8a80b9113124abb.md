# はじめに

CodexとClaude Code、両方を日常的に使い分けている方は多いと思います。ただ、それぞれをOpenAI/Anthropicと個別に契約してAPIキーを管理するのは煩雑ですし、組織で配ろうとすると別の問題が出てきます。誰がどのツールでどれだけ消費しているのか見えない、レート制限もかけられない、という統制の効かない状態です。

Databricksが公開した `ucode` (Unity AI Gateway Coding CLI) は、これらのコーディングエージェントをDatabricks AI Gateway経由でルーティングすることで、この2つの課題をまとめて解消するためのツールです。本記事では、実際に手元のmacOSとAWS上のワークスペースで `ucode` をセットアップし、CodexとClaude Codeを並走させて、ベンダー横断の消費を1枚のレポートで可視化するところまでを検証した記録をまとめます。

https://github.com/databricks/ucode

結論から言うと、APIキーを一切使わずDatabricks認証だけで両エージェントが動き、Anthropic (Opus 4.8) とOpenAI (GPT-5.5) の消費が同じサマリに並びました。

# 解決したい課題

整理すると、課題は2つのレイヤーに分かれます。

ユーザー側の煩雑さとして、CodexとClaude Codeを使い分けるには、本来それぞれのプロバイダーと契約してAPIキーを発行・管理する必要があります。キーの保管やローテーション、複数ツール分の管理は地味に手間です。

管理者側のガバナンス不在として、各自が勝手に契約・利用していると、コスト消費が把握できず、レート制限もかけられません。エージェントは意図しないループや大量リクエストで費用を急増させる要因にもなるため、利用の可視化と統制が効かない状態はリスクになります。

`ucode` とその基盤であるUnity AI Gatewayは、ルーティング先をGatewayのエンドポイントに寄せることで、ユーザー体験 (キー不要・使い分け容易) と管理者統制 (可視化・レート制限・単一請求) の両方を同時に実現します。

# ucodeとは

`ucode` は、Codex、Claude Code、Gemini CLI、OpenCode、GitHub Copilot CLI、Piといったコーディングエージェントを、Databricks経由で動かすための軽量ランチャーです。OAuthを処理し、各エージェントの設定ファイルを書き込み、登録済みのLLMやMCPサーバーにトラフィックをルーティングします。

ポイントは、すべてのエージェントがワークスペースの認証情報を使ってDatabricks AI Gateway経由でルーティングされるため、APIキーが不要になることです。各エージェントの起動も `ucode <agent名>` だけで、初回はワークスペースURLを尋ねられて認証し、2回目以降は直接エージェントに進みます。

公式ドキュメントは以下を参照してください。

- コーディングエージェントとの統合 (日本語): https://docs.databricks.com/aws/ja/ai-gateway/coding-agent-integration-beta
- エージェントおよびLLM向けのUnity AI Gateway (日本語): https://docs.databricks.com/aws/ja/ai-gateway/overview-beta
- ucode リポジトリ (GitHub): https://github.com/databricks/ucode

# 前提条件

検証にあたっての前提は次のとおりです。

ワークスペース側は、Unity AI GatewayがサポートされるリージョンのDatabricksワークスペースで、Unity Catalogが有効になっていること、そしてアカウントでUnity AI Gatewayプレビューが有効化されていることが必要です。これはBeta機能なので、アカウント管理者がアカウントコンソールのPreviewsページで有効化します。

ローカル側は、`Python 3.12+` (`uv` でインストール) と、エージェントCLIを自動インストールさせる場合は `npm` が必要です。

macOSでは `python` コマンドが存在しないことがありますが、`ucode` 自体は `uv` で動くため、素の `python` は必須ではありません。`uv` さえ通れば必要なPythonは `uv` が用意してくれます。

# セットアップ

インストールは1コマンドです。

```bash
uv tool install git+https://github.com/databricks/ucode
```

`uv` が入っていない場合は先にインストールします。

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

# Claude Codeを設定する

いきなり設定ファイルを書き換えず、まず `--dry-run` で何が書き込まれるかを確認します。ワークスペースURLを直接渡すと、対話式のエージェント選択ピッカーをスキップでき、`--agents` で対象を絞れます。

```bash
ucode configure --workspaces https://<your-workspace>.cloud.databricks.com --agents claude --dry-run
```

途中で「Update Claude Code ... (y/n)」とCLI本体の更新を聞かれますが、検証中は変数を増やさないよう `n` で見送って問題ありません。

`--dry-run` で出力された設定ファイルの中身がこちらです。

```json
{
  "apiKeyHelper": "... databricks auth token --host https://<your-workspace>.cloud.databricks.com --profile DEFAULT --force-refresh --output json | jq -r '.access_token' ...",
  "env": {
    "ANTHROPIC_BASE_URL": "https://<your-workspace>.cloud.databricks.com/ai-gateway/anthropic",
    "ANTHROPIC_CUSTOM_HEADERS": "x-databricks-use-coding-agent-mode: true ...",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "databricks-claude-opus-4-8[1m]",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "databricks-claude-sonnet-4-6[1m]",
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "databricks-claude-haiku-4-5"
  }
}
```

ルーティング先が `/ai-gateway/anthropic` になっていること、認証がapiKeyHelper経由でDatabricksトークンを取得する仕組みになっていること、そしてOpus/Sonnet/Haikuが `databricks-claude-*` にマッピングされていることが確認できます。`[1m]` は1Mコンテキストの指定です。Anthropic直契約のキーは一切登場していません。

なお `--dry-run` の場合、最後にvalidationステップが設定ファイルを読みにいって「Settings file not found」エラーを出しますが、これは実ファイルを書いていないためで、設定内容そのものは正常です。

中身に問題がなければ、`--dry-run` を外して本番実行します。

```bash
ucode configure --workspaces https://<your-workspace>.cloud.databricks.com --agents claude
```

今度は設定ファイルが実際に書き込まれ、validationのテストメッセージがGateway経由で送られます。

```
✔ Claude Code is working
✓ Claude Code — run with ucode claude
```

![Screenshot 2026-06-24 at 10.48.24.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/b6d296ea-c156-4031-bb7f-eb0a57e9f1ea.png)

`✔ Claude Code is working` が出れば、Gateway経由で `databricks-claude-*` に到達して応答が返ってきたということです。実際に起動して動作を確認します。

```bash
ucode claude
```

起動後のヘッダーに `Opus 4.8 (1M context)` と表示され、適当なプロンプトに応答が返れば疎通完了です。`API Usage Billing` という表示も、Anthropicアカウント課金ではなくGateway経由で課金される構成になっていることの裏付けです。

# Codexを追加する

同じ要領でCodexを設定します。

```bash
ucode configure --workspaces https://<your-workspace>.cloud.databricks.com --agents codex
```

```
✔ Codex is working
✓ Codex — run with ucode codex
```

![Screenshot 2026-06-24 at 10.52.28.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/e0ad4fd9-913f-4263-9d02-caea7b8d646b.png)

Codexも `✔ Codex is working` が出ました。CodexはClaude Codeと違い、`/ai-gateway/codex/v1` というOpenAI互換エンドポイントを要求します。ここがvalidationで通ったということは、ワークスペースにCodex用のモデルエンドポイントが用意されていることを意味します。

# 2エージェントを並走させる

ここで注意点があります。`--agents` は「追加」ではなく「今回管理する対象の指定」として効くため、`--agents codex` だけで実行すると、直前に設定したClaude Codeが現在の管理状態 (state) から外れてしまいます。両方を1つのstateで並走させたい場合は、カンマ区切りでまとめて指定し直します。

```bash
ucode configure --workspaces https://<your-workspace>.cloud.databricks.com --agents claude,codex
```

`ucode status` で確認すると、両方が `Configured: yes` で並びます。

```
Coding Agent: Codex
  Configured: yes
  Base URL: https://<your-workspace>.cloud.databricks.com/ai-gateway/codex/v1

Coding Agent: Claude Code
  Configured: yes
  Base URL: https://<your-workspace>.cloud.databricks.com/ai-gateway/anthropic
```

別ベンダーの2エージェントが、それぞれ専用のGatewayエンドポイントに向いた状態で並んでいます。これが「使い分け × 一元管理」の構図そのものです。

# 使用量を可視化する

ここが本記事の山場です。`ucode usage` で、Gatewayに記録された消費を確認します。

```bash
ucode usage
```

```
✓ Databricks AI Gateway usage
Today: 169.5K tokens
Active tools: Claude Code, Codex
Top models this week: Claude Opus 4.8 (134.2K), GPT-5.5 (34.3K), Claude Haiku 4.5 (1.0K)
```

![Screenshot 2026-06-24 at 10.53.03.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/cc60cd37-70e4-4763-80e3-574110a4e522.png)

注目すべきは、AnthropicのOpus 4.8とOpenAIのGPT-5.5という別ベンダーのモデル消費が、同じ1つのサマリに並んでいることです。個別契約・個別請求の世界では、こうやってベンダーを横断して一望することはできません。これがGatewayに寄せることの最大の価値です。

ツール別の内訳も記録されます。Codexは2セッションでGPT-5.5を34.3K、Claude Codeは5セッションでOpus 4.8とHaiku 4.5を合わせて135.2Kトークン、というように、誰がどのツールでどのモデルをどれだけ使ったかがセッション数まで含めて見えます。ここにレート制限やグループ単位の権限を被せれば、管理者ガバナンスが完成します。

なお、消費の集計には反映ラグがあります。検証中、応答が返った直後の `ucode usage` では `Today: 0 tokens` でしたが、数分後に再実行したところ正しく数字が乗りました。リアルタイムではない点に注意してください。よりリッチに見たい場合は、AI GatewayページのView dashboardからツール別のグラフを確認できます。

# 干渉しない設計

既存環境への影響が気になるところですが、`ucode` が書き換えるのは対象エージェント専用の設定ファイルだけで、それ以外には手を出しません。検証後の `ucode status` でも、設定していないGemini CLIやOpenCodeなどは `Config file: missing` のままで、干渉していないことが確認できます。

`ucode` が管理するファイルは次のとおりで、上書き前にバックアップが取られます。

- Claude Code: `~/.claude/ucode-settings.json`
- Codex: `~/.codex/ucode.config.toml`

元に戻したくなったら `ucode revert` で、保存された状態をクリアしてバックアップした設定ファイルを復元できます。`--dry-run` で事前確認、`--agents` で対象を絞り込み、`revert` でいつでも復旧、という流れなら既存環境を壊さずに試せます。

# ここから先の発展

`ucode status` の出力には、さらに2つの拡張ポイントが顔を出しています。

1つはMCPです。`ucode configure mcp` で、Databricks Managed MCP (Vector Search、UC Functions、SQLウェアハウス、外部接続など) をMCP対応エージェントに登録できます。Claude Code経由でGenie SpaceやAI Searchのmanaged MCPを叩く、といった連携がここから派生できます。

もう1つはトレーシングです。`ucode configure tracing` で、コーディングセッション自体をMLflowエクスペリメントに記録できます。コーディングエージェントの利用をMLflowトレースとして残せるのは、LLMOpsの観点でも面白い使い方です。

# まとめ

`ucode` を使うことで、CodexとClaude Codeという別ベンダーのエージェントを、個別のAPIキー契約なしにDatabricks認証だけで使い分けられること、そして両方がGateway経由になることでベンダー横断のコスト可視化とレート制限の土台ができることを、実機で確認できました。

机上の説明ではなく、`Configured: yes` が2つ並んだ `ucode status` と、別ベンダーの消費が1枚に出た `ucode usage` という証跡が手元に残るのが、この検証の一番の収穫です。個人で複数のコーディングエージェントを使い分けている方はもちろん、組織でエージェントのガバナンスに頭を悩ませている方にとっても、有力な選択肢になりそうです。
