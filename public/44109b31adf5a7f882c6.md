# はじめに

Databricks のジョブに、AI 関数をそのまま実行できるタスクがベータで追加されました。ジョブ UI のタスクタイプに「ドキュメントインテリジェンス」という分類ができていて、次の 3 つが選べます。

- ドキュメントの解析 (`ai_parse_document`)
- 情報の抽出 (`ai_extract`)
- 分類 (`ai_classify`)

ドキュメントは次のページです。

- [ジョブの AI 関数タスク](https://docs.databricks.com/aws/ja/jobs/tasks/ai-functions/)
- [ドキュメント解析タスク](https://docs.databricks.com/aws/ja/jobs/tasks/ai-functions/document-parsing)
- [情報抽出タスク](https://docs.databricks.com/aws/ja/jobs/tasks/ai-functions/information-extraction)
- [分類タスク](https://docs.databricks.com/aws/ja/jobs/tasks/ai-functions/classification)

以前、[Genie Code にドキュメント処理パイプラインを作らせてみた](https://qiita.com/taka_yayoi/items/2d9a466694880bb22d82) という記事を書きました。そのとき Genie Code が作ったジョブは、`ai_parse_document` や `ai_extract` を呼ぶ SQL ファイルを SQL タスクで順に実行する形でした。今回のタスクでは、SQL を書かずに画面の設定だけで同じ処理をジョブに組み込めます。

素材は、前回の記事で作った架空の請求書 PDF を使いました。解析、抽出、分類の 3 タスクを組んで動かし、2 回目の実行で追加したファイルだけが処理されるところまで確かめたので、そのあたりも含めて書いていきます。

# AI 関数タスクとは

ボリューム内のファイルや、テーブルの各行に AI 関数を実行し、結果を Unity Catalog のテーブルに書き込むタスクです。

| ジョブ UI の名前 | 実行される関数 | 入力 |
| --- | --- | --- |
| ドキュメントの解析 | `ai_parse_document` | ボリューム、または `FILE` / `BINARY` 列 |
| 情報の抽出 | `ai_extract` | テキストまたは `VARIANT` の列 |
| 分類 | `ai_classify` | テキストまたは `VARIANT` の列 |

SQL で AI 関数を呼ぶ場合との一番の違いは、処理が増分になることです。ドキュメントには、各実行で前回以降に追加・変更された入力だけを処理し、削除された入力の結果は出力から削除されると書かれています。

もう一つの特徴は、AI 関数タスクを別の AI 関数タスクの後ろに置くと、前のタスクの出力テーブルの `response` 列が入力として自動で使われることです。解析の結果を抽出に渡すために、テーブル名を指定する必要はありません。

# 準備

## プレビューを有効にする

ワークスペースのプレビューページで「Lakeflow AI Function Task」をオンにします。

![Screenshot 2026-11-05 at 12.12.10.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/3efd2a5a-5c29-4f47-9844-08fdc1650bf3.png)

オンにすると、タスクタイプの一覧に「ドキュメントインテリジェンス」が出てきます。

![Screenshot 2026-11-06 at 17.05.27.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/e9768378-4205-46f8-b13e-ccfebd4fa0fa.png)

## 請求書 PDF をボリュームに置く

ジョブの入力にするボリュームを作ります。

```sql
CREATE SCHEMA IF NOT EXISTS takaakiyayoi_catalog.ai_task_demo;
CREATE VOLUME IF NOT EXISTS takaakiyayoi_catalog.ai_task_demo.invoices;
```

前回の記事で作った請求書 PDF (20 件) から、最初の実行用に 5 件だけコピーしました。残りは 2 回目の実行の前に追加します。

```python
src = "/Volumes/takaakiyayoi_catalog/genie_docproc/invoices"
dst = "/Volumes/takaakiyayoi_catalog/ai_task_demo/invoices"

# 最初の実行で処理する分。013 は複数ページ、017 は画像 PDF
first_batch = ["invoice_001.pdf", "invoice_002.pdf", "invoice_003.pdf",
               "invoice_013.pdf", "invoice_017.pdf"]

for f in first_batch:
    dbutils.fs.cp(f"{src}/{f}", f"{dst}/{f}")

display(dbutils.fs.ls(dst))
```

これで 5 件の PDF がボリュームに入ります。

ボリュームを入力にする場合、テーブルを入力にするときに必要なチェンジデータフィードや行トラッキングの設定は要りません。出力先のスキーマは実行前に存在している必要がありますが、上の SQL で作成済みです。

前回の記事のスキーマ `genie_docproc` には、Genie Code が作った `parsed_invoices` などのテーブルが残っています。タスクが作っていない同名のテーブルがあると実行が失敗するので、出力先は新しいスキーマに分けました。

# タスクを組む

## ドキュメントの解析

ジョブの「タスク」タブで「ドキュメントの解析」を選び、次のように設定します。

- タスク名: デフォルトの `parsing` のまま
- 入力: 「ボリューム」を選び、`/Volumes/takaakiyayoi_catalog/ai_task_demo/invoices/` を指定
- 出力: 「場所」に `takaakiyayoi_catalog.ai_task_demo` を指定。「テーブル名」は空欄
- 要素タイプを説明する: 「なし」

![Screenshot 2026-11-06 at 17.10.02.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/dd5374a2-4e6a-4da9-b979-957f85e3e06f.png)

「要素タイプを説明する」のデフォルトは「サポートされているすべての型」です。図の説明を生成する設定で、請求書には図がほとんどないので「なし」にしました。説明を生成しない分、コンピュートとコストを抑えられます。

テーブル名を空欄にすると、`parsed` で始まる名前が自動で付きます。ドキュメントによると、この名前は実行をまたいでも変わりません。

## 情報の抽出

解析タスクの後ろに「情報の抽出」を追加すると、「Input」欄に「「parsing」の出力を使用」と入った状態で開きます。前のタスクの出力テーブルの `response` 列が、自動で入力になっているということです。

![Screenshot 2026-11-06 at 17.10.52.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/bbca2dd3-bc55-491c-ae42-7dce8344f133.png)

スキーマのフィールドを入れる方法は 3 つあります。

- 「フィールドを追加」から 1 つずつ入力する
- 「Genie Code で定義」で、入力をもとに下書きを作らせる
- 「エージェントからインポート」で、Agent Bricks の情報抽出エージェントからコピーする

「UI」と「JSON」の切り替えもあり、JSON で直接編集することもできます。今回は次の 4 つのフィールドを定義しました。

| フィールド | タイプ |
| --- | --- |
| `invoice_id` | string |
| `issue_date` | string |
| `vendor_name` | string |
| `total_amount` | number |

![Screenshot 2026-11-06 at 17.12.11.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/04fbf00a-8b23-4e09-84ff-e3abc4bf4d0a.png)

オプション設定では「信頼度スコア」と「引用」をオンにしました。「バージョン」には `2.1` と表示されています。ドキュメントによると、実行される `ai_extract` のバージョンはピン留めされるので、関数が更新されてもスケジュール実行の結果は変わりません。

![Screenshot 2026-11-06 at 17.13.29.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/5f25c5e9-31b9-419a-9178-f53253e1f530.png)

「依存先」には `parsing` が入っています。

## 分類

分類も解析の結果を入力にしたかったので、抽出の後ろではなく、解析の後ろに追加しました。ドキュメントの例は「解析 → 抽出」の 1 本道ですが、ここでは解析から抽出と分類の 2 本に分かれる形にしています。

抽出の後ろに追加すると、分類に渡るのは抽出結果 (請求書番号や金額) になります。請求書の本文を分類したい場合は、依存先を `parsing` にします。こちらも「Input」には「「parsing」の出力を使用」と入りました。

ラベルは「ソフトウェア」「ハードウェア」「業務委託」「other」の 4 つにしました。タスクで使えるラベルは 2 〜 10 個です。どれにも当てはまらない入力の受け皿として、`other` のようなラベルを入れておくようドキュメントで案内されています。

![Screenshot 2026-11-06 at 17.19.36.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/5be7f2fd-cfd0-467a-8018-acec28919542.png)

# 実行する

## 下流のタスクは解析が終わるまで待つ

「今すぐ実行」で実行すると、`parsing` が動いている間、`extraction` と `classification` は「保留中」で待ちます。

![Screenshot 2026-11-06 at 17.20.00.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/a41b0c85-eb22-459c-862e-5372a10dad83.png)

今回の環境では、5 件の解析に 3 分ほどかかりました。処理時間は環境やそのときの混み具合で変わります。

## 実行結果とサンプルデータ

タスクをクリックすると、タスクの実行ページが開きます。「行」「成功」「不成功」の件数と、入力のボリューム、出力のテーブルが表示されます。1 回目は 5 行がすべて成功しました。

実行が終わると、同じページの下に「サンプルデータ」として出力テーブルの行が表示されます。列は `id`、`response`、`error` の 3 つです。

![Screenshot 2026-11-06 at 17.41.41.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/1724faa4-d9ad-4344-bb1e-16e3ff5041fe.png)

`id` は `dbfs:/Volumes/...` の形で、ファイルの URI が入ります。ボリュームのパス (`/Volumes/...`) とは書き方が違うので、他のテーブルと結合するときは注意が必要です。

# 抽出結果を取り出す

## response の中身

抽出タスクの出力テーブルをクエリして、結果の `response` 列を展開してみました。`response` 列は `VARIANT` 型で、中は次の 3 つに分かれています。

- `error_message`: 入力ごとのエラー。成功時は `null`
- `metadata`: 引用元の位置 (`citations` の `bbox` とページ)、`ai_extract` のバージョン
- `response`: 抽出した値。フィールドごとに `value`、`confidence_score`、`citation_ids` が入る

![Screenshot 2026-11-06 at 18.04.47.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/a1055a6d-fe6b-44e6-a402-73b17247c7b6.png)

`invoice_001.pdf` では、`invoice_id` の値が `INV-2026-01007`、`confidence_score` が 1 でした。`citation_ids` の番号は、`metadata` の `citations` の `id` に対応しています。どのフィールドを PDF のどの位置から読み取ったかを、この番号でたどれます。

## SQL で列にする

タスクは値ごとに列を作らないので、使うときはクエリで `response` から取り出します。列名の `response` の中に、さらに `response` というキーがある点に注意してください。

```sql
-- 出力テーブル名は自動で付くので、先に確認する
SHOW TABLES IN takaakiyayoi_catalog.ai_task_demo;
```

3 つのタスクの出力テーブルが、それぞれ `parsed`、`extracted`、`classified` で始まる名前で作られていました。

![Screenshot 2026-11-06 at 17.54.11.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/39269bf2-bf8f-4d90-99ff-cc0f124dc51d.png)

```sql
SELECT
  id,
  -- 列 response の中の response キーに、フィールドごとの結果が入っている
  response:response.invoice_id.value::string    AS invoice_id,
  response:response.issue_date.value::string    AS issue_date,
  response:response.vendor_name.value::string   AS vendor_name,
  response:response.total_amount.value::double  AS total_amount,
  -- 信頼度スコアをオンにしたときだけ入る
  response:response.total_amount.confidence_score::double AS total_amount_confidence
FROM takaakiyayoi_catalog.ai_task_demo.<extracted で始まるテーブル名>;
```

これで、請求書ごとに抽出した値が列として並びます。1 回目の 5 件では、`total_amount` の信頼度スコアはすべて 1 でした。

![Screenshot 2026-11-06 at 17.54.44.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/410bc17e-bcd4-461e-8ee8-90b901aafff7.png)

# 追加したファイルだけが処理される

残りの 15 件をボリュームに追加して、もう一度実行しました。

```python
src = "/Volumes/takaakiyayoi_catalog/genie_docproc/invoices"
dst = "/Volumes/takaakiyayoi_catalog/ai_task_demo/invoices"

# 1 回目にコピーしていないファイルだけを追加する
done = {f.name for f in dbutils.fs.ls(dst)}
for f in dbutils.fs.ls(src):
    if f.name.endswith(".pdf") and f.name not in done:
        dbutils.fs.cp(f.path, f"{dst}/{f.name}")
```

ボリュームには 20 件の PDF がありますが、2 回目の実行の「行」は 15 でした。1 回目に処理した 5 件は対象から外れ、追加した 15 件だけが処理されています。

![Screenshot 2026-11-06 at 17.45.56.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/73f2358b-cfbf-4037-8e06-12b36dd1d6b8.png)

SQL タスクで `CREATE OR REPLACE TABLE` を使う作り方では、実行のたびに全件を処理し直します。AI 関数はファイル 1 件ごとにコストがかかるので、新しく届いた請求書だけを処理できるのは、定期実行するジョブでは効いてきます。

ただし、抽出フィールドやラベルを後から変えても、変更が適用されるのは追加・変更された入力だけです。既存の入力すべてに適用したい場合は、新しいテーブル名を指定する必要があります。

2 回目の実行が終わった後に、前の節と同じ SQL を流しました。1 回目の 5 件と、追加した 15 件の合わせて 20 件が返ってきます。

![Screenshot 2026-11-06 at 17.58.28.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/1903b95f-77b8-45db-ad9a-90565fd830ff.png)

`total_amount` の信頼度スコアは、`invoice_011.pdf` だけが 0.95 で、残りの 19 件は 1 でした。

`issue_date` は、`invoice_019.pdf` が `July 30, 2026`、`invoice_020.pdf` が `7 Aug 2026` でした。この 2 件は、前回の記事で日付の書式を変えて作った請求書です。`issue_date` は型を string にして、書式の指示を何も書いていなかったので、PDF に印字された書式のまま取り出されています。書式を揃えたい場合は、オプション設定の「指示」に書式を書くことになります。今回は試していません。その場合も、既存の 20 件に反映するには新しいテーブル名を指定する必要があります。

# まとめ

ジョブの AI 関数タスクで、請求書 PDF の解析、抽出、分類を組んでみて分かったことをまとめます。

- プレビューの「Lakeflow AI Function Task」をオンにすると、タスクタイプに「ドキュメントインテリジェンス」が出る。解析、抽出、分類の 3 つ
- **AI 関数タスクを別の AI 関数タスクの後ろに置くと、前のタスクの出力が自動で入力になる。テーブル名の指定は要らない**
- 依存先を変えれば、解析の結果を抽出と分類の両方に渡す形も組める
- 出力テーブルは `id`、`response`、`error` の 3 列。値は `response` 列の中にあり、SQL で取り出す
- 抽出結果には、フィールドごとに値、信頼度スコア、引用元の番号が入る
- 日付を string で定義して書式を指示しないと、PDF に印字された書式のまま取り出される
- **2 回目の実行では、追加したファイルだけが処理される**
- 出力テーブルの `id` は `dbfs:/Volumes/...` の形で、ボリュームのパスとは書き方が違う

一番の収穫は、SQL を書かずに増分処理のジョブが作れると分かったことでした。前回 Genie Code が作ったジョブは、実行のたびに全件を処理し直す形でした。今回は画面の設定だけで、新しく届いたファイルだけを処理するジョブになります。まずは数件で組んで `response` の中身を確かめてから、件数を増やすのがよさそうです。
