すべての企業には地理空間情報があります。テレコム企業はタワーの位置を追跡します。小売業では店舗の所在をマッピングします。物流ネットワークは、現実世界の地理情報に沿ってルーティングします。しかし、ビジネスユーザーがシンプルな位置情報の質問をした際 - *このリージョンのどのサイトが最も高い利益を生み出しているのか？* - 回答を得るためには、ほとんど常にエンジニアとたくさんのSQLクエリーを必要とし、数時間の時間を要することになります。

このギャップはストレージやコンピュートにあるのではありません。Databricksが両方に対応します。ギャップはラストマイルに存在します: 位置情報の質問を位置情報クエリーに変換する部分です。

# 現在の位置情報SQLの問題

ターゲットのリージョンでパフォーマンスの出ていない店舗がどれかを知りたがっている小売のプランナーを考えてみましょう。現在ではそのような質問には以下が必要です:

- テーブルスキーマ、カラム名、座標を保持しているカラムの理解
- ST_IntersectsやST_GeomFromWKTのような位置情報関数を用いたSQLの記述
- 興味のある領域を定義するためにWKTジオメトリ文字列を手動で組み立て
- 適切な領域に絞り込むための複数のクエリーを通じたイテレーション

エンジニアにとってこれは面倒なことです。ビジネスユーザーにとっては壁となります。結果として、ほとんどの地理空間データが活用されないことになります - プラットフォームが対応できないためではなく、インタフェースが過度な専門性を必要とするからです。

# GeoGenieを召喚: 領域を描き、質問を行い、回答を得る

**[GeoGenie](https://github.com/databricks-solutions/genie-geo-chat)** は、この摩擦を削減するために[**DatabricksのGenieスペース**](https://docs.databricks.com/aws/ja/genie) と[**Databricks Apps**](https://docs.databricks.com/aws/ja/dev-tools/databricks-apps/) をどのように組み合わせるのかを示す、オープンソースのリファレンスアプリケーションです。このワークフローには3つのステップが存在します:

1. ビーコンとしてプロットされるサイトと3Dのインタラクティブな地球を**探索**します。名前、テナント、収益、都市、画像など詳細を調査するために任意のサイトをクリックします。
1. 興味のある領域を定義するために地図上に直接ポリゴンや長方形を**描画**します。
1. 簡素な英語で**質問**します。GeoGenieが残りの面倒を見ます。

背後では、ユーザーが形状を描画した際、GeoGenieはポリゴン座標をWKTに変換し、**Databricks Genie**に送信するプロンプトにジオメトリを追記します。Genieはすでに組み込まれている位置情報フィルターを含むSQLを生成します:

```sql
WITH ranked_sites AS (
  SELECT *,
    RANK() OVER (ORDER BY total_monthly_revenue DESC) AS revenue_rank
  FROM catalog.geogenie.site_locations
  WHERE ST_Intersects(
    ST_GeomFromWKT('POLYGON((-102.3 26.8, -95.2 26.8, -95.2 31.4, -102.3 31.4, -102.3 26.8))'),
    ST_Point(longitude, latitude)
  )
)
SELECT site_name, city, state, tenant_name, total_monthly_revenue
FROM ranked_sites
WHERE revenue_rank <= 5
ORDER BY total_monthly_revenue DESC;
```

この**Genieスペース**は、すでに位置情報クエリーの指示で事前に設定されているので、生成されるSQLは一貫性を持ってST_Intersectsを使用し、はじめにST_Pointで経度を含むポイントを構成し、自動的に位置情報の述語として描画された領域を適用します。ユーザーは質問にフォーカスできます。GeoGenieは位置情報のコンテキストとクエリー生成に対応します。

# 動作原理

![MohanaBasak_0-1773851159799.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/e3b758b5-b53a-4659-ba58-a0dd8a46f3fb.png)

GeoGenieはDatabricksプラットフォームの4つの機能を単一の体験に組み合わせます:

| レイヤー | テクノロジー |
|:--|:--|
|フロントエンド   | [CesiumJS](https://cesium.com/cesiumjs/) 3D globe + Streamlit  |
|AI / text-to-SQL   |  Databricks Genieスペース |
| データガバナンス  |  Unity Catalog + SQLウェアハウス |
| アプリプラットフォーム  | Databricks Apps  |

Cesium globeは、StreamlitのカスタムコンポーネントAPIを通じてレンダリングされるiframe内で稼働し、window.postMessageを通じてPythonバックエンドと通信します。これによって、GeoGenieはリッチなJavaScriptの地理空間UIとシンプルなStreamlitアプリケーションロジックを組み合わせることができます - すべては、サービスプリンシパルとDatabricks Appsを通じてデプロイ、認証されます。

セットアップは単一のノートブックで行われます。[リポジトリ](https://github.com/databricks-solutions/genie-geo-chat)をクローンし、setup_and_deployを実行すると、ノートブックがすべての配備します: Unity Catalogオブジェクト、合成サンプルデータ、位置情報指示を含む設定済みGenieスペース、適切な権限を持つアプリがデプロイされます。セットアップ後は、アプリは皆様のチームで共有可能な状態になります。

# 三つの願い: これは何を解放するのか？

Genieがクエリーを生成する際にGeoGenieがマップにインタラクティブにアプローチする方法は、3つの主要な理由から重要なものとなります:

**新たなペルソナが位置情報分析にアクセス可能に。** ST_Intersectsを書くことができないビジネスアナリストが、領域を描画して質問できるようになります。障壁は「位置情報SQLを知っている」から「地図をポイントできる」まで引き下げられます。

**デフォルトでのガバナンス。** すべてのクエリーはUnity Catalogを通じて実行されます。ビジネスユーザーは直接のテーブルアクセスを許可してもらうことなしに、位置情報に関する回答を得ることになります。Genieスペースはどのテーブル、どのカラムが公開されるのかをコントロールします。これは、ガバナンスのショートカットではありません - 使いやすくしたガバナンスです。

**単なるデモではなくパターン。** ビジュアルなインタラクションレイヤー、自然言語のインタフェース、ガバナンスの効いたデータからなるこのアーキテクチャは再利用可能です。テレコムネットワークの計画、小売サイトのインテリジェンス、物流カバレッジ分析、フィールドアセット管理: 位置情報がデータのファーストクラス次元であるすべてのドメインはこのパターンに従うことができます。
