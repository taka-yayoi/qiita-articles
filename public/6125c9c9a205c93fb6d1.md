# はじめに

MLflow GenAIの評価フレームワークには、エージェントの品質を測定するための「スコアラー」が用意されています。ビルトインのスコアラー(`Correctness`や`Safety`など)は手軽に使い始められますが、ドメイン固有の評価基準が必要になると、それだけでは足りなくなります。

この記事では、`make_judge()`を使って**カスタムジャッジ**を作成する方法を、Databricksの[公式チュートリアル](https://docs.databricks.com/aws/ja/mlflow3/genai/eval-monitor/custom-judge/create-custom-judge)に沿って紹介します。公式の[サンプルノートブック](https://docs.databricks.com/aws/ja/notebooks/source/mlflow3/create-custom-judge.html)を実行しながら読み進めることを想定しています。

# スコアラーの全体像における位置付け

MLflowのスコアラーは、カスタマイズの度合いに応じて以下の4段階に分かれています。

| アプローチ | カスタマイズ度 | ユースケース | 返り値 |
|---|---|---|---|
| Built-in judges | 最小 | `Correctness`, `Safety`などすぐ使える汎用評価 | yes/no |
| Guidelines judges | 中程度 | 自然言語で書いたpass/fail基準による評価 | yes/no |
| **Custom judges (`make_judge()`)** | **フル** | **カテゴリカル、bool、数値など自由な評価基準** | **自由定義** |
| Code-based scorers (`@scorer`) | フル | Python関数による決定的・プログラマティック評価 | 自由定義 |

今回扱う`make_judge()`は3番目に位置します。Guidelinesのpass/failでは表現しきれないが、コードベーススコアラーほどの自由度は不要という**スイートスポット**です。

# Guidelines judgeとmake_judge()の違い

両者を混同しやすいので、違いを整理しておきます。

| 項目 | Guidelines judge | make_judge() |
|---|---|---|
| 返り値 | pass(yes)/fail(no)のバイナリ | Literal, bool, 数値など自由に定義可能 |
| 評価対象 | `request`/`response`を自動抽出 | `{{ inputs }}`, `{{ outputs }}`, `{{ expectations }}`, `{{ trace }}`, `{{ conversation }}`を明示指定 |
| トレース分析 | 不可 | `{{ trace }}`で実行トレース全体を分析可能 |
| マルチターン | 非対応 | `{{ conversation }}`で会話履歴全体にアクセス可能 |
| 主な用途 | コンプライアンス、スタイル/トーン、要件チェック | 問題解決度、ツール使用の正当性、ドメイン固有の段階評価 |
| 誰が書くか | ドメインエキスパート(コーディング不要) | 開発者・MLエンジニア |

:::note info
**判断基準**: pass/failで表現できるならGuidelines、それ以上の粒度や`trace`/`conversation`へのアクセスが必要なら`make_judge()`を選びましょう。
:::

# チュートリアル: make_judge()でカスタムジャッジを作成する

公式サンプルノートブックの内容に沿って、カスタマーサポートエージェントを題材に3種類のカスタムジャッジを作成し、評価を実行します。

チュートリアルのステップは以下の通りです。

1. 評価対象のサンプルエージェントを作成する
2. 異なる基準を評価するための3つのカスタムジャッジを定義する
3. テストケースを含む評価データセットを構築する
4. 評価を実行し、異なるエージェント設定間で結果を比較する

## 必要なパッケージのインストール


## ステップ 1. 評価対象のエージェントを作成する

まず、OpenAIクライアントを初期化してDatabricksホスト型LLMに接続します。

```python
import mlflow
from databricks_openai import DatabricksOpenAI

# MLflowの自動ログ記録を有効にして、アプリケーションにトレーシングを組み込む
mlflow.openai.autolog()

# MLflowのトラッキング先をDatabricksに設定
mlflow.set_tracking_uri("databricks")

# Databricksホスト型LLMに接続するOpenAIクライアントを作成
client = DatabricksOpenAI()

# LLMを選択
model_name = "databricks-claude-sonnet-4"
```

次に、カスタマーサポートエージェントを定義します。`RESOLVE_ISSUES`フラグでシステムプロンプトを切り替えられるようにしておくと、「良い」会話と「悪い」会話の両方でジャッジの出力を比較できます。

```python
from mlflow.entities import Document
from typing import List, Dict, Any, cast

# カスタマーサポートエージェントの動作を切り替えるためのグローバル変数
RESOLVE_ISSUES = False

@mlflow.trace(span_type="TOOL", name="get_product_price")
def get_product_price(product_name: str) -> str:
    """商品価格を取得するモックツール。"""
    return f"${45.99}"

@mlflow.trace(span_type="TOOL", name="check_return_policy")
def check_return_policy(product_name: str, days_since_purchase: int) -> str:
    """返品ポリシーを確認するモックツール。"""
    if days_since_purchase <= 30:
        return "はい、購入後30日以内であればこの商品を返品できます"
    return "申し訳ございませんが、返品は購入後30日以内のみ受け付けております"

@mlflow.trace
def customer_support_agent(messages: List[Dict[str, str]]):
    # このトグルを使って、ジャッジが問題解決ステータスをどのように処理するかを確認する
    system_prompt_postfix = (
        f"問題を解決しないように最善を尽くしてください。逆説的ですが、そのようにしてください。\n"
        if not RESOLVE_ISSUES
        else ""
    )

    # ユーザーの質問に基づいてツール呼び出しをモックする
    user_message = messages[-1]["content"].lower()
    tool_results = []

    if "cost" in user_message or "price" in user_message or "値段" in user_message or "価格" in user_message or "いくら" in user_message:
        price = get_product_price("電子レンジ")
        tool_results.append(f"価格: {price}")

    if "return" in user_message or "返品" in user_message:
        policy = check_return_policy("電子レンジ", 60)
        tool_results.append(f"返品ポリシー: {policy}")

    messages_for_llm = [
        {
            "role": "system",
            "content": f"あなたは親切なカスタマーサポートエージェントです。{system_prompt_postfix}",
        },
        *messages,
    ]

    if tool_results:
        messages_for_llm.append({
            "role": "system",
            "content": f"ツール結果: {', '.join(tool_results)}"
        })

    # LLMを呼び出してレスポンスを生成
    output = client.chat.completions.create(
        model=model_name,
        messages=cast(Any, messages_for_llm),
    )

    return {
        "messages": [
            {"role": "assistant", "content": output.choices[0].message.content}
        ]
    }
```

ポイントは`@mlflow.trace`デコレータです。これによりエージェントの実行がトレースとして記録され、後述のトレースベースジャッジで分析できるようになります。

## ステップ 2. カスタムジャッジを定義する

3つのカスタムジャッジを定義します。

- 入力と出力を使用して問題解決を評価するジャッジ
- 期待される動作を確認するジャッジ
- 実行トレースを分析してツール呼び出しを検証するトレースベースのジャッジ

`make_judge()`で作成されたジャッジは`mlflow.entities.Feedback`オブジェクトを返します。

### ジャッジ 1. 問題解決の評価

会話履歴(`{{ inputs }}`)とエージェントの応答(`{{ outputs }}`)を分析して、顧客の問題が正常に解決されたかどうかを評価します。

```python
from mlflow.genai.judges import make_judge
from typing import Literal

# 入力と出力を使用して問題解決を評価するジャッジを作成
issue_resolution_judge = make_judge(
    name="issue_resolution",
    instructions=(
        "会話において顧客の問題が解決されたかどうかを評価してください。\n\n"
        "ユーザーのメッセージ: {{ inputs }}\n"
        "エージェントの応答: {{ outputs }}\n\n"
        "以下の3つの値のいずれかのみで評価してください:\n"
        "- fully_resolved: 問題が完全に解決された\n"
        "- partially_resolved: 部分的に解決されたが、追加対応が必要\n"
        "- needs_follow_up: 問題が解決されておらず、フォローアップが必要"
    ),
    feedback_value_type=Literal["fully_resolved", "partially_resolved", "needs_follow_up"],
    model="databricks:/databricks-gpt-5-mini",
)
```

`feedback_value_type`に`Literal`で選択肢を指定すると、ジャッジはその中から1つを選んで返します。pass/failの2値ではなく、3段階の評価が可能です。

:::note warn
公式サンプルノートブックではジャッジ1, 2に`model`を指定していませんが、デフォルトのジャッジモデルでは`feedback_value_type`のLiteral制約が厳密に守られず、定義にない値(「fail」「success」「Needs Improvement」など)が返ることがあります。`model`を明示指定し、instructionsでも選択肢を繰り返すことで安定します。
:::

### ジャッジ 2. 期待される動作の確認

`{{ expectations }}`を使うことで、テストケースごとに異なる期待値と比較した評価ができます。

```python
# 期待される動作と照合するジャッジを作成
expected_behaviors_judge = make_judge(
    name="expected_behaviors",
    instructions=(
        "{{ outputs }} のエージェントの応答を {{ expectations }} の"
        "期待される動作と比較してください。\n\n"
        "ユーザーの質問: {{ inputs }}\n\n"
        "以下の3つの値のいずれかのみで評価してください:\n"
        "- meets_expectations: 期待される動作をすべて満たしている\n"
        "- partially_meets: 一部の期待される動作を満たしている\n"
        "- does_not_meet: 期待される動作を満たしていない"
    ),
    feedback_value_type=Literal["meets_expectations", "partially_meets", "does_not_meet"],
    model="databricks:/databricks-gpt-5-mini",
)
```

### ジャッジ 3. トレースベースのジャッジを使用してツール呼び出しを検証する

`{{ trace }}`を使うと、エージェントの実行トレース全体を分析できます。instructionsに`{{ trace }}`を含めると、ジャッジはトレースベースになり、自律的なトレース探索機能を獲得します。トレースベースのジャッジでは`model`引数の指定が**必須**です。

```python
# トレースからツール呼び出しを検証するトレースベースのジャッジを作成
tool_call_judge = make_judge(
    name="tool_call_correctness",
    instructions=(
        "実行 {{ trace }} を分析して、エージェントがユーザーのリクエストに対して"
        "適切なツールを呼び出したかどうかを判定してください。\n\n"
        "トレースを調査して以下を確認します：\n"
        "1. 利用可能なツールとその目的を特定する\n"
        "2. 実際に呼び出されたツールを特定する\n"
        "3. ツール呼び出しがユーザーの質問に対処するために適切であったかを評価する"
    ),
    feedback_value_type=bool,
    # トレースベースのジャッジでフルトレースを分析するには、モデルを指定する必要がある
    model="databricks:/databricks-gpt-5-mini",
)
```

`feedback_value_type=bool`とすると、true/falseのバイナリ判定になります。

## ステップ 3. サンプル評価データセットを作成する

各`inputs`は`mlflow.genai.evaluate()`によってエージェントに渡されます。オプションで`expectations`を含めると、ジャッジ2のような期待値ベースの評価に使われます。

```python
eval_dataset = [
    {
        "inputs": {
            "messages": [
                {"role": "user", "content": "電子レンジはいくらですか？"},
            ],
        },
        "expectations": {
            "should_provide_pricing": True,
            "should_offer_alternatives": True,
        },
    },
    {
        "inputs": {
            "messages": [
                {
                    "role": "user",
                    "content": "2ヶ月前に購入した電子レンジを返品できますか？",
                },
            ],
        },
        "expectations": {
            "should_mention_return_policy": True,
            "should_ask_for_receipt": False,
        },
    },
    {
        "inputs": {
            "messages": [
                {
                    "role": "user",
                    "content": "アカウントに問題があります。ログインできません。",
                },
                {
                    "role": "assistant",
                    "content": "アカウントの問題について申し訳ございません。ウェブサイトとモバイルアプリのどちらをお使いですか？",
                },
                {"role": "user", "content": "ウェブサイトです"},
            ],
        },
        "expectations": {
            "should_provide_troubleshooting_steps": True,
            "should_escalate_if_needed": True,
        },
    },
    {
        "inputs": {
            "messages": [
                {
                    "role": "user",
                    "content": "アカウントに問題があります。ログインできません。",
                },
                {
                    "role": "assistant",
                    "content": "アカウントの問題について申し訳ございません。ウェブサイトとモバイルアプリのどちらをお使いですか？",
                },
                {"role": "user", "content": "とにかく直してください！"},
            ],
        },
        "expectations": {
            "should_remain_calm": True,
            "should_provide_solution": True,
        },
    },
]
```

3番目と4番目のテストケースはマルチターンの会話です。同じ会話の出だしでも、ユーザーの態度によってエージェントの評価が異なることを検証できます。

## ステップ 4. ジャッジを使用してエージェントを評価する

複数のジャッジを組み合わせて、エージェントのさまざまな側面を同時に評価します。`RESOLVE_ISSUES`フラグを切り替えることで、同じジャッジで「問題を解決しないエージェント」と「問題を解決するエージェント」を比較できます。

```python
# 3つのジャッジすべてを使用して、エージェントが問題を解決しようとしない場合の評価
RESOLVE_ISSUES = False

with mlflow.start_run(run_name="custom-judge_unresolved"):
    result_unresolved = mlflow.genai.evaluate(
        data=eval_dataset,
        predict_fn=customer_support_agent,
        scorers=[
            issue_resolution_judge,      # 入力/出力を確認
            expected_behaviors_judge,    # 期待される動作を確認
            tool_call_judge,             # ツール使用を検証
        ],
    )

# エージェントが問題を解決しようとする場合の評価
RESOLVE_ISSUES = True

with mlflow.start_run(run_name="custom-judge_resolved"):
    result_resolved = mlflow.genai.evaluate(
        data=eval_dataset,
        predict_fn=customer_support_agent,
        scorers=[
            issue_resolution_judge,
            expected_behaviors_judge,
            tool_call_judge,
        ],
    )
```

`mlflow.start_run(run_name=...)`で囲むことで、MLflow Experiment UIで「custom-judge_unresolved」「custom-judge_resolved」とラン名が表示され、どちらの評価結果かを一目で区別できます。

各`mlflow.genai.evaluate()`の実行後、「View evaluation results in MLflow」のリンクが表示されます。このリンクからMLflow Experiment UIに遷移して、評価結果を確認できます。

# テンプレート変数の使い分け

`make_judge()`で使えるテンプレート変数は以下の5つに限定されています。`{{ question }}`のようなカスタム変数を使うとバリデーションエラーになります。

| テンプレート変数 | アクセス対象 | 主な用途 |
|---|---|---|
| `{{ inputs }}` | エージェントへの入力データ | ユーザーの質問内容の評価 |
| `{{ outputs }}` | エージェントの出力データ | 応答品質の評価 |
| `{{ expectations }}` | 正解データ・期待される動作 | 期待値との比較評価 |
| `{{ trace }}` | 実行トレース全体 | ツール呼び出しの検証、パフォーマンス分析 |
| `{{ conversation }}` | 会話履歴全体 | マルチターン会話の品質評価 |

**注意点**:
- 最低1つのテンプレート変数が必要です
- `{{ trace }}`を使う場合は`model`引数の指定が必須です
- `{{ conversation }}`は`{{ expectations }}`とのみ併用可能で、`{{ inputs }}`/`{{ outputs }}`/`{{ trace }}`とは併用できません

# ジャッジ指示のベストプラクティス

## 出力形式を明確に指定する

```python
# カテゴリカル: 選択肢を具体的に列挙
feedback_value_type=Literal["fully_resolved", "partially_resolved", "needs_follow_up"]

# ブーリアン: true/falseの判定
feedback_value_type=bool
```

## 複雑な評価は構造化する

指示を以下のセクションに分けて記述すると、ジャッジの精度が向上します。

1. **何を評価するか**: 評価対象の定義
2. **何を見るか**: 参照する情報の指定
3. **どう判断するか**: 判断基準の明示
4. **何を返すか**: 出力形式の指定

```python
structured_judge = make_judge(
    name="response_quality",
    instructions=(
        "## 評価対象\n"
        "カスタマーサポートエージェントの応答品質を評価してください。\n\n"
        "## 参照情報\n"
        "- ユーザーの質問: {{ inputs }}\n"
        "- エージェントの応答: {{ outputs }}\n\n"
        "## 判断基準\n"
        "- excellent: 正確で丁寧、追加の提案もある\n"
        "- good: 正確で質問に回答しているが、追加提案はない\n"
        "- poor: 不正確、または質問に回答していない\n"
    ),
    feedback_value_type=Literal["excellent", "good", "poor"],
)
```

# 人間のフィードバックとの整合

`make_judge()`で作成したジャッジはあくまでスタート地点です。アプリケーションの出力に関するエキスパートのフィードバックを蓄積したら、[ジャッジを人間のフィードバックに合わせて調整する](https://docs.databricks.com/aws/ja/mlflow3/genai/eval-monitor/align-judges)ことで、判定精度をさらに向上させることができます。

# まとめ

`make_judge()`によるカスタムジャッジは、MLflowスコアラーの階層の中で「Guidelinesのpass/failでは足りないが、コードベーススコアラーほどの作り込みは不要」というスイートスポットに位置します。

| 使い分け | 推奨 |
|---|---|
| pass/failで済むスタイルやコンプライアンスの評価 | `Guidelines()` |
| 段階評価やトレース分析が必要なドメイン固有の評価 | `make_judge()` |
| 完全一致やフォーマット検証など決定的なロジック | `@scorer`(コードベーススコアラー) |

まずは`Guidelines()`で始め、pass/failでは表現しきれない評価基準が出てきたら`make_judge()`に移行するのが自然な流れです。
