# 出発点は、1つのプロバイダーだけに頼ることへの懸念

コーディングエージェントを1つだけ使っていても、たいていの作業はこなせます。小さな修正や調べものなら、それで十分です。

それでも複数のプロバイダーのモデルを使いたくなる理由は、大きく分けて2つあります。

## 品質の懸念

同じモデルにコードを書かせて、同じモデルにレビューさせると、見落としに気づきにくくなります。レビューするモデルが、自分の出した答えを前提にして読んでしまうためです。

別のベンダーのモデルにレビューさせると、書いたモデルとは違う観点でコードを読むことになります。実装とレビューを別のモデルに分けたい、という動機はここから来ています。

## 依存の懸念

1つのプロバイダーだけに頼っていると、そのプロバイダー側の変化の影響をそのまま受けます。

- 障害が起きると、作業が止まる
- 料金や利用条件が変わると、そのまま従うしかない
- 別のモデルのほうが得意な作業が出てきても、乗り換えにくい

![fig1_concerns.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/562aa199-6c26-4877-814f-b4b6bf95f971.png)

どちらの懸念から出発しても、行き着く先は同じです。複数のプロバイダーのモデルを組み合わせて使う、という形になります。Databricksのブログでも、最良の結果はもはや1つのハーネス上の1つのモデルからは生まれない、と書かれています。

# モデルを替えるだけなら、ハーネスの中でできる

ここで「ハーネス」という言葉を確認しておきます。ハーネスは、モデルに指示を渡し、モデルが呼び出したツールを実行し、その結果をまたモデルに返す、という繰り返しを回す仕組みです。Claude CodeやCodexはハーネスです。

ハーネスによっては、設定でモデルを切り替えられます。以前の記事で試したopencodeもその1つで、Databricks Model ServingのClaudeをモデルとして使えました。

- [ローカルのopencodeからDatabricks Model ServingのClaudeを使ってみた](https://qiita.com/taka_yayoi/items/df2ffb0d09cbd676c7da)

![fig2_harness_models.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/9a2205c6-dd5c-4c93-8c8f-eaa41c40e3bc.png)

つまり、モデルを差し替えるだけなら、ハーネスの中で済みます。ハーネスという仕組みが、モデルを差し替え可能にしたと言えます。

# それでも各社のハーネスを並べて使う

ところが実際には、Claude CodeとCodexを両方開いて、並べて使っている人が少なくありません。

各社のハーネスは、自社のモデルと一緒に開発されています。そのモデルの力を一番引き出せるのは、そのモデルに合わせて作られたハーネスで使うときだ、というのが筆者の見方です。Claudeを使うならClaude Codeで、OpenAIのモデルを使うならCodexで、という選び方になります。

その結果、複数のモデルを組み合わせようとすると、ハーネスを並べて使うことになります。

![fig3_side_by_side.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/91c68bf1-a5eb-41ee-8eb7-bc2e869831f0.png)


# ハーネスの間には境目がある

ハーネスを並べると、その間に境目ができます。Databricksのブログでは、ハーネスごとに操作方法が違うので、組み合わせたり入れ替えたりするのが難しい、と説明されています。

境目では、人が次の4つの作業を手でやっています。

1. 出力の受け渡し
2. コンテキストの説明し直し
3. 権限とガードレールの設定し直し
4. チームへの結果の共有

4つの作業を1枚の図にまとめると、次のようになります。

![fig4_seams.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/1f224a2e-6fcb-4afb-a14f-8a183650e2b2.png)

ハーネスが2つで作業が少ないうちは、これでも回ります。ハーネスが増え、並行する作業が増えるほど、人の手作業が増えていきます。

ここから1つずつ見ていきます。

## 作業1: 出力の受け渡し

Claude Codeが書いたコードの差分をコピーして、Codexに貼ってレビューを頼みます。レビューの指摘をまたコピーして、Claude Codeに戻します。1本目の記事では、このときの人の役回りを「エージェント間の伝言役」と書きました。

![task1_handoff.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/d23534e1-7978-4d1d-a75f-024c666a2f59.png)

## 作業2: コンテキストの説明し直し

ハーネスごとにセッションが分かれているので、片方で説明した前提は、もう片方には伝わっていません。プロジェクトの方針や、どこまで作業が進んだかを、ハーネスを替えるたびに説明し直すことになります。

![task2_context.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/229c9359-3848-4986-8f00-0e0e83e6fe71.png)

## 作業3: 権限とガードレールの設定し直し

どのコマンドの実行を許すか、どの操作に承認を求めるかは、ハーネスごとに設定します。同じルールを守らせたくても、ハーネスの数だけ設定が必要です。コストについても、複数のハーネスの合計に上限をかけたい場合は、ハーネスの外に仕組みが必要です。

![task3_settings.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/31dc80e2-33dc-4fec-bfd3-7c20323cc63b.png)

## 作業4: チームへの結果の共有

エージェントの作業結果をチームに見せるには、Slackやドキュメントにコピーして貼ることになります。作業中のセッションそのものを見せるのではなく、結果を切り出して渡す形になります。

![task4_share.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/de9e3ac2-0d06-4683-8711-31bb5f433a38.png)

# 境目を1つ上の層で引き受けるのがメタハーネス

メタハーネスは、各社のハーネスを共通の方法で扱えるようにする層です。Databricksのドキュメントでは、Omnigentを次のように説明しています。

> Omnigent は、Claude Code、Codex、Cursor、Pi、および自分で作成したエージェントの上に共通のレイヤーを提供します。

ハーネスそのものは置き換えません。Claude CodeもCodexも、そのままの形で動きます。メタハーネスは、その上で境目の作業を引き受けます。

前のセクションの4つの作業と、Omnigentの3つの機能の対応は次のとおりです。

| 境目での作業 | Omnigentの機能 | Omnigentがやること |
| --- | --- | --- |
| 作業1: 出力の受け渡し | 組み合わせ (Composition) | 実装はClaude Code、レビューはCodex、という分担を1つの流れとして定義して動かす |
| 作業2: コンテキストの説明し直し | 組み合わせ (Composition) | 指示やスキルを1つのエージェント定義にまとめ、どのハーネスで動かすときも同じ定義を使う |
| 作業3: 権限とガードレールの設定し直し | 制御 (Control) | ポリシーを1か所に書き、どのハーネスにも同じように適用する |
| 作業4: チームへの結果の共有 | 共有 (Collaboration) | 動いているセッションをURLで共有し、チームで同時に見る |

![fig5_meta_takes_over.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/f7e81fd4-67ad-4deb-980b-3135839da159.png)

制御については、コスト制御の記事で実際に確かめました。1つのサーバー設定で、Claude CodeとCodexの両方に同じ予算の上限がかかりました。一方で、ハーネスをネイティブのまま動かす場合には効かないポリシーもありました。すべてのポリシーがどのハーネスにも同じように効くわけではない点は、押さえておく必要があります。

- [Omnigentのコスト制御を設定して、予算が実際にどう効くか確かめた](https://qiita.com/taka_yayoi/items/dd61d12eb496e8490aa3)

# 層がもう1つ積み上がった

ここまでの流れを、層の積み上がりとして整理します。

- ハーネスが登場して、ハーネスの下でモデルを差し替えられるようになった
- メタハーネスが登場して、メタハーネスの下でハーネスを差し替えたり組み合わせたりできるようになった

![fig6_layers.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/19fcd698-9b40-4287-a45a-1451bf4c7675.png)

メタハーネスは、ハーネスがモデルに対してやったことを、1つ上の層でハーネスに対してやっている、と言えます。こう整理すると、「ハーネスのハーネス」という言い方も素直に読めるようになります。

# まとめ

メタハーネスが必要になるまでの流れを整理すると、次のようになります。

- 出発点は、1つのプロバイダーだけに頼ることへの懸念。懸念には品質と依存の2種類がある
- モデルを差し替えるだけなら、ハーネスの中でできる
- それでも各社のモデルを活かすには、各社のハーネスを並べて使うことになる
- **ハーネスの間には境目があり、人が次の4つの作業を手でやっている**
    - 出力の受け渡し
    - コンテキストの説明し直し
    - 権限とガードレールの設定し直し
    - チームへの結果の共有
- **メタハーネスは、ハーネスを置き換えずに、その上で境目の作業を引き受ける層**
- ハーネスがモデルを差し替え可能にしたのと同じことを、メタハーネスはハーネスに対してやっている

一番の収穫は、メタハーネスを定義から説明するより、境目で人がやっている作業から説明したほうが伝わる、と気づけたことでした。複数のエージェントの間でコピーと貼り付けを繰り返している方は、その作業がいくつあるかを一度数えてみると、この層の必要性が見えてくると思います。
