# Photon エンジンとは

[Photon](https://docs.databricks.com/ja/compute/photon.html)は、Databricks が開発した C++ ネイティブのベクトル化クエリエンジンです。SQL および DataFrame API のワークロードを、コード変更なしで高速化します。

Photon の主な特徴は以下の通りです。

- C++ で一から書かれたネイティブエンジンで、JVM のオーバーヘッド(ガベージコレクション、シリアライズ)を排除
- カラムナデータをバッチ単位で処理するベクトル化実行により、CPU の SIMD 命令を活用
- Delta Lake / Parquet のスキャン、集約、結合、ソート、書き込みを透過的に高速化
- Spark の物理プランのうち Photon が対応する部分を自動的に置き換え、非対応部分は従来の Spark エンジンにフォールバック

公式ベンチマーク(TPC-DS 1TB)では約 2 倍、実ワークロードでは 3〜8 倍の高速化が報告されています。本記事では、NYC Taxi データセットを使った 6 種類のクエリパターンで Photon の効果を実際に検証します。

# ベンチマーク環境

Photon ON/OFF で同一スペックのクラスターを 2 台用意し、エンジン設定のみを変えて計測しました。

| 項目 | 設定 |
|------|------|
| Databricks Runtime | 17.3 LTS(Apache Spark 4.0.0, Scala 2.13) |
| インスタンスタイプ | r6id.xlarge(32GB メモリ、4 コア) |
| ワーカー数 | 4 台(固定) |
| Autoscaling | 無効 |
| データ | NYC Taxi データセットから約 1,000 万行をサンプリング |

![Screenshot 2026-03-19 at 13.51.01.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/d0abb5a5-d0d7-47fe-b976-e1bc2b8d9be0.png)


公平な比較のため、以下の点に注意しています。

- **キャッシュは使用しない**: `cache()` を使うと Spark のインメモリ形式でデータが保持され、Photon のベクトル化 I/O(Delta/Parquet スキャン高速化)が効かなくなるため、毎回ディスクからの読み込みを含めて計測
- **同一データを使用**: サンプリング済みデータを Delta テーブルとして保存し、ON/OFF の両方で同一テーブルを参照
- **各ベンチマーク 1 回実行**: iterations を重ねるとディスクキャッシュが温まり、初回と条件が変わるため

# ベンチマーク内容

6 種類のクエリパターンで Photon の効果を計測しました。

| # | カテゴリ | 内容 |
|---|---------|------|
| 1 | スキャン + 集約 | 支払い種別ごとの合計金額(GROUP BY + SUM) |
| 2 | フィルタ + 集約 | 高額運賃(fare > 50)のベンダー別統計 |
| 3 | ウィンドウ関数 | 日別売上の 7 日移動平均 |
| 4 | 複雑な集約 | 時間帯 × 曜日のクロス集計(percentile_approx 含む) |
| 5 | ソート | 全レコードの運賃降順 Top 1000 |
| 6 | Delta 書き込み | フィルタ + カラム追加 + Delta テーブルへの書き出し |

# 結果

| ベンチマーク | Photon OFF(秒) | Photon ON(秒) | 高速化倍率 | 短縮時間(秒) |
|---|---|---|---|---|
| スキャン+集約(GROUP BY + SUM) | 8.60 | 4.21 | **2.04x** | +4.39 |
| フィルタ+集約 | 4.38 | 1.76 | **2.49x** | +2.62 |
| ウィンドウ関数(移動平均) | 11.65 | 3.20 | **3.64x** | +8.45 |
| 複雑な集約(クロス集計) | 40.66 | 9.83 | **4.14x** | +30.83 |
| 大規模ソート(ORDER BY) | 18.05 | 11.58 | **1.56x** | +6.47 |
| Delta 書き込み | 133.23 | 52.57 | **2.53x** | +80.66 |

![Screenshot 2026-03-19 at 14.07.16.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/5befc0fb-39af-4ceb-b674-2bf6cc92486f.png)

全体平均で **2.73 倍**の高速化を達成しました。全 6 パターンで Photon ON が上回っています。

# 結果の考察

## 最も効果が大きかったパターン: 複雑な集約(4.14x)

時間帯 × 曜日の 168 グループに対して `count`、`avg`、`percentile_approx` を同時計算するクエリです。Photon のベクトル化集約(PhotonGroupingAgg)が多数のグループキーに対するバッチ処理を効率化し、4 倍以上の高速化を実現しました。

## ウィンドウ関数(3.64x)

日別集計後に 7 日移動平均を計算するクエリです。ウィンドウ関数はデータの並び替えとパーティション内のスライディング計算を必要とし、Photon のソート最適化(PhotonSort)とベクトル化演算の両方が効いています。

## Delta 書き込み(2.53x)

Photon は読み込みだけでなく、Delta Lake への書き込みも高速化します。Photon のベクトル化 I/O により、Parquet ファイルのエンコード処理が高速化されるため、133 秒が 53 秒に短縮されました。

## ソートが最も控えめ(1.56x)

ソートは Photon で高速化されるものの、`ORDER BY` + `LIMIT 1000` というパターンでは、全データのシャッフルとソートが必要になり、ネットワーク I/O がボトルネックになるため、計算処理の高速化だけでは改善幅が限定的です。

# Photon が効果を発揮するワークロード

今回のベンチマークと公式ドキュメントから、Photon が特に有効なケースをまとめます。

- **集約処理**(GROUP BY、SUM、AVG、COUNT、percentile_approx): ベクトル化集約により 2〜4 倍の高速化
- **Delta Lake / Parquet の読み書き**: ベクトル化 I/O によるスキャン・エンコードの高速化
- **ウィンドウ関数**: ソート + スライディング計算の両方を最適化
- **結合処理**: ソートマージ結合をハッシュ結合に自動置換
- **フィルタ + 集約の組み合わせ**: カラムナバッチ処理でフィルタと集約を効率的にパイプライン実行

# Photon が効果を発揮しにくいケース

- **UDF(ユーザー定義関数)**: Python/Scala UDF は JVM/Python プロセスで実行されるため Photon の恩恵を受けない
- **RDD API**: Photon は DataFrame/SQL API のみ対応
- **2 秒未満の軽量クエリ**: エンジン切り替えのオーバーヘッドが相対的に大きい
- **Pandas / scikit-learn など非 Spark 処理**: シングルノード処理には効果なし

# Photon はコストが高い? 実はトータルで安くなる

Photon に対してよくいただく疑問が「DBU 単価が 2 倍になるんでしょ? コストが上がるのでは?」というものです。結論から言うと、**時間単価が 2 倍でも、処理時間が 2 倍以上短縮されれば、トータルコストは下がります**。


## コスト計算の考え方

Databricks のコストは「DBU 単価 × 消費 DBU 数」で決まり、消費 DBU 数は「1 時間あたりの DBU × 実行時間」です。つまりコストの式は以下のようになります。

- Photon OFF のコスト = DBU 単価 × DBU/時 × 実行時間
- Photon ON のコスト = DBU 単価 × **2 倍の** DBU/時 × **短縮された** 実行時間

高速化倍率が 2 倍を超えれば、DBU 単価が 2 倍でもトータルコストは下がります。**損益分岐点は高速化倍率 2.0x** です。

![Screenshot 2026-03-19 at 14.07.43.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/8f7b0f67-e64d-44f2-a896-b0d7f6b784c4.png)

## 今回のベンチマークでのコスト比較

DBU 単価が 2 倍として、各ベンチマークのコスト比率(Photon ON / Photon OFF)を算出しました。1.0 未満ならコスト削減、1.0 以上ならコスト増です。

| ベンチマーク | 高速化倍率 | コスト比率 | 判定 |
|---|---|---|---|
| スキャン+集約 | 2.04x | 0.98 | 2% 削減 |
| フィルタ+集約 | 2.49x | 0.80 | 20% 削減 |
| ウィンドウ関数 | 3.64x | 0.55 | 45% 削減 |
| 複雑な集約 | 4.14x | 0.48 | **52% 削減** |
| 大規模ソート | 1.56x | 1.28 | 28% **増加** |
| Delta 書き込み | 2.53x | 0.79 | 21% 削減 |

![Screenshot 2026-03-19 at 14.07.26.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/cdbf172c-42a5-405c-a517-98c47cf50e28.png)


6 パターン中 5 パターンでコスト削減を達成し、全体平均のコスト比率は **0.81**(19% 削減)です。

注目すべきは大規模ソートです。高速化倍率が 1.56x と損益分岐点(2.0x)を下回るため、Photon ON の方が 28% コスト増になっています。このように**すべてのクエリで無条件にコスト削減になるわけではない**点は重要です。

## コスト最適化の指針

Photon をコスト面で有効に活用するためのポイントは以下の通りです。

- **集約・結合・Delta I/O が中心のワークロード**: 2 倍以上の高速化が期待でき、コスト削減効果が高い
- **混合ワークロード**: ETL パイプラインのように複数のクエリパターンが混在する場合、全体で見ればコスト削減になることが多い(今回の例では全体で 19% 削減)
- **UDF 主体・軽量クエリ中心の場合**: Photon の恩恵が小さく、DBU 単価増がそのままコスト増に直結するため、有効化は推奨しない
- **開発・アドホック用途**: クラスターのアイドル時間が長い場合、その間も高い DBU 単価がかかる。Photon は本番パイプラインなど稼働率の高いクラスターで最もコスト効率が良い

# ベンチマークの再現方法

本記事のベンチマークに使用したノートブックは以下の 3 つです。

1. **photon_benchmark_off**: Photon 無効クラスターで Run All
2. **photon_benchmark_on**: Photon 有効クラスターで Run All
3. **photon_benchmark_compare**: どちらかのクラスターで Run All(比較表とグラフを生成)

ON/OFF は並列実行可能です。それぞれ結果を別の Delta テーブルに保存するため、書き込みが競合しません。

https://github.com/taka-yayoi/photon_benchmark/tree/main

# 性能計測値に関する注意事項

本記事に掲載しているベンチマーク結果は、上記の特定の環境・データ・クエリパターンにおける計測値であり、すべてのワークロードで同等の結果を保証するものではありません。

- 計測値はクラスターの状態(コールドスタート/ウォームスタート)、同一ワークスペース内の他ワークロードの影響、ネットワーク状況などにより変動します
- 各ベンチマークは 1 回のみの実行結果です。統計的に厳密な比較を行う場合は、複数回実行して分散を確認してください
- データの特性(カーディナリティ、スキュー、カラム数、ファイルサイズ)によって Photon の効果は大きく異なります
- 本記事のクラスター構成(r6id.xlarge × 4 ワーカー)は検証目的の小規模構成です。本番環境ではデータ量とクラスター構成に応じた独自の検証を推奨します

# まとめ

NYC Taxi データセット(約 1,000 万行)を使った 6 パターンのベンチマークで、Photon は全パターンで高速化を達成し、平均 2.73 倍の性能向上を確認しました。特に複雑な集約(4.14x)、ウィンドウ関数(3.64x)、Delta 書き込み(2.53x)で大きな効果が出ています。

Photon はコード変更不要で有効化できるため、集約・結合・Delta I/O が中心のワークロードでは積極的に活用する価値があります。
