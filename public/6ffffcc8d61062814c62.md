# はじめに

Omnigent 0.18.0 (2026年10月13日リリース) で、`omnigent agent add` コマンドが追加されました。エージェントを自分用に登録して、新規セッションでいつでも選べるようにするコマンドです。GitHub のリポジトリを指定して、そこに置かれたエージェントを取り込むこともできます。

- [feat(agents): install, list, and remove user agents (#8677)](https://github.com/omnigent-ai/omnigent/pull/8677)
- [omnigent agent add owner/repo で GitHub のリポジトリから取り込む (#9801)](https://github.com/omnigent-ai/omnigent/pull/9801)
- [Reusable user agents (設計ドキュメント)](https://github.com/omnigent-ai/omnigent/blob/v0.19.0/designs/REUSABLE_USER_AGENTS.md)

これまでの Omnigent の記事では、複数のモデルやハーネスを組み合わせる機能と、コストを制御する機能を試してきました。

https://qiita.com/taka_yayoi/items/b4335e26eb1d37d4f52a

今回は、チームで同じエージェントを使う場面を考えます。最初に確認しておきたいのは、`omnigent agent add` で登録したエージェントは、登録した本人しか使えないという点です。チームで1つのエージェントを共通で使う仕組みではなく、各自が自分用に登録する仕組みです。

そこで今回は、チームのエージェントを GitHub のリポジトリに置き、メンバーがそれぞれ自分用に登録する、という使い方を想定して試しました。登録、リポジトリ側の更新、更新の反映の順に確かめています。環境は macOS、Omnigent 0.19.0 です。

# Omnigent のエージェントは2種類ある

設計ドキュメントとコードを読むと、Omnigent のサーバーに登録されるエージェントは2種類あります。

| 種類 | 登録の仕方 | 使える人 | 更新のしかた |
| --- | --- | --- | --- |
| ユーザーエージェント | `omnigent agent add` など | 登録した本人だけ | 本人が取り込み直す |
| サーバーエージェント | サーバー起動時に `omnigent server --agent <ディレクトリ>` で登録 | そのサーバーを使う全員 | サーバーの運用者が登録し直す (サーバーの再起動が必要) |

`omnigent agent add` で登録されるのはユーザーエージェントです。`omnigent agent list` の見出しが「Your agents」になっているのもそのためです。

チームで同じエージェントを使う方法は、この2種類に対応して2通りあります。

- メンバーがそれぞれ、共有のリポジトリから自分用に登録する。エージェントはメンバーの人数分できる
- サーバーの運用者がサーバーに1つ登録し、全員でそれを使う

前者は、各自の手元でも、共有サーバーの上でも使えます。後者は、組織で Omnigent のサーバーを1つ運用している場合の方法です。この記事で試したのは前者です。

なお、ユーザーエージェントは `agent add` 以外でも作られます。`omnigent run ./my-agent` のように定義を指定してセッションを起動した場合も、その定義がユーザーエージェントとして登録されます。検証中に `omnigent agent list` を見ると、`omnigent run` で起動したエージェントが一覧に並んでいました。不要なものは `omnigent agent remove <名前>` で消せます。

# チームのリポジトリからエージェントを取り込む

## omnigent agent add に渡せるもの

CLI のヘルプによると、`omnigent agent add` に渡せるものは次の4種類です。

- エージェントのディレクトリ
- エージェントの YAML ファイル
- `.tar.gz` に固めたバンドル
- GitHub のリポジトリ (`owner/repo[/path][@agent]` の形、または github.com の URL)

ディレクトリやリポジトリを渡した場合は、YAML だけでなく、サブエージェント、スキル、ガードレール、その他の同梱ファイルも一緒に登録されます。

今回は、Omnigent の公式リポジトリの `examples` ディレクトリを、チームのエージェント置き場に見立てて使います。

## 取り込める候補を一覧する

`--list` を付けると、取り込まずに候補だけを表示します。

```bash
omnigent agent add omnigent-ai/omnigent/examples --list
```

```
Found 7 agent(s) in omnigent-ai/omnigent/examples:
  aws_analyst  (examples/aws_analyst)
  debby  (examples/debby)
  deep-research  (examples/deep-research)
  polly  (examples/polly)
  remy  (examples/remy)
  scribe  (examples/scribe)
  sentinel  (examples/sentinel)
```

チームのリポジトリにエージェントを複数置いておけば、メンバーはここから必要なものを選んで取り込めます。

## 1つを指定して取り込む

`@` の後ろにエージェント名を付けると、その1つだけを取り込みます。今回は、Web を調べて出典付きで答える deep-research を選びました。

```bash
omnigent agent add omnigent-ai/omnigent/examples@deep-research
```

```
Found 1 agent(s) in omnigent-ai/omnigent/examples@deep-research:
  deep-research  (examples/deep-research)
Install them? Only install agents from repos you trust [y/N]: y
Installed deep-research (version 1, id bbeda77f02d54af602f30358e0c066a3)
```

取り込む前に確認が入り、信頼できるリポジトリからだけ取り込むよう注意が表示されます。エージェントの定義には、プロンプトだけでなく、使うツールや MCP サーバーの設定も含まれます。他人のリポジトリから取り込むことは、その人が決めた実行内容を自分の環境に入れることなので、この確認は当然といえば当然です。

## 新規セッションで選んで使う

Web UI で新規セッションを開くと、入力欄の右下のエージェントの選択で deep-research を選べるようになっています。

![Screenshot 2026-10-21 at 13.14.21.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/8563e2a1-9bae-45e2-8b79-745f8377b5b4.png)

「omnigent agent add コマンドが何をするものか、公式リポジトリの情報をもとに3行でまとめて」と頼んだところ、Web を検索して、出典付きの回答が返ってきました。

![Screenshot 2026-10-21 at 13.15.47.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/88b8a7b9-62ed-43ce-94fc-ebe10b71b7c6.png)

ここで注目したいのはツールの呼び出しです。`keenable__search_web_pages` という検索ツールが使われています。これは deep-research のディレクトリに同梱されている MCP サーバーの設定 (`tools/mcp/keenable.yaml`) から来ているツールです。

取り込んだ側では、MCP サーバーの設定を何もしていません。チームで同じエージェントを使うとき、プロンプトは共有できても、MCP の設定は各自がそろえる、という形になりがちです。エージェントと一緒に MCP の設定も届くので、メンバーごとに設定がばらつく心配が減ります。

# 共有元が更新されたら取り込み直す

## 共有元のエージェントを書き換える

チームのエージェントは、使っているうちに手が入ります。共有元が更新されたときにメンバー側で何が起きるかを確かめるため、deep-research を手元にコピーして、共有元の更新に見立てた書き換えをしました。

```bash
git clone --depth 1 https://github.com/omnigent-ai/omnigent.git /tmp/omnigent-src
cp -R /tmp/omnigent-src/examples/deep-research ~/deep-research-mine
```

変化が目で分かるように、プロンプトの先頭に「回答の最後に必ず「(社内版 v2)」と1行付けてください。」という指示を足します。

```bash
cd ~/deep-research-mine
perl -0pi -e 's/prompt: \|\n/prompt: |\n  回答の最後に必ず「(社内版 v2)」と1行付けてください。\n/' config.yaml
```

## メンバーが同じ名前で取り込み直す

名前 (`name: deep-research`) は変えずに取り込み直します。チームのリポジトリが更新された場合は、`omnigent agent add org/repo@deep-research` をもう一度実行することに相当します。

```bash
omnigent agent add ~/deep-research-mine
```

```
Installed deep-research (version 2, id bbeda77f02d54af602f30358e0c066a3)
Sessions using it pick up this version on their next turn; terminal sessions do when they relaunch.
```

ID はそのままで、バージョンが2に上がりました。別のエージェントが増えるのではなく、登録済みのエージェントが新しい版に置き換わっています。

ここで大事なのは、置き換わったのは取り込み直した本人のエージェントだけだという点です。ユーザーエージェントは本人のものなので、共有元のリポジトリが更新されても、各メンバーのエージェントは自動では更新されません。メンバーそれぞれが取り込み直す必要があります。

## 新しいセッションには反映された

新規セッションで deep-research を選び、`omnigent agent remove` の役割を尋ねると、回答の最後に「(社内版 v2)」が付きました。取り込み直した版が使われています。

![Screenshot 2026-10-21 at 13.33.37.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/83112c6f-3dd6-4ffe-9083-c3617627720b.png)

## 既存のセッションには次のターンでは反映されなかった

もう一つ注意したいところがあります。取り込み直したときの表示は、そのエージェントを使っているセッションには次のターンから新しい版が反映される、という内容でした。

ところが、取り込み直す前から開いていた deep-research のセッションでは、取り込み直したあとに質問しても「(社内版 v2)」は付きませんでした。

![Screenshot 2026-10-21 at 13.33.51.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/1168882/233957ca-0959-4f3f-af6a-8bfd2f7d7ae1.png)

今回の環境 (claude-sdk ハーネス、Web UI から開いたセッション) で確認できたのは、新しく始めたセッションから新しい版が使われる、というところまでです。既存のセッションに反映される条件は、今回は確認できていません。取り込み直したあとは、新しいセッションを開くのが確実です。

# サーバーに1つ登録して全員で使うには

ここまでの方法では、エージェントはメンバーの人数分あり、更新のたびにメンバー全員が登録し直すことになります。人数が多いチームや、全員に同じ版を使わせたい場合には向きません。

その場合は、サーバーエージェントとして登録する方法があります。エージェントはサーバーに1つだけで、全員がそれを使います。共有の Omnigent サーバーを運用している人が、サーバーの起動時に `--agent` でエージェントのディレクトリを指定します。

```bash
omnigent server --agent ./deep-research
```

設計ドキュメントによると、この方法で登録したエージェントは、そのサーバーを使う全員の新規セッションの選択肢に出ます。代わりに、登録や更新にはサーバーの再起動が必要です。今回は、共有サーバーを立てての確認まではしていません。

2つの方法を並べると、役割は次のように分かれます。

| 方法 | 向いている場面 |
| --- | --- |
| メンバーが `omnigent agent add org/repo` で自分用に登録する | 使うかどうかを各自が選ぶエージェント。更新を反映するタイミングも各自でよいもの |
| 運用者が `omnigent server --agent` でサーバーに1つ登録する | 全員に同じ版を使わせたいエージェント |

# まとめ

チームで同じエージェントを使う場面を想定して、`omnigent agent add` を試しました。

- **`omnigent agent add` で登録したエージェントは、登録した本人だけが使える** 。チームで共通の1つを使う仕組みではなく、各自が自分用に登録する仕組み
- チームで使うには、エージェントを GitHub のリポジトリに置き、メンバーがそれぞれ `omnigent agent add org/repo@名前` で取り込む。`--list` で候補だけを確認できる
- エージェントに同梱された MCP サーバーの設定も一緒に取り込まれる。取り込んだ側で MCP の設定をしなくても、そのままツールが使えた
- 同じ名前で取り込み直すと、ID はそのままでバージョンが上がる。ただし置き換わるのは取り込み直した本人のエージェントだけで、メンバーそれぞれが取り込み直す必要がある
- **新しいセッションには新しい版が反映されたが、既存のセッションには次のターンでは反映されなかった**
- 全員に同じ版を使わせたい場合は、サーバーの運用者が `omnigent server --agent` でサーバーに1つ登録し、全員でそれを使う

一番の収穫は、`agent add` の位置づけがはっきりしたことでした。試し始めたときは、チームでエージェントを共有する機能だと思っていました。実際には、GitHub のリポジトリにあるエージェントを、各自が自分用に登録する機能です。Omnigent が引き受けているのは、その登録をプロンプトと MCP の設定を含めて1コマンドにするところです。全員に同じ版を確実に使わせたいなら、サーバーに1つ登録して全員で使う、という別の方法になります。チームでの使い方を考えるときは、各自が登録するのか、サーバーに1つ置くのかを最初に決めておくのがよさそうです。
